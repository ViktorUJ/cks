# Lab 122 - reference solution (AWS Backup for EKS: composite recovery point,
namespace restore)

All commands run on the worker machine over SSH. kubectl and the aws CLI are already
configured for the lab's cluster and region. Terraform has already created the IAM role
for AWS Backup and the backup vault (component `eks_backup_iam`, module
`eks_v2_backup_iam`) - their ARNs and names are in the hint file `~/lab122_hints.txt`.

```bash
cat ~/lab122_hints.txt
export CLUSTER_NAME=$(grep '^cluster_name' ~/lab122_hints.txt | awk '{print $3}')
export CLUSTER_ARN=$(grep '^cluster_arn' ~/lab122_hints.txt | awk '{print $3}')
export ROLE_ARN=$(grep '^backup_role_arn' ~/lab122_hints.txt | awk '{print $3}')
```

## Task 1. Namespace `eks-122`, a workload on an EBS volume, and a marker

Namespace, Deployment, PVC on the `gp3` class (the `aws-ebs-csi-driver` addon is already
installed by the `eks_addon_ebs_irsa` component), and a ConfigMap with a marker that will
later confirm that the restored object really came from the backup:

```bash
kubectl create namespace eks-122

cat <<'EOF' | kubectl apply -f -
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
parameters:
  type: gp3
  encrypted: "true"
EOF

cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
  namespace: eks-122
spec:
  storageClassName: gp3
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 5Gi
EOF

cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: eks-122
spec:
  replicas: 1
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: app
        image: viktoruj/ping_pong:latest
        volumeMounts:
        - name: data
          mountPath: /data
      volumes:
      - name: data
        persistentVolumeClaim:
          claimName: data
EOF

kubectl rollout status deployment/web -n eks-122

MARKER="MARKER_LAB122_$(tr -dc a-z0-9 </dev/urandom | head -c 8)"
kubectl create configmap marker -n eks-122 --from-literal=marker="$MARKER"

mkdir -p /var/work/tests/artifacts/1
echo -n "$MARKER" > /var/work/tests/artifacts/1/marker.txt
cat /var/work/tests/artifacts/1/marker.txt
```

`volumeBindingMode: WaitForFirstConsumer` defers volume creation until the pod is
scheduled (chapter 23) - the PVC only turns `Bound` after the `web` pod is actually
scheduled. The marker in the artifact will later prove that the restored ConfigMap came
from the backup rather than being recreated by hand.

## Task 2. Opt-in for Amazon EKS in AWS Backup for the region

```bash
mkdir -p /var/work/tests/artifacts/2
BEFORE=$(aws backup describe-region-settings \
  --query "ResourceTypeOptInPreference.EKS" --output text)
echo "before=$BEFORE" > /var/work/tests/artifacts/2/optin.txt

if [[ "$BEFORE" != "True" ]]; then
  aws backup update-region-settings \
    --resource-type-opt-in-preference '{"EKS":true}'
fi

AFTER=$(aws backup describe-region-settings \
  --query "ResourceTypeOptInPreference.EKS" --output text)
echo "after=$AFTER" >> /var/work/tests/artifacts/2/optin.txt
cat /var/work/tests/artifacts/2/optin.txt
```

Without this opt-in, AWS Backup does not see the EKS cluster as a protectable resource,
and `start-backup-job` for the cluster fails (chapter 41, section 41.4).

## Task 3. On-demand backup of the cluster

The cluster was already created with an explicit `authentication_mode =
"API_AND_CONFIG_MAP"` (module `eks_v2_control_plane`), so AWS Backup's requirement for
the authorization mode is already satisfied - the service will create its own access
entry on the first backup job.

```bash
BACKUP_JOB_ID=$(aws backup start-backup-job \
  --backup-vault-name "$VAULT_NAME" \
  --resource-arn "$CLUSTER_ARN" \
  --iam-role-arn "$ROLE_ARN" \
  --query 'BackupJobId' --output text)

echo "backup_job_id=$BACKUP_JOB_ID"

while true; do
  STATE=$(aws backup describe-backup-job --backup-job-id "$BACKUP_JOB_ID" \
    --query 'State' --output text)
  echo "backup job state: $STATE"
  case "$STATE" in
    COMPLETED|PARTIAL|FAILED|ABORTED|EXPIRED) break ;;
  esac
  sleep 15
done

RECOVERY_POINT_ARN=$(aws backup describe-backup-job --backup-job-id "$BACKUP_JOB_ID" \
  --query 'RecoveryPointArn' --output text)
```

The EBS snapshot of the `data` volume can take longer to assemble than the cluster
state, so we wait for a terminal status rather than specifically `COMPLETED`: `PARTIAL`
(chapter 41, section 41.4) also means the backup job has finished and a recovery point
was created, it's just that some of the nested points may not have assembled. Save the
artifact:

```bash
mkdir -p /var/work/tests/artifacts/3
{
  echo "backup_job_id=$BACKUP_JOB_ID"
  echo "status=$STATE"
  echo "recovery_point_arn=$RECOVERY_POINT_ARN"
} > /var/work/tests/artifacts/3/backup_status.txt
cat /var/work/tests/artifacts/3/backup_status.txt
```

## Task 4. Diagnosing the composite recovery point

`RECOVERY_POINT_ARN` from task 3 is a composite recovery point: the parent point groups
the child recovery point of the cluster state and the child recovery point of the `data`
volume as one consistent unit (chapter 41, section 41.4). Let's look at it and at the
nested points:

```bash
aws backup list-recovery-points-by-backup-vault --backup-vault-name "$VAULT_NAME" \
  --query 'RecoveryPoints[].{Arn:RecoveryPointArn,Parent:ParentRecoveryPointArn,IsParent:IsParent,Status:Status}'

aws backup list-recovery-points-by-backup-vault --backup-vault-name "$VAULT_NAME" \
  --by-parent-recovery-point-arn "$RECOVERY_POINT_ARN"
```

Save an explanation of the difference between composite and child points to the
artifact:

```bash
mkdir -p /var/work/tests/artifacts/4
cat > /var/work/tests/artifacts/4/composite.txt <<'EOF'
A composite recovery point is a compound recovery point for an EKS cluster: it groups
several nested (child) points under itself as one consistent unit. For this lab that
means the child recovery point of the cluster state (the Kubernetes object manifests of
namespace eks-122) and the child recovery point of the data volume (an EBS snapshot
behind the PVC).

The composite point has no ParentRecoveryPointArn of its own - it is the top level. Each
child point's ParentRecoveryPointArn field references the ARN of the composite point,
and IsParent=true is set specifically on the composite one. The child of the cluster
state has a 1:1 link with its parent: it cannot be copied, deleted or detached on its
own. The child point of the volume, by contrast, can be copied, deleted and restored
separately from the composite one.

That is exactly why the composite point cannot be deleted while it still has nested
points inside it - the nested points must be deleted or detached first, and only then
the composite point itself.
EOF
cat /var/work/tests/artifacts/4/composite.txt
```

## Task 5. Namespace restore (non-destructive)

We start a restore of the composite recovery point, specifying namespace `eks-122`,
into the same (live) cluster:

`namespaceLevelRestore` alone is not enough here. The composite point also contains an
EBS snapshot, and to restore it AWS Backup **requires an Availability Zone** to create
the volume in. If it's not provided, the child restore job for the volume fails with
`Restore Job failed as no restore metadata was provided`, and the parent one fails with
`All PV restore jobs failed to restore`. This is passed through the `nestedRestoreJobs`
parameter: a map of `nested point ARN -> its metadata`. The zone is taken from an
existing node, otherwise the volume would be created where there's nobody to mount it.

Note the nested encoding: the value of `nestedRestoreJobs` is a JSON string, containing
a map, whose element value is itself a JSON string. An extra level of quoting produces
the error `Invalid JSON format in NestedRestoreMetadata`, so we build it via `jq` (note
the `-r` in the first call - it strips the extra level):

```bash
AZ=$(kubectl get nodes -l 'eks.amazonaws.com/compute-type notin (fargate)' \
  -o jsonpath='{.items[0].metadata.labels.topology\.kubernetes\.io/zone}')

SNAP_ARN=$(aws backup list-recovery-points-by-backup-vault --backup-vault-name "$VAULT_NAME" \
  --by-parent-recovery-point-arn "$RECOVERY_POINT_ARN" \
  --query 'RecoveryPoints[?ResourceType==`EBS`].RecoveryPointArn' --output text)

NESTED=$(jq -rn --arg s "$SNAP_ARN" --arg az "$AZ" \
  '{($s): ({AvailabilityZone: $az} | tostring)} | tostring')

METADATA=$(jq -cn --arg c "$CLUSTER_NAME" --arg n "$NESTED" \
  '{clusterName: $c, newCluster: "false", namespaceLevelRestore: "true",
    namespaces: "[\"eks-122\"]", nestedRestoreJobs: $n}')

RESTORE_JOB_ID=$(aws backup start-restore-job \
  --recovery-point-arn "$RECOVERY_POINT_ARN" \
  --iam-role-arn "$ROLE_ARN" \
  --resource-type EKS \
  --metadata "$METADATA" \
  --query 'RestoreJobId' --output text)

echo "restore_job_id=$RESTORE_JOB_ID"

while true; do
  STATUS=$(aws backup describe-restore-job --restore-job-id "$RESTORE_JOB_ID" \
    --query 'Status' --output text)
  echo "restore job status: $STATUS"
  case "$STATUS" in
    COMPLETED|FAILED|ABORTED) break ;;
  esac
  sleep 15
done
```

We check that Deployment `web` and ConfigMap `marker` were not duplicated and that the
marker matches the one saved in task 1 - this proves the non-destructive behavior of the
restore (chapter 42, section 42.2): objects that already exist in the cluster under the
same name are not overwritten, only skipped, so a restore over a live namespace does not
create a second copy.

```bash
kubectl rollout status deployment/web -n eks-122
kubectl get cm marker -n eks-122 -o jsonpath='{.data.marker}'; echo
cat /var/work/tests/artifacts/1/marker.txt; echo
```

Save an artifact with the explanation:

```bash
mkdir -p /var/work/tests/artifacts/5
cat > /var/work/tests/artifacts/5/restore_status.txt <<EOF
restore_job_id=$RESTORE_JOB_ID
status=$STATUS
A restore in AWS Backup is always non-destructive: existing Kubernetes objects in the
target namespace are not overwritten, only skipped. Deployment web and ConfigMap marker
already existed in eks-122 at the time of the restore with the same content, so the
restore did not create duplicates of them and did not change the marker value - the
objects simply matched and were skipped.
EOF
cat /var/work/tests/artifacts/5/restore_status.txt
```

## Task 6. Why a cluster version rollback does not undo `kubectl delete namespace`

The motivating example from section 41.1 of chapter 41: an engineer mistakenly runs
`kubectl delete namespace prod` against the wrong cluster, and the first thought is
"let's roll it back". But there's nothing to roll back.

```bash
mkdir -p /var/work/tests/artifacts/6
cat > /var/work/tests/artifacts/6/whynonrollback.txt <<'EOF'
A cluster version rollback (chapter 39) works with the control plane and its Kubernetes
version - it does not store or restore Kubernetes objects or volume contents. The
objects that kubectl delete namespace removed live in etcd, and in EKS etcd is managed:
there is no direct access to it, and you cannot take an etcd dump and restore it by hand
as you could on a self-managed cluster. There is also no "return it to how it was
yesterday" command for a managed control plane.

That's exactly why the only working way to bring back a deleted namespace is a backup of
the cluster state made ahead of time via AWS Backup (tasks 3-4) followed by a restore
(task 5), not a control plane version rollback.
EOF
cat /var/work/tests/artifacts/6/whynonrollback.txt
```
