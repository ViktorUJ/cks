# Lab 120 - reference solution (network failures, unhealthy load balancer targets)

All commands run on the worker machine over SSH. kubectl is already configured
for the cluster. Terraform has already created the "broken" security group
(component `eks_network_break_demo`) and an IRSA role for the AWS Load Balancer
Controller (`eks_lbc_irsa`) - names and ids are in `~/lab120_hints.txt`.

```bash
cat ~/lab120_hints.txt
export SG_ID=$(grep '^broken_sg_id' ~/lab120_hints.txt | awk '{print $3}')
export NODE_SG=$(grep '^node_sg_id' ~/lab120_hints.txt | awk '{print $3}')
export CLUSTER=$(grep '^cluster_name' ~/lab120_hints.txt | awk '{print $3}')
```

## Task 2. Baseline connectivity and SG diagnostics

```bash
CLIENT_POD=$(kubectl get pod -n eks-120 -l app=client -o jsonpath='{.items[0].metadata.name}')

mkdir -p /var/work/tests/artifacts/2
kubectl exec -n eks-120 "$CLIENT_POD" -- \
  wget -qO- --timeout=5 http://api.eks-120.svc.cluster.local \
  > /var/work/tests/artifacts/2/connectivity.txt
cat /var/work/tests/artifacts/2/connectivity.txt
```

Connectivity works fine here: the node SG allows traffic between cluster pods,
and SGs are stateful, so the response to this request passes on its own
(chapter 46.3). Let's look at which SGs are actually attached to the `api`
pod's ENI:

```bash
API_IP=$(kubectl get pod -n eks-120 -l app=api -o jsonpath='{.items[0].status.podIP}')

It matters which filter you use to find the ENI. With VPC CNI, the pod's IP is a
**secondary** address on the node's ENI, so the filter `private-ip-address`
(which looks at the interface's primary address) will return `null`. You need
`addresses.private-ip-address`, which searches across all of the interface's
addresses:

```bash
aws ec2 describe-network-interfaces \
  --filters "Name=addresses.private-ip-address,Values=${API_IP}" \
  --query 'NetworkInterfaces[0].Groups' \
  > /var/work/tests/artifacts/2/api_sg.txt
cat /var/work/tests/artifacts/2/api_sg.txt
```

## Task 3. Installing the AWS Load Balancer Controller

```bash
LBC_ROLE_ARN=$(aws iam get-role --role-name "${CLUSTER}-lbc-irsa" \
  --query 'Role.Arn' --output text)

cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: ServiceAccount
metadata:
  name: aws-load-balancer-controller
  namespace: kube-system
  annotations:
    eks.amazonaws.com/role-arn: ${LBC_ROLE_ARN}
EOF

helm repo add eks https://aws.github.io/eks-charts
helm repo update

An important detail of this environment: the `kube-system` namespace falls
under the Fargate profile, so the controller's pods run on Fargate, and Fargate
has **no IMDS**. Without IMDS the controller can't determine the region and VPC
on its own and fails with `failed to get VPC ID: ... ec2imds ... context
deadline exceeded`. So `region` and `vpcId` are set explicitly:

```bash
REGION=eu-central-1
VPC_ID=$(aws eks describe-cluster --name "${CLUSTER}" \
  --query 'cluster.resourcesVpcConfig.vpcId' --output text)

helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName="${CLUSTER}" \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set region="${REGION}" \
  --set vpcId="${VPC_ID}"

kubectl rollout status deployment/aws-load-balancer-controller -n kube-system
```

## Task 4. Symptom: NLB with unhealthy targets

We set the "broken" SG as the balancer's own security group. As soon as an SG
is specified explicitly via the annotation, the LBC stops adding the missing
inbound rule to the node SG for us - that's exactly the failure (chapter 46.6):

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Service
metadata:
  name: api-lb
  namespace: eks-120
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: external
    service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: ip
    service.beta.kubernetes.io/aws-load-balancer-scheme: internet-facing
    service.beta.kubernetes.io/aws-load-balancer-security-groups: ${SG_ID}
spec:
  type: LoadBalancer
  selector:
    app: api
  ports:
    - port: 80
      targetPort: 8080
EOF

kubectl get svc api-lb -n eks-120 -w
```

We wait for the external address, find the target group, and check the
targets' health:

```bash
HOSTNAME=$(kubectl get svc api-lb -n eks-120 \
  -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
LB_ARN=$(aws elbv2 describe-load-balancers \
  --query "LoadBalancers[?DNSName=='${HOSTNAME}'].LoadBalancerArn" --output text)
TG_ARN=$(aws elbv2 describe-target-groups --load-balancer-arn "$LB_ARN" \
  --query 'TargetGroups[0].TargetGroupArn' --output text)

mkdir -p /var/work/tests/artifacts/4
aws elbv2 describe-target-health --target-group-arn "$TG_ARN" \
  --query 'TargetHealthDescriptions[].[Target.Id,TargetHealth.State,TargetHealth.Reason]' \
  --output table > /var/work/tests/artifacts/4/unhealthy.txt
cat /var/work/tests/artifacts/4/unhealthy.txt
```

All targets are `unhealthy` - the balancer's SG doesn't let the health check
through to the node SG, and so it never reaches the `api` pod either.

## Task 5. Diagnostics: whose SG is blocking the health check

```bash
aws ec2 describe-security-groups --group-ids "$SG_ID" \
  --query 'SecurityGroups[0].IpPermissions'
```

The empty list confirms it: the balancer's SG has not a single inbound rule.

```bash
mkdir -p /var/work/tests/artifacts/5
cat > /var/work/tests/artifacts/5/diagnosis.txt <<EOF
The balancer's security group (${SG_ID}) is assigned to api-lb via the
aws-load-balancer-security-groups annotation and contains no inbound rules.
The health check from the NLB arrives as a new TCP connection from the
balancer's security group to the node security group (${NODE_SG}) on the
application's port 8080. The node security group does not allow inbound
traffic from the balancer's security group on this port, so the health check
fails and the targets stay unhealthy (chapter 46.6).
EOF
cat /var/work/tests/artifacts/5/diagnosis.txt
```

## Task 6. Fix: authorize-security-group-ingress, targets healthy

Two rules: allow the health check and application traffic from the balancer's
SG to the node SG, and open the NLB listener for clients on port 80:

```bash
aws ec2 authorize-security-group-ingress \
  --group-id "$NODE_SG" \
  --protocol tcp --port 8080 \
  --source-group "$SG_ID"

aws ec2 authorize-security-group-ingress \
  --group-id "$SG_ID" \
  --protocol tcp --port 80 \
  --cidr 0.0.0.0/0
```

We wait until the targets become `healthy` (usually 1-2 minutes) and verify
with curl:

```bash
sleep 90

mkdir -p /var/work/tests/artifacts/6
{
  aws elbv2 describe-target-health --target-group-arn "$TG_ARN" \
    --query 'TargetHealthDescriptions[].[Target.Id,TargetHealth.State]' --output table
  echo
  curl -s --max-time 5 "http://${HOSTNAME}"
} > /var/work/tests/artifacts/6/healthy.txt
cat /var/work/tests/artifacts/6/healthy.txt
```

## Task 7. DNS works: a contrasting check

```bash
mkdir -p /var/work/tests/artifacts/7
kubectl run dnstest --image=busybox:1.36 --rm -i --restart=Never -- \
  sh -c 'nslookup kubernetes.default.svc.cluster.local; nslookup example.com' \
  > /var/work/tests/artifacts/7/dns.txt
cat /var/work/tests/artifacts/7/dns.txt
```

We query the internal name by its full FQDN. The short `kubernetes.default`
through `nslookup` from busybox returns `NXDOMAIN`: this resolver doesn't
append the search domains from `/etc/resolv.conf` the way a regular client
does, and that response is easy to mistake for a DNS failure that isn't there.

Both names resolve fine (`kubernetes.default.svc.cluster.local` to the
`kubernetes` service's address, `example.com` to external addresses) - DNS is
not the source of the problem in this lab (chapters 46.5, 46.7), unlike the
security group from tasks 4-6.
