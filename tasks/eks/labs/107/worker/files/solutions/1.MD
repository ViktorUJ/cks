# Lab 107 - reference solution (EFS CSI: ReadWriteMany across AZs)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster. The `aws-efs-csi-driver` driver (provisioner `efs.csi.aws.com`) is already
installed as a managed addon with a role via IRSA (component `eks_addon_efs_irsa`), the
EFS filesystem and mount target in each AZ are already created by terraform - no need to
create them again.

## Task 1. Namespace `eks-107`

```bash
kubectl create namespace eks-107
```

## Task 2. StorageClass `efs-sc` pointing at the real `fileSystemId`

The filesystem was created by terraform beforehand, the driver only works on top of it.
We find its ID via AWS CLI (tag `Name` is built from the lab's `prefix`):

```bash
FS_ID=$(aws efs describe-file-systems --region eu-central-1 \
  --query "FileSystems[?Tags[?Key=='Name' && Value=='eks-task107-efs']].FileSystemId" \
  --output text)
echo "$FS_ID"

cat <<EOF | kubectl apply -f -
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: efs-sc
provisioner: efs.csi.aws.com
parameters:
  provisioningMode: efs-ap
  fileSystemId: ${FS_ID}
  directoryPerms: "755"
  uid: "1000"
  gid: "1000"
  basePath: "/dynamic"
mountOptions: ["tls"]
EOF
```

`provisioningMode: efs-ap` means dynamic provisioning: for each PVC the driver creates a
separate access point inside this filesystem, instead of handing out the whole filesystem.

## Task 3. PVC `shared-data` (`ReadWriteMany`, `5Gi`)

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: shared-data
  namespace: eks-107
spec:
  accessModes: ["ReadWriteMany"]
  storageClassName: efs-sc
  resources:
    requests:
      storage: 5Gi
EOF

kubectl get pvc shared-data -n eks-107
```

EFS is a regional system, so the PVC transitions to `Bound` regardless of which zone the
pods later land in: the mount target is reachable from any AZ where it's created.

## Task 4. Deployment `writer` (3 replicas, different AZs, shared PVC)

`topologySpreadConstraints` on key `topology.kubernetes.io/zone` makes the scheduler
spread replicas across different zones:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: writer
  namespace: eks-107
spec:
  replicas: 3
  selector:
    matchLabels:
      app: writer
  template:
    metadata:
      labels:
        app: writer
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: writer
      containers:
      - name: app
        image: viktoruj/ping_pong:alpine
        volumeMounts:
        - name: data
          mountPath: /data
      volumes:
      - name: data
        persistentVolumeClaim:
          claimName: shared-data
EOF

kubectl rollout status deployment/writer -n eks-107
kubectl get po -n eks-107 -l app=writer -o wide
```

Check that the replicas landed across different AZs:

```bash
kubectl get po -n eks-107 -l app=writer \
  -o custom-columns='POD:.metadata.name,NODE:.spec.nodeName' --no-headers | \
  while read -r pod node; do
    zone=$(kubectl get node "$node" -o jsonpath='{.metadata.labels.topology\.kubernetes\.io/zone}')
    echo "$pod  node=$node  zone=$zone"
  done
```

All 3 replicas are `Running` at the same time and mount the same PVC `shared-data`, even
though they're in different AZs. With EBS this is impossible (`ReadWriteOnce`, error
`Multi-Attach error`), because EBS is a zonal block volume, while EFS is a regional
NFS system with a mount target in each zone.

## Task 5. Shared access: write from one replica, read from another

```bash
PODS=($(kubectl get po -n eks-107 -l app=writer -o jsonpath='{.items[*].metadata.name}'))
WRITER_POD=${PODS[0]}
READER_POD=${PODS[1]}

kubectl exec -n eks-107 "$WRITER_POD" -- sh -c \
  'echo "efs-rwx-test from $(hostname)" >> /data/shared.txt'

mkdir -p /var/work/tests/artifacts/5
kubectl exec -n eks-107 "$READER_POD" -- cat /data/shared.txt \
  > /var/work/tests/artifacts/5/readback.txt
cat /var/work/tests/artifacts/5/readback.txt
```

The line written by pod `$WRITER_POD` in one AZ is read by pod `$READER_POD` in another
AZ - this confirms it's truly a shared network volume over NFS, not a local copy on the
node's disk.

## Task 6. Checking for the absence of a zonal `nodeAffinity`

```bash
mkdir -p /var/work/tests/artifacts/6

PV=$(kubectl get pvc shared-data -n eks-107 -o jsonpath='{.spec.volumeName}')
kubectl get pv "$PV" -o yaml > /var/work/tests/artifacts/6/pv.yaml
grep -A3 nodeAffinity /var/work/tests/artifacts/6/pv.yaml
echo "exit code: $?"

cat > /var/work/tests/artifacts/6/explanation.txt <<'EOF'
The PV created by efs.csi.aws.com has no spec.nodeAffinity section (unlike EBS, chapter
23, where nodeAffinity pins down a specific AZ via key topology.ebs.csi.aws.com/zone).
The reason is that EFS is a regional filesystem with a mount target in every AZ, so a pod
using this volume can be recreated in any other zone of the cluster and will keep seeing
the same data through the mount target of its new zone. The scheduler doesn't need to pin
the pod to a specific node or zone because of the volume, the way it does with EBS.
EOF
cat /var/work/tests/artifacts/6/explanation.txt
```

The `grep -A3 nodeAffinity` command finds nothing (empty output, exit code `1`) - that's
the confirmation that the section is absent. Compare with the `pv.yaml` from lab 106
(EBS), where `spec.nodeAffinity.required.nodeSelectorTerms` rigidly pins the volume's zone.

## Task 7. Diagnostics: mount target SG and port 2049 (read-only)

Breaking real infrastructure is risky, so this task only confirms the current state via
AWS CLI and explains the consequences of the rule being absent.

```bash
mkdir -p /var/work/tests/artifacts/7

FS_ID=$(aws efs describe-file-systems --region eu-central-1 \
  --query "FileSystems[?Tags[?Key=='Name' && Value=='eks-task107-efs']].FileSystemId" \
  --output text)

MT_SG=$(aws efs describe-mount-targets --region eu-central-1 --file-system-id "$FS_ID" \
  --query 'MountTargets[0].MountTargetId' --output text | \
  xargs -I{} aws efs describe-mount-target-security-groups --region eu-central-1 \
  --mount-target-id {} --query 'SecurityGroups[0]' --output text)

aws ec2 describe-security-groups --region eu-central-1 --group-ids "$MT_SG" \
  --query 'SecurityGroups[0].IpPermissions[?ToPort==`2049`]' \
  > /var/work/tests/artifacts/7/sg-rule.txt
cat /var/work/tests/artifacts/7/sg-rule.txt
```

Make sure the output has a rule `FromPort/ToPort: 2049`, `IpProtocol: tcp`, and that the
source (`UserIdGroupPairs`) is the cluster node security group, not a CIDR. Save the
diagnosis of causes and effects:

```bash
cat > /var/work/tests/artifacts/7/diagnosis.txt <<'EOF'
The mount target's security group allows inbound TCP 2049 (NFS) from the cluster node
security group - this is confirmed by the output of aws ec2 describe-security-groups
(sg-rule.txt). The rule is required for every mount target: without it, the
efs.csi.aws.com driver can still create the mount point at the API level, but the actual
mount process on the node won't be able to establish an NFS connection to the mount
target.

If this rule is removed, mounting won't fail immediately with an explicit error: TCP
packets to port 2049 will be dropped by the security group, and the kernel on the node
will wait for the NFS server's response until the timeout expires. The pod will stay in
Pending/ContainerCreating, and kubectl describe pod will show a FailedMount event with
text like "Unable to mount... connection timed out" - visually similar to a slow network
rather than an explicit access denial, and without diagnosing the security group it's easy
to mistake the cause for a problem with the NFS server itself or the subnet.
EOF
cat /var/work/tests/artifacts/7/diagnosis.txt
```
