# Лаба 107 - эталонное решение (EFS CSI: ReadWriteMany между AZ)

Все команды выполняются на рабочей машине (worker) по SSH. kubectl уже настроен на
кластер. Драйвер `aws-efs-csi-driver` (провизионер `efs.csi.aws.com`) уже установлен как
managed addon с ролью через IRSA (компонент `eks_addon_efs_irsa`), файловая система EFS и
mount target в каждой AZ уже созданы terraform - создавать их заново не нужно.

## Задание 1. Namespace `eks-107`

```bash
kubectl create namespace eks-107
```

## Задание 2. StorageClass `efs-sc` на реальный `fileSystemId`

Файловая система создана terraform заранее, драйвер только работает поверх неё. Находим
её ID через AWS CLI (тег `Name` собран из `prefix` лабы):

```bash
FS_ID=$(aws efs describe-file-systems --region eu-central-1 \
  --query "FileSystems[?Tags[?Key=='Name' && Value=='eks-task107-efs']].FileSystemId" \
  --output text)
echo "$FS_ID"

cat <<EOF | kubectl apply -f -
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: efs-sc
provisioner: efs.csi.aws.com
parameters:
  provisioningMode: efs-ap
  fileSystemId: ${FS_ID}
  directoryPerms: "755"
  uid: "1000"
  gid: "1000"
  basePath: "/dynamic"
mountOptions: ["tls"]
EOF
```

`provisioningMode: efs-ap` означает динамический провижининг: на каждый PVC драйвер
создаёт отдельный access point в этой файловой системе, а не отдаёт всю ФС целиком.

## Задание 3. PVC `shared-data` (`ReadWriteMany`, `5Gi`)

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: shared-data
  namespace: eks-107
spec:
  accessModes: ["ReadWriteMany"]
  storageClassName: efs-sc
  resources:
    requests:
      storage: 5Gi
EOF

kubectl get pvc shared-data -n eks-107
```

EFS - региональная система, поэтому PVC переходит в `Bound` независимо от того, в какой
зоне потом окажутся поды: доступ к mount target есть из любой AZ, где он создан.

## Задание 4. Deployment `writer` (3 реплики, разные AZ, общий PVC)

`topologySpreadConstraints` по ключу `topology.kubernetes.io/zone` заставляет
планировщик раскладывать реплики по разным зонам:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: writer
  namespace: eks-107
spec:
  replicas: 3
  selector:
    matchLabels:
      app: writer
  template:
    metadata:
      labels:
        app: writer
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: writer
      containers:
      - name: app
        image: viktoruj/ping_pong:alpine
        volumeMounts:
        - name: data
          mountPath: /data
      volumes:
      - name: data
        persistentVolumeClaim:
          claimName: shared-data
EOF

kubectl rollout status deployment/writer -n eks-107
kubectl get po -n eks-107 -l app=writer -o wide
```

Проверяем, что реплики разъехались по разным AZ:

```bash
kubectl get po -n eks-107 -l app=writer \
  -o custom-columns='POD:.metadata.name,NODE:.spec.nodeName' --no-headers | \
  while read -r pod node; do
    zone=$(kubectl get node "$node" -o jsonpath='{.metadata.labels.topology\.kubernetes\.io/zone}')
    echo "$pod  node=$node  zone=$zone"
  done
```

Все 3 реплики одновременно `Running` и монтируют один и тот же PVC `shared-data`, хотя
находятся в разных AZ. С EBS это невозможно (`ReadWriteOnce`, ошибка
`Multi-Attach error`), потому что EBS - зональный блочный том, а EFS - региональная
NFS-система с mount target в каждой зоне.

## Задание 5. Общий доступ: пишем из одной реплики, читаем из другой

```bash
PODS=($(kubectl get po -n eks-107 -l app=writer -o jsonpath='{.items[*].metadata.name}'))
WRITER_POD=${PODS[0]}
READER_POD=${PODS[1]}

kubectl exec -n eks-107 "$WRITER_POD" -- sh -c \
  'echo "efs-rwx-test from $(hostname)" >> /data/shared.txt'

mkdir -p /var/work/tests/artifacts/5
kubectl exec -n eks-107 "$READER_POD" -- cat /data/shared.txt \
  > /var/work/tests/artifacts/5/readback.txt
cat /var/work/tests/artifacts/5/readback.txt
```

Строка, записанная подом `$WRITER_POD` в одной AZ, читается подом `$READER_POD` в другой
AZ - это подтверждает, что это правда общий сетевой том NFS, а не локальная копия на
диске ноды.

## Задание 6. Проверка отсутствия `nodeAffinity` на зону

```bash
mkdir -p /var/work/tests/artifacts/6

PV=$(kubectl get pvc shared-data -n eks-107 -o jsonpath='{.spec.volumeName}')
kubectl get pv "$PV" -o yaml > /var/work/tests/artifacts/6/pv.yaml
grep -A3 nodeAffinity /var/work/tests/artifacts/6/pv.yaml
echo "exit code: $?"

cat > /var/work/tests/artifacts/6/explanation.txt <<'EOF'
В PV, созданном efs.csi.aws.com, секции spec.nodeAffinity нет (в отличие от EBS, глава
23, где nodeAffinity фиксирует конкретную AZ через ключ topology.ebs.csi.aws.com/zone).
Причина - EFS - региональная файловая система с mount target в каждой AZ, поэтому под с
этим томом можно пересоздать в любой другой зоне кластера, и он продолжит видеть те же
данные через mount target своей новой зоны. Планировщику не нужно привязывать под к
конкретной ноде или зоне из-за тома, как это происходит с EBS.
EOF
cat /var/work/tests/artifacts/6/explanation.txt
```

Команда `grep -A3 nodeAffinity` ничего не находит (пустой вывод, код возврата `1`) - это
и есть подтверждение отсутствия секции. Сравните с `pv.yaml` из лабы 106 (EBS), где
`spec.nodeAffinity.required.nodeSelectorTerms` жёстко фиксирует зону тома.

## Задание 7. Диагностика: SG mount target и порт 2049 (read-only)

Ломать реальную инфраструктуру рискованно, поэтому задание только подтверждает текущее
состояние через AWS CLI и объясняет последствия отсутствия правила.

```bash
mkdir -p /var/work/tests/artifacts/7

FS_ID=$(aws efs describe-file-systems --region eu-central-1 \
  --query "FileSystems[?Tags[?Key=='Name' && Value=='eks-task107-efs']].FileSystemId" \
  --output text)

MT_SG=$(aws efs describe-mount-targets --region eu-central-1 --file-system-id "$FS_ID" \
  --query 'MountTargets[0].MountTargetId' --output text | \
  xargs -I{} aws efs describe-mount-target-security-groups --region eu-central-1 \
  --mount-target-id {} --query 'SecurityGroups[0]' --output text)

aws ec2 describe-security-groups --region eu-central-1 --group-ids "$MT_SG" \
  --query 'SecurityGroups[0].IpPermissions[?ToPort==`2049`]' \
  > /var/work/tests/artifacts/7/sg-rule.txt
cat /var/work/tests/artifacts/7/sg-rule.txt
```

Убедитесь, что в выводе есть правило `FromPort/ToPort: 2049`, `IpProtocol: tcp`, и что
источник (`UserIdGroupPairs`) - это security group нод кластера, а не CIDR. Сохраняем
диагностику причин и следствий:

```bash
cat > /var/work/tests/artifacts/7/diagnosis.txt <<'EOF'
Security group mount target разрешает inbound TCP 2049 (NFS) от security group нод
кластера - это подтверждено выводом aws ec2 describe-security-groups (sg-rule.txt).
Правило обязательно для каждого mount target: без него драйвер efs.csi.aws.com может
создать точку монтирования на уровне API, но сам процесс mount на ноде не сможет
установить NFS-соединение с mount target.

Если убрать это правило, монтирование не завершится с явной ошибкой сразу: TCP-пакеты на
порт 2049 будут отброшены security group, ядро на ноде будет ждать ответа NFS-сервера до
истечения таймаута. Под останется в Pending/ContainerCreating, а kubectl describe pod
покажет событие FailedMount с текстом вида "Unable to mount... connection timed out" - то
есть визуально похоже на медленную сеть, а не на явный отказ доступа, и без диагностики
security group причину легко перепутать с проблемой самого NFS-сервера или подсети.
EOF
cat /var/work/tests/artifacts/7/diagnosis.txt
```
