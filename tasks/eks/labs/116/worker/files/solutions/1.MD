## Задание 2. Симптом: IMDS недоступен из пода

NodePool `hardened` (единственный в этой лабе) выставляет на всех своих нодах
`httpPutResponseHopLimit=1` через `metadataOptions` EC2NodeClass. Пакет от процесса на
хосте идёт до IMDS за один hop, а пакет из пода делает лишний hop (сетевой namespace
контейнера) - и не укладывается в лимит. Заводим Deployment со спящим контейнером,
чтобы можно было зайти внутрь:

```bash
kubectl create deployment probe --image=curlimages/curl:latest -n eks-116 \
  -- sleep 3600
kubectl rollout status deployment/probe -n eks-116
```

Запрос IMDSv2 из пода (сначала токен, потом данные), с ограничением по времени:

```bash
POD=$(kubectl get po -n eks-116 -l app=probe -o jsonpath='{.items[0].metadata.name}')
mkdir -p /var/work/tests/artifacts/2

kubectl exec -n eks-116 "$POD" -- sh -c '
  echo "=== PUT token ===";
  TOKEN=$(curl -sX PUT --max-time 5 "http://169.254.169.254/latest/api/token" \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 21600");
  if [ -z "$TOKEN" ]; then
    echo "no token received: request timed out (hop limit blocked the pod)";
  else
    echo "=== GET with token ===";
    curl -s --max-time 5 -H "X-aws-ec2-metadata-token: $TOKEN" \
      http://169.254.169.254/latest/meta-data/iam/security-credentials/ \
      || echo "GET timed out (hop limit blocked the pod)";
  fi
' 2>&1 | tee /var/work/tests/artifacts/2/imds.txt

cat /var/work/tests/artifacts/2/imds.txt
```

При hop limit `1` `curl` не получает ответ за отведённые `5` секунд, и в файле
оказывается строка про таймаут (`curl` печатает `curl: (28) ... timeout` при `-v`, а
без токена скрипт сам добавляет пояснение `timed out`).

## Задание 3. Проверка через AWS API: hop limit и IMDSv2 на ноде

Смотрим, на какой ноде живёт `probe`, достаём `providerID` и вырезаем id инстанса:

```bash
NODE=$(kubectl get po -n eks-116 -l app=probe -o jsonpath='{.items[0].spec.nodeName}')
PROVIDER_ID=$(kubectl get node "$NODE" -o jsonpath='{.spec.providerID}')
# providerID вида aws:///eu-central-1a/i-0abc123def456789
INSTANCE_ID=$(echo "$PROVIDER_ID" | awk -F'/' '{print $NF}')
echo "node=$NODE instance=$INSTANCE_ID"

mkdir -p /var/work/tests/artifacts/3
aws ec2 describe-instances --instance-ids "$INSTANCE_ID" \
  --query 'Reservations[].Instances[].MetadataOptions' --output json \
  | tee /var/work/tests/artifacts/3/metadata_options.txt
```

В выводе должно быть `"HttpTokens": "required"` и `"HttpPutResponseHopLimit": 1` - это
именно то, что задал `vng.metadataOptions` в `eks_karpenter_hardened_vng/terragrunt.hcl`
и что EC2NodeClass передал в launch template ноды.

## Задание 4. Pod Security Admission: отказ привилегированному поду

Включаем restricted на namespace лейблами (PSA встроен в EKS, но по умолчанию namespace
без лейблов работает как `privileged` - ничего не ограничивает):

```bash
kubectl label namespace eks-116 \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest
```

Пробуем привилегированный под - admission должен отклонить создание:

```bash
mkdir -p /var/work/tests/artifacts/4
kubectl run priv-test -n eks-116 --image=busybox --restart=Never \
  --overrides='{"spec":{"containers":[{"name":"priv-test","image":"busybox","securityContext":{"privileged":true}}]}}' \
  2>&1 | tee /var/work/tests/artifacts/4/psa_reject.txt

kubectl get pod priv-test -n eks-116 2>&1 | tee -a /var/work/tests/artifacts/4/psa_reject.txt
cat /var/work/tests/artifacts/4/psa_reject.txt
```

Ожидаемый вывод похож на:

```
Error from server (Forbidden): pods "priv-test" is forbidden: violates PodSecurity "restricted:latest": privileged (container "priv-test" must not set securityContext.privileged=true)
```

Под не создаётся (`kubectl get pod priv-test` вернёт `NotFound`), в сообщении есть слова
`privileged` и `restricted`/`violates` - это и требуется по критериям приёмки.

## Задание 5. Разрешённый путь: под, совместимый с restricted

Собираем под со всеми полями, которые требует профиль `restricted`:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: safe-pod
  namespace: eks-116
spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: busybox:latest
    command: ["sleep", "3600"]
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: ["ALL"]
EOF

kubectl get pod safe-pod -n eks-116 -o wide
```

Под проходит admission и переходит в `Running` - тот же namespace, тот же профиль
`restricted`, но требования выполнены полностью: `runAsNonRoot`,
`allowPrivilegeEscalation: false`, `capabilities.drop: ["ALL"]`, `seccompProfile`
`RuntimeDefault`.

## Задание 6. Приватный доступ control plane и VPC endpoints

Проверяем `resourcesVpcConfig` кластера - модуль `eks_v2_control_plane` уже включает оба
флага (`endpoint_public_access = true`, `endpoint_private_access = true`):

```bash
CLUSTER=$(kubectl config current-context | sed 's|.*/||')
mkdir -p /var/work/tests/artifacts/6

aws eks describe-cluster --name "$CLUSTER" \
  --query 'cluster.resourcesVpcConfig' --output json \
  | tee /var/work/tests/artifacts/6/private_endpoint.txt
```

В выводе - `"endpointPrivateAccess": true`. Дополняем файл объяснением:

```bash
cat >> /var/work/tests/artifacts/6/private_endpoint.txt <<'EOF'

Для полностью приватного кластера (ноды без выхода в интернет) нужны VPC endpoints:
ecr.api и ecr.dkr (тянуть образы контейнеров), s3 gateway endpoint (слои образов ECR
физически лежат в S3, поэтому без него образ не скачается даже с ecr.api и ecr.dkr на
месте), sts (обмен токена IRSA на временные креды), ec2 (регистрация ноды и DNS-имя),
logs (доставка логов в CloudWatch) и eks (доступ к API EKS из VPC). Private access
control plane (уже включён в этом кластере) обязателен отдельно от списка endpoints -
без него ноды не смогут зарегистрироваться в API-сервере из приватной подсети.
EOF

cat /var/work/tests/artifacts/6/private_endpoint.txt
```
