# Lab 116 - reference solution (IMDSv2 hop limit, Pod Security Admission, private endpoint)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster (kubeconfig was built via `aws eks update-kubeconfig` when the machine booted).

## Task 1. Namespace `eks-116`

```bash
kubectl create namespace eks-116
```

## Task 2. Symptom: IMDS is unreachable from the pod

The `hardened` NodePool (the only one in this lab) sets `httpPutResponseHopLimit=1` on
all its nodes via the EC2NodeClass `metadataOptions`. A packet from a process on the
host reaches IMDS in one hop, while a packet from a pod makes one extra hop (the
container network namespace) - and does not fit the limit. Create a Deployment with a
sleeping container so you can exec into it:

```bash
kubectl create deployment probe --image=curlimages/curl:latest -n eks-116 \
  -- sleep 3600
kubectl rollout status deployment/probe -n eks-116
```

Run an IMDSv2 request from the pod (token first, then data), with a time limit:

```bash
POD=$(kubectl get po -n eks-116 -l app=probe -o jsonpath='{.items[0].metadata.name}')
mkdir -p /var/work/tests/artifacts/2

kubectl exec -n eks-116 "$POD" -- sh -c '
  echo "=== PUT token ===";
  TOKEN=$(curl -sX PUT --max-time 5 "http://169.254.169.254/latest/api/token" \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 21600");
  if [ -z "$TOKEN" ]; then
    echo "no token received: request timed out (hop limit blocked the pod)";
  else
    echo "=== GET with token ===";
    curl -s --max-time 5 -H "X-aws-ec2-metadata-token: $TOKEN" \
      http://169.254.169.254/latest/meta-data/iam/security-credentials/ \
      || echo "GET timed out (hop limit blocked the pod)";
  fi
' 2>&1 | tee /var/work/tests/artifacts/2/imds.txt

cat /var/work/tests/artifacts/2/imds.txt
```

With hop limit `1`, `curl` does not get a response within the allotted `5` seconds, and
the file ends up with a line about a timeout (`curl` prints `curl: (28) ... timeout`
with `-v`, and without a token the script itself adds the `timed out` note).

## Task 3. Verifying via the AWS API: hop limit and IMDSv2 on the node

Find which node `probe` runs on, grab its `providerID` and extract the instance id:

```bash
NODE=$(kubectl get po -n eks-116 -l app=probe -o jsonpath='{.items[0].spec.nodeName}')
PROVIDER_ID=$(kubectl get node "$NODE" -o jsonpath='{.spec.providerID}')
# providerID looks like aws:///eu-central-1a/i-0abc123def456789
INSTANCE_ID=$(echo "$PROVIDER_ID" | awk -F'/' '{print $NF}')
echo "node=$NODE instance=$INSTANCE_ID"

mkdir -p /var/work/tests/artifacts/3
aws ec2 describe-instances --instance-ids "$INSTANCE_ID" \
  --query 'Reservations[].Instances[].MetadataOptions' --output json \
  | tee /var/work/tests/artifacts/3/metadata_options.txt
```

The output should show `"HttpTokens": "required"` and `"HttpPutResponseHopLimit": 1` -
exactly what `vng.metadataOptions` in `eks_karpenter_hardened_vng/terragrunt.hcl` set,
and what the EC2NodeClass passed to the node's launch template.

## Task 4. Pod Security Admission: rejecting a privileged pod

Enable restricted on the namespace via labels (PSA is built into EKS, but by default a
namespace without labels behaves like `privileged` - nothing is restricted):

```bash
kubectl label namespace eks-116 \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest
```

Try a privileged pod - admission should reject the creation:

```bash
mkdir -p /var/work/tests/artifacts/4
kubectl run priv-test -n eks-116 --image=busybox --restart=Never \
  --overrides='{"spec":{"containers":[{"name":"priv-test","image":"busybox","securityContext":{"privileged":true}}]}}' \
  2>&1 | tee /var/work/tests/artifacts/4/psa_reject.txt

kubectl get pod priv-test -n eks-116 2>&1 | tee -a /var/work/tests/artifacts/4/psa_reject.txt
cat /var/work/tests/artifacts/4/psa_reject.txt
```

Expected output looks like:

```
Error from server (Forbidden): pods "priv-test" is forbidden: violates PodSecurity "restricted:latest": privileged (container "priv-test" must not set securityContext.privileged=true)
```

The pod is not created (`kubectl get pod priv-test` returns `NotFound`), and the message
contains the words `privileged` and `restricted`/`violates` - which is exactly what the
acceptance criteria require.

## Task 5. The allowed path: a pod compatible with restricted

Build a pod with all the fields the `restricted` profile requires. `runAsNonRoot: true`
only forbids running as root - the `busybox:latest` image does not declare a non-root
user by default, so without an explicit `runAsUser` (any non-zero UID) kubelet blocks
the container start with a separate error, `container has runAsNonRoot and image will
run as root`, after admission has already let the pod through:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: safe-pod
  namespace: eks-116
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: busybox:latest
    command: ["sleep", "3600"]
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: ["ALL"]
EOF

kubectl get pod safe-pod -n eks-116 -o wide
```

The pod passes admission and moves to `Running` - same namespace, same `restricted`
profile, but the requirements are fully met: `runAsNonRoot` with an explicit
`runAsUser`, `allowPrivilegeEscalation: false`, `capabilities.drop: ["ALL"]`,
`seccompProfile` `RuntimeDefault`.

## Task 6. Private control plane access and VPC endpoints

Check the cluster's `resourcesVpcConfig` - the `eks_v2_control_plane` module already
enables both flags (`endpoint_public_access = true`, `endpoint_private_access = true`):

```bash
CLUSTER=$(kubectl config current-context | sed 's|.*/||')
mkdir -p /var/work/tests/artifacts/6

aws eks describe-cluster --name "$CLUSTER" \
  --query 'cluster.resourcesVpcConfig' --output json \
  | tee /var/work/tests/artifacts/6/private_endpoint.txt
```

The output shows `"endpointPrivateAccess": true`. Append an explanation to the file:

```bash
cat >> /var/work/tests/artifacts/6/private_endpoint.txt <<'EOF'

A fully private cluster (nodes without internet access) needs VPC endpoints: ecr.api
and ecr.dkr (to pull container images), the s3 gateway endpoint (ECR image layers
physically live in S3, so without it the image will not download even with ecr.api and
ecr.dkr in place), sts (exchanging the IRSA token for temporary credentials), ec2 (node
registration and DNS name), logs (shipping logs to CloudWatch) and eks (accessing the
EKS API from the VPC). Private access to the control plane (already enabled on this
cluster) is required separately from the endpoint list - without it, nodes cannot
register with the API server from a private subnet.
EOF

cat /var/work/tests/artifacts/6/private_endpoint.txt
```
