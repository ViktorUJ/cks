# Lab 132 - reference solution (Cilium in CNI chaining mode over VPC CNI)

All commands are run on the worker machine over SSH. kubectl and helm are already
configured (kubeconfig was built via `aws eks update-kubeconfig` at machine boot).

> Cilium versions and the exact names of chaining-mode values flags change quickly between
> releases. The commands below were verified on a live bench with Cilium `1.20.0` and EKS
> `1.36`. If you're using a different version, check the syntax against the Cilium
> documentation (`https://docs.cilium.io/en/stable/installation/cni-chaining-aws-cni/`).

```bash
kubectl create namespace eks-132
```

## Task 2. Workload on the `cilium-demo` pool without Cilium

The NodePool `cilium-demo` already exists as code (taint `dedicated=cilium-demo:NoSchedule`,
label `work_type=cilium-demo`), but until a pod with a matching toleration lands on it,
Karpenter won't bring up a single node. We create Deployment `api` and `client` right away
with `nodeSelector` and toleration, so they land exactly there:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: eks-132
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      nodeSelector:
        work_type: cilium-demo
      tolerations:
        - key: dedicated
          operator: Equal
          value: cilium-demo
          effect: NoSchedule
      containers:
      - name: app
        image: viktoruj/ping_pong:latest
        ports:
        - containerPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: api
  namespace: eks-132
spec:
  selector:
    app: api
  ports:
  - port: 8080
    targetPort: 8080
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: client
  namespace: eks-132
spec:
  replicas: 1
  selector:
    matchLabels:
      app: client
  template:
    metadata:
      labels:
        app: client
    spec:
      nodeSelector:
        work_type: cilium-demo
      tolerations:
        - key: dedicated
          operator: Equal
          value: cilium-demo
          effect: NoSchedule
      containers:
      - name: curl
        image: curlimages/curl:latest
        command: ["sleep", "3600"]
EOF

kubectl rollout status deployment/api -n eks-132
kubectl rollout status deployment/client -n eks-132
```

Karpenter brings up a new node in the `cilium-demo` pool (usually 60-90 seconds). As soon
as `rollout status` confirms readiness, we check connectivity over plain VPC CNI - Cilium
is not installed yet:

```bash

CLIENT_POD=$(kubectl get po -n eks-132 -l app=client -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n eks-132 "$CLIENT_POD" -- \
  curl -s -o /dev/null --connect-timeout 5 --max-time 8 \
  -w "HTTP_CODE=%{http_code}\n" http://api.eks-132.svc.cluster.local:8080 \
  > /var/work/tests/artifacts/2/connectivity_before.txt
cat /var/work/tests/artifacts/2/connectivity_before.txt
```

## Task 3. Cilium via Helm in CNI chaining mode, only on `cilium-demo`

We add the Cilium repository and prepare a values file. The key parameter is
`cni.chainingMode: aws-cni`: VPC CNI (`aws-node`) remains the main IPAM, Cilium plugs into
the chain and adds eBPF programs on top of the pod interface already configured.

Three `nodeSelector`/`tolerations` blocks (top level for the agent, `envoy` and `operator`)
confine all Cilium components to the `cilium-demo` pool. The top-level `nodeSelector` is
only inherited by the `cilium` DaemonSet; `cilium-envoy` and `cilium-operator` have their
own sections, and without them the Envoy pods hang in `Pending` on all the other nodes, and
`cilium status` shows `Envoy DaemonSet: 1 errors`.

Separately we turn off `operator.unmanagedPodWatcher.restart`. This is a mandatory flag for
this bench, not a fine-tuning option: by default the operator deletes pods without a
`CiliumEndpoint` every 15 seconds so they restart and join the CNI chain. `coredns` pods
live on Fargate, where there is no Cilium agent and can never be one, so they will never
become managed - the operator kills them endlessly, spinning up a new Fargate node every
time, and DNS in the cluster goes down (details in the "Gotchas" section below).

```bash
helm repo add cilium https://helm.cilium.io/
helm repo update

cat <<'EOF' > /tmp/cilium-values.yaml
cni:
  chainingMode: aws-cni
  exclusive: false
enableIPv4Masquerade: false
routingMode: native
nodeSelector:
  work_type: cilium-demo
tolerations:
  - key: dedicated
    operator: Equal
    value: cilium-demo
    effect: NoSchedule
envoy:
  nodeSelector:
    work_type: cilium-demo
  tolerations:
    - key: dedicated
      operator: Equal
      value: cilium-demo
      effect: NoSchedule
operator:
  nodeSelector:
    work_type: cilium-demo
  tolerations:
    - key: dedicated
      operator: Equal
      value: cilium-demo
      effect: NoSchedule
  unmanagedPodWatcher:
    restart: false
EOF

helm install cilium cilium/cilium --version 1.20.0 \
  --namespace kube-system \
  -f /tmp/cilium-values.yaml

kubectl -n kube-system rollout status daemonset/cilium --timeout=300s
kubectl get pods -n kube-system -l k8s-app=cilium -o wide
```

The `api` and `client` pods were started before Cilium was installed, so CNI chaining has
not taken effect on them yet (the Cilium documentation explicitly warns about this:
existing pods need to be restarted). We restart both Deployments:

```bash
kubectl rollout restart deployment/api -n eks-132
kubectl rollout restart deployment/client -n eks-132
kubectl rollout status deployment/api -n eks-132
kubectl rollout status deployment/client -n eks-132
```

We install the Cilium CLI and check the status:

```bash

CLI_ARCH=amd64
if [ "$(uname -m)" = "aarch64" ]; then CLI_ARCH=arm64; fi
curl -L --fail --remote-name-all \
  "https://github.com/cilium/cilium-cli/releases/download/${CILIUM_CLI_VERSION}/cilium-linux-${CLI_ARCH}.tar.gz"
sudo tar xzvfC "cilium-linux-${CLI_ARCH}.tar.gz" /usr/local/bin
rm "cilium-linux-${CLI_ARCH}.tar.gz"

mkdir -p /var/work/tests/artifacts/3
cilium status | tee /var/work/tests/artifacts/3/cilium_status.txt
```

The output should contain `Cilium: OK`, `Operator: OK` and `Envoy DaemonSet: OK`, and the
`Desired` count for both DaemonSets should match the number of `cilium-demo` nodes.

## Task 5. L7 policy: GET only

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: "cilium.io/v2"
kind: CiliumNetworkPolicy
metadata:
  name: cilium-l7-allow-get
  namespace: eks-132
spec:
  endpointSelector:
    matchLabels:
      app: api
  ingress:
  - fromEndpoints:
    - matchLabels:
        app: client
    toPorts:
    - ports:
      - port: "8080"
        protocol: TCP
      rules:
        http:
        - method: "GET"
          path: "/.*"
EOF

kubectl get ciliumnetworkpolicies.cilium.io cilium-l7-allow-get -n eks-132
```

We check the allowed GET and the blocked POST:

```bash
mkdir -p /var/work/tests/artifacts/5
CLIENT_POD=$(kubectl get po -n eks-132 -l app=client -o jsonpath='{.items[0].metadata.name}')

kubectl exec -n eks-132 "$CLIENT_POD" -- \
  curl -s -o /dev/null --connect-timeout 5 --max-time 8 \
  -w "HTTP_CODE=%{http_code}\n" http://api.eks-132.svc.cluster.local:8080 \
  > /var/work/tests/artifacts/5/allowed_get.txt
cat /var/work/tests/artifacts/5/allowed_get.txt

kubectl exec -n eks-132 "$CLIENT_POD" -- \
  curl -s -o /dev/null --connect-timeout 5 --max-time 8 -X POST \
  -w "HTTP_CODE=%{http_code}\n" http://api.eks-132.svc.cluster.local:8080 \
  > /var/work/tests/artifacts/5/blocked_post.txt || true
cat /var/work/tests/artifacts/5/blocked_post.txt
```

GET goes through (`HTTP_CODE=200`), POST is blocked by Cilium's Envoy proxy at the L7 level
(`HTTP_CODE=403`, access denied before the request even reaches the application). The
built-in VPC CNI NetworkPolicy has no such HTTP-method filter - only L3/L4 (chapter 8).

Use the full name `ciliumnetworkpolicies.cilium.io`: the short name `cnp` is ambiguous in
this cluster, because VPC CNI brings its own resource
`clusternetworkpolicies.networking.k8s.aws`, and kubectl warns about it.

## Task 6. FQDN policy: egress only to `aws.amazon.com`

There are two places where this policy behaves differently from the typical example in the
documentation.

First: the DNS rule can't be written via `toEndpoints` with the label `k8s-app: kube-dns`.
`toEndpoints` works by Cilium identity, and `coredns` pods in this cluster live on Fargate,
where there is no Cilium agent - they have no `CiliumEndpoint`, don't end up in `ipcache`,
and from the policy's point of view look like `reserved:world`. A label-based rule would
never match, DNS would be closed by default-deny, and `curl` couldn't even resolve the
name. So we allow DNS by CIDR instead: the cluster's service range (`172.20.0.0/16`, where
the `kube-dns` ClusterIP lives) and the VPC CIDR (`10.10.0.0/16`, where the `coredns` pods
themselves live). L7 `rules.dns` rules on `toCIDRSet` work as expected - this is exactly
how Cilium documents the case of an external DNS server.

Second: the `endpointSelector` on `app: client` turns on default-deny for all egress of
this pod. If we only leave `toFQDNs` and DNS, the GET to `api` from task 5 breaks - its
packets get dropped. So as a third block we explicitly allow egress to `api:8080`. This way
the bench's final state is consistent: task 5 and task 6 are both true at the same time.

The order of the blocks matters: `toFQDNs` must stay first (`egress[0]`), the automated
test looks exactly there.

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: "cilium.io/v2"
kind: CiliumNetworkPolicy
metadata:
  name: cilium-fqdn-allow-aws
  namespace: eks-132
spec:
  endpointSelector:
    matchLabels:
      app: client
  egress:
  - toFQDNs:
    - matchName: "aws.amazon.com"
    toPorts:
    - ports:
      - port: "443"
        protocol: TCP
  - toCIDRSet:
    - cidr: 172.20.0.0/16
    - cidr: 10.10.0.0/16
    toPorts:
    - ports:
      - port: "53"
        protocol: ANY
      rules:
        dns:
        - matchPattern: "*"
  - toEndpoints:
    - matchLabels:
        app: api
    toPorts:
    - ports:
      - port: "8080"
        protocol: TCP
EOF

kubectl get ciliumnetworkpolicies.cilium.io cilium-fqdn-allow-aws -n eks-132
```

We check it:

```bash
mkdir -p /var/work/tests/artifacts/6
CLIENT_POD=$(kubectl get po -n eks-132 -l app=client -o jsonpath='{.items[0].metadata.name}')

kubectl exec -n eks-132 "$CLIENT_POD" -- \
  curl -s -o /dev/null --connect-timeout 5 --max-time 10 \
  -w "HTTP_CODE=%{http_code}\n" https://aws.amazon.com \
  > /var/work/tests/artifacts/6/allowed_fqdn.txt || true
cat /var/work/tests/artifacts/6/allowed_fqdn.txt

kubectl exec -n eks-132 "$CLIENT_POD" -- \
  curl -s -o /dev/null --connect-timeout 5 --max-time 10 \
  -w "HTTP_CODE=%{http_code}\n" https://example.com \
  > /var/work/tests/artifacts/6/blocked_other_domain.txt || true
cat /var/work/tests/artifacts/6/blocked_other_domain.txt
```

`aws.amazon.com` resolves and `curl` goes through - `HTTP_CODE=200`. `example.com` also
resolves (DNS is allowed), but the TCP session to its address is not covered by `toFQDNs`,
packets get dropped, and `curl` hangs until `--max-time` - `HTTP_CODE=000`. The built-in
VPC CNI NetworkPolicy has no such DNS-name-based policy at all - only `ipBlock` by IP/CIDR
(chapter 8).

## Task 7. Hubble: flow observability with verdict

We enable Hubble relay on top of the already installed Cilium, with the same
`nodeSelector` on `cilium-demo`:

```bash
cat <<'EOF' >> /tmp/cilium-values.yaml
hubble:
  relay:
    enabled: true
    nodeSelector:
      work_type: cilium-demo
    tolerations:
      - key: dedicated
        operator: Equal
        value: cilium-demo
        effect: NoSchedule
EOF

helm upgrade cilium cilium/cilium --version 1.20.0 \
  --namespace kube-system \
  -f /tmp/cilium-values.yaml

kubectl -n kube-system rollout status deployment/hubble-relay --timeout=240s
```

We install the Hubble CLI:

```bash
HUBBLE_VERSION=$(curl -fsSL https://raw.githubusercontent.com/cilium/hubble/main/stable.txt)
HUBBLE_ARCH=amd64
if [ "$(uname -m)" = "aarch64" ]; then HUBBLE_ARCH=arm64; fi
curl -L --fail --remote-name-all \
  "https://github.com/cilium/hubble/releases/download/${HUBBLE_VERSION}/hubble-linux-${HUBBLE_ARCH}.tar.gz"
sudo tar xzvfC "hubble-linux-${HUBBLE_ARCH}.tar.gz" /usr/local/bin
rm "hubble-linux-${HUBBLE_ARCH}.tar.gz"
```

We start a port-forward to the relay (`4245`), repeat the blocked requests from tasks 5 and
6 to get `DROPPED` events, and read the flow:

```bash
setsid nohup kubectl -n kube-system port-forward service/hubble-relay 4245:80 \
  </dev/null >/tmp/pf.log 2>&1 &
sleep 5

CLIENT_POD=$(kubectl get po -n eks-132 -l app=client -o jsonpath='{.items[0].metadata.name}')
for i in 1 2 3; do
  kubectl exec -n eks-132 "$CLIENT_POD" -- \
    curl -s -o /dev/null --connect-timeout 3 --max-time 5 -X POST \
    http://api.eks-132.svc.cluster.local:8080 >/dev/null 2>&1 || true
  kubectl exec -n eks-132 "$CLIENT_POD" -- \
    curl -s -o /dev/null --connect-timeout 3 --max-time 5 \
    https://example.com >/dev/null 2>&1 || true
done

mkdir -p /var/work/tests/artifacts/7
hubble observe --server localhost:4245 -n eks-132 --last 200 \
  | tee /var/work/tests/artifacts/7/hubble_denied.txt
grep -c DROPPED /var/work/tests/artifacts/7/hubble_denied.txt
```

Always start the port-forward via `setsid nohup ... </dev/null &`: a plain
`kubectl port-forward &` holds on to the SSH session and gets killed when you disconnect.

The file should contain lines with verdict `DROPPED` - these are dropped SYNs to
`example.com` addresses (`policy-verdict:none ... Policy denied DROPPED`). The built-in VPC
CNI network policy's diagnostics has no such per-flow verdict map - only
`aws-network-policy-agent` logs and metrics (chapter 8).

## Gotchas encountered in this lab

All four points were verified on a live bench.

1. `cilium-operator` takes down cluster DNS. By default
   `operator.unmanagedPodWatcher.restart=true`: the operator deletes pods without a
   `CiliumEndpoint` every 15 seconds. `coredns` on Fargate will never become one, so its
   pods get deleted in a loop, a new Fargate micro-VM is born for each one, and DNS in the
   cluster comes and goes. The symptom from the pod's side: `nslookup` returns
   `connection timed out; no servers could be reached`. Who exactly is deleting the pods
   can be seen in the control plane audit log: entries with `verb: delete` on `coredns`
   pods show `user.username = system:serviceaccount:kube-system:cilium-operator` and
   `userAgent = cilium-operator-generic/1.20.0`. It's fixed by the flag
   `operator.unmanagedPodWatcher.restart=false` (`cilium-config` will get
   `unmanaged-pod-watcher-interval: "0"`).

2. The Fargate profile doesn't know `nodeSelector`. If the profile covers the whole
   `kube-system` namespace (`selectors = [{ namespace = "kube-system" }]`), the Fargate
   webhook tags with its profile ANY pod you add to this namespace later, including
   `cilium-operator`. From then on the pod is scheduled only by `fargate-scheduler`, which
   knows neither `hostNetwork` nor `nodeSelector` and never falls back to the regular
   scheduler. Symptoms: `Pod not supported on Fargate: fields not supported: HostNetwork,
   port contains HostIP or HostPort`, and after `operator.hostNetwork=false` -
   `MatchNodeSelector failed: Fargate profile kube-system cannot satisfy pod's node
   selector/affinity requirements`. That's why in this lab the profile is narrowed by the
   label selector `eks.amazonaws.com/component: coredns` (see
   `eks_fargate_system/terragrunt.hcl`).

3. The Fargate profile was recreated - restart the pods it should pick up. Pod mutation
   only happens at the moment a pod is created, so a `karpenter` pod created before the new
   profile became `ACTIVE` will stay in `Pending` forever with
   `0/N nodes are available: N node(s) had untolerated taint(s)`. It's fixed with
   `kubectl delete pod` on that pod.

4. `cilium-envoy` pods hang in `Pending` if only the top-level `nodeSelector` is set. The
   `cilium-envoy` DaemonSet has its own `envoy.nodeSelector` / `envoy.tolerations` section;
   without it, it targets all Linux nodes, and `cilium status` shows
   `Envoy DaemonSet: 1 errors`.
