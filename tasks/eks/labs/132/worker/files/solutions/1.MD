# Лаба 132 - эталонное решение (Cilium в режиме CNI chaining над VPC CNI)

Все команды выполняются на рабочей машине (worker) по SSH. kubectl и helm уже настроены
(kubeconfig собран через `aws eks update-kubeconfig` при загрузке машины).

> Версии Cilium и точные имена values-флагов chaining-режима быстро меняются между
> релизами. Перед реальным прогоном лабы сверьте актуальный синтаксис с документацией
> Cilium (`https://docs.cilium.io/en/stable/installation/cni-chaining-aws-cni/`) - команды
> ниже проверены по этой странице на момент написания решения, но конкретный набор флагов
> Helm chart может измениться в новых версиях Cilium.

## Задание 2. Нагрузка на пуле `cilium-demo` без Cilium

NodePool `cilium-demo` уже существует как код (taint `dedicated=cilium-demo:NoSchedule`,
label `work_type=cilium-demo`), но пока в него не поступит под с toleration, Karpenter не
поднимет ни одной ноды. Deployment `api` и `client` создаём сразу с `nodeSelector` и
toleration, чтобы они попали именно туда:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: eks-132
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      nodeSelector:
        work_type: cilium-demo
      tolerations:
        - key: dedicated
          operator: Equal
          value: cilium-demo
          effect: NoSchedule
      containers:
      - name: app
        image: viktoruj/ping_pong:latest
        ports:
        - containerPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: api
  namespace: eks-132
spec:
  selector:
    app: api
  ports:
  - port: 8080
    targetPort: 8080
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: client
  namespace: eks-132
spec:
  replicas: 1
  selector:
    matchLabels:
      app: client
  template:
    metadata:
      labels:
        app: client
    spec:
      nodeSelector:
        work_type: cilium-demo
      tolerations:
        - key: dedicated
          operator: Equal
          value: cilium-demo
          effect: NoSchedule
      containers:
      - name: curl
        image: curlimages/curl:latest
        command: ["sleep", "3600"]
EOF

kubectl rollout status deployment/api -n eks-132
kubectl rollout status deployment/client -n eks-132
```

Karpenter поднимает новую ноду в пуле `cilium-demo` (обычно 60-90 секунд). Как только
`rollout status` подтвердил готовность, проверяем связность через штатный VPC CNI - Cilium
ещё не установлен:

```bash
mkdir -p /var/work/tests/artifacts/2
CLIENT_POD=$(kubectl get po -n eks-132 -l app=client -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n eks-132 "$CLIENT_POD" -- \
  curl -s -o /dev/null --connect-timeout 5 --max-time 8 \
  -w "HTTP_CODE=%{http_code}\n" http://api.eks-132.svc.cluster.local:8080 \
  > /var/work/tests/artifacts/2/connectivity_before.txt
cat /var/work/tests/artifacts/2/connectivity_before.txt
```

## Задание 3. Cilium через Helm в режиме CNI chaining, только на `cilium-demo`

Добавляем репозиторий Cilium и готовим values-файл. Ключевой параметр -
`cni.chainingMode: aws-cni`: VPC CNI (`aws-node`) остаётся основным IPAM, Cilium
подключается в цепочку и добавляет eBPF-программы поверх уже настроенного интерфейса пода.
`nodeSelector` и `tolerations` ограничивают агент и оператор только пулом `cilium-demo`,
чтобы не тронуть системные Fargate-поды и общий default-пул:

```bash
helm repo add cilium https://helm.cilium.io/
helm repo update

cat <<'EOF' > /tmp/cilium-values.yaml
cni:
  chainingMode: aws-cni
  exclusive: false
enableIPv4Masquerade: false
routingMode: native
nodeSelector:
  work_type: cilium-demo
tolerations:
  - key: dedicated
    operator: Equal
    value: cilium-demo
    effect: NoSchedule
operator:
  nodeSelector:
    work_type: cilium-demo
  tolerations:
    - key: dedicated
      operator: Equal
      value: cilium-demo
      effect: NoSchedule
EOF

helm install cilium cilium/cilium --version 1.20.0 \
  --namespace kube-system \
  -f /tmp/cilium-values.yaml

kubectl -n kube-system rollout status daemonset/cilium --timeout=300s
kubectl get pods -n kube-system -l k8s-app=cilium -o wide
```

Поды `api` и `client` были запущены до установки Cilium, поэтому CNI chaining на них ещё
не подействовал (документация Cilium прямо предупреждает про это: существующие поды нужно
перезапустить). Перезапускаем оба Deployment:

```bash
kubectl rollout restart deployment/api -n eks-132
kubectl rollout restart deployment/client -n eks-132
kubectl rollout status deployment/api -n eks-132
kubectl rollout status deployment/client -n eks-132
```

Устанавливаем Cilium CLI и проверяем состояние:

```bash
CILIUM_CLI_VERSION=$(curl -s https://raw.githubusercontent.com/cilium/cilium-cli/main/stable.txt)
CLI_ARCH=amd64
if [ "$(uname -m)" = "aarch64" ]; then CLI_ARCH=arm64; fi
curl -L --fail --remote-name-all \
  "https://github.com/cilium/cilium-cli/releases/download/${CILIUM_CLI_VERSION}/cilium-linux-${CLI_ARCH}.tar.gz"
sudo tar xzvfC "cilium-linux-${CLI_ARCH}.tar.gz" /usr/local/bin
rm "cilium-linux-${CLI_ARCH}.tar.gz"

mkdir -p /var/work/tests/artifacts/3
cilium status | tee /var/work/tests/artifacts/3/cilium_status.txt
```

В выводе должны быть строки `Cilium:` и `OK` (агент и оператор здоровы).

## Задание 5. L7-политика: только GET

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: "cilium.io/v2"
kind: CiliumNetworkPolicy
metadata:
  name: cilium-l7-allow-get
  namespace: eks-132
spec:
  endpointSelector:
    matchLabels:
      app: api
  ingress:
  - fromEndpoints:
    - matchLabels:
        app: client
    toPorts:
    - ports:
      - port: "8080"
        protocol: TCP
      rules:
        http:
        - method: "GET"
          path: "/.*"
EOF

kubectl get cnp cilium-l7-allow-get -n eks-132
```

Проверяем разрешённый GET и заблокированный POST:

```bash
mkdir -p /var/work/tests/artifacts/5
CLIENT_POD=$(kubectl get po -n eks-132 -l app=client -o jsonpath='{.items[0].metadata.name}')

kubectl exec -n eks-132 "$CLIENT_POD" -- \
  curl -s -o /dev/null --connect-timeout 5 --max-time 8 \
  -w "HTTP_CODE=%{http_code}\n" http://api.eks-132.svc.cluster.local:8080 \
  > /var/work/tests/artifacts/5/allowed_get.txt
cat /var/work/tests/artifacts/5/allowed_get.txt

kubectl exec -n eks-132 "$CLIENT_POD" -- \
  curl -s -o /dev/null --connect-timeout 5 --max-time 8 -X POST \
  -w "HTTP_CODE=%{http_code}\n" http://api.eks-132.svc.cluster.local:8080 \
  > /var/work/tests/artifacts/5/blocked_post.txt || true
cat /var/work/tests/artifacts/5/blocked_post.txt
```

GET проходит (`HTTP_CODE=200`), POST блокируется Envoy-прокси Cilium на уровне L7 (обычно
`HTTP_CODE=403`, доступ отклонён до того, как запрос дошёл до приложения). У встроенного
VPC CNI NetworkPolicy такого фильтра по HTTP-методу нет - только L3/L4 (глава 8).

## Задание 6. FQDN-политика: egress только на `aws.amazon.com`

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: "cilium.io/v2"
kind: CiliumNetworkPolicy
metadata:
  name: cilium-fqdn-allow-aws
  namespace: eks-132
spec:
  endpointSelector:
    matchLabels:
      app: client
  egress:
  - toFQDNs:
    - matchName: "aws.amazon.com"
    toPorts:
    - ports:
      - port: "443"
        protocol: TCP
  - toEndpoints:
    - matchLabels:
        "k8s:io.kubernetes.pod.namespace": kube-system
        "k8s:k8s-app": kube-dns
    toPorts:
    - ports:
      - port: "53"
        protocol: ANY
      rules:
        dns:
        - matchPattern: "*"
EOF

kubectl get cnp cilium-fqdn-allow-aws -n eks-132
```

Первый блок egress - `toFQDNs.matchName` разрешает трафик только на `aws.amazon.com` по
TCP `443`. Второй блок разрешает DNS-запросы к `kube-dns`, иначе имя вообще не
разрезолвится (без этого правила Cilium не даст поду сходить в DNS). Проверяем:

```bash
mkdir -p /var/work/tests/artifacts/6
CLIENT_POD=$(kubectl get po -n eks-132 -l app=client -o jsonpath='{.items[0].metadata.name}')

kubectl exec -n eks-132 "$CLIENT_POD" -- \
  curl -s -o /dev/null --connect-timeout 5 --max-time 8 \
  -w "HTTP_CODE=%{http_code}\n" https://aws.amazon.com \
  > /var/work/tests/artifacts/6/allowed_fqdn.txt || true
cat /var/work/tests/artifacts/6/allowed_fqdn.txt

kubectl exec -n eks-132 "$CLIENT_POD" -- \
  curl -s -o /dev/null --connect-timeout 5 --max-time 8 \
  -w "HTTP_CODE=%{http_code}\n" https://example.com \
  > /var/work/tests/artifacts/6/blocked_other_domain.txt || true
cat /var/work/tests/artifacts/6/blocked_other_domain.txt
```

`aws.amazon.com` резолвится (правило DNS разрешает запрос) и `curl` проходит - код `2xx`
или `3xx`. `example.com` тоже резолвится (DNS не заблокирован), но сама TCP-сессия на его
адрес не входит в `toFQDNs`, поэтому пакеты дропаются, и `curl` виснет до `--max-time` -
код `000` или не `200`. Такой политики по DNS-имени у встроенного VPC CNI NetworkPolicy
нет вовсе - только `ipBlock` по IP/CIDR (глава 8).

## Задание 7. Hubble: наблюдаемость потоков с verdict

Включаем Hubble relay поверх уже установленного Cilium, тем же `nodeSelector` на
`cilium-demo`:

```bash
cat <<'EOF' >> /tmp/cilium-values.yaml
hubble:
  relay:
    enabled: true
    nodeSelector:
      work_type: cilium-demo
    tolerations:
      - key: dedicated
        operator: Equal
        value: cilium-demo
        effect: NoSchedule
EOF

helm upgrade cilium cilium/cilium --version 1.20.0 \
  --namespace kube-system \
  -f /tmp/cilium-values.yaml

kubectl -n kube-system rollout status deployment/hubble-relay --timeout=180s
```

Устанавливаем Hubble CLI:

```bash
HUBBLE_VERSION=$(curl -s https://raw.githubusercontent.com/cilium/hubble/main/stable.txt)
HUBBLE_ARCH=amd64
if [ "$(uname -m)" = "aarch64" ]; then HUBBLE_ARCH=arm64; fi
curl -L --fail --remote-name-all \
  "https://github.com/cilium/hubble/releases/download/${HUBBLE_VERSION}/hubble-linux-${HUBBLE_ARCH}.tar.gz"
sudo tar xzvfC "hubble-linux-${HUBBLE_ARCH}.tar.gz" /usr/local/bin
rm "hubble-linux-${HUBBLE_ARCH}.tar.gz"
```

Повторяем заблокированный запрос (POST из задания 5 или `example.com` из задания 6), чтобы
получить событие `DROPPED`, и сразу читаем поток через Hubble Relay (порт-форвард на
`4245`):

```bash
kubectl -n kube-system port-forward service/hubble-relay 4245:80 &
sleep 3

CLIENT_POD=$(kubectl get po -n eks-132 -l app=client -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n eks-132 "$CLIENT_POD" -- \
  curl -s -o /dev/null --connect-timeout 5 --max-time 8 -X POST \
  http://api.eks-132.svc.cluster.local:8080 || true

mkdir -p /var/work/tests/artifacts/7
hubble observe --server localhost:4245 -n eks-132 --last 50 \
  | tee /var/work/tests/artifacts/7/hubble_denied.txt
```

Убедитесь, что в файле встречается verdict `DROPPED` (если нет - повторите заблокированный
запрос и команду `hubble observe` ещё раз, поток может уже уйти из буфера). Такой карты
потоков с per-flow verdict у встроенного VPC CNI network policy нет - там только логи
агента `aws-network-policy-agent` и метрики (глава 8).

## Задание 8. Сравнение: VPC CNI NP против Cilium в этой лабе

```bash
mkdir -p /var/work/tests/artifacts/8
cat > /var/work/tests/artifacts/8/comparison.txt <<'EOF'
Что умеет встроенный VPC CNI NetworkPolicy - что добавил Cilium - чем платите:

1. VPC CNI NetworkPolicy покрывает только L3/L4 (стандартный NetworkPolicy плюс
   ClusterNetworkPolicy networking.k8s.aws/v1alpha1). Cilium в этой лабе добавил
   L7-правило по HTTP-методу (GET разрешён, POST заблокирован Envoy-прокси).

2. У VPC CNI NP нет политик по DNS-имени. Cilium добавил CiliumNetworkPolicy с toFQDNs -
   egress разрешён только на aws.amazon.com, остальной внешний трафик заблокирован.

3. Диагностика встроенного VPC CNI NP - это только логи агента и метрики. Cilium принёс
   Hubble: карту потоков с per-flow verdict (ALLOWED/DROPPED) через hubble observe.

4. Плата за это: свой Helm-релиз Cilium, свои апгрейды и совместимость с версией
   кластера, вторая модель CRD (CiliumNetworkPolicy) для команды, дополнительный слой
   в датапасе между VPC CNI и подом.

5. Полная замена VPC CNI (когда aws-node удаляется и Cilium сам становится IPAM) в объём
   этой лабы не входит: смена CNI на живом кластере - это blue/green через новые ноды,
   а не переключение флага на лету (глава 8, раздел 8.8). В этой лабе отработан только
   безопасный вариант - CNI chaining.
EOF
cat /var/work/tests/artifacts/8/comparison.txt
```
