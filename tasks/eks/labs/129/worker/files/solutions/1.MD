# Lab 129 - reference solution (Mountpoint for S3: file semantics and backup)

All commands run on the worker machine over SSH. kubectl is already configured on the
cluster. The `aws-mountpoint-s3-csi-driver` driver (provisioner `s3.csi.aws.com`) is
already installed as a managed addon with a role via IRSA (component
`eks_addon_s3_csi_irsa`), and a bucket with versioning enabled and a test object
`readme.txt` has already been created by terraform.

## Task 1. Namespace `eks-129`

```bash
kubectl create namespace eks-129
```

## Task 2. Static PV/PVC on a real bucket

Find the real bucket name:

```bash
BUCKET=$(aws s3api list-buckets \
  --query "Buckets[?contains(Name,'mountpoint-demo')].Name" --output text)
echo "$BUCKET"
```

Mountpoint only supports static provisioning: the PV is written by hand and references an
already existing bucket.

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: PersistentVolume
metadata:
  name: s3-pv
spec:
  capacity:
    storage: 1200Gi
  accessModes: ["ReadWriteMany"]
  storageClassName: ""
  claimRef:
    namespace: eks-129
    name: s3-pvc
  mountOptions:
    - region eu-central-1
  csi:
    driver: s3.csi.aws.com
    volumeHandle: s3-csi-demo-volume
    volumeAttributes:
      bucketName: $BUCKET
EOF

cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: s3-pvc
  namespace: eks-129
spec:
  accessModes: ["ReadWriteMany"]
  storageClassName: ""
  resources:
    requests:
      storage: 1200Gi
  volumeName: s3-pv
EOF

kubectl get pv s3-pv
kubectl get pvc s3-pvc -n eks-129
```

`capacity`/`requests.storage` are placeholder values - the schema requires them, but
Mountpoint ignores them: the real size is determined by the bucket's contents.

## Task 3. Successful operations: a new file and reading

Bring up a pod with this PVC:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mountpoint-app
  namespace: eks-129
spec:
  replicas: 1
  selector:
    matchLabels:
      app: mountpoint-app
  template:
    metadata:
      labels:
        app: mountpoint-app
    spec:
      containers:
      - name: app
        image: busybox:1.36
        command: ["sh", "-c", "sleep 86400"]
        volumeMounts:
        - name: s3
          mountPath: /data
      volumes:
      - name: s3
        persistentVolumeClaim:
          claimName: s3-pvc
EOF

kubectl rollout status deployment/mountpoint-app -n eks-129
POD=$(kubectl get po -n eks-129 -l app=mountpoint-app -o jsonpath='{.items[0].metadata.name}')
```

The image here is specifically `busybox`, not an application from other course labs: there
is neither `sh` nor `cat` in `viktoruj/ping_pong`, and `kubectl exec` into it answers with
`exec: "sh": executable file not found in $PATH` (verified). This whole lab is about
filesystem operations inside the pod, so an image with a shell, `mv` and `dd` is needed.
The pod just needs to keep running, hence the `command` with `sleep`.

Creating a new file is a sequential write from the start, which fits the `PutObject` model
of a whole object, so it works:

```bash
mkdir -p /var/work/tests/artifacts/3
kubectl exec "$POD" -n eks-129 -- sh -c 'echo test > /data/newfile.txt && cat /data/newfile.txt' \
  > /var/work/tests/artifacts/3/create.txt
cat /var/work/tests/artifacts/3/create.txt
```

Reading, including reading the bucket's existing object `readme.txt`, also works - it's a
`GetObject`:

```bash
kubectl exec "$POD" -n eks-129 -- cat /data/readme.txt \
  > /var/work/tests/artifacts/3/read.txt
cat /var/work/tests/artifacts/3/read.txt
```

## Task 4. Symptom: `rename` fails

Renaming isn't a cheap operation on object storage, and Mountpoint honestly rejects it on
regular buckets:

```bash
mkdir -p /var/work/tests/artifacts/4
kubectl exec "$POD" -n eks-129 -- \
  mv /data/newfile.txt /data/renamed.txt \
  > /var/work/tests/artifacts/4/rename.txt 2>&1
cat /var/work/tests/artifacts/4/rename.txt
```

The output is `mv: can't rename '/data/newfile.txt': Function not implemented` (verified on
the stand, driver v1.15.0-eksbuild.1, busybox 1.36). Pay attention to the errno: it's
`ENOSYS`, Mountpoint doesn't implement the `rename` syscall at all. Task 5 will have a
different kind of failure - `EPERM`, `Operation not permitted`: there the operation is
implemented but forbidden by mount settings. It's useful to tell these apart on call:
`ENOSYS` means "this isn't in the driver and never will be", while `EPERM` means "it might
work with different mount options".

The file `newfile.txt` stays in place, and `renamed.txt` doesn't appear: the operation
never started and didn't leave the bucket in an intermediate state. You can verify this
from the AWS side:

```bash
aws s3api list-objects-v2 --bucket "$BUCKET" --query 'Contents[].Key' --output text
```

## Task 5. Symptom: append and a write into the middle fail

Both cases are attempts at a partial modification of an already existing object, and an
S3 object is immutable - it's only updated whole, via a new `PutObject`:

```bash
mkdir -p /var/work/tests/artifacts/5

{
  echo "=== append (echo >>) ==="
  kubectl exec "$POD" -n eks-129 -- sh -c 'echo more >> /data/newfile.txt' 2>&1

  echo
  echo "=== write into the middle of the file (dd seek + conv=notrunc) ==="
  kubectl exec "$POD" -n eks-129 -- sh -c \
    'echo patched | dd of=/data/newfile.txt bs=1 seek=1 conv=notrunc' 2>&1

  echo
  echo "=== overwriting an existing file (needs allow-overwrite) ==="
  kubectl exec "$POD" -n eks-129 -- sh -c 'echo test2 > /data/newfile.txt' 2>&1

  echo
  echo "=== deleting a file (needs allow-delete) ==="
  kubectl exec "$POD" -n eks-129 -- rm /data/newfile.txt 2>&1

  echo
  echo "Explanation: an S3 object is immutable. Updating a key is a new PutObject of the"
  echo "whole object, so Mountpoint can't append to the end (append) or change bytes in"
  echo "the middle of an already uploaded file - both operations fail explicitly with"
  echo "Operation not permitted, rather than silently corrupting the data. For the same"
  echo "reason, overwrite and delete are forbidden by default: they're enabled by the"
  echo "mount options allow-overwrite and allow-delete, and enabling them should be a"
  echo "deliberate choice."
} > /var/work/tests/artifacts/5/writesemantics.txt

cat /var/work/tests/artifacts/5/writesemantics.txt
```

The four failures above are all the same `EPERM`, and all four can be turned on or off with
mount settings, unlike the `rename` from task 4. A useful contrast: `mkdir /data/sub` goes
through SILENTLY with no error, because a directory in S3 is virtual - no object gets
created for it, and `aws s3api list-objects-v2` won't show a new key. But writing into a
nonexistent nested prefix (`echo x > /data/sub2/nested.txt`) fails with
`nonexistent directory`: a `mkdir` is needed first. This is exactly the "almost a
filesystem" that chapter 25 warns about.

## Task 6. Why there is no backup via AWS Backup, but there is versioning

AWS Backup for EKS (chapters 41-42) protects data through EBS volume CSI snapshots. A
Mountpoint volume has no EBS under the hood at all: the files in `/data` are objects in an
S3 bucket, not blocks on a disk, so PVC `s3-pvc` has no snapshot in the sense a `gp3`
volume does (chapter 23). What protects the data here is S3 itself - primarily bucket
versioning, which terraform enabled in advance (`aws_s3_bucket_versioning`):

```bash
mkdir -p /var/work/tests/artifacts/6

{
  echo "=== aws s3api get-bucket-versioning --bucket $BUCKET ==="
  aws s3api get-bucket-versioning --bucket "$BUCKET"

  echo
  echo "Explanation: PVC s3-pvc is mounted through Mountpoint S3 CSI, not EBS CSI. The"
  echo "data already lives in S3 as objects, not on a block device, so this volume has no"
  echo "snapshot via AWS Backup for EKS (that mechanism works through EBS VolumeSnapshot,"
  echo "chapter 41). Protection against accidental overwrite or deletion of objects on"
  echo "such a bucket is versioning (enabled by terraform) and the lifecycle policies of"
  echo "S3 itself, not a backup of the whole volume."
} > /var/work/tests/artifacts/6/backup.txt

cat /var/work/tests/artifacts/6/backup.txt
```
