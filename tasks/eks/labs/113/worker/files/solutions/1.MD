# Lab 113 - reference solution (cluster upgrade and rollback)

All commands run on the worker machine over SSH. kubectl and aws cli are already configured
for the lab's cluster. First, save the cluster name into a variable - you'll need it in
almost every command:

```bash
CLUSTER=$(aws eks list-clusters --query 'clusters[0]' --output text)
echo "$CLUSTER"
```

## Task 1. Namespace and the cluster's starting version

```bash
kubectl create namespace eks-113

aws eks describe-cluster --name "$CLUSTER" --query 'cluster.version'
```

Expected output - `"1.35"`. This lab's cluster deliberately starts one minor below the
current GA version `1.36`, so that you can go through a real upgrade and rollback later.

Extra (not checked, but useful before the upgrade): look at which `apiVersion` the API
server currently serves, to compare with the version after the upgrade later:

```bash
kubectl get --raw /apis | grep -o '"groupVersion":"[^"]*"'
```

## Task 2. Checking upgrade readiness

Upgrade insights is a built-in EKS check that looks for things that could block the upgrade:
use of APIs that will be removed in the target version, and overall cluster health. The list
of cluster insights without `--filter` includes all categories, including upgrade:

```bash
mkdir -p /var/work/tests/artifacts/2
aws eks list-insights --cluster-name "$CLUSTER" \
  > /var/work/tests/artifacts/2/upgrade_insights.json
cat /var/work/tests/artifacts/2/upgrade_insights.json
```

Check that there's no `ERROR` status among the insights (it blocks the upgrade until fixed):

```bash
grep '"status"' /var/work/tests/artifacts/2/upgrade_insights.json
```

If some insight has status `WARNING` - that's not a blocker, but it's worth reading the
recommendation via `aws eks describe-insight --cluster-name "$CLUSTER" --id <insight-id>`.
If there is an `ERROR`, fix the cause (usually a deprecated `apiVersion` in manifests) and
run `aws eks list-insights` again - EKS refreshes insights once every 24 hours, you can force
a refresh via `aws eks start-insights-refresh --cluster-name "$CLUSTER"`.

## Task 3. Upgrading the control plane to 1.36

The upgrade only moves one minor at a time: `1.35` -> `1.36`. Start it and save the update
`id`:

```bash
UPDATE_ID=$(aws eks update-cluster-version --name "$CLUSTER" --kubernetes-version 1.36 \
  --query 'update.id' --output text)
echo "$UPDATE_ID"
```

The control plane update runs in the background and can take 20-40 minutes. Wait for status
`Successful`:

```bash
while true; do
  status=$(aws eks describe-update --name "$CLUSTER" --update-id "$UPDATE_ID" \
    --query 'update.status' --output text)
  echo "status=$status"
  [[ "$status" == "Successful" || "$status" == "Failed" || "$status" == "Cancelled" ]] && break
  sleep 30
done
```

Confirm the new version:

```bash
aws eks describe-cluster --name "$CLUSTER" --query 'cluster.version'
```

Expected output - `"1.36"`. Nodes and add-ons don't change version yet at this point - that's
the next step.

## Task 4. Upgrading the core add-ons to versions for 1.36

The control plane has been updated, but `kube-proxy` and `coredns` don't follow it
automatically - they're updated separately, to versions compatible with the new minor. Check
the exact compatible versions like this (if you don't have the course table handy):

```bash
aws eks describe-addon-versions --addon-name kube-proxy --kubernetes-version 1.36 \
  --query 'addons[].addonVersions[].{Version:addonVersion,Default:compatibilities[0].defaultVersion}'
aws eks describe-addon-versions --addon-name coredns --kubernetes-version 1.36 \
  --query 'addons[].addonVersions[].{Version:addonVersion,Default:compatibilities[0].defaultVersion}'
```

Update both add-ons (same versions as in lab 101, where the cluster starts directly on
`1.36`):

```bash
aws eks update-addon --cluster-name "$CLUSTER" --addon-name kube-proxy \
  --addon-version v1.36.0-eksbuild.14
aws eks update-addon --cluster-name "$CLUSTER" --addon-name coredns \
  --addon-version v1.14.3-eksbuild.3
```

Wait for `ACTIVE` for each of them:

```bash
for addon in kube-proxy coredns; do
  while true; do
    status=$(aws eks describe-addon --cluster-name "$CLUSTER" --addon-name "$addon" \
      --query 'addon.status' --output text)
    echo "$addon status=$status"
    [[ "$status" == "ACTIVE" || "$status" == "DEGRADED" ]] && break
    sleep 10
  done
done
```

Check the resulting versions:

```bash
aws eks describe-addon --cluster-name "$CLUSTER" --addon-name kube-proxy \
  --query 'addon.addonVersion'
aws eks describe-addon --cluster-name "$CLUSTER" --addon-name coredns \
  --query 'addon.addonVersion'
```

`vpc-cni` and `eks-pod-identity-agent` aren't tied to the Kubernetes minor as tightly as
`kube-proxy` and `coredns`, so within this lab you can leave them alone - but in real
operation it's still worth checking their versions via `describe-addon-versions`.

## Task 5. Checking rollback readiness

Rollback readiness insights only appear after an upgrade and live for exactly 7 days - the
rollback window. Look at them with a category filter:

```bash
mkdir -p /var/work/tests/artifacts/5
aws eks list-insights --cluster-name "$CLUSTER" \
  --filter '{"categories": ["ROLLBACK_READINESS"]}' \
  > /var/work/tests/artifacts/5/rollback_readiness.json
cat /var/work/tests/artifacts/5/rollback_readiness.json
```

Check the statuses - `ERROR` and `UNKNOWN` block the rollback:

```bash
grep '"status"' /var/work/tests/artifacts/5/rollback_readiness.json
```

If you recently fixed one of the blockers and don't want to wait for the daily refresh:

```bash
aws eks start-insights-refresh --cluster-name "$CLUSTER"
```

## Task 6. Rolling the control plane back to 1.35

In task 4 we upgraded `kube-proxy` to the `1.36`-compatible version. If you try to roll the
control plane back right now, EKS recalculates the rollback readiness insights again at the
moment `update-cluster-version` is called and finds an `ERROR` on the `kube-proxy version
rollback compatibility` check: `kube-proxy` version `1.36`, after the control plane rolls
back to `1.35`, would end up newer than the control plane, which violates the version skew
policy. This is exactly why chapter 39 says "roll back nodes/add-ons before the control plane
if the add-on version is ahead of the target version" - `aws eks list-insights` right after
the upgrade won't show this problem yet (rollback insights are recalculated against the
cluster's current state), but it will appear if you request them again after the add-on
update.

The correct order is to first bring `kube-proxy` back to a `1.35`-compatible version, and
only then roll back the control plane:

```bash
aws eks update-addon --cluster-name "$CLUSTER" --addon-name kube-proxy \
  --addon-version v1.35.3-eksbuild.13

while true; do
  status=$(aws eks describe-addon --cluster-name "$CLUSTER" --addon-name kube-proxy \
    --query 'addon.status' --output text)
  echo "kube-proxy status=$status"
  [[ "$status" == "ACTIVE" || "$status" == "DEGRADED" ]] && break
  sleep 10
done
```

Check that the kube-proxy insight became `PASSING` (you can force a recalculation if you
don't want to wait a day):

```bash
aws eks start-insights-refresh --cluster-name "$CLUSTER"
sleep 30
aws eks list-insights --cluster-name "$CLUSTER" \
  --filter '{"categories": ["ROLLBACK_READINESS"]}' \
  --query 'insights[].{name:name,status:insightStatus.status}'
```

Now you can roll back the control plane without `--force` - the standard way, same as the
upgrade, but with the previous version:

```bash
ROLLBACK_ID=$(aws eks update-cluster-version --name "$CLUSTER" --kubernetes-version 1.35 \
  --query 'update.id' --output text)
echo "$ROLLBACK_ID"

aws eks describe-update --name "$CLUSTER" --update-id "$ROLLBACK_ID" \
  --query 'update.type'
```

The update type in the response is `VersionRollback`, not a regular `VersionUpdate`. Save
this to an artifact:

```bash
mkdir -p /var/work/tests/artifacts/6
aws eks describe-update --name "$CLUSTER" --update-id "$ROLLBACK_ID" \
  --query 'update.type' --output text > /var/work/tests/artifacts/6/rollback_update.txt
cat /var/work/tests/artifacts/6/rollback_update.txt
```

The rollback also runs in the background and can take 20-40 minutes. Wait for `Successful`:

```bash
while true; do
  status=$(aws eks describe-update --name "$CLUSTER" --update-id "$ROLLBACK_ID" \
    --query 'update.status' --output text)
  echo "status=$status"
  [[ "$status" == "Successful" || "$status" == "Failed" || "$status" == "Cancelled" ]] && break
  sleep 30
done
```

Confirm that the control plane is back on `1.35`:

```bash
aws eks describe-cluster --name "$CLUSTER" --query 'cluster.version'
```

Expected output - `"1.35"`. The etcd data, workloads, and persistent volumes aren't touched
during the rollback - only the control plane version rolls back, this isn't a substitute for
a backup.
