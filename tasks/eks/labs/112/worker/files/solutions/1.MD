# Lab 112 - reference solution (Fargate: profiles, limitations, cost)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster (kubeconfig is assembled via `aws eks update-kubeconfig` when the machine boots).
The Fargate profile `workload` for namespace `eks-112` is already created by the lab's
infrastructure - the student only needs to create the namespace and the objects inside it.

## Task 1. Namespace `eks-112`

```bash
kubectl create namespace eks-112
```

The `workload` profile matches on `namespace = eks-112` with no `labels`, so the entire
namespace lands on Fargate - there will be no exceptions inside it.

## Task 2. A Guaranteed pod `fg-app` on Fargate

Fargate only runs pods where `requests` equal `limits` (the `Guaranteed` class). We create
a Deployment with explicitly equal values:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: fg-app
  namespace: eks-112
spec:
  replicas: 2
  selector:
    matchLabels:
      app: fg-app
  template:
    metadata:
      labels:
        app: fg-app
    spec:
      containers:
      - name: app
        image: viktoruj/ping_pong:latest
        resources:
          requests:
            cpu: "500m"
            memory: "1Gi"
          limits:
            cpu: "500m"
            memory: "1Gi"
EOF

kubectl rollout status deployment/fg-app -n eks-112
```

We check that the pods land on a Fargate node (node name starts with `fargate-`, not `ip-`):

```bash
kubectl get po -n eks-112 -l app=fg-app -o wide
```

## Task 3. Artifact: the actually provisioned capacity

Fargate rounds the sum of requests up to a fixed vCPU/memory combination and adds `256 MB`
for Kubernetes components (`kubelet`, `kube-proxy`, `containerd`). The actually provisioned
capacity is visible in the `CapacityProvisioned` annotation:

```bash
mkdir -p /var/work/tests/artifacts/3
POD=$(kubectl get po -n eks-112 -l app=fg-app -o jsonpath='{.items[0].metadata.name}')
kubectl get pod "$POD" -n eks-112 \
  -o jsonpath='{.metadata.annotations.CapacityProvisioned}' \
  > /var/work/tests/artifacts/3/capacity.txt
echo >> /var/work/tests/artifacts/3/capacity.txt
cat /var/work/tests/artifacts/3/capacity.txt
```

For a request of `500m` CPU and `1Gi` memory plus `256 MB` overhead, Fargate will pick the
nearest matching combination (e.g. `0.5vCPU 1GB`, or `0.5vCPU 2GB` if the total memory after
the overhead exceeds `1 GB`) - `kubectl describe pod` will show exactly this line.

## Task 4. Symptom: a privileged pod won't start

Fargate strictly forbids privileged containers, DaemonSets, hostNetwork/hostPort, hostPath
and GPUs. We try to create a privileged pod in `eks-112`:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: fg-privileged
  namespace: eks-112
spec:
  containers:
  - name: app
    image: viktoruj/ping_pong:latest
    securityContext:
      privileged: true
EOF

kubectl get po fg-privileged -n eks-112
kubectl describe po fg-privileged -n eks-112 | sed -n '/Events/,$p'
```

The pod doesn't reach `Running`: Fargate rejects privileged containers at the admission
stage, which is visible in the pod's events. We save the explanation to an artifact:

```bash
mkdir -p /var/work/tests/artifacts/4
cat > /var/work/tests/artifacts/4/privileged.txt <<'EOF'
Pod fg-privileged does not start because it requests privileged: true. Fargate does not
support privileged containers: this is one of the mode's hard limitations, alongside
DaemonSets, hostNetwork/hostPort, hostPath and GPUs. The error shows up in the pod's events
as an admission rejection, not as a regular Pending due to insufficient resources.
EOF
cat /var/work/tests/artifacts/4/privileged.txt
```

We can remove the pod so it doesn't interfere with later checks:

```bash
kubectl delete pod fg-privileged -n eks-112
```

## Task 5. Extending the ephemeral disk to 30Gi

By default Fargate provides `20 GiB` of ephemeral disk, up to `175 GiB` via
`ephemeral-storage` in `resources` (requests must equal limits, the pod stays Guaranteed).
We update `fg-app`:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: fg-app
  namespace: eks-112
spec:
  replicas: 2
  selector:
    matchLabels:
      app: fg-app
  template:
    metadata:
      labels:
        app: fg-app
    spec:
      containers:
      - name: app
        image: viktoruj/ping_pong:latest
        resources:
          requests:
            cpu: "500m"
            memory: "1Gi"
            ephemeral-storage: "30Gi"
          limits:
            cpu: "500m"
            memory: "1Gi"
            ephemeral-storage: "30Gi"
EOF

kubectl rollout status deployment/fg-app -n eks-112
kubectl get po -n eks-112 -l app=fg-app -o wide
```

The pod starts normally: `30Gi` is within the allowed `175 GiB`, and the `requests ==
limits` requirement is satisfied.

## Task 6. Cost structure: Fargate versus node group

The key difference is the billing unit. Fargate charges for the vCPU and memory of a
specific pod for its lifetime; a node group charges for the whole EC2 instance regardless
of how loaded it is. The automated check for this artifact looks for the word `pod`
alongside `vCPU`, so the artifact below mentions both:

```bash
mkdir -p /var/work/tests/artifacts/6
cat > /var/work/tests/artifacts/6/costmodel.txt <<'EOF'
Fargate charges for the vCPU and memory of the pod itself for the time it actually
runs: if the pod is not running, there is no charge, and you never overpay for idle
capacity. A node group, on the contrary, charges for the whole instance: you pay even for
the time nodes sit idle between pods or are under-utilized. Per unit of resource, Fargate is
usually more expensive than the equivalent resource on a node group node, so the final
economics depend on utilization: at high, predictable load a node group is cheaper, while
under spiky or unpredictable demand Fargate avoids paying for idle instances.
EOF
cat /var/work/tests/artifacts/6/costmodel.txt
```
