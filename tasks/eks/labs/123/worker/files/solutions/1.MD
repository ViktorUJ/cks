# Lab 123 - reference solution (Karpenter: NodePool, consolidation, StatefulSet)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster (kubeconfig was assembled via `aws eks update-kubeconfig` when the machine booted).

## Task 1. Namespace `eks-123`

```bash
kubectl create namespace eks-123
```

We look at which pools are already configured in the cluster: the default `default` (spot
and on-demand) and the new `stateful` (on-demand only, taint `dedicated=stateful`):

```bash
mkdir -p /var/work/tests/artifacts/2

  kubectl get nodepools -o wide

cat /var/work/tests/artifacts/2/inventory.txt
```

The output should contain lines with the names `default` and `stateful` - these are two
independent NodePools, each with its own `EC2NodeClass` (chapter 12.2-12.3).

## Task 3. StatefulSet `db` on the `stateful` pool

The `stateful` pool is closed off by the taint `dedicated=stateful:NoSchedule`, so the pod
needs a toleration. Volumes aren't required for the purposes of this lab - the focus is on
disruption, not on EBS (a StatefulSet's volume with its own PVC is covered in chapter 23):

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
  namespace: eks-123
spec:
  serviceName: db
  replicas: 3
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
    spec:
      tolerations:
        - key: dedicated
          operator: Equal
          value: stateful
          effect: NoSchedule
      containers:
        - name: app
          image: viktoruj/ping_pong:latest
          resources:
            requests:
              cpu: "250m"
              memory: "128Mi"
EOF

kubectl rollout status statefulset/db -n eks-123
```

We check that all replicas landed on the `stateful` pool (node label `work_type=stateful`):

```bash
kubectl get po -n eks-123 -l app=db -o wide
kubectl get nodes -L work_type
```

## Task 4. PodDisruptionBudget `db-pdb`

`maxUnavailable: 1` is the main brake on voluntary eviction. Karpenter drains through the
Eviction API, so the PDB won't allow more than one replica to be evicted at a time:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: db-pdb
  namespace: eks-123
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: db
EOF

kubectl get pdb db-pdb -n eks-123
```

## Task 5. Symptom: a PDB with no eviction rights blocks consolidation

The nodes of the `stateful` pool are already underutilized: three replicas at `250m` each
ended up spread across two `m6g.medium` nodes, and Karpenter with `consolidateAfter: 30s`
keeps trying to consolidate them. There's no need to force any load - we just need to look
at what's blocking the consolidation.

Important: with `maxUnavailable: 1` the PDB does NOT block consolidation. It allows one
eviction at a time (`ALLOWED DISRUPTIONS=1`), Karpenter drains the node one replica at a
time and calmly deletes it. Blocking only happens when the PDB allows zero evictions.
We tighten the protection to a full lockdown - `minAvailable: 3` with three replicas:

```bash
kubectl patch pdb db-pdb -n eks-123 --type=merge \
  -p '{"spec":{"maxUnavailable":null,"minAvailable":3}}'

kubectl get pdb db-pdb -n eks-123
```

The `ALLOWED DISRUPTIONS` column now shows `0`. After 1-2 minutes, a blocking event appears
on the pool's nodes. Note: this is NOT `Unconsolidatable`, but a separate
`DisruptionBlocked`:

```bash
for n in $(kubectl get nodes -l work_type=stateful -o jsonpath='{.items[*].metadata.name}'); do
  echo "=== $n ==="
  kubectl describe node "$n" | grep -A2 DisruptionBlocked
done
```

Expected line: `Pdb prevents pod evictions (PodDisruptionBudget=[eks-123/db-pdb])`. The
controller's own logs live in the `karpenter` namespace (not in `kube-system` - that only
has add-ons, Karpenter is deployed as a separate release on the Fargate profile):

```bash
kubectl logs -n karpenter -l app.kubernetes.io/name=karpenter --tail=500 \
  | grep -i "disrupting node"
```

We save the observation to an artifact - the `get pdb` output plus the actual node event:

```bash
mkdir -p /var/work/tests/artifacts/5
{
  echo "Symptom: a PDB that allows zero evictions blocks consolidation."
  echo "db-pdb tightened to minAvailable=3 with 3 replicas -> ALLOWED DISRUPTIONS=0."
  kubectl get pdb db-pdb -n eks-123
  echo
  echo "=== events on the stateful pool's nodes ==="
  for n in $(kubectl get nodes -l work_type=stateful -o jsonpath='{.items[*].metadata.name}'); do
    kubectl describe node "$n" | grep -E "DisruptionBlocked|Unconsolidatable" | sed "s|^|$n |"
  done
} > /var/work/tests/artifacts/5/consolidation.txt

cat /var/work/tests/artifacts/5/consolidation.txt
```

We return the PDB to a working state, otherwise task 4 won't pass, and the pool's node
will never be able to leave:

```bash
kubectl patch pdb db-pdb -n eks-123 --type=merge \
  -p '{"spec":{"minAvailable":null,"maxUnavailable":1}}'

kubectl get pdb db-pdb -n eks-123
```

`ALLOWED DISRUPTIONS` is back to `1`. Takeaway for operations: `minAvailable` equal to the
replica count (or `maxUnavailable: 0`) stops not only consolidation but any drain -
meaning node updates and cluster upgrades too (chapter 12.6, chapter 40).

## Task 6. Fix: a targeted `do-not-disrupt`

The correct protection for a StatefulSet is a combination of three parts (chapter 12.7),
not one blanket annotation on everything. The PDB (task 4) already gives per-replica
eviction. The `stateful` pool's disruption budget (`nodes: 50%` in
`eks_karpenter_stateful_vng/terragrunt.hcl`) limits the pace, so Karpenter doesn't touch all
the pool's nodes at once. The third part is `do-not-disrupt`, targeted only at the replica
where a disruption is currently unacceptable (for example `db-0` holds leadership or a
long-running operation), not the whole StatefulSet:

```bash
kubectl annotate pod db-0 -n eks-123 karpenter.sh/do-not-disrupt=true
kubectl get po db-0 db-1 db-2 -n eks-123 \
  -o custom-columns=NAME:.metadata.name,DO_NOT_DISRUPT:'.metadata.annotations.karpenter\.sh/do-not-disrupt'
```

`db-1` and `db-2` don't get the annotation - otherwise the protection would become a
blanket lockdown and would block not only consolidation but also drift (AMI updates), as
described in chapter 12.8.

That the annotation is actually working can be seen through the same mechanism as the PDB
in task 5 - Karpenter writes a separate event on the node holding `db-0`:

```bash
NODE=$(kubectl get po db-0 -n eks-123 -o jsonpath='{.spec.nodeName}')
kubectl describe node "$NODE" | grep -A1 'do-not-disrupt'
```

Expected line: `DisruptionBlocked ... Pod has "karpenter.sh/do-not-disrupt" annotation
(Pod=eks-123/db-0)`. In other words, the targeted annotation only stops consolidation of
the one node holding the protected replica, while Karpenter can still touch the pool's
other nodes.

We save the explanation to an artifact:

```bash
mkdir -p /var/work/tests/artifacts/6
cat > /var/work/tests/artifacts/6/fix.txt <<'EOF'
The correct protection for StatefulSet db during consolidation is three independent parts,
not one blanket annotation:

1. PDB db-pdb (maxUnavailable: 1) - per-replica eviction, quorum is never lost. This exact
   value is what leaves ALLOWED DISRUPTIONS=1. A blanket lockdown (minAvailable=3 with three
   replicas) gives ALLOWED DISRUPTIONS=0 and a DisruptionBlocked "Pdb prevents pod
   evictions" event - forever, until the PDB itself is fixed (task 5).
2. The stateful pool's disruption budget (nodes: 50%) - limits how many of the pool's nodes
   Karpenter can touch at the same time, so it doesn't consolidate the whole pool at once.
3. karpenter.sh/do-not-disrupt=true targeted at db-0 - protects the specific replica where a
   disruption is currently unacceptable, not the whole StatefulSet.

If do-not-disrupt were set on db-0, db-1 and db-2 at the same time, it would block not only
consolidation but also drift: when a new AMI comes out, the stateful pool's nodes wouldn't
be able to update, and a CVE backlog would build up (chapter 12.8). That's why the
annotation is placed on just one replica and removed once the critical operation is done.
EOF

cat /var/work/tests/artifacts/6/fix.txt
```
