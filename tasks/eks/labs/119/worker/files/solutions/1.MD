# Lab 119 - reference solution (troubleshooting: node not reaching Ready)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster, the `aws` CLI is configured for the same account and region.

First, save the cluster name into a variable - almost every command will need it:

```bash
CLUSTER=$(aws eks list-clusters --query 'clusters[0]' --output text)
echo "$CLUSTER"
```

## Task 1. Namespace `eks-119`

```bash
kubectl create namespace eks-119
```

## Task 2. Inventory: a healthy managed node group as the norm

The lab already has a managed node group running (separate from Karpenter) - this is
the healthy sample against which the broken self-managed instance from the following
tasks is compared.

mkdir -p /var/work/tests/artifacts/2

{

If `health.issues` is not an empty list - this is exactly the `NodeCreationFailure` from

from the managed node group is visible in `kubectl get nodes` with status `Ready`.

## Task 3. Test IAM role for the self-managed instance

The node role must get `AmazonEKSWorkerNodePolicy`, `AmazonEC2ContainerRegistryReadOnly`,
and `AmazonEKS_CNI_Policy` (chapter 45.2) - the same set as the healthy managed node
group's role. The third policy here is not a formality: the `vpc-cni` addon runs without
its own IRSA role, so `aws-node` takes credentials from the node's role, and without
`AmazonEKS_CNI_Policy` the node stays `NotReady` forever with `cni plugin not
initialized`. Exactly one thing must be broken in this lab - the missing access entry.
The role name must contain `-test-`, otherwise the worker will not be able to manage it.

```bash
ROLE_NAME="eks-task119-test-node"
aws iam create-role --role-name "$ROLE_NAME" --assume-role-policy-document '{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "ec2.amazonaws.com"},
    "Action": "sts:AssumeRole"
  }]
}'

aws iam attach-role-policy --role-name "$ROLE_NAME" \
  --policy-arn arn:aws:iam::aws:policy/AmazonEKSWorkerNodePolicy
aws iam attach-role-policy --role-name "$ROLE_NAME" \
  --policy-arn arn:aws:iam::aws:policy/AmazonEC2ContainerRegistryReadOnly
aws iam attach-role-policy --role-name "$ROLE_NAME" \
  --policy-arn arn:aws:iam::aws:policy/AmazonEKS_CNI_Policy

aws iam create-instance-profile --instance-profile-name "$ROLE_NAME"
aws iam add-role-to-instance-profile --instance-profile-name "$ROLE_NAME" --role-name "$ROLE_NAME"

ROLE_ARN=$(aws iam get-role --role-name "$ROLE_NAME" --query 'Role.Arn' --output text)
mkdir -p /var/work/tests/artifacts/3
echo "$ROLE_ARN" > /var/work/tests/artifacts/3/test_role_arn.txt
cat /var/work/tests/artifacts/3/test_role_arn.txt
```

The instance profile is created right away: the instance needs exactly that, not the
role directly. Give the profile 10-15 seconds to propagate before launching the
instance.

## Task 4. Self-managed EC2 instance on AL2023 without an access entry

We take the same AMI, the same private subnet, and the same nodes' security group as
the cluster's regular nodes, but do NOT create an access entry - this is the
deliberately incomplete setup.

```bash
AMI_ID=$(aws ssm get-parameter \
  --name /aws/service/eks/optimized-ami/1.36/amazon-linux-2023/x86_64/standard/recommended/image_id \
  --query 'Parameter.Value' --output text)

VPC_ID=$(aws eks describe-cluster --name "$CLUSTER" --query 'cluster.resourcesVpcConfig.vpcId' --output text)
SUBNET_ID=$(aws ec2 describe-subnets --filters "Name=vpc-id,Values=$VPC_ID" \
  "Name=tag:kubernetes.io/cluster/$CLUSTER,Values=owned" "Name=tag:kubernetes.io/role/internal-elb,Values=1" \
  --query 'Subnets[0].SubnetId' --output text)
SG_ID=$(aws ec2 describe-security-groups --filters "Name=tag:karpenter.sh/discovery,Values=$CLUSTER" \
  --query 'SecurityGroups[0].GroupId' --output text)

API_ENDPOINT=$(aws eks describe-cluster --name "$CLUSTER" --query 'cluster.endpoint' --output text)
CA_DATA=$(aws eks describe-cluster --name "$CLUSTER" --query 'cluster.certificateAuthority.data' --output text)
SERVICE_CIDR=$(aws eks describe-cluster --name "$CLUSTER" \
  --query 'cluster.kubernetesNetworkConfig.serviceIpv4Cidr' --output text)
```

Build the user data: a MIME document with a `NodeConfig` for `nodeadm` (chapter 10.5 and
chapter 45.4).

```bash
cat > /tmp/user-data.yaml <<EOF
MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="BOUNDARY"

--BOUNDARY
Content-Type: application/node.eks.aws

apiVersion: node.eks.aws/v1alpha1
kind: NodeConfig
spec:
  cluster:
    name: ${CLUSTER}
    apiServerEndpoint: ${API_ENDPOINT}
    certificateAuthority: ${CA_DATA}
    cidr: ${SERVICE_CIDR}

--BOUNDARY--
EOF
```

Launch the instance with the test instance profile and the same AMI/subnet/SG as the
production nodes. The `Name` tag with `-test-` is needed for the worker's permissions,
and it must be provided in both `--tag-specifications` sections at once - both for
`instance` and for `volume`. The worker's policy allows `RunInstances` on `instance/*`
and `volume/*` only under the condition `aws:RequestTag/Name = *-test-*`, and
`RunInstances` also creates a root volume together with the instance. Without a tag on
the volume, AWS responds with `UnauthorizedOperation ... on resource: .../volume/*`,
even though the instance itself is tagged correctly:

```bash
INSTANCE_ID=$(aws ec2 run-instances \
  --image-id "$AMI_ID" \
  --instance-type t3.medium \
  --subnet-id "$SUBNET_ID" \
  --security-group-ids "$SG_ID" \
  --iam-instance-profile "Name=eks-task119-test-node" \
  --user-data file:///tmp/user-data.yaml \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=eks-task119-test-node}]' \
    'ResourceType=volume,Tags=[{Key=Name,Value=eks-task119-test-node}]' \
  --query 'Instances[0].InstanceId' --output text)

mkdir -p /var/work/tests/artifacts/4
echo "$INSTANCE_ID" > /var/work/tests/artifacts/4/instance_id.txt
cat /var/work/tests/artifacts/4/instance_id.txt
```

## Task 5. Symptom: `running` in EC2, but not in `kubectl get nodes`

Give the instance 3-5 minutes to boot and bootstrap, then compare the two sources of
truth.

```bash
sleep 240

  --query 'Reservations[0].Instances[0].State.Name' --output text)
NODES=$(kubectl get nodes -o wide)

mkdir -p /var/work/tests/artifacts/5
{
  echo "instance $INSTANCE_ID state: $STATE"
  echo "=== kubectl get nodes ==="
  echo "$NODES"
} > /var/work/tests/artifacts/5/no_join_symptom.txt
cat /var/work/tests/artifacts/5/no_join_symptom.txt
```

The instance is `running`, yet it is absent from the node list - exactly the symptom
that opens chapter 45.

## Task 6. Diagnosis: what the role is missing

```bash
aws eks list-access-entries --cluster-name "$CLUSTER"
```

The ARN of the role `eks-task119-test-node` is absent from the list. The role has
managed policies (`AmazonEKSWorkerNodePolicy`, `AmazonEC2ContainerRegistryReadOnly`),
but no authorization inside the cluster - without an access entry of type `EC2_LINUX`,
kubelet does not pass authorization.

```bash
mkdir -p /var/work/tests/artifacts/6
cat > /var/work/tests/artifacts/6/why_no_access_entry.txt <<EOF
Instance $INSTANCE_ID is running in EC2, but did not appear in kubectl get nodes. The
reason is that role $ROLE_ARN has managed policies (AmazonEKSWorkerNodePolicy,
AmazonEC2ContainerRegistryReadOnly), but no access entry in the cluster. The role's IAM
permissions and the role's authorization in the cluster are two different things
(chapter 45.2). aws eks list-access-entries for $CLUSTER does not show this role. A
managed node group creates such an entry automatically, while for self-managed nodes an
access entry of type EC2_LINUX must be created manually with aws eks
create-access-entry.
EOF
cat /var/work/tests/artifacts/6/why_no_access_entry.txt
```

## Task 7. Fix: an access entry of type `EC2_LINUX`

```bash
aws eks create-access-entry --cluster-name "$CLUSTER" \
  --principal-arn "$ROLE_ARN" --type EC2_LINUX
```

Give the node time to register and move to `Ready` (usually 1-2 minutes after creating
the access entry, since kubelet was already running and waiting for authorization):

```bash
for i in $(seq 1 20); do
  kubectl get nodes -o wide | grep -q "$INSTANCE_ID" && break
  sleep 15
done
kubectl get nodes -o wide
```

The node's identifier in the cluster is the instance's private DNS name, not the
`INSTANCE_ID` itself; to find the line for the specific instance, match it against
`PrivateDnsName`:

```bash
NODE_NAME=$(aws ec2 describe-instances --instance-ids "$INSTANCE_ID" \
  --query 'Reservations[0].Instances[0].PrivateDnsName' --output text)
kubectl get node "$NODE_NAME"
```

Wait for actual `Ready`, not just the node appearing in the list: right after
registration it stays `NotReady` for a few dozen seconds while `aws-node` comes up. Then
capture the evidence - after task 9, neither the node nor its private DNS name will
exist any more:

```bash
for i in $(seq 1 20); do
  STATUS=$(kubectl get node "$NODE_NAME" --no-headers | awk '{print $2}')
  echo "node status=$STATUS"
  [[ "$STATUS" == "Ready" ]] && break
  sleep 15
done

mkdir -p /var/work/tests/artifacts/7
cat > /var/work/tests/artifacts/7/node_ready.txt <<EOF
node_name=$NODE_NAME
node_status=$STATUS
EOF
cat /var/work/tests/artifacts/7/node_ready.txt
```

## Task 8. Verification: the node actually accepts pods

`Ready` is not yet proof that the node is functional. Schedule a pod onto it
specifically:

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: probe
  namespace: eks-119
spec:
  nodeSelector:
    kubernetes.io/hostname: ${NODE_NAME}
  containers:
  - name: app
    image: viktoruj/ping_pong:latest
EOF

kubectl wait --for=condition=Ready pod/probe -n eks-119 --timeout=240s
kubectl get pod probe -n eks-119 -o wide
```

Capture the evidence the same way as in task 7: the pod lives on this node and will
disappear together with it once the instance is terminated in task 9.

```bash
mkdir -p /var/work/tests/artifacts/8
cat > /var/work/tests/artifacts/8/probe.txt <<EOF
pod_phase=$(kubectl get pod probe -n eks-119 -o jsonpath='{.status.phase}')
pod_node=$(kubectl get pod probe -n eks-119 -o jsonpath='{.spec.nodeName}')
EOF
cat /var/work/tests/artifacts/8/probe.txt
```

## Task 9. Cleanup: terminate the self-managed instance

This EC2 instance is not part of the lab's terraform state: `make delete_eks_task` will
not touch it. Terminate it yourself before closing out the lab:

```bash
aws ec2 terminate-instances --instance-ids "$INSTANCE_ID"
aws ec2 wait instance-terminated --instance-ids "$INSTANCE_ID"

mkdir -p /var/work/tests/artifacts/9
echo "terminated $INSTANCE_ID at $(date -u +%FT%TZ)" > /var/work/tests/artifacts/9/terminated.txt
```

The access entry, the test role, and the instance profile are also worth removing: they
do not cost money, but their names are static, so they will remain in the account even
after `make delete_eks_task`. Order matters - the access entry first, then the role:

```bash
aws eks delete-access-entry --cluster-name "$CLUSTER" --principal-arn "$ROLE_ARN"
aws iam remove-role-from-instance-profile --instance-profile-name eks-task119-test-node \
  --role-name eks-task119-test-node
aws iam delete-instance-profile --instance-profile-name eks-task119-test-node
for p in AmazonEKSWorkerNodePolicy AmazonEC2ContainerRegistryReadOnly AmazonEKS_CNI_Policy; do
  aws iam detach-role-policy --role-name eks-task119-test-node \
    --policy-arn arn:aws:iam::aws:policy/$p
done
aws iam delete-role --role-name eks-task119-test-node
```
