# Лаба 119 - эталонное решение (troubleshooting: нода не доходит до Ready)

Все команды выполняются на рабочей машине (worker) по SSH. kubectl уже настроен на
кластер, `aws` CLI настроен на тот же аккаунт и регион.

Сначала сохраняем имя кластера в переменную - она понадобится почти всем командам:

```bash
CLUSTER=$(aws eks list-clusters --query 'clusters[0]' --output text)
echo "$CLUSTER"
```

## Задание 1. Namespace `eks-119`

```bash
kubectl create namespace eks-119
```

## Задание 2. Инвентаризация: здоровая managed node group как норма

В лабе уже поднята managed node group (отдельно от Karpenter) - это здоровый образец,
с которым сравнивают сломанный self-managed инстанс из следующих заданий.

```bash
mkdir -p /var/work/tests/artifacts/2
NODEGROUP=$(aws eks list-nodegroups --cluster-name "$CLUSTER" --query 'nodegroups[0]' --output text)
{
  echo "=== aws eks describe-nodegroup health.issues (норма - пустой список) ==="
  aws eks describe-nodegroup --cluster-name "$CLUSTER" --nodegroup-name "$NODEGROUP" \
    --query 'nodegroup.health.issues'
  echo "=== kubectl get nodes -o wide ==="
  kubectl get nodes -o wide
} > /var/work/tests/artifacts/2/nodegroup_health.txt
cat /var/work/tests/artifacts/2/nodegroup_health.txt
```

Если `health.issues` не пустой список - это и есть `NodeCreationFailure` из главы 45,
и здоровым образцом для сравнения он уже не будет. В норме нода из managed node group
видна в `kubectl get nodes` со статусом `Ready`.

## Задание 3. Тестовая IAM-роль для self-managed инстанса

Роль ноды должна получить `AmazonEKSWorkerNodePolicy`, `AmazonEC2ContainerRegistryReadOnly`
и `AmazonEKS_CNI_Policy` (глава 45.2) - тот же набор, что у роли здоровой managed node
group. Третья политика здесь не формальность: аддон `vpc-cni` работает без своей
IRSA-роли, поэтому `aws-node` берёт креды из роли ноды, и без `AmazonEKS_CNI_Policy` нода
навсегда остаётся `NotReady` с `cni plugin not initialized`. Сломанной в этой лабе должна
быть ровно одна вещь - отсутствие access entry. Имя роли обязано содержать `-test-`, иначе
worker не сможет ей управлять.

```bash
ROLE_NAME="eks-task119-test-node"
aws iam create-role --role-name "$ROLE_NAME" --assume-role-policy-document '{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "ec2.amazonaws.com"},
    "Action": "sts:AssumeRole"
  }]
}'

aws iam attach-role-policy --role-name "$ROLE_NAME" \
  --policy-arn arn:aws:iam::aws:policy/AmazonEKSWorkerNodePolicy
aws iam attach-role-policy --role-name "$ROLE_NAME" \
  --policy-arn arn:aws:iam::aws:policy/AmazonEC2ContainerRegistryReadOnly
aws iam attach-role-policy --role-name "$ROLE_NAME" \
  --policy-arn arn:aws:iam::aws:policy/AmazonEKS_CNI_Policy

aws iam create-instance-profile --instance-profile-name "$ROLE_NAME"
aws iam add-role-to-instance-profile --instance-profile-name "$ROLE_NAME" --role-name "$ROLE_NAME"

ROLE_ARN=$(aws iam get-role --role-name "$ROLE_NAME" --query 'Role.Arn' --output text)
mkdir -p /var/work/tests/artifacts/3
echo "$ROLE_ARN" > /var/work/tests/artifacts/3/test_role_arn.txt
cat /var/work/tests/artifacts/3/test_role_arn.txt
```

Instance profile создаётся сразу же: инстансу нужен именно он, а не роль напрямую.
Дайте профилю 10-15 секунд на распространение перед запуском инстанса.

## Задание 4. Self-managed EC2-инстанс на AL2023 без access entry

Берём тот же AMI, ту же приватную подсеть и ту же security group нод, что и у обычных
нод кластера, но НЕ создаём access entry - это и есть намеренно неполная настройка.

```bash
AMI_ID=$(aws ssm get-parameter \
  --name /aws/service/eks/optimized-ami/1.36/amazon-linux-2023/x86_64/standard/recommended/image_id \
  --query 'Parameter.Value' --output text)

VPC_ID=$(aws eks describe-cluster --name "$CLUSTER" --query 'cluster.resourcesVpcConfig.vpcId' --output text)
SUBNET_ID=$(aws ec2 describe-subnets --filters "Name=vpc-id,Values=$VPC_ID" \
  "Name=tag:kubernetes.io/cluster/$CLUSTER,Values=owned" "Name=tag:kubernetes.io/role/internal-elb,Values=1" \
  --query 'Subnets[0].SubnetId' --output text)
SG_ID=$(aws ec2 describe-security-groups --filters "Name=tag:karpenter.sh/discovery,Values=$CLUSTER" \
  --query 'SecurityGroups[0].GroupId' --output text)

API_ENDPOINT=$(aws eks describe-cluster --name "$CLUSTER" --query 'cluster.endpoint' --output text)
CA_DATA=$(aws eks describe-cluster --name "$CLUSTER" --query 'cluster.certificateAuthority.data' --output text)
SERVICE_CIDR=$(aws eks describe-cluster --name "$CLUSTER" \
  --query 'cluster.kubernetesNetworkConfig.serviceIpv4Cidr' --output text)
```

Собираем user data: MIME-документ с `NodeConfig` для `nodeadm` (глава 10.5 и глава 45.4).

```bash
cat > /tmp/user-data.yaml <<EOF
MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="BOUNDARY"

--BOUNDARY
Content-Type: application/node.eks.aws

apiVersion: node.eks.aws/v1alpha1
kind: NodeConfig
spec:
  cluster:
    name: ${CLUSTER}
    apiServerEndpoint: ${API_ENDPOINT}
    certificateAuthority: ${CA_DATA}
    cidr: ${SERVICE_CIDR}

--BOUNDARY--
EOF
```

Запускаем инстанс с тестовым instance profile и той же AMI/подсетью/SG, что у боевых нод.
Тег `Name` с `-test-` нужен для прав worker, и указать его надо в двух секциях
`--tag-specifications` сразу - и для `instance`, и для `volume`. Политика worker разрешает
`RunInstances` на `instance/*` и `volume/*` только при условии
`aws:RequestTag/Name = *-test-*`, а `RunInstances` создаёт вместе с инстансом ещё и
корневой том. Без тега на томе AWS отвечает `UnauthorizedOperation ... on resource:
.../volume/*`, хотя сам инстанс размечен правильно:

```bash
INSTANCE_ID=$(aws ec2 run-instances \
  --image-id "$AMI_ID" \
  --instance-type t3.medium \
  --subnet-id "$SUBNET_ID" \
  --security-group-ids "$SG_ID" \
  --iam-instance-profile "Name=eks-task119-test-node" \
  --user-data file:///tmp/user-data.yaml \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=eks-task119-test-node}]' \
    'ResourceType=volume,Tags=[{Key=Name,Value=eks-task119-test-node}]' \
  --query 'Instances[0].InstanceId' --output text)

mkdir -p /var/work/tests/artifacts/4
echo "$INSTANCE_ID" > /var/work/tests/artifacts/4/instance_id.txt
cat /var/work/tests/artifacts/4/instance_id.txt
```

## Задание 5. Симптом: `running` в EC2, но нет в `kubectl get nodes`

## Задание 6. Диагностика: чего не хватает роли

```bash
aws eks list-access-entries --cluster-name "$CLUSTER"
```

ARN роли `eks-task119-test-node` в списке отсутствует. У роли есть managed-политики
(`AmazonEKSWorkerNodePolicy`, `AmazonEC2ContainerRegistryReadOnly`), но нет авторизации
внутри кластера - без access entry типа `EC2_LINUX` kubelet не проходит authorization.

```bash
mkdir -p /var/work/tests/artifacts/6
cat > /var/work/tests/artifacts/6/why_no_access_entry.txt <<EOF
Инстанс $INSTANCE_ID running в EC2, но не появился в kubectl get nodes. Причина - у роли
$ROLE_ARN есть managed-политики (AmazonEKSWorkerNodePolicy,
AmazonEC2ContainerRegistryReadOnly), но нет access entry в кластере. IAM-права роли
и авторизация роли в кластере - две разные вещи (глава 45.2). aws eks
list-access-entries для $CLUSTER не показывает эту роль. Managed node group заводит
такую запись автоматически, а для self-managed нод access entry типа EC2_LINUX нужно
создавать вручную командой aws eks create-access-entry.
EOF
cat /var/work/tests/artifacts/6/why_no_access_entry.txt
```

## Задание 7. Починка: access entry типа `EC2_LINUX`

```bash
aws eks create-access-entry --cluster-name "$CLUSTER" \
  --principal-arn "$ROLE_ARN" --type EC2_LINUX
```

Даём ноде время зарегистрироваться и пройти в `Ready` (обычно 1-2 минуты после создания
access entry, kubelet уже был запущен и ждал авторизации):

```bash
for i in $(seq 1 20); do
  kubectl get nodes -o wide | grep -q "$INSTANCE_ID" && break
  sleep 15
done
kubectl get nodes -o wide
```

Идентификатор ноды в кластере - private DNS name инстанса, не сам `INSTANCE_ID`; чтобы
найти строку про конкретный инстанс, сверьте её с `PrivateDnsName`:

```bash
NODE_NAME=$(aws ec2 describe-instances --instance-ids "$INSTANCE_ID" \
  --query 'Reservations[0].Instances[0].PrivateDnsName' --output text)
kubectl get node "$NODE_NAME"
```

Дождитесь именно `Ready`, а не просто появления ноды в списке: сразу после регистрации она
несколько десятков секунд висит `NotReady`, пока поднимается `aws-node`. Затем фиксируем
свидетельство - после задания 9 ни ноды, ни её private DNS name уже не будет:

```bash
for i in $(seq 1 20); do
  STATUS=$(kubectl get node "$NODE_NAME" --no-headers | awk '{print $2}')
  echo "node status=$STATUS"
  [[ "$STATUS" == "Ready" ]] && break
  sleep 15
done

mkdir -p /var/work/tests/artifacts/7
cat > /var/work/tests/artifacts/7/node_ready.txt <<EOF
node_name=$NODE_NAME
node_status=$STATUS
EOF
cat /var/work/tests/artifacts/7/node_ready.txt
```

## Задание 8. Проверка: нода реально принимает поды

`Ready` - это ещё не доказательство, что нода рабочая. Планируем под именно на неё:

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: probe
  namespace: eks-119
spec:
  nodeSelector:
    kubernetes.io/hostname: ${NODE_NAME}
  containers:
  - name: app
    image: viktoruj/ping_pong:latest
EOF

kubectl wait --for=condition=Ready pod/probe -n eks-119 --timeout=240s
kubectl get pod probe -n eks-119 -o wide
```

Фиксируем свидетельство так же, как в задании 7: под живёт на этой ноде и исчезнет вместе
с ней, когда в задании 9 инстанс будет терминирован.

```bash
mkdir -p /var/work/tests/artifacts/8
cat > /var/work/tests/artifacts/8/probe.txt <<EOF
pod_phase=$(kubectl get pod probe -n eks-119 -o jsonpath='{.status.phase}')
pod_node=$(kubectl get pod probe -n eks-119 -o jsonpath='{.spec.nodeName}')
EOF
cat /var/work/tests/artifacts/8/probe.txt
```

## Задание 9. Уборка: терминировать self-managed инстанс

Этот EC2-инстанс не входит в состояние terraform лабы: `make delete_eks_task` его не
затронет. Терминируйте его сами, прежде чем закрывать лабу:

```bash
aws ec2 terminate-instances --instance-ids "$INSTANCE_ID"
aws ec2 wait instance-terminated --instance-ids "$INSTANCE_ID"

mkdir -p /var/work/tests/artifacts/9
echo "terminated $INSTANCE_ID at $(date -u +%FT%TZ)" > /var/work/tests/artifacts/9/terminated.txt
```

Access entry, тестовую роль и instance profile тоже стоит убрать: денег они не стоят, но
имена у них статические, поэтому в аккаунте они останутся и после `make delete_eks_task`.
Порядок важен - сначала access entry, потом роль:

```bash
aws eks delete-access-entry --cluster-name "$CLUSTER" --principal-arn "$ROLE_ARN"
aws iam remove-role-from-instance-profile --instance-profile-name eks-task119-test-node \
  --role-name eks-task119-test-node
aws iam delete-instance-profile --instance-profile-name eks-task119-test-node
for p in AmazonEKSWorkerNodePolicy AmazonEC2ContainerRegistryReadOnly AmazonEKS_CNI_Policy; do
  aws iam detach-role-policy --role-name eks-task119-test-node \
    --policy-arn arn:aws:iam::aws:policy/$p
done
aws iam delete-role --role-name eks-task119-test-node
```
