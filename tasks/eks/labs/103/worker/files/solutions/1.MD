# Lab 103 - reference solution (address plan: ENI limits, prefix delegation, secondary CIDR)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster (kubeconfig is assembled via `aws eks update-kubeconfig` when the machine boots).

```bash
export CLUSTER=$(aws eks list-clusters --query 'clusters[0]' --output text)
kubectl create namespace eks-103
```

## Task 1. max-pods by formula, checked against the actual value

Create the baseline workload and wait for Karpenter to bring up an EC2 node for it in the
regular (per-address) VPC CNI mode - the addon isn't switched to prefix delegation yet:

```bash
kubectl create deployment baseline --image=viktoruj/ping_pong:latest --replicas=2 -n eks-103
kubectl rollout status deployment/baseline -n eks-103

NODE=$(kubectl get po -n eks-103 -l app=baseline -o jsonpath='{.items[0].spec.nodeName}')
TYPE=$(kubectl get node "$NODE" \
  -o jsonpath='{.metadata.labels.node\.kubernetes\.io/instance-type}')
echo "node=$NODE type=$TYPE"
```

Get ENI count, IPs per ENI and vCPU for this instance type:

```bash
ENI=$(aws ec2 describe-instance-types --instance-types "$TYPE" \
  --query 'InstanceTypes[0].NetworkInfo.MaximumNetworkInterfaces' --output text)
IPS=$(aws ec2 describe-instance-types --instance-types "$TYPE" \
  --query 'InstanceTypes[0].NetworkInfo.Ipv4AddressesPerInterface' --output text)
VCPU=$(aws ec2 describe-instance-types --instance-types "$TYPE" \
  --query 'InstanceTypes[0].VCpuInfo.DefaultVCpus' --output text)
echo "eni=$ENI ips_per_eni=$IPS vcpu=$VCPU"
```

Compute the formula `max-pods = ENI * (IPs per ENI - 1) + 2` and apply the managed node
group cap (`110` when `vCPU < 30`, otherwise `250`):

```bash
FORMULA=$((ENI * (IPS - 1) + 2))
if [ "$VCPU" -lt 30 ]; then CAP=110; else CAP=250; fi
if [ "$FORMULA" -lt "$CAP" ]; then EXPECTED=$FORMULA; else EXPECTED=$CAP; fi
echo "formula=$FORMULA cap=$CAP expected_max_pods=$EXPECTED"

ACTUAL=$(kubectl get node "$NODE" -o jsonpath='{.status.allocatable.pods}')
echo "actual_allocatable_pods=$ACTUAL"
```

Example for `m5.large`: `ENI=3`, `IPs per ENI=10` give `formula = 3*(10-1)+2 = 29`, the cap
`110` doesn't kick in (`29 < 110`), so `expected_max_pods = 29` - and that's exactly what
`kubectl get node` should show.

Save the calculation and the actual value as an artifact:

```bash
mkdir -p /var/work/tests/artifacts/1
cat > /var/work/tests/artifacts/1/maxpods.txt <<EOF
node=$NODE
instance_type=$TYPE
eni=$ENI
ips_per_eni=$IPS
vcpu=$VCPU
formula=$FORMULA
cap=$CAP
expected_max_pods=$EXPECTED
actual_allocatable_pods=$ACTUAL
EOF
cat /var/work/tests/artifacts/1/maxpods.txt
```

If `expected_max_pods` and `actual_allocatable_pods` don't match - kubelet learns max-pods
only at node startup, so the check needs to run against a node that's already fully Ready.

## Task 2. Prefix delegation: new node vs. old node

Capture the old node's state (per-address mode) before enabling prefix delegation:

```bash
OLD_NODE="$NODE"
OLD_PODS=$(kubectl get node "$OLD_NODE" -o jsonpath='{.status.allocatable.pods}')
echo "old_node=$OLD_NODE old_node_allocatable_pods=$OLD_PODS"
```

Enable prefix delegation on the managed `vpc-cni` addon (works only on Nitro-based
instances, so it matters that the NodePool uses those types):

```bash
aws eks update-addon --cluster-name "$CLUSTER" --addon-name vpc-cni \
  --configuration-values '{"env":{"ENABLE_PREFIX_DELEGATION":"true","WARM_PREFIX_TARGET":"1"}}' \
  --resolve-conflicts PRESERVE

aws eks describe-addon --cluster-name "$CLUSTER" --addon-name vpc-cni \
  --query 'addon.configurationValues'
```

Prefix delegation only affects new nodes: the old `baseline` node already got its
`allocatable.pods` limit from kubelet at startup and won't recalculate it until it's
recreated. Trigger a new node by adding a workload that doesn't fit on the old one:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: scale
  namespace: eks-103
spec:
  replicas: 6
  selector:
    matchLabels:
      app: scale
  template:
    metadata:
      labels:
        app: scale
    spec:
      containers:
      - name: app
        image: viktoruj/ping_pong:latest
        resources:
          requests:
            cpu: "1"
            memory: "128Mi"
EOF

kubectl rollout status deployment/scale -n eks-103
```

Identify the new node and compare the limits:

```bash
NEW_NODE=$(kubectl get po -n eks-103 -l app=scale -o jsonpath='{.items[*].spec.nodeName}' \
  | tr ' ' '\n' | grep -v "^${OLD_NODE}$" | head -n1)
NEW_TYPE=$(kubectl get node "$NEW_NODE" \
  -o jsonpath='{.metadata.labels.node\.kubernetes\.io/instance-type}')
NEW_PODS=$(kubectl get node "$NEW_NODE" -o jsonpath='{.status.allocatable.pods}')
echo "new_node=$NEW_NODE new_node_instance_type=$NEW_TYPE new_node_allocatable_pods=$NEW_PODS"
```

Example for `m5.large` in prefix mode: the limit jumps from `29` to `434` (capped by the
managed node group cap `110`, so the actual ceiling is `110`, but that's still much higher
than the `29` of per-address mode).

Save the comparison and explanation as an artifact:

```bash
mkdir -p /var/work/tests/artifacts/2
cat > /var/work/tests/artifacts/2/prefixdelegation.txt <<EOF
old_node=$OLD_NODE
old_node_allocatable_pods=$OLD_PODS
new_node=$NEW_NODE
new_node_instance_type=$NEW_TYPE
new_node_allocatable_pods=$NEW_PODS

old_node_allocatable_pods did not change because kubelet computes max-pods once, at node
startup, and prefix delegation only affects new nodes, not ones that are already running.
new_node was created after prefix delegation was enabled, so its ENIs hold /28 prefixes
(16 addresses each) instead of single IPs, and the pod limit is noticeably higher.
EOF
cat /var/work/tests/artifacts/2/prefixdelegation.txt
```

## Task 3. Planning subnet size for growth

Compute the final requirement: `850` pods, a `20%` margin for the warm pool, then another
`15%` for a rolling update (the margins multiply sequentially):

```bash
python3 - <<'EOF'
base = 850
after_warm = base * 1.20
after_roll = after_warm * 1.15
print(f"base={base} after_warm_pool={after_warm:.0f} after_rolling_update={after_roll:.0f}")
EOF
```

Result: `850 * 1.20 = 1020`, `1020 * 1.15 = 1173` - the final requirement is roughly `1173`
addresses. Compare against the table of available addresses per subnet prefix (AWS reserves
`5` addresses per subnet):

- `/24` - total `256`, available `251` - less than `1173`, doesn't fit;
- `/22` - total `1024`, available `1019` - also less than `1173`, doesn't fit;
- `/20` - total `4096`, available `4091` - fits with plenty of headroom.

`4091 / 1173 ≈ 3.5` times the margin, which covers both the current calculation and future
growth, so `/20` is the choice.

```bash
mkdir -p /var/work/tests/artifacts/3
cat > /var/work/tests/artifacts/3/cidrplan.txt <<'EOF'
Requirement: 850 pods * 1.20 (warm pool margin) * 1.15 (rolling update margin)
= 1173 addresses (final address requirement).

/24 (total 256, available 251) - doesn't fit, available is less than the requirement.
/22 (total 1024, available 1019) - doesn't fit, available is less than the requirement (1173).
/20 (total 4096, available 4091) - fits: 4091 / 1173 ~= 3.5x margin.

Choice: /20. Karpenter's warm pool and a concurrent rolling update briefly hold extra
addresses busy, so the subnet must be noticeably bigger than the point-in-time peak, not
just barely above 1173 addresses.
EOF
cat /var/work/tests/artifacts/3/cidrplan.txt
```

## Task 4. Secondary CIDR: expanding the VPC's address plan

Get the cluster's `vpc-id` and attach a secondary CIDR from the RFC 6598 shared address
space (`100.64.0.0/16` doesn't overlap with this VPC's primary CIDR `10.10.0.0/16`):

```bash
VPC=$(aws eks describe-cluster --name "$CLUSTER" \
  --query 'cluster.resourcesVpcConfig.vpcId' --output text)

aws ec2 associate-vpc-cidr-block --vpc-id "$VPC" --cidr-block 100.64.0.0/16
```

Wait for `associated` state (right after the call the block may be `associating`):

```bash
until aws ec2 describe-vpcs --vpc-ids "$VPC" \
    --query "Vpcs[].CidrBlockAssociationSet[?CidrBlock=='100.64.0.0/16'].CidrBlockState.State" \
    --output text | grep -q associated; do
  echo "waiting for secondary CIDR to become associated..."
  sleep 5
done

aws ec2 describe-vpcs --vpc-ids "$VPC" \
  --query 'Vpcs[].CidrBlockAssociationSet[].{CIDR:CidrBlock,State:CidrBlockState.State}'
```

Create a subnet in the new block:

```bash
SUBNET=$(aws ec2 create-subnet --vpc-id "$VPC" --cidr-block 100.64.1.0/24 \
  --availability-zone eu-central-1a --query 'Subnet.SubnetId' --output text)
echo "subnet=$SUBNET"
```

Save the result as an artifact:

```bash
mkdir -p /var/work/tests/artifacts/4
{
  echo "secondary_cidr=100.64.0.0/16"
  aws ec2 describe-vpcs --vpc-ids "$VPC" \
    --query 'Vpcs[].CidrBlockAssociationSet[].{CIDR:CidrBlock,State:CidrBlockState.State}' \
    --output table
  echo "subnet_id=$SUBNET"
} > /var/work/tests/artifacts/4/secondary_cidr.txt
cat /var/work/tests/artifacts/4/secondary_cidr.txt
```

If we tried `172.16.0.0/12` or `192.168.0.0/16` instead of `100.64.0.0/16`, AWS wouldn't
let us add them to a VPC whose primary CIDR is already in the `10.0.0.0/8` range (an
overlap between RFC 1918 private ranges), which is why RFC 6598 is the usual pick.

## Task 5. Diagnosing address shortage (without a real failure)

Don't touch the lab's infrastructure: don't shrink subnets and don't artificially exhaust
addresses. Look at the current state of the cluster's subnets - these are the same
commands used to diagnose an address shortage on a live cluster:

```bash
aws ec2 describe-subnets --filters "Name=vpc-id,Values=$VPC" \
  --query 'Subnets[].[SubnetId,AvailabilityZone,CidrBlock,AvailableIpAddressCount]' \
  --output table
```

Save the diagnostic explanation as an artifact:

```bash
mkdir -p /var/work/tests/artifacts/5
cat > /var/work/tests/artifacts/5/diagnostics.txt <<'EOF'
How to diagnose an IP address shortage on a live cluster:

1. Symptom on the pod: kubectl describe pod shows a FailedCreatePodSandBox event from
   aws-cni in Events - this is the first signal that VPC CNI couldn't allocate an
   address.

2. General address shortage in a subnet: aws ec2 describe-subnets --query
   'Subnets[].[SubnetId,AvailabilityZone,CidrBlock,AvailableIpAddressCount]' - if
   AvailableIpAddressCount for that AZ is 0, it's a direct diagnosis of address
   exhaustion in that subnet and AZ.

3. Fragmentation instead of a real shortage: if prefix delegation is enabled but there's
   no contiguous /28 block left in the subnet (addresses are scattered across
   individually occupied IPs), the ipamd/aws-node logs will show an
   InsufficientCidrBlocks error, even when the subnet's AvailableIpAddressCount looks
   large. These are different causes of the same external symptom (a pod can't get an
   address), and they're fixed differently: an address shortage is fixed by expanding
   the CIDR or adding a secondary CIDR (task 4), fragmentation is fixed by freeing up
   space for a contiguous block or creating a new subnet.
EOF
cat /var/work/tests/artifacts/5/diagnostics.txt
```
