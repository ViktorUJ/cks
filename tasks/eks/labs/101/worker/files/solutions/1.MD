# Lab 101 - reference solution (cluster as code: access, compute, network, AMI)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster (kubeconfig is assembled via `aws eks update-kubeconfig` when the machine boots).

## Task 1. Namespace `eks-101`

```bash
kubectl create namespace eks-101
```

## Task 2. Deployment `web` (viktoruj/ping_pong, 3 replicas) on EC2 nodes

System pods (kube-system, karpenter) run on Fargate, while any pod in a regular namespace
gets scheduled to an EC2 node provisioned by Karpenter. So the Deployment in `eks-101`
lands on EC2 automatically:

```bash
kubectl create deployment web --image=viktoruj/ping_pong:latest --replicas=3 -n eks-101
kubectl rollout status deployment/web -n eks-101
```

Check that the pods are not on Fargate (the node name starts with `ip-`, not `fargate-`):

```bash
kubectl get po -n eks-101 -l app=web -o wide
```

Why: Fargate only runs a pod if the pod's namespace matches a Fargate profile. In this lab
the profile is set up for `kube-system` and `karpenter`, and there's no profile for
`eks-101`, so Karpenter (EC2) picks up the `eks-101` workload. You'll write this
explanation down in task 7.

## Task 3. Artifact: splitting system nodes from worker nodes

Save the node list showing which ones are Fargate and which are EC2:

## Task 4. Artifact: pod IP from the VPC CIDR

VPC CNI assigns pods routable addresses from the node's subnet (`10.10.15.0/24` or
`10.10.16.0/24`), i.e. from VPC `10.10.0.0/16`:

```bash
mkdir -p /var/work/tests/artifacts/4
kubectl get po -n eks-101 -l app=web -o jsonpath='{.items[0].status.podIP}' \
  > /var/work/tests/artifacts/4/podip.txt
echo >> /var/work/tests/artifacts/4/podip.txt
cat /var/work/tests/artifacts/4/podip.txt
```

To get a feel for VPC CNI, compare the pod address against the private subnet CIDRs (the pod
got an IP from its node's subnet):

```bash
VPC=$(aws eks describe-cluster --name "$(kubectl config current-context | sed 's|.*/||')" \
  --query 'cluster.resourcesVpcConfig.vpcId' --output text 2>/dev/null)
aws ec2 describe-subnets --filters "Name=vpc-id,Values=$VPC" \
  --query 'Subnets[].[CidrBlock,AvailabilityZone]' --output table
```

## Task 6. Deployment `batch` (6 replicas with a CPU request) - scaling via Karpenter

A workload with explicit requests makes Karpenter add compute capacity. Create the
deployment with a CPU request and wait for all replicas to become ready:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: batch
  namespace: eks-101
spec:
  replicas: 6
  selector:
    matchLabels:
      app: batch
  template:
    metadata:
      labels:
        app: batch
    spec:
      containers:
      - name: app
        image: viktoruj/ping_pong:latest
        resources:
          requests:
            cpu: "500m"
            memory: "128Mi"
EOF

kubectl rollout status deployment/batch -n eks-101
```

You can watch Karpenter bring up nodes like this:

```bash
kubectl get nodeclaims.karpenter.sh
kubectl get nodes -l work_type=default -o wide
kubectl logs -n karpenter -l app.kubernetes.io/instance=karpenter | tail -n 20
```

## Task 7. Boundary of responsibility: symptom and explanation

Intentionally ask for Fargate where it doesn't exist. The pod should get stuck in `Pending`:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: fg-probe
  namespace: eks-101
spec:
  nodeSelector:
    eks.amazonaws.com/compute-type: fargate
  containers:
  - name: app
    image: viktoruj/ping_pong:latest
EOF

kubectl get po fg-probe -n eks-101 -o wide
kubectl describe po fg-probe -n eks-101 | sed -n '/Events/,$p'
# namespace-wide events sorted by time - an SRE skill for diagnosing scheduling failures
kubectl get events -n eks-101 --sort-by='.metadata.creationTimestamp'
```

The pod stays `Pending`: there's no Fargate profile for `eks-101`, so EKS won't schedule the
pod on Fargate, and Karpenter won't create an EC2 node either, because its nodes don't carry
the `eks.amazonaws.com/compute-type: fargate` label. Nobody can satisfy this requirement.

Save the explanation as an artifact:

```bash
mkdir -p /var/work/tests/artifacts/7
cat > /var/work/tests/artifacts/7/whyfargate.txt <<'EOF'
The web and batch pods went to Karpenter's EC2 nodes, not Fargate: Fargate only runs a pod
if the pod's namespace matches a Fargate profile. The cluster has a profile for kube-system
and karpenter, but there is no profile for eks-101.

fg-probe got stuck in Pending because it explicitly requests Fargate (nodeSelector
eks.amazonaws.com/compute-type: fargate), but there's no profile for eks-101, and
Karpenter's EC2 nodes don't carry that label. Neither Fargate nor Karpenter can satisfy
the requirement.
EOF
cat /var/work/tests/artifacts/7/whyfargate.txt
```

The boundary of responsibility becomes clear: which namespaces go to Fargate is up to you
(via Fargate profiles, chapter 9), not something EKS decides "on its own".
