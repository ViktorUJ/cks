# Lab 128 - reference solution (Gateway API on AWS: ALB Gateway API and VPC Lattice)

All commands run on the worker machine over SSH. kubectl is already configured on the
cluster. Terraform has already created IAM roles for both controllers (components
`eks_lbc_irsa`, `eks_vpclattice_irsa`) - their ARNs are in `~/lab128_hints.txt`.

```bash
cat ~/lab128_hints.txt
export CLUSTER=$(kubectl config current-context | sed 's|.*/||')
export LBC_ROLE_ARN=$(grep '^lbc_role_arn' ~/lab128_hints.txt | awk '{print $3}')
export LATTICE_ROLE_ARN=$(grep '^vpclattice_role_arn' ~/lab128_hints.txt | awk '{print $3}')
export NODE_SG=$(grep '^node_sg_id' ~/lab128_hints.txt | awk '{print $3}')
export VPC_ID=$(grep '^vpc_id' ~/lab128_hints.txt | awk '{print $3}')
export ACCOUNT_ID=$(grep '^account_id' ~/lab128_hints.txt | awk '{print $3}')
export REGION=eu-central-1
```

## Task 1. Gateway API CRDs and the lab's namespaces

```bash
kubectl apply --server-side=true \
  -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.2.0/standard-install.yaml

kubectl create namespace eks-128
kubectl create namespace eks-128-backend
```

## Task 2. AWS Load Balancer Controller and a Gateway of the ALB class (L7)

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: ServiceAccount
metadata:
  name: aws-load-balancer-controller
  namespace: kube-system
  annotations:
    eks.amazonaws.com/role-arn: ${LBC_ROLE_ARN}
EOF

helm repo add eks https://aws.github.io/eks-charts
helm repo update

helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName="${CLUSTER}" \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set region="${REGION}" \
  --set vpcId="${VPC_ID}"

kubectl rollout status deployment/aws-load-balancer-controller -n kube-system
```

`region` and `vpcId` are mandatory here, and this isn't cosmetic. The controller's pod
lands in `kube-system`, and that namespace is covered by a Fargate profile, where there's
no IMDS at all. Without the flags the controller falls into `CrashLoopBackOff` with
`failed to get VPC ID ... ec2imds: GetMetadata ... context deadline exceeded` (verified on
the stand). The same trap awaits any controller you install into `kube-system` on Fargate
(chapters 15 and 26).

Creating a `GatewayClass` for ALB and the `Gateway` itself:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: aws-alb
spec:
  controllerName: gateway.k8s.aws/alb
EOF

cat <<'EOF' | kubectl apply -f -
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: web
  namespace: eks-128
spec:
  gatewayClassName: aws-alb
  listeners:
    - name: http
      protocol: HTTP
      port: 80
EOF

kubectl get gateway web -n eks-128 -o wide
```

`gateway.k8s.aws/alb` is the same AWS Load Balancer Controller as in labs 108/109, just
with ingress described through Gateway API resources instead of Ingress: L7 routes
`HTTPRoute` and `GRPCRoute` turn into ALB listeners and rules (chapter 28, section 28.4).

## Task 3. HTTPRoute on ALB: application routing

```bash
kubectl create deployment frontend --image=viktoruj/ping_pong:latest \
  --replicas=2 -n eks-128
kubectl rollout status deployment/frontend -n eks-128
kubectl expose deployment frontend -n eks-128 --port=80 --target-port=8080

cat <<'EOF' | kubectl apply -f -
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: app
  namespace: eks-128
spec:
  parentRefs:
    - kind: Gateway
      name: web
      sectionName: http
  rules:
    - backendRefs:
        - name: frontend
          port: 80
EOF
```

One route isn't enough: the controller needs to be told what type of targets to register.
The default type is inferred as `instance`, and `instance` requires a Service of type
`NodePort` or `LoadBalancer`. With `ClusterIP` the load balancer stays under-programmed:
`Gateway` goes into `Accepted: False` with `reason: Invalid`, and the controller log keeps
repeating `TargetGroup port is empty. When using Instance targets, your service must be of
type 'NodePort' or 'LoadBalancer'` (reproduced on the stand). In the Ingress world this was
fixed by the `alb.ingress.kubernetes.io/target-type: ip` annotation, in Gateway API there's
a separate typed object instead of an annotation, and it must live in the namespace of its
own Service:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: gateway.k8s.aws/v1
kind: TargetGroupConfiguration
metadata:
  name: frontend
  namespace: eks-128
spec:
  targetReference:
    name: frontend
  defaultConfiguration:
    targetType: ip
EOF
```

Waiting for the address and confirming via AWS CLI that this is indeed an ALB:

```bash
for i in $(seq 1 30); do
  ADDR=$(kubectl get gateway web -n eks-128 -o jsonpath='{.status.addresses[0].value}')
  [[ -n "$ADDR" ]] && break
  sleep 10
done
echo "gateway address: $ADDR"

LB_ARN=$(aws elbv2 describe-load-balancers \
  --query "LoadBalancers[?DNSName=='${ADDR}'].LoadBalancerArn" --output text)

mkdir -p /var/work/tests/artifacts/3
aws elbv2 describe-load-balancers --load-balancer-arns "$LB_ARN" \
  > /var/work/tests/artifacts/3/alb.txt
cat /var/work/tests/artifacts/3/alb.txt
```

`Type` in the output should be `application` - a `Gateway` of class `aws-alb` creates an
ALB the same way an `Ingress` with `ingressClassName: alb` did in lab 109, just through a
typed resource instead of annotations.

What's left is to wait for `Programmed: True` and confirm the traffic actually flows. The
load balancer is internal (`internal-...`), so the request is made from the worker - it's
in the same VPC:

```bash
for i in $(seq 1 30); do
  p=$(kubectl get gateway web -n eks-128 \
    -o jsonpath='{.status.conditions[?(@.type=="Programmed")].status}')
  [[ "$p" == "True" ]] && break
  sleep 10
done
kubectl get gateway web -n eks-128 -o wide

curl -s -o /dev/null -w "http=%{http_code}\n" "http://${ADDR}/"
```

The `http=200` response arrives a minute or two after `Programmed: True`: first the ALB
becomes active, then the targets pass the health check (target state is visible in
`aws elbv2 describe-target-health`).

## Task 4. AWS Gateway API Controller and a Gateway of the VPC Lattice class

First, open the node SG for VPC Lattice traffic - without this rule the pods won't get
traffic from the Service Network (chapter 28, section 28.4 of the controller deployment
docs):

```bash
PREFIX_LIST_ID=$(aws ec2 describe-managed-prefix-lists \
  --query "PrefixLists[?PrefixListName=='com.amazonaws.eu-central-1.vpc-lattice'].PrefixListId" \
  --output text)

aws ec2 authorize-security-group-ingress --group-id "$NODE_SG" \
  --ip-permissions "PrefixListIds=[{PrefixListId=${PREFIX_LIST_ID}}],IpProtocol=-1"
```

Installing the controller: namespace, ServiceAccount with the role, a Helm chart with the
`defaultServiceNetwork` parameter - the controller will create the Service Network
`eks-task128-mesh` itself and associate the cluster's VPC with it. The chart and image live
in a public ECR and are pulled anonymously, `helm registry login` isn't needed (the worker
role doesn't have `ecr-public:GetAuthorizationToken`, and that's correct - a public
registry is readable without a token):

```bash
kubectl create namespace aws-application-networking-system

cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: ServiceAccount
metadata:
  name: gateway-api-controller
  namespace: aws-application-networking-system
  annotations:
    eks.amazonaws.com/role-arn: ${LATTICE_ROLE_ARN}
EOF

helm install gateway-api-controller \
  oci://public.ecr.aws/aws-application-networking-k8s/aws-gateway-controller-chart \
  --version=v1.1.0 \
  --namespace aws-application-networking-system \
  --set=serviceAccount.create=false \
  --set=defaultServiceNetwork=eks-task128-mesh \
  --set=awsRegion="${REGION}" \
  --set=awsAccountId="${ACCOUNT_ID}" \
  --set=clusterVpcId="${VPC_ID}" \
  --set=clusterName="${CLUSTER}"

kubectl rollout status deployment -n aws-application-networking-system --timeout=180s
```

These four last flags are mandatory for the same reason `region` and `vpcId` are for the
LBC, but the symptom is different and worth remembering. This controller's pod runs on a
regular EC2 node, so IMDS exists in principle, but IMDSv2 comes with hop limit 1, and a
request from the pod's network namespace gets dropped. Without the flags the controller
fails instantly with
`init config failed: vpcId is not specified: EC2MetadataError ... status code: 401`
(verified on the stand). This exact hop limit is covered in chapters 10 and 19: it protects
the node role's credentials from pods, and along the way it breaks any controller that
relies on the metadata service.

Creating a `GatewayClass` for VPC Lattice and the `Gateway` itself:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: gateway.networking.k8s.io/v1beta1
kind: GatewayClass
metadata:
  name: amazon-vpc-lattice
spec:
  controllerName: application-networking.k8s.aws/gateway-api-controller
EOF

cat <<'EOF' | kubectl apply -f -
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: eks-task128-mesh
  namespace: eks-128
spec:
  gatewayClassName: amazon-vpc-lattice
  listeners:
    - name: http
      protocol: HTTP
      port: 80
EOF

kubectl get gateway eks-task128-mesh -n eks-128 -o wide
```

The `Gateway` name here isn't arbitrary, and that's the main trap in this task. The VPC
Lattice controller looks up the Service Network by the `Gateway` object's NAME, not by the
value of `defaultServiceNetwork`. Name the `Gateway` `mesh`, and it will stay
`Programmed: False` forever with the message `VPC Lattice Service Network not found`,
because the network in the account is called `eks-task128-mesh` (verified on the stand:
two `Gateway` objects side by side, the one with a matching name shows
`Programmed: True` and the network's ARN in the message, the one with a mismatched name
shows `not found`). Hence the rule: `Gateway` name = Service Network name.

A `Gateway` of class `amazon-vpc-lattice` maps to a VPC Lattice Service Network: it's an
east-west connection between cluster services, not an entry point from outside like
`aws-alb` (chapter 28, section 28.5).

## Task 5. Symptom: HTTPRoute without a ReferenceGrant

Bringing up the backend in a neighboring namespace:

```bash
kubectl create deployment backend --image=viktoruj/ping_pong:latest \
  --replicas=1 -n eks-128-backend
kubectl rollout status deployment/backend -n eks-128-backend
kubectl expose deployment backend -n eks-128-backend --port=80 --target-port=8080

cat <<'EOF' | kubectl apply -f -
apiVersion: gateway.k8s.aws/v1
kind: TargetGroupConfiguration
metadata:
  name: backend
  namespace: eks-128-backend
spec:
  targetReference:
    name: backend
  defaultConfiguration:
    targetType: ip
EOF
```

`TargetGroupConfiguration` is needed for the same reason as in task 3, and it also shows
the separation of ownership: the object lives in the namespace of the Service's owner,
not next to the route.

Route `rates` lives in `eks-128`, but references a Service in `eks-128-backend`. Its
parent is `Gateway` `web` of class `aws-alb`:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: rates
  namespace: eks-128
spec:
  parentRefs:
    - kind: Gateway
      name: web
      sectionName: http
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /rates
      backendRefs:
        - name: backend
          namespace: eks-128-backend
          port: 80
EOF
```

The same route, but on a `Gateway` of class `amazon-vpc-lattice` - this is the control
experiment, needed for the task's conclusion:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: rates-lattice
  namespace: eks-128
spec:
  parentRefs:
    - kind: Gateway
      name: eks-task128-mesh
      sectionName: http
  rules:
    - backendRefs:
        - name: backend
          namespace: eks-128-backend
          port: 80
EOF

sleep 25
mkdir -p /var/work/tests/artifacts/5
{
  echo "rates status=$(kubectl get httproute rates -n eks-128 -o jsonpath='{.status.parents[0].conditions[?(@.type=="ResolvedRefs")].status}')"
  echo "rates reason=$(kubectl get httproute rates -n eks-128 -o jsonpath='{.status.parents[0].conditions[?(@.type=="ResolvedRefs")].reason}')"
  echo "rates message=$(kubectl get httproute rates -n eks-128 -o jsonpath='{.status.parents[0].conditions[?(@.type=="ResolvedRefs")].message}')"
  echo "rates-lattice status=$(kubectl get httproute rates-lattice -n eks-128 -o jsonpath='{.status.parents[0].conditions[?(@.type=="ResolvedRefs")].status}')"
  echo "rates-lattice reason=$(kubectl get httproute rates-lattice -n eks-128 -o jsonpath='{.status.parents[0].conditions[?(@.type=="ResolvedRefs")].reason}')"
} > /var/work/tests/artifacts/5/refnotpermitted.txt
cat /var/work/tests/artifacts/5/refnotpermitted.txt
```

We don't use `kubectl -o yaml | grep -A...`: for CRD objects (unstructured), condition
fields get serialized in alphabetical order (`reason`, `status` come before `type`), so
it's more reliable to pull the needed condition directly via `jsonpath`.

A `backendRefs` entry with a `namespace` field points to a Service in a different
namespace - by default such a reference is forbidden, so a developer in `eks-128` can't
route traffic to someone else's service without permission from its owner (chapter 28,
section 28.2). For route `rates` the `ResolvedRefs` condition will be `status: "False"`,
`reason: RefNotPermitted`, message
`No explicit ReferenceGrant exists to allow the reference.`

But here's the output the control experiment is really about: `rates-lattice`'s condition
is immediately `ResolvedRefs: True`, even though there's no `ReferenceGrant` in
`eks-128-backend` yet (verified on the stand). The `ReferenceGrant` rule is part of the
Gateway API spec, but it's ENFORCED by the implementation, not the API server: the AWS
Load Balancer Controller checks it, the VPC Lattice controller version v1.1.0 doesn't.
The practical conclusion: identical YAML across two Gateway API implementations gives you
a different trust boundary between teams, and you can only rely on `ReferenceGrant` as
protection where you've verified the controller's behavior.

## Task 6. Fix: ReferenceGrant allows the cross-namespace reference

`ReferenceGrant` is created by the owner of the **target** backend - namespace
`eks-128-backend`, not the one making the reference:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: allow-from-eks-128
  namespace: eks-128-backend
spec:
  from:
    - group: gateway.networking.k8s.io
      kind: HTTPRoute
      namespace: eks-128
  to:
    - group: ""
      kind: Service
EOF

sleep 15
mkdir -p /var/work/tests/artifacts/6
{
  echo "ResolvedRefs status=$(kubectl get httproute rates -n eks-128 \
    -o jsonpath='{.status.parents[0].conditions[?(@.type=="ResolvedRefs")].status}')"
  echo "curl /rates http=$(curl -s -o /dev/null -w '%{http_code}' -m 10 "http://${ADDR}/rates")"
} > /var/work/tests/artifacts/6/resolved.txt
cat /var/work/tests/artifacts/6/resolved.txt
```

The artifact's second line checks not the status but the traffic itself: `http=200` from
the `backend` pod means the whole chain came together - the route was permitted by the
grant, the target group of type `ip` was created, and the targets passed the health check.
If `ResolvedRefs` is already `True` but `curl` returns `503`, wait a minute: target
registration happens after the target group appears.

Once the `ReferenceGrant` appears, `rates`'s `ResolvedRefs` condition flips to `True`
within seconds - the controller re-evaluates permitted references on the next
reconciliation, and the route starts resolving `backend` in the neighboring namespace.
Note that permission is granted by the target's OWNER namespace: delete the
`ReferenceGrant`, and the route goes back to `RefNotPermitted`, even though nobody touched
the route itself.
