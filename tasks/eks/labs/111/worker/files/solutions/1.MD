# Lab 111 - reference solution (spot nodes: diversification, interruptions, graceful drain)

All commands run on the worker machine via SSH. kubectl is already configured for the
cluster (kubeconfig built via `aws eks update-kubeconfig` when the machine booted).

## Task 1. Namespace `eks-111`

```bash
kubectl create namespace eks-111
```

## Task 2. Deployment `spotapp` on the spot pool with a toleration and graceful shutdown

The pool `spot-lab` is closed off with the taint `dedicated=spot-lab:NoSchedule`, so the
pod must carry the matching toleration, otherwise Karpenter won't be able to place it on
this NodePool. `terminationGracePeriodSeconds: 60` fits inside the two-minute spot
interruption window, and `preStop` with `sleep 5` gives the load balancer time to drain
traffic before the container stops.

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: spotapp
  namespace: eks-111
spec:
  replicas: 4
  selector:
    matchLabels:
      app: spotapp
  template:
    metadata:
      labels:
        app: spotapp
    spec:
      terminationGracePeriodSeconds: 60
      tolerations:
        - key: "dedicated"
          value: "spot-lab"
          effect: "NoSchedule"
      containers:
        - name: app
          image: viktoruj/ping_pong:latest
          lifecycle:
            preStop:
              exec:
                command: ["sh", "-c", "sleep 5"]
EOF

kubectl rollout status deployment/spotapp -n eks-111
```

Checking that all 4 replicas landed on spot nodes:

```bash
kubectl get po -n eks-111 -l app=spotapp -o wide
NODES=$(kubectl get po -n eks-111 -l app=spotapp -o jsonpath='{.items[*].spec.nodeName}')
for n in $NODES; do
  kubectl get node "$n" -L karpenter.sh/capacity-type --no-headers
done
```

Karpenter takes roughly 60-90 seconds to bring up a new EC2 node, so the pods may sit in
`Pending` at first. Wait for `rollout status` before moving on.

mkdir -p /var/work/tests/artifacts/3

  | grep -A5 'instance-category' > /var/work/tests/artifacts/3/nodepool.txt

`nodes.txt` should have at least one node with `capacity-type=spot`. `nodepool.txt`
should contain the three instance categories `c`, `m`, `r` - that's exactly the
diversification requirement: the spot-lab pool isn't narrowed down to a single instance
family.

## Task 4. PodDisruptionBudget for `spotapp`

`minAvailable: 3` out of 4 replicas protects against excessive voluntary eviction:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: spotapp-pdb
  namespace: eks-111
spec:
  minAvailable: 3
  selector:
    matchLabels:
      app: spotapp
EOF

kubectl get pdb spotapp-pdb -n eks-111 -o yaml
```

## Task 5. Symptom: drain gets blocked by PDB, but that doesn't save you from spot AWS

Pick a node running at least one `spotapp` pod, cordon it and try a drain. With 4
replicas and `minAvailable: 3` the PDB allows evicting no more than one replica at a time
(`disruptionsAllowed` doesn't exceed 1) - the drain won't get past one replica.

```bash
NODE=$(kubectl get po -n eks-111 -l app=spotapp -o jsonpath='{.items[0].spec.nodeName}')
kubectl cordon "$NODE"
kubectl get pdb spotapp-pdb -n eks-111 -o jsonpath='{.status.disruptionsAllowed}'
echo

# what would try to get evicted, without actually draining the whole node
kubectl drain "$NODE" --ignore-daemonsets --dry-run=client
```

Recording the symptom and the explanation of the PDB's boundary of responsibility in an
artifact:

```bash
mkdir -p /var/work/tests/artifacts/5
cat > /var/work/tests/artifacts/5/drain.txt <<'EOF'
The node is cordoned, drain tries to evict the spotapp pods through the eviction API. PDB
spotapp-pdb with minAvailable: 3 doesn't allow evicting more than one replica at a time
(disruptionsAllowed <= 1 with 4 replicas): when an eviction attempt would break the
budget, it's refused, and drain doesn't move past one replica.

Important boundary: PDB protects only voluntary eviction - kubectl drain, node upgrades,
Karpenter consolidation. It doesn't save you from a forced reclaim of a spot instance by
AWS itself: if AWS actually reclaims the instance once the two-minute notice expires, the
pods on it terminate regardless of the PDB, because that's not a voluntary Kubernetes
action but the instance itself being stopped.
EOF
cat /var/work/tests/artifacts/5/drain.txt

kubectl uncordon "$NODE"
```

## Task 6. Checking Karpenter's interruption handling

Karpenter handles spot interruptions itself via an interruption queue
(`interruptionQueue`, configured in the `eks_v2_karpenter` module independently of this
lab). We confirm the mechanism through the controller logs - the worker might not have
permissions for `aws sqs list-queues`, so we use `kubectl logs`:

```bash
mkdir -p /var/work/tests/artifacts/6
kubectl logs -n karpenter -l app.kubernetes.io/name=karpenter --tail=500 \
  | grep -i interrupt > /var/work/tests/artifacts/6/interruption.txt

# if there haven't been any interruption events yet, record the fact the mechanism exists:
if [[ ! -s /var/work/tests/artifacts/6/interruption.txt ]]; then
  echo "no interruption events yet, but Karpenter interruption handling is configured via interruptionQueue" \
    > /var/work/tests/artifacts/6/interruption.txt
fi
cat /var/work/tests/artifacts/6/interruption.txt
```
