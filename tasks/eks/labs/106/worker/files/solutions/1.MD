# Lab 106 - reference solution (EBS CSI: gp3, AZ binding, expansion, snapshot)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster. The `aws-ebs-csi-driver` driver (provisioner `ebs.csi.aws.com`) is already
installed as a managed addon with a role via IRSA (component `eks_addon_ebs_irsa`) -
there's no need to create the role again.

## Task 1. Namespace `eks-106`

```bash
kubectl create namespace eks-106
```

## Task 2. StorageClass `gp3-immediate` (broken configuration)

We deliberately pick `volumeBindingMode: Immediate` - it's exactly what catches the volume
in a random zone:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3-immediate
provisioner: ebs.csi.aws.com
volumeBindingMode: Immediate
allowVolumeExpansion: true
parameters:
  type: gp3
  encrypted: "true"
EOF
```

## Task 3. StatefulSet `db` on `gp3-immediate`

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
  namespace: eks-106
spec:
  serviceName: db
  replicas: 1
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
    spec:
      containers:
      - name: app
        image: viktoruj/ping_pong:latest
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      storageClassName: gp3-immediate
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 5Gi
EOF

kubectl get pvc -n eks-106
kubectl get po db-0 -n eks-106 -o wide
```

The lab's cluster is brought up in two AZs (`eu-central-1a` and `eu-central-1b`). With
`Immediate`, the driver creates the volume right after the PVC appears, without waiting to
see where the scheduler will place the pod, so the volume's zone is chosen independently
of where Karpenter actually brings up a node. Across two AZs a
`volume node affinity conflict` really can happen, but it's not guaranteed on every run:
the volume may happen to land in the same zone where a suitable node already exists.
That's exactly why the diagnosis in task 4 is required regardless of the outcome.

## Task 4. Diagnosis: the Immediate symptom versus zone binding

```bash
mkdir -p /var/work/tests/artifacts/4

kubectl describe pod db-0 -n eks-106 | sed -n '/Events/,$p' \
  > /var/work/tests/artifacts/4/describe.txt

PV=$(kubectl get pvc data-db-0 -n eks-106 -o jsonpath='{.spec.volumeName}')
kubectl get pv "$PV" -o yaml > /var/work/tests/artifacts/4/pv.yaml
grep -A6 nodeAffinity /var/work/tests/artifacts/4/pv.yaml
```

Let's check where the pod actually landed and whether the volume's zone matches the
node's zone:

```bash
PHASE=$(kubectl get po db-0 -n eks-106 -o jsonpath='{.status.phase}')
NODE=$(kubectl get po db-0 -n eks-106 -o jsonpath='{.spec.nodeName}')
PV_ZONE=$(kubectl get pv "$PV" \
  -o jsonpath='{.spec.nodeAffinity.required.nodeSelectorTerms[0].matchExpressions[0].values[0]}')
echo "phase=$PHASE node=$NODE pv_zone=$PV_ZONE"
```

Save the explanation as an artifact. The wording needs to hold in both cases - whether the
pod got stuck in `Pending` or happened to get lucky:

```bash
cat > /var/work/tests/artifacts/4/diagnosis.txt <<'EOF'
StorageClass gp3-immediate uses volumeBindingMode: Immediate. This means the CSI driver
ebs.csi.aws.com creates the EBS volume right after the PVC appears, before the scheduler
has picked a node for the pod. The volume's zone gets locked in on the PV via
spec.nodeAffinity.required.nodeSelectorTerms[].matchExpressions[].key:
topology.ebs.csi.aws.com/zone, and the scheduler is required to respect this binding.

If pod db-0 is Pending, kubectl describe pod shows an event
"0/N nodes are available: N node(s) had volume node affinity conflict" - the volume was
created in a zone that has no suitable node.

If pod db-0 is Running, that doesn't mean the configuration is correct: the cluster only
has two AZs (eu-central-1a, eu-central-1b), and with Immediate the volume simply happened
to land in a zone where a node already existed. On a different run, during Karpenter
consolidation, or after moving to a larger number of AZs, the same StorageClass will
produce a volume node affinity conflict again. Only WaitForFirstConsumer works correctly
by construction, where the volume's zone always matches the zone of an already chosen
node - that's task 5.
EOF
cat /var/work/tests/artifacts/4/diagnosis.txt
```

## Task 5. The fix: StorageClass `gp3` with `WaitForFirstConsumer`

A PVC binds to its StorageClass once, and you can't change the class on an existing PVC,
so the fix isn't a patch to `gp3-immediate` but a new class and a new StatefulSet:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
parameters:
  type: gp3
  encrypted: "true"
EOF

cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db-fixed
  namespace: eks-106
spec:
  serviceName: db-fixed
  replicas: 1
  selector:
    matchLabels:
      app: db-fixed
  template:
    metadata:
      labels:
        app: db-fixed
    spec:
      containers:
      - name: app
        image: viktoruj/ping_pong:latest
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      storageClassName: gp3
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 5Gi
EOF

kubectl rollout status statefulset/db-fixed -n eks-106
```

With `WaitForFirstConsumer`, volume provisioning is deferred until the scheduler has
picked a node for `db-fixed-0`. Only after that does the driver create the volume in that
node's zone, and a `nodeAffinity` conflict becomes impossible by construction. Let's check
that the volume's zone matches the node's zone:

```bash
NODE=$(kubectl get po db-fixed-0 -n eks-106 -o jsonpath='{.spec.nodeName}')
NODE_ZONE=$(kubectl get node "$NODE" \
  -o jsonpath='{.metadata.labels.topology\.kubernetes\.io/zone}')
PV=$(kubectl get pvc data-db-fixed-0 -n eks-106 -o jsonpath='{.spec.volumeName}')
PV_ZONE=$(kubectl get pv "$PV" \
  -o jsonpath='{.spec.nodeAffinity.required.nodeSelectorTerms[0].matchExpressions[0].values[0]}')
echo "node_zone=$NODE_ZONE pv_zone=$PV_ZONE"
```

The values of `node_zone` and `pv_zone` should match - that's the sign of correct behavior
rather than a lucky coincidence. On top of that, you can explicitly restrict the set of
zones via `allowedTopologies` on the StorageClass (key `topology.ebs.csi.aws.com/zone`),
if you need to exclude a specific AZ from volume provisioning.

## Task 6. Expanding volume `data-db-fixed-0` from 5Gi to 10Gi

`allowVolumeExpansion: true` on `gp3` allows expansion on the fly, without recreating the
pod:

```bash
kubectl patch pvc data-db-fixed-0 -n eks-106 \
  -p '{"spec":{"resources":{"requests":{"storage":"10Gi"}}}}'

# wait for the CSI driver to finish modifying the volume and file system
until [[ "$(kubectl get pvc data-db-fixed-0 -n eks-106 \
  -o jsonpath='{.status.capacity.storage}')" == "10Gi" ]]; do
  sleep 5
done

kubectl get pvc data-db-fixed-0 -n eks-106 \
  -o jsonpath='{.status.capacity.storage}'
echo
```

You can't shrink a volume - only grow it, and not more often than the EBS modification
limit allows.

## Task 7. Volume snapshot and restore (best effort)

A snapshot works through three objects: `VolumeSnapshotClass`, `VolumeSnapshot`, and an
automatically created `VolumeSnapshotContent`. The snapshot-controller and CRDs in the
cluster are already installed via the managed addon `snapshot-controller` (component
`eks_addons`):

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: ebs-snapclass
driver: ebs.csi.aws.com
deletionPolicy: Delete
EOF

cat <<'EOF' | kubectl apply -f -
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: db-snap
  namespace: eks-106
spec:
  volumeSnapshotClassName: ebs-snapclass
  source:
    persistentVolumeClaimName: data-db-fixed-0
EOF

kubectl get volumesnapshot db-snap -n eks-106
```

Wait for the snapshot to become ready (`readyToUse: true`), and restore it into a new PVC.
An EBS snapshot is a regional object, but the volume restored from it is zonal again, so a
class with `WaitForFirstConsumer` is needed here too:

```bash
kubectl wait --for=jsonpath='{.status.readyToUse}'=true \
  volumesnapshot/db-snap -n eks-106 --timeout=180s

cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-restored
  namespace: eks-106
spec:
  storageClassName: gp3
  accessModes: ["ReadWriteOnce"]
  dataSource:
    kind: VolumeSnapshot
    name: db-snap
    apiGroup: snapshot.storage.k8s.io
  resources:
    requests:
      storage: 10Gi
EOF

kubectl get pvc data-restored -n eks-106
```

`data-restored` will stay `Pending` until a pod references it (class `gp3` -
`WaitForFirstConsumer`), and that's expected: provisioning of the restored volume is also
deferred until scheduling happens. If for some reason the cluster has no
snapshot-controller or CRDs, this task alone doesn't block the rest of the lab - it's a
separate, optional verification step.
