```bash
mkdir -p /var/work/tests/artifacts/2
```

Both commands fail with `error: Metrics API not available` - the Metrics API
(`metrics.k8s.io`) is not registered because metrics-server is not installed yet.

## Task 3. Base layer: the metrics-server addon

```bash
CLUSTER_NAME=$(kubectl config current-context | sed 's|.*/||')

aws eks create-addon --cluster-name "$CLUSTER_NAME" --addon-name metrics-server

aws eks wait addon-active --cluster-name "$CLUSTER_NAME" --addon-name metrics-server
aws eks describe-addon --cluster-name "$CLUSTER_NAME" --addon-name metrics-server \
  --query 'addon.status'
```

Wait until the Metrics API starts returning real numbers (usually takes a minute or two
after the addon becomes `ACTIVE`):

```bash
for i in $(seq 1 24); do
  out=$(kubectl top nodes 2>&1)
  if [[ "$out" != *"not available"* ]]; then
    break
  fi
  sleep 10
done

mkdir -p /var/work/tests/artifacts/3
kubectl top nodes > /var/work/tests/artifacts/3/kubectl_top_after.txt
cat /var/work/tests/artifacts/3/kubectl_top_after.txt
```

## Task 4. Container Insights: the amazon-cloudwatch-observability addon

The addon needs permissions to publish to CloudWatch. EKS Pod Identity does not use the
cluster's OIDC provider, so the role's trust policy trusts the `pods.eks.amazonaws.com`
service directly:

```bash
ROLE_NAME="eks-task114-test-cw-agent"

cat > /tmp/trust.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "pods.eks.amazonaws.com" },
      "Action": ["sts:AssumeRole", "sts:TagSession"]
    }
  ]
}
EOF

aws iam create-role --role-name "$ROLE_NAME" \
  --assume-role-policy-document file:///tmp/trust.json

aws iam attach-role-policy --role-name "$ROLE_NAME" \
  --policy-arn arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy

ROLE_ARN=$(aws iam get-role --role-name "$ROLE_NAME" --query 'Role.Arn' --output text)
echo "$ROLE_ARN"
```

Install the addon with a Pod Identity association on this ServiceAccount:

```bash
aws eks create-addon --cluster-name "$CLUSTER_NAME" \
  --addon-name amazon-cloudwatch-observability \
  --pod-identity-associations serviceAccount=cloudwatch-agent,roleArn="$ROLE_ARN"

aws eks wait addon-active --cluster-name "$CLUSTER_NAME" \
  --addon-name amazon-cloudwatch-observability

for i in $(seq 1 30); do
  running=$(kubectl get pods -n amazon-cloudwatch \
    -l app.kubernetes.io/name=cloudwatch-agent \
    -o jsonpath='{.items[*].status.phase}')
  [[ "$running" == *Running* ]] && break
  sleep 10
done

mkdir -p /var/work/tests/artifacts/4
kubectl get pods -n amazon-cloudwatch > /var/work/tests/artifacts/4/cloudwatch_agent_pods.txt
cat /var/work/tests/artifacts/4/cloudwatch_agent_pods.txt
```

## Task 5. kube-prometheus-stack: real application metrics collection

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

helm install kube-prometheus-stack prometheus-community/kube-prometheus-stack \
  -n monitoring --create-namespace \
  --set prometheus.prometheusSpec.serviceMonitorSelectorNilUsesHelmValues=false

kubectl rollout status statefulset/prometheus-kube-prometheus-stack-prometheus \
  -n monitoring --timeout=300s
```

`serviceMonitorSelectorNilUsesHelmValues=false` matters: without it Prometheus will only see
the ServiceMonitor from its own Helm release and will ignore `ping-app` in another
namespace.

Deploy the application with a metrics endpoint and a ServiceMonitor for it:

```bash
kubectl create deployment ping-app --image=viktoruj/ping_pong:latest --replicas=1 -n eks-114
kubectl rollout status deployment/ping-app -n eks-114

kubectl expose deployment ping-app -n eks-114 --port=9090 --target-port=9090 \
  --name=ping-app
kubectl label service ping-app -n eks-114 app=ping-app --overwrite

kubectl -n eks-114 patch service ping-app --type merge -p '
spec:
  ports:
    - name: metrics
      port: 9090
      targetPort: 9090
'

cat <<'EOF' | kubectl apply -f -
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: ping-app
  namespace: eks-114
spec:
  selector:
    matchLabels:
      app: ping-app
  endpoints:
    - port: metrics
      path: /metrics
EOF
```

Wait for Prometheus to pick up the target (usually one scrape cycle, up to a minute), then
query the metric via the API. The `prometheus` container image is minimal and has neither
`wget` nor `curl`, not even `which` - `kubectl exec` won't work for an HTTP request. It's
simpler to forward the port to the worker machine and make the request from there:

```bash
sleep 60

kubectl port-forward -n monitoring svc/kube-prometheus-stack-prometheus 9090:9090 &
PF_PID=$!
sleep 5

mkdir -p /var/work/tests/artifacts/5
curl -s 'http://localhost:9090/api/v1/query?query=requests_total' \
  > /var/work/tests/artifacts/5/prom_query.txt
cat /var/work/tests/artifacts/5/prom_query.txt

kill "$PF_PID"
```

The Prometheus service name is `<release-name>-prometheus` (in this solution the release is
named `kube-prometheus-stack`, so the service is `kube-prometheus-stack-prometheus`; don't
confuse it with `prometheus-operated`, a headless service without a ClusterIP).

The response is JSON with `"status":"success"` and a `"result"` array where each element
has a `"metric"` field - this confirms that the application's metric made it to Prometheus
through the ServiceMonitor, rather than through a manually configured `scrape_config`.

## Task 6. Managed Prometheus: the workspace is ready to accept metrics

```bash
WORKSPACE_ID=$(aws amp list-workspaces --alias eks-task114-amp \
  --query 'workspaces[0].workspaceId' --output text)
echo "$WORKSPACE_ID"

mkdir -p /var/work/tests/artifacts/6
aws amp describe-workspace --workspace-id "$WORKSPACE_ID" \
  > /var/work/tests/artifacts/6/amp_endpoint.txt
cat /var/work/tests/artifacts/6/amp_endpoint.txt
```

In the output, `workspace.prometheusEndpoint` contains
`aps-workspaces.<region>.amazonaws.com` - this is the remote-write endpoint. The collection
pipeline itself (managed collector or ADOT) is out of scope for this lab: the goal is to
show that a managed Prometheus-compatible backend has already been created and is ready to
accept data - the third metrics path from chapter 33, alongside Container Insights and
self-managed kube-prometheus-stack.
