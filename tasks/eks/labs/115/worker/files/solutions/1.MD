## Task 2. Symptom: logs disappear without a collector

Create a Deployment whose container prints a marker and crashes - the Deployment's
`restartPolicy: Always` recreates the container inside the same pod, but the pod name
doesn't change across container restarts (this is a separate case from pod deletion):

```bash
kubectl create deployment flaky-before -n eks-115 \
  --image=busybox:1.36 -- sh -c 'echo BEFORE_MARKER_LAB115; sleep 5; exit 1'
kubectl wait --for=condition=Available deployment/flaky-before -n eks-115 --timeout=60s \
  2>/dev/null || true
sleep 15

POD=$(kubectl get po -n eks-115 -l app=flaky-before -o jsonpath='{.items[0].metadata.name}')
kubectl logs "$POD" -n eks-115
kubectl logs "$POD" -n eks-115 --previous
```

Both calls show `BEFORE_MARKER_LAB115` - the pod is alive, both the current and the
previous container run are available. Now we simulate what happens when the whole pod
is recreated (node replacement, Karpenter consolidation, a Deployment update) - we delete
the pod itself:

```bash
kubectl delete pod "$POD" -n eks-115
sleep 10
kubectl get po -n eks-115 -l app=flaky-before
```

The Deployment created a pod under a new name. Let's query the old name:

```bash
kubectl logs "$POD" -n eks-115 2>&1 | tee /tmp/notfound.txt
```

We get `Error from server (NotFound): pods "..." not found` - the logs of the crashed run
disappeared along with the pod, there's nowhere left to retrieve them from (section 34.1).
Record this in the artifact:

```bash
mkdir -p /var/work/tests/artifacts/2
{
  echo "OLD_POD_NAME=$POD"
  echo "BEFORE_MARKER_LAB115"
  cat /tmp/notfound.txt
} > /var/work/tests/artifacts/2/before_symptom.txt
cat /var/work/tests/artifacts/2/before_symptom.txt
```

## Task 3. Fluent Bit DaemonSet with an IRSA role

Add the AWS chart repository and prepare `values.yaml` with the role annotation, OOM
protection under backpressure (`Mem_Buf_Limit`, `storage.type filesystem`, section 34.7)
and output into CloudWatch Logs:

```bash
helm repo add eks https://aws.github.io/eks-charts
helm repo update

cat > ~/values.yaml <<EOF
serviceAccount:
  create: true
  annotations:
    eks.amazonaws.com/role-arn: "${ROLE_ARN}"

service:
  extraService: |
    HTTP_Server  On
    HTTP_Listen  0.0.0.0
    HTTP_PORT    2020
    storage.path /var/fluent-bit/state/flb-storage/

input:
  memBufLimit: 50MB
  multilineParser: "cri"
  extraInputs: |
    storage.type      filesystem

cloudWatchLogs:
  enabled: true
  region: "eu-central-1"
  logGroupName: "${LOG_GROUP}"
  logStreamPrefix: "fluentbit-"
  autoCreateGroup: true
EOF

helm install aws-for-fluent-bit eks/aws-for-fluent-bit \
  --namespace amazon-cloudwatch --create-namespace \
  -f ~/values.yaml

kubectl rollout status daemonset/aws-for-fluent-bit -n amazon-cloudwatch --timeout=120s
kubectl get pods -n amazon-cloudwatch -o wide
```

Verify that the role annotation and OOM protection landed in the ConfigMap:

```bash
kubectl get sa aws-for-fluent-bit -n amazon-cloudwatch -o yaml | grep role-arn
kubectl get cm aws-for-fluent-bit -n amazon-cloudwatch -o jsonpath='{.data.fluent-bit\.conf}' \
  | grep -E 'Mem_Buf_Limit|storage.type'
```

## Task 4. Fix proven: logs are found after pod deletion

The same scenario as in task 2, but now Fluent Bit is already streaming logs off the node.
This time the container doesn't crash - it lives long enough for the line to be shipped:

```bash
kubectl create deployment flaky-after -n eks-115 \
  --image=busybox:1.36 -- sh -c 'echo AFTER_MARKER_LAB115; sleep 3600'
kubectl rollout status deployment/flaky-after -n eks-115

sleep 60   # give Fluent Bit time to read the file and ship the record

POD2=$(kubectl get po -n eks-115 -l app=flaky-after -o jsonpath='{.items[0].metadata.name}')
echo "$POD2"

kubectl delete pod "$POD2" -n eks-115
sleep 10
kubectl logs "$POD2" -n eks-115 2>&1 | tee /tmp/notfound2.txt
```

`NotFound` again - but this time the line isn't lost, it's already in CloudWatch Logs:

```bash
aws logs filter-log-events --log-group-name "$LOG_GROUP" \
  --filter-pattern "AFTER_MARKER_LAB115" \
  --query 'events[*].message' --output text | tee /tmp/found_after.txt
```

The line is found even though the pod with this name is already deleted - Fluent Bit had
already shipped it off the node before the pod disappeared. Record this in the artifact:

```bash
mkdir -p /var/work/tests/artifacts/4
{
  echo "OLD_POD_NAME=$POD2"
  cat /tmp/notfound2.txt
  echo "=== found in CloudWatch Logs ==="
  cat /tmp/found_after.txt
} > /var/work/tests/artifacts/4/after_fixed.txt
cat /var/work/tests/artifacts/4/after_fixed.txt
```

## Task 5. Filtering: cutting noise before shipping

Add a `FILTER grep` section to `values.yaml` to drop lines with `/healthz` right on the
node, before ingestion into CloudWatch (section 34.6 - cutting noise at the source is
cheaper than cleaning up storage after the fact):

```bash
cat >> ~/values.yaml <<'EOF'

additionalFilters: |
  [FILTER]
      Name   grep
      Match  kube.*
      Exclude log /healthz
EOF

helm upgrade aws-for-fluent-bit eks/aws-for-fluent-bit \
  -n amazon-cloudwatch -f ~/values.yaml

kubectl rollout status daemonset/aws-for-fluent-bit -n amazon-cloudwatch --timeout=120s
```

Only after the new Fluent Bit pods are up do we generate traffic with a noisy line and a
normal one:

```bash
kubectl run access-log-gen -n eks-115 --image=busybox:1.36 --restart=Never \
  -- sh -c 'echo "GET /healthz 200"; sleep 3; echo NORMAL_MARKER_LAB115; sleep 3600'

sleep 60
```

Check both sides of the filter:

```bash
aws logs filter-log-events --log-group-name "$LOG_GROUP" \
  --filter-pattern "healthz" --query 'events' --output text
# empty - the line was dropped by the grep filter

aws logs filter-log-events --log-group-name "$LOG_GROUP" \
  --filter-pattern "NORMAL_MARKER_LAB115" --query 'events[*].message' --output text
# the record is there - the filter doesn't touch normal lines
```

Record the explanation:

```bash
mkdir -p /var/work/tests/artifacts/5
cat > /var/work/tests/artifacts/5/filter_check.txt <<'EOF'
FILTER grep with Exclude log /healthz dropped the line "GET /healthz 200" right on the
node, before shipping to CloudWatch Logs - the log group has no such record at all. The
normal line NORMAL_MARKER_LAB115 is untouched by the filter and reaches CloudWatch. Cutting
noise this way is cheaper than cleaning up logs in storage after the fact: you pay for
ingestion, and a filtered-out line never creates ingestion (section 34.6).
EOF
cat /var/work/tests/artifacts/5/filter_check.txt
```

## Task 6. Retention policy on the log group

By default, logs in CloudWatch are kept forever (`retentionInDays` empty). Set a period:

```bash
aws logs put-retention-policy --log-group-name "$LOG_GROUP" --retention-in-days 7

mkdir -p /var/work/tests/artifacts/6
aws logs describe-log-groups --log-group-name-prefix "$LOG_GROUP" \
  --query "logGroups[].[logGroupName,retentionInDays]" --output table \
  | tee /var/work/tests/artifacts/6/retention.txt
```

## Task 7. Multiline: a stack trace as one record

`input.multilineParser` already holds `cri` - it merges what the container runtime itself
splits, into a whole JSON log line. Adding the built-in `python` parser there via a comma
won't work: `cri` matches the `start_state` of any CRI line, so Fluent Bit only applies
that one, and it never gets to `python` (issue fluent/fluent-bit #5235 - multiple parsers
in a single `multiline.parser` only work if their `start_state` values don't overlap). The
correct approach is a separate `multiline` FILTER with the built-in `python` type (section
34.7), which must run in the pipeline before the `kubernetes` FILTER (merged records are
re-emitted at the head of the pipeline, and if `kubernetes` has already processed them
before the multiline filter, it would apply a second time to the result):

```bash
cat >> ~/values.yaml <<'EOF'

filter:
  enabled: false

additionalFilters: |
  [FILTER]
      Name                  multiline
      Match                 kube.*
      multiline.key_content log
      multiline.parser      python

  [FILTER]
      Name                kubernetes
      Match               kube.*
      Kube_URL            https://kubernetes.default.svc.cluster.local:443
      Merge_Log           On
      Merge_Log_Key       data
      Keep_Log            On
      K8S-Logging.Parser  On
      K8S-Logging.Exclude On
      Buffer_Size         32k

  [FILTER]
      Name   grep
      Match  kube.*
      Exclude log /healthz
EOF
```

The `filter.enabled: false` section disables the chart's built-in `kubernetes` FILTER (it
already goes into `additionalFilters` together with the `multiline` FILTER and the old
`grep` FILTER from task 5 - without `filter.enabled: false` the config would have two
`kubernetes` FILTERs in a row, the second one redundant). Apply it:

```bash
helm upgrade aws-for-fluent-bit eks/aws-for-fluent-bit \
  -n amazon-cloudwatch -f ~/values.yaml

kubectl rollout status daemonset/aws-for-fluent-bit -n amazon-cloudwatch --timeout=120s
```

Only after Fluent Bit restarts do we print four lines in a row, simulating a Python
Traceback:

```bash
kubectl run stacktrace-app -n eks-115 --image=busybox:1.36 --restart=Never \
  -- sh -c 'printf "Traceback (most recent call last):\n  File \"app.py\", line 10, in <module>\n    raise ValueError(\"CRASH_TRACE_LAB115\")\nValueError: CRASH_TRACE_LAB115\n"; sleep 3600'

sleep 60
```

Check that all four lines arrived as one CloudWatch record, not four:

```bash
aws logs filter-log-events --log-group-name "$LOG_GROUP" \
  --filter-pattern "CRASH_TRACE_LAB115" \
  --query 'events[*].message' --output text | tee /tmp/multiline_msg.txt
```

In the output, one message contains both `Traceback` and `CRASH_TRACE_LAB115` - the
`python` parser merged the four log lines into one record. Without it, CloudWatch would
have received four separate events, and Logs Insights would count that as four different
"crashes". Record this:

```bash
mkdir -p /var/work/tests/artifacts/7
{
  echo "=== merged CloudWatch event ==="
  cat /tmp/multiline_msg.txt
  echo ""
  echo "FILTER multiline with the built-in python type merged 4 Traceback lines into"
  echo "one CloudWatch record instead of splitting them into 4 separate events."
} > /var/work/tests/artifacts/7/multiline.txt
cat /var/work/tests/artifacts/7/multiline.txt
```
