# Lab 108 - reference solution (AWS Load Balancer Controller: NLB for a Service)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster. Terraform has already created the IAM role for the controller (component
`eks_lbc_irsa`, module `eks_v2_lbc_irsa`) - all that's left is to grab its ARN and install
the controller itself.

## Task 1. Namespace `eks-108`

```bash
kubectl create namespace eks-108
```

## Task 2. ServiceAccount and installing the AWS Load Balancer Controller

Find the ARN of the role terraform created (role name `<cluster-name>-lbc-irsa`):

```bash
ROLE_ARN=$(aws iam list-roles \
  --query "Roles[?contains(RoleName,'lbc-irsa')].Arn" --output text)
echo "$ROLE_ARN"
```

Create the ServiceAccount in `kube-system` with an annotation pointing to that role. LBC is
installed via Helm with `serviceAccount.create=false`, so the ServiceAccount needs to exist
beforehand:

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: ServiceAccount
metadata:
  name: aws-load-balancer-controller
  namespace: kube-system
  annotations:
    eks.amazonaws.com/role-arn: ${ROLE_ARN}
EOF
```

Install the controller itself from the official chart:

```bash
helm repo add eks https://aws.github.io/eks-charts
helm repo update

CLUSTER_NAME=$(kubectl config view --minify -o jsonpath='{.clusters[0].name}' | sed 's/.*\///')
VPC_ID=$(aws eks describe-cluster --name "${CLUSTER_NAME}" \
  --query 'cluster.resourcesVpcConfig.vpcId' --output text)
echo "$VPC_ID"

helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName="${CLUSTER_NAME}" \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set region=eu-central-1 \
  --set vpcId="${VPC_ID}"

kubectl rollout status deployment/aws-load-balancer-controller -n kube-system
```

The controller runs on Fargate (namespace `kube-system` under the Fargate profile), and
Fargate has no EC2 instance metadata service (IMDS) at all - without explicit
`vpcId`/`region`, the controller tries to get the VPC ID via IMDS and crashes into
`CrashLoopBackOff` with an error like `failed to fetch VPC ID from instance metadata: ...
context deadline exceeded`. On managed EC2 nodes these flags aren't needed (IMDS is
available there), but on Fargate you always have to pass them explicitly.

Check that the controller is up and sees the role:

```bash
kubectl get deploy aws-load-balancer-controller -n kube-system
kubectl get sa aws-load-balancer-controller -n kube-system -o yaml | grep role-arn
```

## Task 4. Service `web` of type LoadBalancer: NLB instead of CLB

By default the in-tree cloud provider creates a legacy Classic Load Balancer for a Service
of type LoadBalancer. The `aws-load-balancer-type: external` annotation hands reconciliation
over to the AWS Load Balancer Controller, which creates a modern Network Load Balancer:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: eks-108
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: external
    service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: ip
    service.beta.kubernetes.io/aws-load-balancer-scheme: internet-facing
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080
EOF
```

Wait for the external address:

```bash
kubectl get svc web -n eks-108 -w
```

Confirm via AWS CLI that an NLB (type `network`) was created, not a CLB, and that the scheme
is `internet-facing`:

```bash
HOSTNAME=$(kubectl get svc web -n eks-108 \
  -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
LB_ARN=$(aws elbv2 describe-load-balancers \
  --query "LoadBalancers[?DNSName=='${HOSTNAME}'].LoadBalancerArn" --output text)

mkdir -p /var/work/tests/artifacts/4
aws elbv2 describe-load-balancers --load-balancer-arns "$LB_ARN" \
  > /var/work/tests/artifacts/4/nlb.txt
cat /var/work/tests/artifacts/4/nlb.txt
```

In the output `Type` should be `network` (NLB), and `Scheme` should be `internet-facing`.
If the `aws-load-balancer-type` annotation weren't there, the in-tree provider would have
created `Type: classic` - that's exactly the "asked for LoadBalancer, got a CLB" symptom
from chapter 26.

## Task 5. Checking targets: pod IPs, not node instance IDs

`target-type: ip` registers pod addresses from VPC CNI in the target group, not nodes by
`InstanceId`. Verify this via `describe-target-groups` and `describe-target-health`:

```bash
TG_ARN=$(aws elbv2 describe-target-groups --load-balancer-arn "$LB_ARN" \
  --query 'TargetGroups[0].TargetGroupArn' --output text)

mkdir -p /var/work/tests/artifacts/5
{
  aws elbv2 describe-target-groups --target-group-arns "$TG_ARN"
  aws elbv2 describe-target-health --target-group-arn "$TG_ARN"
} > /var/work/tests/artifacts/5/targets.txt

cat /var/work/tests/artifacts/5/targets.txt
```

In the file, `TargetType` should be `ip`, and each target's `Target.Id` should be an
address from `10.10.0.0/16` (this lab's VPC subnet), not `i-...` (an instance ID). This is
exactly what an NLB target group with `target-type: ip` looks like: the controller
registers the pod's IP directly, bypassing NodePort, which removes the extra hop through
kube-proxy.

## Task 6. Diagnostics: a successful reconciliation vs. AccessDenied

Look at the controller log to see what a normal Service reconciliation looks like - it
should contain the ARN of the created load balancer:

```bash
kubectl logs -n kube-system deploy/aws-load-balancer-controller --tail=200 \
  | grep -i 'successfully reconciled\|loadBalancerARN\|arn:aws:elasticloadbalancing' \
  | tail -n 10
```

If the ServiceAccount didn't have a role attached (or the role lacked the necessary
permissions), the controller wouldn't be able to call the ELBv2 API, and the log would show
a message like `AccessDenied: User: ... is not authorized to perform:
elasticloadbalancing:CreateLoadBalancer`, and the Service would stay in `<pending>` without
an external address - because reconciliation fails on the very first API call, before the
NLB gets created.

Save both observations into a single artifact:

```bash
mkdir -p /var/work/tests/artifacts/6
{
  echo "=== Successful reconciliation (real controller log) ==="
  kubectl logs -n kube-system deploy/aws-load-balancer-controller --tail=200 \
    | grep -i 'successfully reconciled\|arn:aws:elasticloadbalancing'
  echo
  echo "=== Expected symptom without IAM permissions (not reproduced on the live role) ==="
  echo "AccessDenied: User: arn:aws:sts::<account>:assumed-role/<cluster>-lbc-irsa/... " \
       "is not authorized to perform: elasticloadbalancing:CreateLoadBalancer " \
       "on resource: arn:aws:elasticloadbalancing:<region>:<account>:loadbalancer/*"
  echo "With this error the web Service stays in <pending>: EXTERNAL-IP never shows up," \
       "because the controller couldn't create the NLB through the ELBv2 API."
} > /var/work/tests/artifacts/6/reconcile.txt

cat /var/work/tests/artifacts/6/reconcile.txt
```
