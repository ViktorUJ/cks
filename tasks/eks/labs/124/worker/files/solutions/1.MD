# Lab 124 - reference solution (HPA, KEDA, Prometheus)

All commands run on the worker machine over SSH. kubectl and helm are already configured
(kubeconfig is assembled via `aws eks update-kubeconfig` when the machine boots).

## Task 1. Namespace `eks-124`

```bash
kubectl create namespace eks-124
```

## Task 2. kube-prometheus-stack in namespace `monitoring`

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

helm install kube-prometheus-stack prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace \
  --set grafana.enabled=false \
  --set alertmanager.enabled=false \
  --set prometheus.prometheusSpec.resources.requests.cpu=200m \
  --set prometheus.prometheusSpec.resources.requests.memory=512Mi
```

These three flags are not cosmetic. The lab doesn't need Grafana or Alertmanager, and
Grafana is the heaviest pod in the chart (roughly 325 MiB on the test bench). Explicit
`requests` move Prometheus from `BestEffort` to `Burstable`: both the scheduler and
Karpenter, which sizes the node based on the sum of `requests`, can see its needs. Without
this the monitoring stack lands on the cheapest instance, and kubelet evicts Prometheus
under memory pressure - see the detailed breakdown in the lab README.

Wait for the pods to become ready:

```bash
kubectl get pods -n monitoring -w
```

Wait until all pods reach `Running` and `1/1` (or `2/2`) Ready - this usually takes 2-3
minutes. Check the Service that KEDA will watch, and the pod's QoS class:

```bash
kubectl get svc -n monitoring kube-prometheus-stack-prometheus
kubectl get pod -n monitoring prometheus-kube-prometheus-stack-prometheus-0 \
  -o jsonpath='{.status.qosClass}{"\n"}'
```

The expected output of the second command is `Burstable`.

## Task 5. ScaledObject with the `prometheus` scaler

The cAdvisor metric `container_cpu_usage_seconds_total` is collected by
kube-prometheus-stack from every pod out of the box, with no ServiceMonitor needed. We
compute the total CPU usage of the load GENERATOR's pods from task 6, not of `demo-app`
itself: the application scales based on someone else's load, and a regular CPU-based HPA
cannot do that - external metrics exist precisely for this.

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: demo-app
  namespace: eks-124
spec:
  scaleTargetRef:
    name: demo-app
  minReplicaCount: 1
  maxReplicaCount: 5
  triggers:
  - type: prometheus
    metadata:
      serverAddress: http://kube-prometheus-stack-prometheus.monitoring.svc:9090
      query: sum(rate(container_cpu_usage_seconds_total{namespace="eks-124", pod=~"stress-generator.*"}[1m]))
      threshold: "0.1"
EOF
```

You can check that the query actually returns something right from the cluster (while
there's no generator yet, the answer will be empty, and that's normal - in that case KEDA
reports zero to HPA):

```bash
kubectl run promq --rm -i --restart=Never -n default --image=curlimages/curl -- \
  -sG --data-urlencode \
  'query=sum(rate(container_cpu_usage_seconds_total{namespace="eks-124",pod=~"stress-generator.*"}[1m]))' \
  http://kube-prometheus-stack-prometheus.monitoring.svc:9090/api/v1/query
```

Check that KEDA took the ScaledObject under management and created the HPA:

```bash
kubectl get scaledobject demo-app -n eks-124
kubectl get hpa -A | grep keda-hpa
kubectl get hpa keda-hpa-demo-app -n eks-124
```

The HPA is called `keda-hpa-demo-app` - this is proof that KEDA does not substitute HPA, it
creates and manages a regular `HorizontalPodAutoscaler` under the hood.

## Task 6. Load test: scaling up

First we record the state before the load:

```bash
mkdir -p /var/work/tests/artifacts/6
kubectl get hpa keda-hpa-demo-app -n eks-124 > /var/work/tests/artifacts/6/hpa_before.txt
cat /var/work/tests/artifacts/6/hpa_before.txt
```

Create the load generator. It has its own label (`app=stress-generator`) - the PromQL
query from task 5 selects pods by NAME, not by label, so mixing the generator into
`demo-app`'s selector is unnecessary and harmful: two Deployments with overlapping
selectors is an anti-pattern. `limits.cpu` is mandatory, otherwise the four CPU workers
starve kubelet of CPU and the node goes `NotReady`. `nodeSelector` is needed because
`polinux/stress` is only built for `amd64`, while this lab's NodePool also allows `arm64`:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: stress-generator
  namespace: eks-124
spec:
  replicas: 2
  selector:
    matchLabels:
      app: stress-generator
  template:
    metadata:
      labels:
        app: stress-generator
    spec:
      nodeSelector:
        kubernetes.io/arch: amd64
      containers:
      - name: stress
        image: polinux/stress
        command: ["stress"]
        args: ["--cpu", "2"]
        resources:
          requests:
            cpu: "200m"
          limits:
            cpu: "500m"
EOF
```

Watch the metric and the replica count grow:

```bash
watch kubectl get hpa keda-hpa-demo-app -n eks-124
```

Wait 1-2 minutes (KEDA polls Prometheus, HPA computes replicas, Karpenter adds a node if
needed). On the test bench it looked like this:

```
06:36:41 replicas=1 0/100m (avg)
06:37:04 replicas=1 1251m/100m (avg)
06:37:26 replicas=4 382m/100m (avg)
```

As soon as `REPLICAS` becomes greater than `1`, save:

```bash
kubectl get hpa keda-hpa-demo-app -n eks-124 > /var/work/tests/artifacts/6/hpa_after.txt
cat /var/work/tests/artifacts/6/hpa_after.txt
```

## Task 7. Removing the load: scaling down

```bash
kubectl delete deployment stress-generator -n eks-124
```

The generator's pods disappear, their series are gone from Prometheus, KEDA reports zero to
HPA. The `TARGETS` value drops to zero in about 30 seconds, but the replica count holds:
`stabilizationWindowSeconds` for scaleDown on HPA defaults to 300 seconds. A measurement
from the test bench - metric zero at 06:40:07, replicas `5 -> 2 -> 1` at 06:44:40 and
06:45:07:

```bash
watch kubectl get hpa keda-hpa-demo-app -n eks-124
```

As soon as `REPLICAS` returns to `1`, save the artifact:

```bash
mkdir -p /var/work/tests/artifacts/7
kubectl get hpa keda-hpa-demo-app -n eks-124 > /var/work/tests/artifacts/7/hpa_after_cooldown.txt
cat /var/work/tests/artifacts/7/hpa_after_cooldown.txt
```

## Task 8. A regular HPA versus an HPA created by KEDA

```bash
kubectl get hpa -A
```

In the output, HPA `keda-hpa-demo-app` looks identical column-wise to a regular HPA - the
same `TARGETS`, `MINPODS`, `MAXPODS`, `REPLICAS`. The only difference is the name (prefix
`keda-hpa-`) and who controls it: an engineer creates and edits a regular HPA directly via
a `HorizontalPodAutoscaler` manifest, while `keda-hpa-demo-app` is created and controlled -
in Russian, `управляется` - by the KEDA operator based on the `ScaledObject` resource -
delete the `ScaledObject`, and KEDA deletes this HPA along with it.

Save the explanation to the artifact:

```bash
mkdir -p /var/work/tests/artifacts/8
cat > /var/work/tests/artifacts/8/hpa_compare.txt <<'EOF'
In kubectl get hpa -A, a regular HPA and HPA keda-hpa-demo-app look identical column-wise:
TARGETS/MINPODS/MAXPODS/REPLICAS - the only difference is the name and the object's origin.

KEDA does not replace HPA: the KEDA operator watches the ScaledObject and itself creates
and управляет (controls) a regular HorizontalPodAutoscaler named keda-hpa-<ScaledObject
name>, while the KEDA metrics adapter feeds it the metric value through
external.metrics.k8s.io. Replicas are still computed by the same HPA mechanism as always.
EOF
cat /var/work/tests/artifacts/8/hpa_compare.txt
```
