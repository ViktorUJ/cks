# Lab 117 - reference solution (per-AZ NAT vs. a single NAT, VPC endpoints, cross-AZ)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster (kubeconfig was built via `aws eks update-kubeconfig` when the machine booted).

```bash
export CLUSTER=$(aws eks list-clusters --query 'clusters[0]' --output text)
export VPC=$(aws eks describe-cluster --name "$CLUSTER" \
  --query 'cluster.resourcesVpcConfig.vpcId' --output text)
kubectl create namespace eks-117
```

## Task 1. How many NAT Gateways, and in which zones

The lab's network is set up so that a NAT Gateway exists in only two of the three private
AZs. Let's find all NAT Gateways in this VPC:

```bash
aws ec2 describe-nat-gateways --filter "Name=vpc-id,Values=$VPC" \
  --query 'NatGateways[].[NatGatewayId,SubnetId,State]' --output table
```

For each NAT, let's determine its subnet's AZ:

```bash
NAT1=$(aws ec2 describe-nat-gateways --filter "Name=vpc-id,Values=$VPC" \
  --query 'NatGateways[0].NatGatewayId' --output text)
NAT1_SUBNET=$(aws ec2 describe-nat-gateways --nat-gateway-ids "$NAT1" \
  --query 'NatGateways[0].SubnetId' --output text)
NAT1_AZ=$(aws ec2 describe-subnets --subnet-ids "$NAT1_SUBNET" \
  --query 'Subnets[0].AvailabilityZone' --output text)

NAT2=$(aws ec2 describe-nat-gateways --filter "Name=vpc-id,Values=$VPC" \
  --query 'NatGateways[1].NatGatewayId' --output text)
NAT2_SUBNET=$(aws ec2 describe-nat-gateways --nat-gateway-ids "$NAT2" \
  --query 'NatGateways[0].SubnetId' --output text)
NAT2_AZ=$(aws ec2 describe-subnets --subnet-ids "$NAT2_SUBNET" \
  --query 'Subnets[0].AvailabilityZone' --output text)

echo "nat1=$NAT1 az=$NAT1_AZ / nat2=$NAT2 az=$NAT2_AZ"
```

Both AZs that have a NAT are `eu-central-1a` and `eu-central-1b`. The private subnet in
`eu-central-1c` exists (it carries the `karpenter.sh/discovery` tag, so Karpenter can place
nodes there), but there's no NAT Gateway in that zone:

```bash
mkdir -p /var/work/tests/artifacts/1
cat > /var/work/tests/artifacts/1/natdiscovery.txt <<EOF
nat_count=2
nat_1_id=$NAT1
nat_1_az=$NAT1_AZ
nat_2_id=$NAT2
nat_2_az=$NAT2_AZ
no_nat_az=eu-central-1c
EOF
cat /var/work/tests/artifacts/1/natdiscovery.txt
```

## Task 2. Reproducing the cross-AZ trap

Let's find the route table of subnet `private-subnet-3` (it's in `eu-central-1c`, with no
NAT):

```bash
RTB_C=$(aws ec2 describe-route-tables --filters "Name=tag:Name,Values=private-subnet-3" \
  --query 'RouteTables[0].RouteTableId' --output text)
echo "route table AZ 1c = $RTB_C"
```

Let's point this route table's `0.0.0.0/0` route at one of the neighboring AZs' NAT
Gateway - we take `NAT1` (in `eu-central-1a`), and this is exactly the step that creates
the cross-AZ path:

```bash
aws ec2 create-route --route-table-id "$RTB_C" \
  --destination-cidr-block 0.0.0.0/0 --nat-gateway-id "$NAT1"

aws ec2 describe-route-tables --route-table-ids "$RTB_C" \
  --query 'RouteTables[0].Routes'
```

Let's create a workload that specifically requests zone `eu-central-1c`, so that Karpenter
brings up a node there. The image is `curlimages/curl:latest` with a sleeping `command`:
from this pod we'll later check egress via `kubectl exec`, so the container needs a shell
and `curl`:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: crossaz
  namespace: eks-117
spec:
  replicas: 1
  selector:
    matchLabels:
      app: crossaz
  template:
    metadata:
      labels:
        app: crossaz
    spec:
      nodeSelector:
        topology.kubernetes.io/zone: eu-central-1c
      containers:
      - name: app
        image: curlimages/curl:latest
        command: ["sleep", "3600"]
EOF

kubectl rollout status deployment/crossaz -n eks-117
```

Let's check the node and its zone, then egress from inside the pod:

```bash
POD=$(kubectl get po -n eks-117 -l app=crossaz -o jsonpath='{.items[0].metadata.name}')
NODE=$(kubectl get po -n eks-117 -l app=crossaz -o jsonpath='{.items[0].spec.nodeName}')
NODE_ZONE=$(kubectl get node "$NODE" \
  -o jsonpath='{.metadata.labels.topology\.kubernetes\.io/zone}')
echo "node=$NODE zone=$NODE_ZONE"

HTTP_CODE=$(kubectl exec -n eks-117 "$POD" -- \
  curl -s -o /dev/null -w '%{http_code}' https://checkip.amazonaws.com)
echo "egress_http_code=$HTTP_CODE"
```

Egress works (`200`), but this is exactly the trap from chapter 31: the pod lives in
`eu-central-1c`, while its packets first cross the AZ boundary to the NAT in
`eu-central-1a`, and only then head out. That hop is billed as cross-AZ traffic separately
from the NAT's own processing fee - meaning you pay twice for the same byte. The correct
pattern is a NAT Gateway in every AZ that has nodes (as is already done for
`eu-central-1a` and `eu-central-1b` in this lab), so that a node's traffic never leaves its
own zone before reaching a NAT.

```bash
mkdir -p /var/work/tests/artifacts/2
cat > /var/work/tests/artifacts/2/crossaz.txt <<EOF
subnet_c_route_table_id=$RTB_C
nat_gateway_id_used=$NAT1
nat_gateway_az_used=$NAT1_AZ
pod_node=$NODE
pod_node_zone=$NODE_ZONE
egress_http_code=$HTTP_CODE

The 0.0.0.0/0 route of the eu-central-1c subnet points to a NAT Gateway in a different
zone ($NAT1_AZ), so all outbound traffic from a node in eu-central-1c goes cross-AZ: first
an inter-AZ hop to the NAT, then processing on the NAT itself. This is billed twice - once
for inter-AZ (cross-AZ) traffic and once for the NAT-processed gigabytes. The correct
pattern is a NAT Gateway in every AZ that has nodes, so traffic never crosses a zone
boundary at all.
EOF
cat /var/work/tests/artifacts/2/crossaz.txt
```

## Task 3. Gateway VPC endpoint for S3 - a free route

Let's find the route tables of all three private subnets:

```bash
RTB_A=$(aws ec2 describe-route-tables --filters "Name=tag:Name,Values=private-subnet-1" \
  --query 'RouteTables[0].RouteTableId' --output text)
RTB_B=$(aws ec2 describe-route-tables --filters "Name=tag:Name,Values=private-subnet-2" \
  --query 'RouteTables[0].RouteTableId' --output text)
echo "rtb_a=$RTB_A rtb_b=$RTB_B rtb_c=$RTB_C"
```

Let's create a gateway endpoint for S3 and attach it to all three route tables right away:

```bash
S3_EP=$(aws ec2 create-vpc-endpoint --vpc-id "$VPC" \
  --vpc-endpoint-type Gateway --service-name com.amazonaws.eu-central-1.s3 \
  --route-table-ids "$RTB_A" "$RTB_B" "$RTB_C" \
  --query 'VpcEndpoint.VpcEndpointId' --output text)

until aws ec2 describe-vpc-endpoints --vpc-endpoint-ids "$S3_EP" \
    --query 'VpcEndpoints[0].State' --output text | grep -q available; do
  echo "waiting for the S3 endpoint to become available..."
  sleep 5
done

aws ec2 describe-vpc-endpoints --vpc-endpoint-ids "$S3_EP" \
  --query 'VpcEndpoints[0].{State:State,RouteTableIds:RouteTableIds}'
```

A gateway endpoint for S3 doesn't create an ENI and isn't billed either hourly or for
processed gigabytes - it's just a route table entry, which makes it the first and most
cost-effective optimization step:

```bash
mkdir -p /var/work/tests/artifacts/3
cat > /var/work/tests/artifacts/3/s3endpoint.txt <<EOF
vpc_endpoint_id=$S3_EP
state=available
route_tables=$RTB_A,$RTB_B,$RTB_C

A gateway endpoint for S3 is just a route table entry, and it is free of charge (бесплат):
there is neither an hourly fee nor a per-processed-data fee, unlike an interface endpoint.
EOF
cat /var/work/tests/artifacts/3/s3endpoint.txt
```

## Task 4. Interface VPC endpoint for a high-traffic service

Let's choose `sts` - every pod using IRSA or EKS Pod Identity exchanges its token for
temporary credentials via STS on every start and on every credential refresh, and without
an endpoint that exchange goes through NAT for every such request. (The alternative is
`ecr.api`: image registry authorization on every pull; choosing either one is accepted by
the test.)

Let's take the default security group and immediately allow inbound HTTPS from the VPC
CIDR in it. Without this rule the endpoint would be created but unreachable: the default
security group's inbound rule only allows traffic from members of the same group, while
Karpenter's nodes and pods live in other groups.

```bash
SG=$(aws ec2 describe-security-groups --filters "Name=vpc-id,Values=$VPC" \
  "Name=group-name,Values=default" --query 'SecurityGroups[0].GroupId' --output text)

aws ec2 authorize-security-group-ingress --group-id "$SG" \
  --protocol tcp --port 443 --cidr 10.10.0.0/16

STS_EP=$(aws ec2 create-vpc-endpoint --vpc-id "$VPC" \
  --vpc-endpoint-type Interface --service-name com.amazonaws.eu-central-1.sts \
  --subnet-ids "$(aws ec2 describe-subnets --filters "Name=tag:Name,Values=private-subnet-1" \
    --query 'Subnets[0].SubnetId' --output text)" \
    "$(aws ec2 describe-subnets --filters "Name=tag:Name,Values=private-subnet-2" \
    --query 'Subnets[0].SubnetId' --output text)" \
  --security-group-ids "$SG" --private-dns-enabled \
  --query 'VpcEndpoint.VpcEndpointId' --output text)

until aws ec2 describe-vpc-endpoints --vpc-endpoint-ids "$STS_EP" \
    --query 'VpcEndpoints[0].State' --output text | grep -q available; do
  echo "waiting for the sts endpoint to become available..."
  sleep 5
done

aws ec2 describe-vpc-endpoints --vpc-endpoint-ids "$STS_EP" \
  --query 'VpcEndpoints[0].{State:State,PrivateDnsEnabled:PrivateDnsEnabled}'
```

Let's check that the endpoint actually responds from inside the cluster -
`private_dns_enabled=true` means the name `sts.eu-central-1.amazonaws.com` now resolves to
the endpoint ENI's private addresses across the whole VPC, and if the `443` rule wasn't
added, STS would stop working for every pod at once:

```bash
kubectl exec -n eks-117 "$POD" -- nslookup sts.eu-central-1.amazonaws.com
kubectl exec -n eks-117 "$POD" -- \
  curl -s -o /dev/null -w '%{http_code}\n' --connect-timeout 8 \
  https://sts.eu-central-1.amazonaws.com
```

The name resolves to addresses from `10.10.15.0/24` and `10.10.16.0/24` (these are the
endpoint's ENIs), and `curl` returns code `302` - a real STS response over PrivateLink.
Code `000` and a timeout would have meant the endpoint's security group wasn't letting
traffic in from the pods.

```bash
mkdir -p /var/work/tests/artifacts/4
cat > /var/work/tests/artifacts/4/interfaceendpoint.txt <<EOF
service_chosen=sts
vpc_endpoint_id=$STS_EP
state=available
private_dns_enabled=true

Chose sts: IRSA and EKS Pod Identity exchange a token for temporary keys via STS on every
pod start and on every credentials refresh, this is a frequent request, and without an
endpoint it goes through NAT. An interface endpoint removes this traffic from NAT, at the
cost of an hourly fee per ENI in each AZ plus a fee for processed gigabytes.
EOF
cat /var/work/tests/artifacts/4/interfaceendpoint.txt
```

## Task 5. NAT metrics: how many bytes went through each gateway

Let's get the sum of `BytesOutToDestination` for the last few hours for each NAT
(namespace `AWS/NATGateway`):

```bash
START=$(date -u -d '3 hours ago' +%Y-%m-%dT%H:%M:%S)
END=$(date -u +%Y-%m-%dT%H:%M:%S)

NAT_A_SUM=$(aws cloudwatch get-metric-statistics --namespace AWS/NATGateway \
  --metric-name BytesOutToDestination --statistics Sum --period 3600 \
  --dimensions Name=NatGatewayId,Value="$NAT1" \
  --start-time "$START" --end-time "$END" \
  --query 'sum(Datapoints[].Sum)' --output text)
[[ "$NAT_A_SUM" == "None" ]] && NAT_A_SUM=0

NAT_B_SUM=$(aws cloudwatch get-metric-statistics --namespace AWS/NATGateway \
  --metric-name BytesOutToDestination --statistics Sum --period 3600 \
  --dimensions Name=NatGatewayId,Value="$NAT2" \
  --start-time "$START" --end-time "$END" \
  --query 'sum(Datapoints[].Sum)' --output text)
[[ "$NAT_B_SUM" == "None" ]] && NAT_B_SUM=0

TOTAL=$(python3 -c "print(int(${NAT_A_SUM%.*}) + int(${NAT_B_SUM%.*}))")
echo "nat_a=$NAT1 sum=$NAT_A_SUM / nat_b=$NAT2 sum=$NAT_B_SUM / total=$TOTAL"
```

`NAT1` is the same NAT Gateway that task 2 pointed the `eu-central-1c` subnet's route at.
It took on both the regular traffic of its own zone `eu-central-1a` and the cross-AZ
traffic from the `crossaz` node, so it's expected to show a larger volume of
`BytesOutToDestination` over the same window than `NAT2`, which only serves its own AZ:

```bash
mkdir -p /var/work/tests/artifacts/5
cat > /var/work/tests/artifacts/5/natmetrics.txt <<EOF
nat_a_id=$NAT1
nat_a_bytes_out_sum=${NAT_A_SUM%.*}
nat_b_id=$NAT2
nat_b_bytes_out_sum=${NAT_B_SUM%.*}
total_bytes_out_sum=$TOTAL

Metric: AWS/NATGateway BytesOutToDestination, sum across data points over the period.
NAT $NAT1 took on cross-AZ traffic from the crossaz node in eu-central-1c (task 2) in
addition to the regular traffic of its own zone, so it is expected to show a larger
BytesOutToDestination volume than $NAT2, which only serves its own AZ.
EOF
cat /var/work/tests/artifacts/5/natmetrics.txt
```

If the test workload managed to generate noticeable traffic (for example, repeated `curl`
requests from the `crossaz` pod), the difference in sums is already visible in the first
metric window; if the load was a one-off, the difference may be small - what matters is the
fact that the NAT which took on the cross-AZ node shows a volume no smaller than the other
one.
