export CLUSTER=$(aws eks list-clusters --query 'clusters[0]' --output text)

## Задание 1. Сколько NAT Gateway и в каких зонах

Сеть лабы создана так, что NAT Gateway есть только в двух из трёх приватных AZ. Находим
все NAT Gateway этой VPC:

```bash
aws ec2 describe-nat-gateways --filter "Name=vpc-id,Values=$VPC" \
  --query 'NatGateways[].[NatGatewayId,SubnetId,State]' --output table
```

Для каждого NAT определяем AZ его подсети:

```bash
NAT1=$(aws ec2 describe-nat-gateways --filter "Name=vpc-id,Values=$VPC" \
  --query 'NatGateways[0].NatGatewayId' --output text)
NAT1_SUBNET=$(aws ec2 describe-nat-gateways --nat-gateway-ids "$NAT1" \
  --query 'NatGateways[0].SubnetId' --output text)
NAT1_AZ=$(aws ec2 describe-subnets --subnet-ids "$NAT1_SUBNET" \
  --query 'Subnets[0].AvailabilityZone' --output text)

NAT2=$(aws ec2 describe-nat-gateways --filter "Name=vpc-id,Values=$VPC" \
  --query 'NatGateways[1].NatGatewayId' --output text)
NAT2_SUBNET=$(aws ec2 describe-nat-gateways --nat-gateway-ids "$NAT2" \
  --query 'NatGateways[0].SubnetId' --output text)
NAT2_AZ=$(aws ec2 describe-subnets --subnet-ids "$NAT2_SUBNET" \
  --query 'Subnets[0].AvailabilityZone' --output text)

echo "nat1=$NAT1 az=$NAT1_AZ / nat2=$NAT2 az=$NAT2_AZ"
```

Обе AZ, где стоят NAT, - `eu-central-1a` и `eu-central-1b`. Приватная подсеть в
`eu-central-1c` существует (тег `karpenter.sh/discovery` на ней есть, Karpenter может
ставить туда ноды), но NAT Gateway в этой зоне нет:

```bash
mkdir -p /var/work/tests/artifacts/1
cat > /var/work/tests/artifacts/1/natdiscovery.txt <<EOF
nat_count=2
nat_1_id=$NAT1
nat_1_az=$NAT1_AZ
nat_2_id=$NAT2
nat_2_az=$NAT2_AZ
no_nat_az=eu-central-1c
EOF
cat /var/work/tests/artifacts/1/natdiscovery.txt
```

## Задание 2. Воспроизведение cross-AZ ловушки

Находим route table подсети `private-subnet-3` (она в `eu-central-1c`, без NAT):

```bash
RTB_C=$(aws ec2 describe-route-tables --filters "Name=tag:Name,Values=private-subnet-3" \
  --query 'RouteTables[0].RouteTableId' --output text)
echo "route table AZ 1c = $RTB_C"
```

Направляем маршрут `0.0.0.0/0` этой route table на NAT Gateway одной из соседних AZ -
берём `NAT1` (в `eu-central-1a`), это и есть шаг, который создаёт cross-AZ путь:

```bash
aws ec2 create-route --route-table-id "$RTB_C" \
  --destination-cidr-block 0.0.0.0/0 --nat-gateway-id "$NAT1"

aws ec2 describe-route-tables --route-table-ids "$RTB_C" \
  --query 'RouteTables[0].Routes'
```

Создаём нагрузку, которая просит именно зону `eu-central-1c`, чтобы Karpenter поднял туда
ноду. Образ - `curlimages/curl:latest` со спящим `command`: из этого пода мы потом проверим
egress через `kubectl exec`, поэтому в контейнере нужны шелл и `curl`:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: crossaz
  namespace: eks-117
spec:
  replicas: 1
  selector:
    matchLabels:
      app: crossaz
  template:
    metadata:
      labels:
        app: crossaz
    spec:
      nodeSelector:
        topology.kubernetes.io/zone: eu-central-1c
      containers:
      - name: app
        image: curlimages/curl:latest
        command: ["sleep", "3600"]
EOF

kubectl rollout status deployment/crossaz -n eks-117
```

Проверяем ноду и её зону, затем egress изнутри пода:

```bash
POD=$(kubectl get po -n eks-117 -l app=crossaz -o jsonpath='{.items[0].metadata.name}')
NODE=$(kubectl get po -n eks-117 -l app=crossaz -o jsonpath='{.items[0].spec.nodeName}')
NODE_ZONE=$(kubectl get node "$NODE" \
  -o jsonpath='{.metadata.labels.topology\.kubernetes\.io/zone}')
echo "node=$NODE zone=$NODE_ZONE"

HTTP_CODE=$(kubectl exec -n eks-117 "$POD" -- \
  curl -s -o /dev/null -w '%{http_code}' https://checkip.amazonaws.com)
echo "egress_http_code=$HTTP_CODE"
```

Egress работает (`200`), но это именно та ловушка из главы 31: под живёт в
`eu-central-1c`, а его пакеты сначала пересекают границу AZ до NAT в `eu-central-1a`, и
только потом идут наружу. Такой переход тарифицируется как cross-AZ трафик отдельно от
платы за обработку самого NAT - то есть платят дважды за один и тот же байт. Правильная
схема - NAT Gateway в каждой AZ, где есть ноды (как уже сделано для `eu-central-1a` и
`eu-central-1b` в этой лабе), чтобы трафик ноды не покидал свою зону до выхода на NAT.

```bash
mkdir -p /var/work/tests/artifacts/2
cat > /var/work/tests/artifacts/2/crossaz.txt <<EOF
subnet_c_route_table_id=$RTB_C
nat_gateway_id_used=$NAT1
nat_gateway_az_used=$NAT1_AZ
pod_node=$NODE
pod_node_zone=$NODE_ZONE
egress_http_code=$HTTP_CODE

Маршрут 0.0.0.0/0 подсети eu-central-1c ведёт на NAT Gateway в другой зоне ($NAT1_AZ),
поэтому весь исходящий трафик ноды в eu-central-1c идёт cross-AZ: сначала межзонный
переход до NAT, потом обработка на самом NAT. Это тарифицируется дважды - платой за
межзонный (cross-AZ) трафик и платой за обработанные NAT гигабайты. Правильная схема -
NAT Gateway в каждой AZ, где есть ноды, чтобы трафик не пересекал границу зоны вообще.
EOF
cat /var/work/tests/artifacts/2/crossaz.txt
```

## Задание 3. Gateway VPC endpoint для S3 - бесплатный маршрут

Находим route table всех трёх приватных подсетей:

```bash
RTB_A=$(aws ec2 describe-route-tables --filters "Name=tag:Name,Values=private-subnet-1" \
  --query 'RouteTables[0].RouteTableId' --output text)
RTB_B=$(aws ec2 describe-route-tables --filters "Name=tag:Name,Values=private-subnet-2" \
  --query 'RouteTables[0].RouteTableId' --output text)
echo "rtb_a=$RTB_A rtb_b=$RTB_B rtb_c=$RTB_C"
```

Создаём gateway endpoint для S3 и сразу привязываем его ко всем трём route table:

```bash
S3_EP=$(aws ec2 create-vpc-endpoint --vpc-id "$VPC" \
  --vpc-endpoint-type Gateway --service-name com.amazonaws.eu-central-1.s3 \
  --route-table-ids "$RTB_A" "$RTB_B" "$RTB_C" \
  --query 'VpcEndpoint.VpcEndpointId' --output text)

until aws ec2 describe-vpc-endpoints --vpc-endpoint-ids "$S3_EP" \
    --query 'VpcEndpoints[0].State' --output text | grep -q available; do
  echo "waiting for the S3 endpoint to become available..."
  sleep 5
done

aws ec2 describe-vpc-endpoints --vpc-endpoint-ids "$S3_EP" \
  --query 'VpcEndpoints[0].{State:State,RouteTableIds:RouteTableIds}'
```

Gateway endpoint для S3 не создаёт ENI и не тарифицируется ни почасово, ни за
обработанные гигабайты - это просто запись в route table, поэтому это первый и самый
выгодный шаг оптимизации:

```bash
mkdir -p /var/work/tests/artifacts/3
cat > /var/work/tests/artifacts/3/s3endpoint.txt <<EOF
vpc_endpoint_id=$S3_EP
state=available
route_tables=$RTB_A,$RTB_B,$RTB_C

Gateway endpoint для S3 - это только маршрут в route table, он бесплатный: нет ни
почасовой платы, ни платы за обработанные данные, в отличие от interface endpoint.
EOF
cat /var/work/tests/artifacts/3/s3endpoint.txt
```

## Задание 4. Interface VPC endpoint для сервиса с высоким трафиком

Выбираем `sts` - каждый под с IRSA или EKS Pod Identity обменивает свой токен на
временные креды через STS при старте и при обновлении credentials, и без endpoint этот
обмен идёт через NAT на каждый такой запрос. (Альтернатива - `ecr.api`: авторизация в
реестр образов при каждом pull; выбор любого из двух засчитывается тестом.)

Берём security group по умолчанию и сразу разрешаем в ней входящий HTTPS из CIDR VPC. Без
этого правила endpoint будет создан, но недоступен: у default security group входящее
правило пускает только участников этой же группы, а ноды Karpenter и поды живут в других
группах.

```bash
SG=$(aws ec2 describe-security-groups --filters "Name=vpc-id,Values=$VPC" \
  "Name=group-name,Values=default" --query 'SecurityGroups[0].GroupId' --output text)

aws ec2 authorize-security-group-ingress --group-id "$SG" \
  --protocol tcp --port 443 --cidr 10.10.0.0/16

STS_EP=$(aws ec2 create-vpc-endpoint --vpc-id "$VPC" \
  --vpc-endpoint-type Interface --service-name com.amazonaws.eu-central-1.sts \
  --subnet-ids "$(aws ec2 describe-subnets --filters "Name=tag:Name,Values=private-subnet-1" \
    --query 'Subnets[0].SubnetId' --output text)" \
    "$(aws ec2 describe-subnets --filters "Name=tag:Name,Values=private-subnet-2" \
    --query 'Subnets[0].SubnetId' --output text)" \
  --security-group-ids "$SG" --private-dns-enabled \
  --query 'VpcEndpoint.VpcEndpointId' --output text)

until aws ec2 describe-vpc-endpoints --vpc-endpoint-ids "$STS_EP" \
    --query 'VpcEndpoints[0].State' --output text | grep -q available; do
  echo "waiting for the sts endpoint to become available..."
  sleep 5
done

aws ec2 describe-vpc-endpoints --vpc-endpoint-ids "$STS_EP" \
  --query 'VpcEndpoints[0].{State:State,PrivateDnsEnabled:PrivateDnsEnabled}'
```

Проверяем, что endpoint реально отвечает изнутри кластера - `private_dns_enabled=true`
означает, что имя `sts.eu-central-1.amazonaws.com` теперь резолвится в приватные адреса
ENI endpoint для всей VPC, и если правило `443` не добавлено, STS перестаёт работать у всех
подов сразу:

```bash
kubectl exec -n eks-117 "$POD" -- nslookup sts.eu-central-1.amazonaws.com
kubectl exec -n eks-117 "$POD" -- \
  curl -s -o /dev/null -w '%{http_code}\n' --connect-timeout 8 \
  https://sts.eu-central-1.amazonaws.com
```

Имя резолвится в адреса из `10.10.15.0/24` и `10.10.16.0/24` (это ENI endpoint), а `curl`
отдаёт код `302` - ответ реального STS через PrivateLink. Код `000` и таймаут означали бы,
что security group endpoint не пускает трафик от подов.

```bash
mkdir -p /var/work/tests/artifacts/4
cat > /var/work/tests/artifacts/4/interfaceendpoint.txt <<EOF
service_chosen=sts
vpc_endpoint_id=$STS_EP
state=available
private_dns_enabled=true

Выбран sts: IRSA и EKS Pod Identity обменивают токен на временные ключи через STS при
каждом старте пода и при обновлении credentials, это частые запросы, и без endpoint они
идут через NAT. Interface endpoint убирает этот трафик с NAT, ценой почасовой платы за
ENI в каждой AZ и платы за обработанные гигабайты.
EOF
cat /var/work/tests/artifacts/4/interfaceendpoint.txt
```

## Задание 5. Метрики NAT: сколько байт прошло через каждый шлюз

Берём сумму `BytesOutToDestination` за последние несколько часов по каждому NAT
(namespace `AWS/NATGateway`):

```bash
START=$(date -u -d '3 hours ago' +%Y-%m-%dT%H:%M:%S)
END=$(date -u +%Y-%m-%dT%H:%M:%S)

NAT_A_SUM=$(aws cloudwatch get-metric-statistics --namespace AWS/NATGateway \
  --metric-name BytesOutToDestination --statistics Sum --period 3600 \
  --dimensions Name=NatGatewayId,Value="$NAT1" \
  --start-time "$START" --end-time "$END" \
  --query 'sum(Datapoints[].Sum)' --output text)
[[ "$NAT_A_SUM" == "None" ]] && NAT_A_SUM=0

NAT_B_SUM=$(aws cloudwatch get-metric-statistics --namespace AWS/NATGateway \
  --metric-name BytesOutToDestination --statistics Sum --period 3600 \
  --dimensions Name=NatGatewayId,Value="$NAT2" \
  --start-time "$START" --end-time "$END" \
  --query 'sum(Datapoints[].Sum)' --output text)
[[ "$NAT_B_SUM" == "None" ]] && NAT_B_SUM=0

TOTAL=$(python3 -c "print(int(${NAT_A_SUM%.*}) + int(${NAT_B_SUM%.*}))")
echo "nat_a=$NAT1 sum=$NAT_A_SUM / nat_b=$NAT2 sum=$NAT_B_SUM / total=$TOTAL"
```

`NAT1` - это тот же NAT Gateway, на который в задании 2 направлен маршрут подсети
`eu-central-1c`. Он принял и обычный трафик своей зоны `eu-central-1a`, и cross-AZ
трафик от ноды `crossaz`, поэтому у него ожидается больший объём `BytesOutToDestination`
за то же окно, чем у `NAT2`, который обслуживает только свою собственную AZ:

```bash
mkdir -p /var/work/tests/artifacts/5
cat > /var/work/tests/artifacts/5/natmetrics.txt <<EOF
nat_a_id=$NAT1
nat_a_bytes_out_sum=${NAT_A_SUM%.*}
nat_b_id=$NAT2
nat_b_bytes_out_sum=${NAT_B_SUM%.*}
total_bytes_out_sum=$TOTAL

Метрика: AWS/NATGateway BytesOutToDestination, сумма по точкам за период.
NAT $NAT1 принял cross-AZ трафик ноды crossaz из eu-central-1c (задание 2) в
дополнение к обычному трафику своей зоны, поэтому у него ожидается больший объём
BytesOutToDestination, чем у $NAT2, который обслуживает только свою AZ.
EOF
cat /var/work/tests/artifacts/5/natmetrics.txt
```

Если тестовая нагрузка успела сгенерировать заметный трафик (например, повторные
запросы `curl` из пода `crossaz`), разница в суммах видна уже в первом окне метрики;
если нагрузка была разовой, разница может быть небольшой - важен сам факт, что у NAT,
принявшего cross-AZ ноду, объём не меньше, чем у второго.
