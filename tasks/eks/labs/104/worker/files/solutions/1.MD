# Лаба 104 - эталонное решение (workload identity: IRSA и Pod Identity)

Все команды выполняются на рабочей машине (worker) по SSH. kubectl уже настроен на
кластер, а terraform уже создал бакет S3, секрет Secrets Manager и обе IAM-роли -
их имена и ARN лежат в файле-подсказке `/home/ubuntu/lab104_hints.txt`.

```bash
cat ~/lab104_hints.txt
```

Дальше в примерах используются переменные из этого файла - подставьте свои значения или
экспортируйте их в начале сессии:

```bash
export BUCKET_NAME=$(grep '^bucket_name' ~/lab104_hints.txt | awk '{print $3}')
export SECRET_NAME=$(grep '^secret_name' ~/lab104_hints.txt | awk '{print $3}')
export IRSA_ROLE_ARN=$(grep '^irsa_role_arn' ~/lab104_hints.txt | awk '{print $3}')
export POD_IDENTITY_ROLE_ARN=$(grep '^pod_identity_role_arn' ~/lab104_hints.txt | awk '{print $3}')
export CLUSTER_NAME=$(grep '^cluster_name' ~/lab104_hints.txt | awk '{print $3}')
```

## Задание 1. Namespace `eks-104`

```bash
kubectl create namespace eks-104
```

## Задание 2. ServiceAccount с аннотацией IRSA

Роль `irsa_role_arn` уже создана terraform с trust policy, которая доверяет ровно этому
`ServiceAccount` (`system:serviceaccount:eks-104:s3-reader-irsa` - главы 16). Создаём SA с
аннотацией:

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: ServiceAccount
metadata:
  name: s3-reader-irsa
  namespace: eks-104
  annotations:
    eks.amazonaws.com/role-arn: ${IRSA_ROLE_ARN}
EOF

kubectl get sa s3-reader-irsa -n eks-104 -o yaml
```

## Задание 3. Под с IRSA: проверка идентичности

Создаём под, который использует этот SA. Pod Identity Webhook внедрит переменные
`AWS_ROLE_ARN` и `AWS_WEB_IDENTITY_TOKEN_FILE` (глава 16) при старте пода:

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: irsa-app
  namespace: eks-104
spec:
  serviceAccountName: s3-reader-irsa
  containers:
  - name: aws-cli
    image: amazon/aws-cli:2.15.0
    command: ["sleep", "3600"]
EOF

kubectl wait --for=condition=Ready pod/irsa-app -n eks-104 --timeout=120s
```

Проверяем, что SDK внутри пода получил креды через web identity, а не роль ноды:

```bash
mkdir -p /var/work/tests/artifacts/3
kubectl exec irsa-app -n eks-104 -- aws sts get-caller-identity \
  > /var/work/tests/artifacts/3/irsa_identity.txt
cat /var/work/tests/artifacts/3/irsa_identity.txt
```

В выводе `Arn` должен быть вида `arn:aws:sts::<account>:assumed-role/<prefix>-irsa-role/...`
- это доказывает, что под ходит под ролью IRSA, а не ролью ноды.

## Задание 4. Чтение объекта из S3 через IRSA

Роль `irsa` несёт только `s3:ListBucket` и `s3:GetObject` на этот конкретный бакет (глава
16, least privilege). Читаем объект, который terraform положил в бакет:

```bash
mkdir -p /var/work/tests/artifacts/4
kubectl exec irsa-app -n eks-104 -- aws s3 cp "s3://${BUCKET_NAME}/hello.txt" - \
  > /var/work/tests/artifacts/4/s3_read.txt
cat /var/work/tests/artifacts/4/s3_read.txt
```

В файле должна быть строка `hello from s3` - содержимое объекта, положенного модулем
`eks_v2_workload_identity_demo`.

## Задание 5. Ассоциация Pod Identity

В отличие от IRSA, для Pod Identity аннотация на SA не нужна - связь `namespace + SA ->
роль` живёт в API EKS, а не в Kubernetes (глава 17). Создаём SA и ассоциацию:

```bash
kubectl create serviceaccount secret-reader-podid -n eks-104

aws eks create-pod-identity-association \
  --cluster-name "${CLUSTER_NAME}" \
  --namespace eks-104 \
  --service-account secret-reader-podid \
  --role-arn "${POD_IDENTITY_ROLE_ARN}"

mkdir -p /var/work/tests/artifacts/5
aws eks list-pod-identity-associations --cluster-name "${CLUSTER_NAME}" --namespace eks-104 \
  > /var/work/tests/artifacts/5/association.txt
cat /var/work/tests/artifacts/5/association.txt
```

## Задание 6. Под с Pod Identity: секрет вместо роли ноды

Создаём под с SA `secret-reader-podid`. Агент `eks-pod-identity-agent` (уже установлен как
managed addon в этой лабе) раздаст ему креды роли `pod_identity_role_arn` через локальный
endpoint `169.254.170.23` (глава 17):

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: podid-app
  namespace: eks-104
spec:
  serviceAccountName: secret-reader-podid
  containers:
  - name: aws-cli
    image: amazon/aws-cli:2.15.0
    command: ["sleep", "3600"]
EOF

kubectl wait --for=condition=Ready pod/podid-app -n eks-104 --timeout=120s
```

Читаем секрет и проверяем идентичность одной командой:

```bash
mkdir -p /var/work/tests/artifacts/6
{
  echo "--- caller identity ---"
  kubectl exec podid-app -n eks-104 -- aws sts get-caller-identity
  echo "--- secret value ---"
  kubectl exec podid-app -n eks-104 -- aws secretsmanager get-secret-value \
    --secret-id "${SECRET_NAME}" --query SecretString --output text
} > /var/work/tests/artifacts/6/secret_read.txt
cat /var/work/tests/artifacts/6/secret_read.txt
```

`Arn` из `get-caller-identity` покажет `assumed-role/<prefix>-pod-identity-role/...`, а
значение секрета - JSON с полями `username`/`password` (`demo`/`demo123`), которые
terraform положил в Secrets Manager.

## Задание 7. Симптом: роль ноды не имеет доступа к бакету

Создаём под **без** привязки к IRSA или Pod Identity - он унаследует только права роли
ноды (глава 16, раздел 16.1: «дали роль ноде - и права утекли всем подам» работает и в
обратную сторону, роль ноды прикладных прав не несёт вовсе):

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: plain-app
  namespace: eks-104
spec:
  containers:
  - name: aws-cli
    image: amazon/aws-cli:2.15.0
    command: ["sleep", "3600"]
EOF

kubectl wait --for=condition=Ready pod/plain-app -n eks-104 --timeout=120s
```

```bash
mkdir -p /var/work/tests/artifacts/7
kubectl exec plain-app -n eks-104 -- aws s3 ls "s3://${BUCKET_NAME}/" \
  > /var/work/tests/artifacts/7/node_role_denied.txt 2>&1
cat /var/work/tests/artifacts/7/node_role_denied.txt
```

Команда должна завершиться ошибкой `AccessDenied` (или `is not authorized to perform`) -
роль ноды не несёт `s3:*` на этот бакет, у неё только права системных компонентов (pull из
ECR, работа CNI). Это наглядно показывает разницу: без IRSA или Pod Identity под получает
лишь то, что есть у роли ноды, а не «всё, что настроено где-то в аккаунте».
