# Lab 104 - reference solution (workload identity: IRSA and Pod Identity)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster, and terraform has already created the S3 bucket, the Secrets Manager secret and
both IAM roles - their names and ARNs are in the hint file
`/home/ubuntu/lab104_hints.txt`.

```bash
cat ~/lab104_hints.txt
```

The examples below use variables from that file - substitute your own values or export
them at the start of the session:

```bash
export BUCKET_NAME=$(grep '^bucket_name' ~/lab104_hints.txt | awk '{print $3}')
export SECRET_NAME=$(grep '^secret_name' ~/lab104_hints.txt | awk '{print $3}')
export IRSA_ROLE_ARN=$(grep '^irsa_role_arn' ~/lab104_hints.txt | awk '{print $3}')
export POD_IDENTITY_ROLE_ARN=$(grep '^pod_identity_role_arn' ~/lab104_hints.txt | awk '{print $3}')
export CLUSTER_NAME=$(grep '^cluster_name' ~/lab104_hints.txt | awk '{print $3}')
```

## Task 1. Namespace `eks-104`

```bash
kubectl create namespace eks-104
```

## Task 2. ServiceAccount with an IRSA annotation

The `irsa_role_arn` role was already created by terraform with a trust policy that trusts
exactly this `ServiceAccount` (`system:serviceaccount:eks-104:s3-reader-irsa` - chapter 16).
Create the SA with the annotation:

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: ServiceAccount
metadata:
  name: s3-reader-irsa
  namespace: eks-104
  annotations:
    eks.amazonaws.com/role-arn: ${IRSA_ROLE_ARN}
EOF

kubectl get sa s3-reader-irsa -n eks-104 -o yaml
```

## Task 3. Pod with IRSA: checking identity

Create a pod that uses this SA. The Pod Identity Webhook injects the `AWS_ROLE_ARN` and
`AWS_WEB_IDENTITY_TOKEN_FILE` variables (chapter 16) when the pod starts:

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: irsa-app
  namespace: eks-104
spec:
  serviceAccountName: s3-reader-irsa
  containers:
  - name: aws-cli
    image: amazon/aws-cli:2.15.0
    command: ["sleep", "3600"]
EOF

kubectl wait --for=condition=Ready pod/irsa-app -n eks-104 --timeout=120s
```

Check that the SDK inside the pod obtained credentials via web identity, not the node role:

```bash
mkdir -p /var/work/tests/artifacts/3
kubectl exec irsa-app -n eks-104 -- aws sts get-caller-identity \
  > /var/work/tests/artifacts/3/irsa_identity.txt
cat /var/work/tests/artifacts/3/irsa_identity.txt
```

The `Arn` in the output should look like
`arn:aws:sts::<account>:assumed-role/<prefix>-irsa-role/...` - this proves the pod is
running under the IRSA role, not the node role.

## Task 4. Reading an object from S3 via IRSA

The `irsa` role carries only `s3:ListBucket` and `s3:GetObject` on this specific bucket
(chapter 16, least privilege). Read the object that terraform placed in the bucket:

```bash
mkdir -p /var/work/tests/artifacts/4
kubectl exec irsa-app -n eks-104 -- aws s3 cp "s3://${BUCKET_NAME}/hello.txt" - \
  > /var/work/tests/artifacts/4/s3_read.txt
cat /var/work/tests/artifacts/4/s3_read.txt
```

The file should contain the line `hello from s3` - the content of the object placed by the
`eks_v2_workload_identity_demo` module.

## Task 5. Pod Identity association

Unlike IRSA, Pod Identity doesn't need an annotation on the SA - the `namespace + SA ->
role` link lives in the EKS API, not in Kubernetes (chapter 17). Create the SA and the
association:

```bash
kubectl create serviceaccount secret-reader-podid -n eks-104

aws eks create-pod-identity-association \
  --cluster-name "${CLUSTER_NAME}" \
  --namespace eks-104 \
  --service-account secret-reader-podid \
  --role-arn "${POD_IDENTITY_ROLE_ARN}"

mkdir -p /var/work/tests/artifacts/5
aws eks list-pod-identity-associations --cluster-name "${CLUSTER_NAME}" --namespace eks-104 \
  > /var/work/tests/artifacts/5/association.txt
cat /var/work/tests/artifacts/5/association.txt
```

## Task 6. Pod with Pod Identity: secret instead of the node role

Create a pod with SA `secret-reader-podid`. The `eks-pod-identity-agent` agent (already
installed as a managed addon in this lab) hands it the credentials of the
`pod_identity_role_arn` role via the local endpoint `169.254.170.23` (chapter 17):

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: podid-app
  namespace: eks-104
spec:
  serviceAccountName: secret-reader-podid
  containers:
  - name: aws-cli
    image: amazon/aws-cli:2.15.0
    command: ["sleep", "3600"]
EOF

kubectl wait --for=condition=Ready pod/podid-app -n eks-104 --timeout=120s
```

Read the secret and check identity in one command:

```bash
mkdir -p /var/work/tests/artifacts/6
{
  echo "--- caller identity ---"
  kubectl exec podid-app -n eks-104 -- aws sts get-caller-identity
  echo "--- secret value ---"
  kubectl exec podid-app -n eks-104 -- aws secretsmanager get-secret-value \
    --secret-id "${SECRET_NAME}" --query SecretString --output text
} > /var/work/tests/artifacts/6/secret_read.txt
cat /var/work/tests/artifacts/6/secret_read.txt
```

The `Arn` from `get-caller-identity` will show `assumed-role/<prefix>-pod-identity-role/...`,
and the secret value is a JSON with the fields `username`/`password` (`demo`/`demo123`)
that terraform placed in Secrets Manager.

## Task 7. Symptom: the node role has no access to the bucket

Create a pod **without** a binding to IRSA or Pod Identity - it will inherit only the
node role's permissions (chapter 16, section 16.1: "give the node a role and the
permissions leak to every pod" also works the other way around - the node role carries no
application permissions at all):

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: plain-app
  namespace: eks-104
spec:
  containers:
  - name: aws-cli
    image: amazon/aws-cli:2.15.0
    command: ["sleep", "3600"]
EOF

kubectl wait --for=condition=Ready pod/plain-app -n eks-104 --timeout=120s
```

```bash
mkdir -p /var/work/tests/artifacts/7
kubectl exec plain-app -n eks-104 -- aws s3 ls "s3://${BUCKET_NAME}/" \
  > /var/work/tests/artifacts/7/node_role_denied.txt 2>&1
cat /var/work/tests/artifacts/7/node_role_denied.txt
```

The command should fail with `AccessDenied` (or `is not authorized to perform`) - the node
role doesn't carry `s3:*` on this bucket, it only has the permissions of system components
(pulling from ECR, running the CNI). This clearly shows the difference: without IRSA or
Pod Identity, a pod gets only what the node role has, not "whatever is configured
somewhere in the account."
