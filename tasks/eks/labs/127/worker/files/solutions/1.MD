# Lab 127 - reference solution (ValidatingAdmissionPolicy on CEL)

All commands run on the worker machine over SSH. kubectl is already configured on the
cluster (kubeconfig is assembled via `aws eks update-kubeconfig` when the machine boots).

## Task 1. Namespace `eks-127`

```bash
kubectl create namespace eks-127
```

## Task 2. CEL policy in Audit mode lets a pod with `:latest` through

We create a `ValidatingAdmissionPolicy` and a `ValidatingAdmissionPolicyBinding` with
`validationActions: ["Audit"]`. The policy applies only to namespace `eks-127` via a
`namespaceSelector` (label `kubernetes.io/metadata.name`, which k8s sets on the namespace
automatically):

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: disallow-latest-tag
spec:
  matchConstraints:
    namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: eks-127
    resourceRules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["pods"]
  validations:
    - expression: "object.spec.containers.all(c, !c.image.endsWith(':latest'))"
      message: "the :latest tag is forbidden, specify a concrete image version"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: disallow-latest-tag-binding
spec:
  policyName: disallow-latest-tag
  validationActions: ["Audit"]
EOF
```

Check that both objects are in place:

```bash
kubectl get validatingadmissionpolicy disallow-latest-tag
kubectl get validatingadmissionpolicybinding disallow-latest-tag-binding
```

Now create a pod with a `:latest` image while in `Audit` mode - it should be CREATED,
because `Audit` only writes the violation to the audit log without blocking the request:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: latest-audit-pod
  namespace: eks-127
spec:
  containers:
  - name: app
    image: viktoruj/ping_pong:latest
EOF

kubectl get pod latest-audit-pod -n eks-127
```

The pod is created even though it violates the rule - that's the whole point of `Audit`:
try out the policy without risking breaking the existing workload.

## Task 3. Switching to Deny - a pod with `:latest` is rejected

We update the Binding, changing only `validationActions`:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: disallow-latest-tag-binding
spec:
  policyName: disallow-latest-tag
  validationActions: ["Deny"]
EOF
```

We try to create another pod with `:latest` - now the apiserver should reject the request:

```bash
mkdir -p /var/work/tests/artifacts/3
cat <<'EOF' | kubectl apply -f - 2> /var/work/tests/artifacts/3/denied.txt
apiVersion: v1
kind: Pod
metadata:
  name: latest-deny-pod
  namespace: eks-127
spec:
  containers:
  - name: app
    image: viktoruj/ping_pong:latest
EOF

cat /var/work/tests/artifacts/3/denied.txt
```

The `denied.txt` file must contain the apiserver's error message with the policy's text
(the words `latest` and `forbidden`). Pod `latest-deny-pod` is NOT created - `kubectl get
pod latest-deny-pod -n eks-127` returns `NotFound`.

## Task 4. A legit pod with an explicit tag gets through even under Deny

The policy only checks for `:latest`, so a pod with a specific image version goes through
with no problem. Tag `53833ea` is a real commit tag in `viktoruj/ping_pong`, it exists and
is built for both amd64 and arm64. It's important to use an existing tag: admission only
looks at the image string, so a pod with a made-up tag would still be created and would
hang in `ErrImagePull` - the policy formally "didn't get in the way", but there would be
nothing left to verify that claim with:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: tagged-pod
  namespace: eks-127
spec:
  containers:
  - name: app
    image: viktoruj/ping_pong:53833ea
EOF

kubectl get pod tagged-pod -n eks-127
```

## Task 5. Second CEL policy: mandatory `resources.requests`

Another `ValidatingAdmissionPolicy` straight in `Deny` mode - we require that every
container has `resources.requests` set:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: require-resources-requests
spec:
  matchConstraints:
    namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: eks-127
    resourceRules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["pods"]
  validations:
    - expression: "object.spec.containers.all(c, has(c.resources) && has(c.resources.requests))"
      message: "every container must have resources.requests set"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: require-resources-requests-binding
spec:
  policyName: require-resources-requests
  validationActions: ["Deny"]
EOF
```

A pod without `requests` is rejected:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: no-requests-pod
  namespace: eks-127
spec:
  containers:
  - name: app
    image: viktoruj/ping_pong:53833ea
EOF
```

The command returns an admission error, and `kubectl get pod no-requests-pod -n eks-127`
shows `NotFound`. A pod with `requests` set goes through normally:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: requests-ok-pod
  namespace: eks-127
spec:
  containers:
  - name: app
    image: viktoruj/ping_pong:53833ea
    resources:
      requests:
        cpu: "100m"
        memory: "64Mi"
EOF

kubectl get pod requests-ok-pod -n eks-127
```

## Task 6. `failurePolicy: Fail` and how it differs from an external webhook

We explicitly set `failurePolicy: Fail` on the first policy (this is the default, but we
fix it explicitly):

```bash
kubectl patch validatingadmissionpolicy disallow-latest-tag --type merge \
  -p '{"spec":{"failurePolicy":"Fail"}}'

kubectl get validatingadmissionpolicy disallow-latest-tag -o jsonpath='{.spec.failurePolicy}'
```

`failurePolicy` reacts to an error EVALUATING the CEL expression (for example, accessing a
field that doesn't exist on an object from an older API version), not to an external
service being unreachable. The built-in `ValidatingAdmissionPolicy` has no external webhook
at all - CEL is evaluated right inside the apiserver, so it has none of the "the webhook
didn't answer" risk that Kyverno and Gatekeeper have (there, the
rules run in a separate service behind a webhook, and if it's unreachable, `failurePolicy:
Fail` either queues up or blocks requests).

We save the explanation to an artifact:

```bash
mkdir -p /var/work/tests/artifacts/6
cat > /var/work/tests/artifacts/6/failurepolicy.txt <<'EOF'
failurePolicy on a ValidatingAdmissionPolicy only reacts to an error evaluating the CEL
expression (for example, accessing a field missing from the object), not to an external
service being unreachable.

The built-in ValidatingAdmissionPolicy has no external webhook at all: the CEL expression
is evaluated right inside the apiserver, with no network call out. That's why there is no
"the webhook didn't answer" risk here, which is characteristic of
Kyverno and Gatekeeper, where the rules run in a separate service behind a webhook and the
apiserver waits for its response.
EOF
cat /var/work/tests/artifacts/6/failurepolicy.txt
```
