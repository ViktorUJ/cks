# Lab 118 - reference solution (GitOps: Argo CD, drift and self-heal, sync waves)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster (kubeconfig is assembled via `aws eks update-kubeconfig` when the machine boots).

## Task 1. Installing Argo CD via Helm

```bash
kubectl create namespace argocd

helm repo add argo https://argoproj.github.io/argo-helm
helm repo update

helm install argocd argo/argo-cd -n argocd

kubectl rollout status deployment/argocd-server -n argocd
```

Check that the server came up:

```bash
kubectl get deploy argocd-server -n argocd
kubectl get pods -n argocd
```

## Task 2. Namespace `eks-118` and the Application object

```bash
kubectl create namespace eks-118
```

The Application links a Git source (the course repository itself, branch `AG-155`, path
`tasks/eks/labs/118/gitops-demo`) with the target cluster and namespace `eks-118`.
`selfHeal: true` rolls back manual edits, `prune: true` removes from the cluster
resources that were removed from Git:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: demo-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/ViktorUJ/cks.git
    targetRevision: AG-155
    path: tasks/eks/labs/118/gitops-demo
  destination:
    server: https://kubernetes.default.svc
    namespace: eks-118
  syncPolicy:
    automated:
      selfHeal: true
      prune: true
EOF
```

Wait for the Application to reach `Synced` and `Healthy`:

```bash
kubectl get application demo-app -n argocd -o jsonpath='{.status.sync.status}'
echo
kubectl get application demo-app -n argocd -o jsonpath='{.status.health.status}'
echo
```

Both commands should eventually return `Synced` and `Healthy` respectively (Argo CD
polls Git and applies manifests automatically, auto-sync is on by default).

## Task 3. Checking that the objects were actually applied

```bash
kubectl get deployment demo-app -n eks-118
kubectl get configmap demo-config -n eks-118 -o yaml
kubectl rollout status deployment/demo-app -n eks-118
```

Deployment `demo-app` (image `viktoruj/ping_pong:latest`, 2 replicas) and ConfigMap

## Task 4. Drift and self-heal

An important detail that only shows up on a live cluster: with `selfHeal` enabled, the
controller rolls back drift within seconds, and catching `OutOfSync` with your own eyes
is practically impossible (a manual `kubectl scale` gets rolled back before the first
`kubectl get application`). So drift is shown in two steps: first disable
self-healing, catch `OutOfSync`, then re-enable self-healing and watch the rollback.

Step 1. Disable only `selfHeal`, leave `prune` enabled:

```bash
kubectl patch application demo-app -n argocd --type=merge \
  -p '{"spec":{"syncPolicy":{"automated":{"selfHeal":false,"prune":true}}}}'
```

Step 2. Break the live state bypassing Git and capture the drift:

```bash
kubectl scale deployment demo-app -n eks-118 --replicas=5

for i in $(seq 1 20); do
  status=$(kubectl get application demo-app -n argocd -o jsonpath='{.status.sync.status}')
  [[ "$status" == "OutOfSync" ]] && break
  sleep 3
done

mkdir -p /var/work/tests/artifacts/4
{
  echo "=== drift with selfHeal=false (manual kubectl scale --replicas=5) ==="
  kubectl get application demo-app -n argocd \
    -o jsonpath='sync={.status.sync.status} health={.status.health.status}'
  echo
  kubectl get deploy demo-app -n eks-118 -o jsonpath='replicas={.spec.replicas}'
  echo
} > /var/work/tests/artifacts/4/drift.txt
```

Without self-heal the Application stays `OutOfSync`: auto-sync reacts to changes in
Git, while a diff created inside the cluster is what `selfHeal` fixes.

Step 3. Re-enable `selfHeal` and watch the automatic rollback to the state from Git:

```bash
kubectl patch application demo-app -n argocd --type=merge \
  -p '{"spec":{"syncPolicy":{"automated":{"selfHeal":true,"prune":true}}}}'

for i in $(seq 1 40); do
  status=$(kubectl get application demo-app -n argocd -o jsonpath='{.status.sync.status}')
  replicas=$(kubectl get deploy demo-app -n eks-118 -o jsonpath='{.spec.replicas}')
  [[ "$status" == "Synced" ]] && [[ "$replicas" == "2" ]] && break
  sleep 3
done

{
  echo "=== after re-enabling selfHeal: rollback to the state from Git ==="
  kubectl get application demo-app -n argocd \
    -o jsonpath='sync={.status.sync.status} health={.status.health.status}'
  echo
  kubectl get deploy demo-app -n eks-118 -o jsonpath='replicas={.spec.replicas}'
  echo
} >> /var/work/tests/artifacts/4/drift.txt

cat /var/work/tests/artifacts/4/drift.txt
```

The file contains both `OutOfSync` (drift without self-healing) and `Synced` (self-heal
brought back the state from Git). `replicas` is `2` again at the end.

## Task 5. Sync waves: order of application

`gitops-demo/configmap.yaml` carries the annotation `argocd.argoproj.io/sync-wave: "0"`,
and `gitops-demo/deployment.yaml` carries `argocd.argoproj.io/sync-wave: "1"`. The lower
wave number is applied first, so the ConfigMap is guaranteed to land in the cluster
before the Deployment (this matters if the Deployment reads values from the ConfigMap
via `envFrom`):

```bash
kubectl get configmap demo-config -n eks-118 \
  -o jsonpath='{.metadata.annotations.argocd\.argoproj\.io/sync-wave}'
echo
kubectl get deployment demo-app -n eks-118 \
  -o jsonpath='{.metadata.annotations.argocd\.argoproj\.io/sync-wave}'
echo
```

Confirm that both objects end up synced despite being in different waves:

```bash
kubectl get application demo-app -n argocd -o jsonpath='{.status.sync.status}'
echo
kubectl get application demo-app -n argocd -o jsonpath='{.status.resources}' | head -c 400
```

## Task 6. What prune removes and what it doesn't: resource ownership

`prune: true` is already enabled from task 2. Manually create a ConfigMap in `eks-118`
that doesn't exist in `gitops-demo/` - an ordinary manual object, as if someone created
it outside of Git:

```bash
kubectl create configmap manual-extra -n eks-118 --from-literal=note=manual

kubectl patch application demo-app -n argocd --type=merge \
  -p '{"metadata":{"annotations":{"argocd.argoproj.io/refresh":"hard"}}}'

sleep 30
kubectl get configmap manual-extra -n eks-118
kubectl get application demo-app -n argocd -o jsonpath='{.status.sync.status}'; echo
```

Unexpected result: `prune=true` is enabled, but `manual-extra` is **not removed**, while
the Application stays `Synced`. The reason lies in the ownership model: Argo CD only
manages objects that are marked as belonging to the application. In Argo CD 3.x this is
the `argocd.argoproj.io/tracking-id` annotation - check how the object that came from
Git is marked:

```bash
kubectl get configmap demo-config -n eks-118 \
  -o jsonpath='{.metadata.annotations.argocd\.argoproj\.io/tracking-id}'; echo
# demo-app:/ConfigMap:eks-118/demo-config
```

The manual object has no such mark, so for Argo CD it's a stranger (orphaned) and
doesn't fall under prune. Record this observation:

```bash
mkdir -p /var/work/tests/artifacts/6
{
  echo "=== without a tracking annotation, prune doesn't touch the object ==="
  echo "manual-extra: $(kubectl get configmap manual-extra -n eks-118 -o jsonpath='{.metadata.name}')"
  echo "sync: $(kubectl get application demo-app -n argocd -o jsonpath='{.status.sync.status}')"
} > /var/work/tests/artifacts/6/prune.txt
```

Now mark the ConfigMap as belonging to the application. The value format is
`<app>:<group>/<Kind>:<namespace>/<name>`, for core resources the group is empty:

```bash
kubectl annotate configmap manual-extra -n eks-118 \
  'argocd.argoproj.io/tracking-id=demo-app:/ConfigMap:eks-118/manual-extra' --overwrite

kubectl patch application demo-app -n argocd --type=merge \
  -p '{"metadata":{"annotations":{"argocd.argoproj.io/refresh":"hard"}}}'

for i in $(seq 1 20); do
  kubectl get configmap manual-extra -n eks-118 >/dev/null 2>&1 || break
  sleep 5
done

kubectl get configmap manual-extra -n eks-118 2>&1
```

Now the object is tracked by the application, it's absent from Git - and prune removes
it. Meanwhile `demo-config` and `demo-app` stay in place, because they're described in
`gitops-demo/`:

```bash
{
  echo "=== after adding the tracking annotation, prune removed the object ==="
  echo "manual-extra: $(kubectl get configmap manual-extra -n eks-118 2>&1 | tail -n1)"
  echo "demo-config: $(kubectl get configmap demo-config -n eks-118 -o jsonpath='{.metadata.name}')"
  echo "demo-app: $(kubectl get deploy demo-app -n eks-118 -o jsonpath='{.metadata.name}')"
  echo
  echo "prune only removes resources TRACKED by the application that are missing from Git."
  echo "An object created by hand without a tracking annotation is a stranger to Argo CD"
  echo "(orphaned) and doesn't fall under prune - that was the first observed result."
  echo "demo-config and demo-app stayed because they're described in gitops-demo/ and"
  echo "Argo CD keeps syncing them."
} >> /var/work/tests/artifacts/6/prune.txt

cat /var/work/tests/artifacts/6/prune.txt
```

## Task 7. Diagnostics: sync status and health status - two different axes

Disable auto-sync (and self-heal along with it, since it lives inside the same block),
so the symptom can be triggered calmly without an immediate rollback:

```bash
kubectl patch application demo-app -n argocd --type=merge \
  -p '{"spec":{"syncPolicy":{"automated":null}}}'
```

Break the container's readinessProbe directly in the cluster. Careful: the training
image `ping_pong` responds `200` on any path, so a probe on a "nonexistent URL" passes
fine and gives no symptom. Point the probe at closed port `9999` - nothing listens
there:

```bash
kubectl patch deployment demo-app -n eks-118 --type=json -p='[
  {"op":"add","path":"/spec/template/spec/containers/0/readinessProbe","value":{
    "httpGet": {"path": "/healthz", "port": 9999},
    "initialDelaySeconds": 2,
    "periodSeconds": 3,
    "failureThreshold": 2
  }}
]'
```

Wait and capture the statuses. Sync and health are independent axes: sync reflects the
difference between Git and the live state, health is the actual health of the resources
(pod readiness and so on):

```bash
sleep 30
mkdir -p /var/work/tests/artifacts/7
{
  echo "=== observed statuses after the manual readinessProbe edit ==="
  kubectl get application demo-app -n argocd \
    -o jsonpath='sync={.status.sync.status} health={.status.health.status}'
  echo
  echo
  echo "=== explanation: sync status and health status are different axes ==="
  echo "Sync status (Synced/OutOfSync) compares the live state of objects against what"
  echo "is recorded in Git: matches - Synced, diverges - OutOfSync."
  echo "Health status (Healthy/Progressing/Degraded/Missing) is the actual health of"
  echo "the resource right now: are pods ready, did readiness/liveness probes pass."
  echo "Because of the probe on a closed port, the new demo-app pods fail readiness, so"
  echo "health moves to Progressing (and becomes Degraded after progressDeadlineSeconds),"
  echo "while sync stays Synced. The reason: the readinessProbe field isn't described in"
  echo "the Git manifest, so the manually added field doesn't count toward the diff; but"
  echo "replicas is in Git, so its manual edit in task 4 produced OutOfSync."
  echo "This proves that both axes are computed independently: you can be Synced and"
  echo "Degraded/Progressing at the same time, just like OutOfSync and Healthy at the same time."
} > /var/work/tests/artifacts/7/health.txt

cat /var/work/tests/artifacts/7/health.txt
```

Re-enable auto-sync and self-heal:

```bash
kubectl patch application demo-app -n argocd --type=merge \
  -p '{"spec":{"syncPolicy":{"automated":{"selfHeal":true,"prune":true}}}}'
```

An important observation: self-heal will **not** fix this breakage. For Argo CD there's
no diff from Git (`sync=Synced`), so there's nothing to fix - meanwhile `health` honestly
shows `Progressing`, then `Degraded`. The practical conclusion: `Synced` doesn't mean the
cluster matches Git byte for byte; fields absent from the manifest remain the operator's
responsibility. So remove the probe by hand:

```bash
kubectl patch deployment demo-app -n eks-118 --type=json \
  -p='[{"op":"remove","path":"/spec/template/spec/containers/0/readinessProbe"}]'

for i in $(seq 1 20); do
  health=$(kubectl get application demo-app -n argocd -o jsonpath='{.status.health.status}')
  ready=$(kubectl get deploy demo-app -n eks-118 -o jsonpath='{.status.readyReplicas}')
  [[ "$health" == "Healthy" ]] && [[ "$ready" == "2" ]] && break
  sleep 5
done

kubectl get application demo-app -n argocd \
  -o jsonpath='sync={.status.sync.status} health={.status.health.status}'
echo
```
