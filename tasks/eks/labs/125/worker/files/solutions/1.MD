# Lab 125 - reference solution (EKS Auto Mode vs. your own stack)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster. The cluster was created with Auto Mode enabled and one built-in NodePool
`general-purpose` - there is no Fargate profile, managed addons, or Karpenter in this lab.

We take the cluster name from kubeconfig: `list-clusters[0]` would return the account's
first cluster, and it's not necessarily ours.

```bash
export CLUSTER=$(kubectl config current-context | awk -F/ '{print $NF}')
echo "$CLUSTER"
```

## Task 1. Confirming the mode: Auto Mode is enabled

```bash
mkdir -p /var/work/tests/artifacts/1
{
  echo "=== aws eks describe-cluster computeConfig ==="
  aws eks describe-cluster --name "$CLUSTER" --query 'cluster.computeConfig'
  echo
  echo "=== kubectl get nodepools ==="
  kubectl get nodepools
} > /var/work/tests/artifacts/1/automode.txt
cat /var/work/tests/artifacts/1/automode.txt
```

`computeConfig.enabled` must be `true`, and `nodePools` must contain `general-purpose`.
`kubectl get nodepools` shows the same NodePool as a regular Kubernetes resource - Auto
Mode materializes enabled built-in pools through the Kubernetes API (chapter 9).

## Task 2. The second built-in NodePool is disabled

```bash
kubectl get nodepools
```

`system` is not in the list - a built-in NodePool appears as a cluster resource only when
its name is present in `computeConfig.nodePools`; in this lab only `general-purpose` is
listed there.

```bash
mkdir -p /var/work/tests/artifacts/2
cat > /var/work/tests/artifacts/2/twopools.txt <<'EOF'
EKS Auto Mode has two built-in NodePools: general-purpose and system. The system NodePool
carries the CriticalAddonsOnly taint, tolerated by components critical for the cluster
(for example CoreDNS) - this is a way to separate them from regular workload so they don't
compete for resources with applications and don't get evicted during general-purpose node
consolidation.

In this lab node_pools contains only general-purpose, so system is not created as a
cluster resource: kubectl get nodepools doesn't show it. Enabling it means editing
computeConfig.nodePools on the control plane, not creating a kubectl object.
EOF
cat /var/work/tests/artifacts/2/twopools.txt
```

## Task 3. Workload on general-purpose and trying to fix the built-in NodePool

```bash
kubectl create namespace eks-125
kubectl create deployment web --image=viktoruj/ping_pong:latest --replicas=2 -n eks-125
kubectl rollout status deployment/web -n eks-125

kubectl get pods -n eks-125 -o wide
```

Both replicas reach `Running` on a node that Auto Mode brought up itself under
`general-purpose` - no Fargate profile and no external Karpenter, which are required in
the base of lab 101.

We try to edit the built-in NodePool. AWS documents built-in NodePools as "enabled or
disabled but not modified", but this needs checking by hand - there is no admission-level
ban:

```bash
mkdir -p /var/work/tests/artifacts/3
{
  echo "=== kubectl patch of the built-in pool ==="
  kubectl patch nodepool general-purpose --type merge -p '{"spec":{"limits":{"cpu":"100"}}}'
  echo "limits after the edit: $(kubectl get nodepool general-purpose -o jsonpath='{.spec.limits}')"
  echo
  echo "=== who owns the object ==="
  kubectl get nodepool general-purpose -o jsonpath='labels={.metadata.labels}{"\n"}'
  kubectl get nodepool general-purpose \
    -o jsonpath='managedFields managers={range .metadata.managedFields[*]}{.manager}{","}{end}{"\n"}'
  echo
  echo "=== conclusion ==="
  echo "The edit is accepted: the command returned patched, the value stayed in the object."
  echo "But the object belongs to the service: label app.kubernetes.io/managed-by=eks,"
  echo "fields owned by manager eks-auto-mode. There is only one supported way to manage"
  echo "it - enabling and disabling the pool name in computeConfig.nodePools. Changing"
  echo "that list deletes the resource along with its nodes and recreates it from scratch,"
  echo "without our edits."
} > /var/work/tests/artifacts/3/builtin.txt
cat /var/work/tests/artifacts/3/builtin.txt
```

We return the pool to its original state - we don't need a stray `limits` on an object we
don't own:

```bash
kubectl patch nodepool general-purpose --type merge -p '{"spec":{"limits":null}}'
kubectl get nodepool general-purpose -o jsonpath='{.spec.limits}{"\n"}'
```

Warning: `kubectl delete nodepool general-purpose` also goes through, but EKS does NOT
recreate the object, while the pool's nodes drain - the cluster is left without compute.
Recovery is only through `computeConfig` (recipe in the README's "Deletion" section).

## Task 4. No access to the node: SSH and SSM closed by design

In Auto Mode the node name is the instance ID itself, no need to parse `providerID`
separately:

```bash
NODE=$(kubectl get pods -n eks-125 -l app=web -o jsonpath='{.items[0].spec.nodeName}')
echo "node=$NODE"
```

We gather three pieces of evidence. First - the instance has no key pair (`KeyName`), so
SSH by key is impossible regardless of whether anything is listening on port 22:

```bash
mkdir -p /var/work/tests/artifacts/4
{
  echo "=== key pair and node image ==="
  aws ec2 describe-instances --instance-ids "$NODE" \
    --query 'Reservations[0].Instances[0].[KeyName,ImageId,PlatformDetails]' --output text
  echo "KeyName is empty (None) - the node has no key pair"
  echo
  echo "=== SSM: no connection ==="
  aws ssm get-connection-status --target "$NODE" --output json
  echo "SSM inventory (the node should not be there):"
  aws ssm describe-instance-information \
    --query 'InstanceInformationList[].[InstanceId,PingStatus]' --output text
} > /var/work/tests/artifacts/4/nossh.txt
```

Don't use `aws ssm start-session` here: the worker machine has no `ssm:StartSession`
permission, so the command returns `AccessDeniedException` - that's a fact about the
worker's policy, not about the node. `get-connection-status` with status `notconnected`
answers the task's question.

The third piece of evidence goes the other way: the host is not isolated from the
cluster. A privileged pod with a `hostPath` on `/` reads the node's file system:

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: hostprobe
  namespace: eks-125
spec:
  nodeName: $NODE
  restartPolicy: Never
  containers:
  - name: p
    image: busybox
    command: ["sh","-c","cat /host/etc/os-release; echo ---; ls /host/bin | head -5"]
    securityContext:
      privileged: true
    volumeMounts:
    - name: h
      mountPath: /host
  volumes:
  - name: h
    hostPath:
      path: /
EOF

kubectl wait --for=condition=Ready pod/hostprobe -n eks-125 --timeout=90s 2>/dev/null
sleep 5
{
  echo
  echo "=== the host as seen from a privileged pod ==="
  kubectl logs hostprobe -n eks-125
  echo
  echo "=== conclusion ==="
  echo "SSH is impossible (no KeyName key pair), SSM is not connected (notconnected) -"
  echo "there is no operator access to the node. But the Bottlerocket image can be read"
  echo "from a privileged pod: Auto Mode closes the operator's door, not the cluster-admin"
  echo "door. The latter is covered by Pod Security Admission and admission policies"
  echo "(chapters 19 and 22)."
} >> /var/work/tests/artifacts/4/nossh.txt

kubectl delete pod hostprobe -n eks-125
cat /var/work/tests/artifacts/4/nossh.txt
```

Auto Mode nodes are Bottlerocket with a read-only root and SELinux in enforcing mode, with
no shell and no package manager, with a maximum node lifetime of 21 days and automatic
replacement (chapter 9). Debugging it with familiar SSH and SSM tools is fundamentally
impossible - that's the cost of minimal operations.

## Task 5. Your own NodePool with explicit limits

Built-in pools have no `limits` - with unlimited demand they would grow without a ceiling
(chapter 9, section 9.7). Your own NodePool references the built-in `NodeClass` `default`
and sets the limits itself:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: custom-limited
spec:
  template:
    spec:
      nodeClassRef:
        group: eks.amazonaws.com
        kind: NodeClass
        name: default
      requirements:
        - key: "eks.amazonaws.com/instance-category"
          operator: In
          values: ["c", "m", "r"]
        - key: "kubernetes.io/arch"
          operator: In
          values: ["amd64"]
  limits:
    cpu: "10"
    memory: 10Gi
EOF

kubectl get nodepool custom-limited
```

Your own NodePools don't inherit the built-in pools' restrictions (C/M/R only, on-demand
only, generation 5+) - you set them yourself by hand, including `limits`, otherwise the
pool grows without a ceiling (chapter 9, section 9.7).
