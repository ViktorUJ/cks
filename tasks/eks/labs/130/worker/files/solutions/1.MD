# Lab 130 - reference solution (ECR and supply chain)

All commands are run on the worker machine over SSH. The AWS CLI is already configured
for the right account via the instance role (no extra `aws configure` needed), and kubectl
is configured for the lab's cluster. We use `podman` instead of `docker` (already
installed on the worker).

Let's define the account id and the private registry address once:

```bash
export AWS_REGION=eu-central-1
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
export ECR_HOST="${ACCOUNT_ID}.dkr.ecr.${AWS_REGION}.amazonaws.com"
echo "$ECR_HOST"
```

## Task 1. Repository with IMMUTABLE tags and scanOnPush

```bash
aws ecr create-repository \
  --repository-name eks-lab130/app \
  --image-tag-mutability IMMUTABLE \
  --image-scanning-configuration scanOnPush=true \
  --region "$AWS_REGION"

aws ecr describe-repositories --repository-names eks-lab130/app --region "$AWS_REGION"
```

Make sure the output shows `imageTagMutability: IMMUTABLE` and
`imageScanningConfiguration.scanOnPush: true`.

## Task 2. Push an image with the v1 tag

Log in to the registry with a 12-hour token and retag a public image:

```bash
aws ecr get-login-password --region "$AWS_REGION" \
  | podman login --username AWS --password-stdin "$ECR_HOST"

podman pull docker.io/library/alpine:3.19
podman tag docker.io/library/alpine:3.19 "$ECR_HOST/eks-lab130/app:v1"
podman push "$ECR_HOST/eks-lab130/app:v1"

aws ecr describe-images --repository-name eks-lab130/app --region "$AWS_REGION"
```

The `describe-images` output should show a single image tagged `v1`.

Two practical notes. First: `alpine` was chosen here not for being "smaller", but because
ECR's basic scanning can parse its package database - task 4 will get real findings
(verified: HIGH 1, MEDIUM 1, LOW 2 on `alpine:3.19`). Second: keep tasks 2-6 in a single
SSH session. `podman login` writes the token to `$XDG_RUNTIME_DIR/containers/auth.json`,
and that directory gets removed along with the user session, so after reconnecting, push
responds with `unauthorized: authentication required` even while the 12-hour ECR token is
still valid.

## Task 3. Symptom: a repeat push of tag v1 is rejected

Take a different image, tag it with the same `v1`, and try to overwrite it:

```bash
podman pull docker.io/library/busybox:1.36
podman tag docker.io/library/busybox:1.36 "$ECR_HOST/eks-lab130/app:v1"

mkdir -p /var/work/tests/artifacts/3
podman push "$ECR_HOST/eks-lab130/app:v1" 2>&1 \
  | tee /var/work/tests/artifacts/3/denied.txt
```

The push ends with a registry rejection (verified on the test bed):

```
tag invalid: The image tag 'v1' already exists in the 'eks-lab130/app' repository
and cannot be overwritten because the tag is immutable.
```

This is exactly how IMMUTABLE works: the `v1` tag is already taken by the first image, and
it can't be overwritten. The output will be long - `podman` tries several manifest formats
in sequence (OCI, docker v2, docker v1) and gets the same rejection on each; in the
`denied.txt` artifact the needed line appears in every attempt. Notice that the layers were
already uploaded at that point: IMMUTABLE protects the TAG BINDING specifically, not the
blob storage.

## Task 4. Scan findings (scan on push)

Scanning starts automatically on push (task 2). We wait for it to finish via a retry loop
(this CLI version has a ready-made wait command):

```bash
aws ecr wait image-scan-complete \
  --repository-name eks-lab130/app --image-id imageTag=v1 --region "$AWS_REGION"

mkdir -p /var/work/tests/artifacts/4
aws ecr describe-image-scan-findings \
  --repository-name eks-lab130/app --image-id imageTag=v1 --region "$AWS_REGION" \
  --query '{status: imageScanStatus.status, bySeverity: imageScanFindings.findingSeverityCounts}' \
  > /var/work/tests/artifacts/4/scan-summary.txt

cat /var/work/tests/artifacts/4/scan-summary.txt
```

If `aws ecr wait image-scan-complete` isn't available in your CLI version, replace it with
a manual retry loop:

```bash
for i in $(seq 1 30); do
  status=$(aws ecr describe-image-scan-findings \
    --repository-name eks-lab130/app --image-id imageTag=v1 --region "$AWS_REGION" \
    --query 'imageScanStatus.status' --output text 2>/dev/null)
  [[ "$status" == "COMPLETE" ]] && break
  sleep 5
done
```

`findingSeverityCounts` shows the number of findings by severity - on `alpine:3.19` this
was `{"HIGH": 1, "MEDIUM": 1, "LOW": 2}` (verified on the test bed, the exact numbers depend
on the scan date and vulnerability database).

There's an important boundary of applicability worth checking yourself. ECR's basic
scanning reads the package database of known distributions, so an image built `FROM
scratch` (for example a static Go binary) or distroless CANNOT be scanned:

```bash
aws ecr describe-image-scan-findings --repository-name eks-lab130/app \
  --image-id imageTag=<scratch image tag> --region "$AWS_REGION" \
  --query 'imageScanStatus' --output json
# {
#   "status": "FAILED",
#   "description": "UnsupportedImageError: The operating system and/or package manager
#                   are not supported."
# }
```

The practical takeaway: "the scanner found no vulnerabilities" and "the scanner couldn't
look" are different things, but in summary reports they easily blend into "no findings". If
a gate policy requires a clean scan, check the status specifically, not just the finding
count.

## Task 5. Deploy by digest

The digest of the `v1` image can be taken from ECR (more reliable than `podman inspect`,
since it's the digest of the exact manifest stored in the registry):

```bash
DIGEST=$(aws ecr describe-images --repository-name eks-lab130/app --image-ids imageTag=v1 \
  --region "$AWS_REGION" --query 'imageDetails[0].imageDigest' --output text)
echo "$DIGEST"

kubectl create namespace eks-130 --dry-run=client -o yaml | kubectl apply -f -

cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: digest-app
  namespace: eks-130
  labels:
    app: digest-app
spec:
  nodeSelector:
    kubernetes.io/arch: amd64
  containers:
  - name: app
    image: ${ECR_HOST}/eks-lab130/app@${DIGEST}
    command: ["sh", "-c", "sleep 86400"]
EOF

kubectl wait --for=condition=Ready pod/digest-app -n eks-130 --timeout=600s
kubectl get po -n eks-130 digest-app -o wide
```

The `nodeSelector` here is mandatory, and it's a trap that's easy to fall into. The worker
machine is x86_64, so `podman push` sent a SINGLE-ARCH manifest (`amd64` only) to ECR, while
the lab's NodePool also allows `arm64`. Verified on the test bed: without the selector,
Karpenter brought up a `t4g.small`, the image downloaded just fine, and the container died
with `exitCode 255` and empty logs - `CrashLoopBackOff` with no clear reason. The same class
of problem is covered in lab 124 (the `polinux/stress` image was `amd64` only). The
takeaway for production: either build multi-arch manifests, or explicitly pin the workload
to an architecture.

The Karpenter node role already carries the managed policy
`AmazonEC2ContainerRegistryReadOnly` (configured in the `eks_v2_karpenter` module), so the
pod successfully pulls the image and moves to `Running` without `imagePullSecrets`. A
reference by `@sha256:` pins exactly the byte set you scanned and checked in tasks 2-4 - a
tag could drift away, a digest can't.

## Task 6. Pull through cache for registry.k8s.io

A rule without authentication - the upstream is public:

```bash
aws ecr create-pull-through-cache-rule \
  --ecr-repository-prefix k8s-cache \
  --upstream-registry-url registry.k8s.io \
  --region "$AWS_REGION"
```

When the FIRST rule in the account is created, ECR sets up the service-linked role
`AWSServiceRoleForECRPullThroughCache`, so the caller needs the `iam:CreateServiceLinkedRole`
permission (the worker machine's policy has it, with the condition
`iam:AWSServiceName = pullthroughcache.ecr.amazonaws.com`). Without it, ECR doesn't respond
about the user's IAM directly, but with a wrapper that's easy to mistake for a parameter
error: `ValidationException ... The Amazon ECR action failed due to an IAM exception: ...
is not authorized to perform: iam:CreateServiceLinkedRole` (reproduced on the test bed).

The first pull through the cache creates the repository `k8s-cache/pause` in your ECR and
caches the image:

```bash
podman pull "${ECR_HOST}/k8s-cache/pause:3.9"

aws ecr describe-repositories --region "$AWS_REGION" \
  --query "repositories[?starts_with(repositoryName,'k8s-cache/pause')].repositoryName"
```

## Task 7. Docker Hub pull through cache with a secret (no actual pull)

The lab's topic specifically calls for a secret, so we create it for real, but with a
placeholder instead of a real Docker Hub token: an actual pull with these creds won't
succeed, but the configuration (the secret plus the cache rule) isn't affected by that and
is checked in full.

```bash
aws secretsmanager create-secret \
  --name ecr-pullthroughcache/dockerhub-creds \
  --description "Docker Hub creds for ECR pull through cache (lab placeholder)" \
  --secret-string '{"username":"lab-placeholder-user","accessToken":"lab-placeholder-token"}' \
  --region "$AWS_REGION"

SECRET_ARN=$(aws secretsmanager describe-secret \
  --secret-id ecr-pullthroughcache/dockerhub-creds --region "$AWS_REGION" \
  --query 'ARN' --output text)
echo "$SECRET_ARN"

aws ecr create-pull-through-cache-rule \
  --ecr-repository-prefix docker-hub \
  --upstream-registry-url registry-1.docker.io \
  --credential-arn "$SECRET_ARN" \
  --region "$AWS_REGION"

aws ecr describe-pull-through-cache-rules --region "$AWS_REGION"
```

The secret must have the `ecr-pullthroughcache/` prefix - otherwise ECR won't accept it for
a cache rule. An actual `podman pull` through `docker-hub/...` with this placeholder will
expectedly fail (the creds aren't real) - the task checks the configuration (the secret and
the rule exist), not the fact of a successful pull. Task 6 (registry.k8s.io, without
authentication) is what demonstrates a successful pull through the cache.

Important: don't use real Docker Hub creds here. The secret is only for checking this
lab's own configuration.

## Task 8. Lifecycle policy

A rule: keep no more than 5 images tagged `v.*`, delete the rest by tag age:

```bash
cat <<'EOF' > /tmp/lifecycle.json
{
  "rules": [
    {
      "rulePriority": 1,
      "description": "keep last 5 tagged images",
      "selection": {
        "tagStatus": "tagged",
        "tagPrefixList": ["v"],
        "countType": "imageCountMoreThan",
        "countNumber": 5
      },
      "action": { "type": "expire" }
    }
  ]
}
EOF

aws ecr put-lifecycle-policy \
  --repository-name eks-lab130/app \
  --lifecycle-policy-text file:///tmp/lifecycle.json \
  --region "$AWS_REGION"

aws ecr get-lifecycle-policy --repository-name eks-lab130/app --region "$AWS_REGION"
aws ecr start-lifecycle-policy-preview \
  --repository-name eks-lab130/app --region "$AWS_REGION" >/dev/null
sleep 5
aws ecr get-lifecycle-policy-preview \
  --repository-name eks-lab130/app --region "$AWS_REGION"
```

`get-lifecycle-policy-preview` might not return a result right away (the preview is
computed asynchronously) - if the status is still `IN_PROGRESS`, repeat the request after a
few seconds.
