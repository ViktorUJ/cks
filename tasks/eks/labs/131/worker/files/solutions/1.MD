# Lab 131 - reference solution (PDB blocks drain, topology spread, matchLabelKeys)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster (kubeconfig was built via `aws eks update-kubeconfig` when the machine booted).

## Task 1. Namespace `eks-131`

```bash
kubectl create namespace eks-131
```

## Task 2. Deployment `web` with topology spread and matchLabelKeys

The lab's cluster runs in two zones (`eu-central-1a` and `eu-central-1b`), with private
subnets `eks1`/`eks2` for each. That's enough for Karpenter to spread nodes across two
zones, and for `topologySpreadConstraints` to spread pods across them.

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: eks-131
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: web
          matchLabelKeys:
            - pod-template-hash
      containers:
        - name: app
          image: viktoruj/ping_pong:latest
EOF

kubectl rollout status deployment/web -n eks-131
```

Check readiness and the spread across zones:

```bash
kubectl get pods -n eks-131 -l app=web -o wide
kubectl get nodes -L topology.kubernetes.io/zone
```

The `NODE` column for the three pods must show at least two different nodes, and those
nodes must have different `topology.kubernetes.io/zone` values. `matchLabelKeys:
[pod-template-hash]` doesn't affect the first deployment yet (there is only one revision) -
it will matter in task 6.

## Task 3. Symptom: a too strict PDB blocks drain

Create a PDB that requires all 3 replicas to be available - the budget doesn't allow
evicting a single pod:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
  namespace: eks-131
spec:
  minAvailable: 3
  selector:
    matchLabels:
      app: web
EOF
```

Take the node hosting one of the `web` replicas and try to drain it:

```bash
NODE=$(kubectl get pod -n eks-131 -l app=web -o jsonpath='{.items[0].spec.nodeName}')
echo "node: $NODE"

mkdir -p /var/work/tests/artifacts/3
kubectl drain "$NODE" --ignore-daemonsets --delete-emptydir-data --timeout=60s \
  > /var/work/tests/artifacts/3/drain_blocked.txt 2>&1
echo "drain exit code: $?"
cat /var/work/tests/artifacts/3/drain_blocked.txt
```

The command fails: `kubectl drain` tries to call the eviction API for the `web` pod, but
the API responds with `429` for a budget violation, and after `--timeout=60s` drain fails
with `global timeout reached`. The reason is PDB `web-pdb` with `minAvailable: 3`, which
requires 3 available replicas while there are exactly 3, so the budget never allows
evicting even one: eviction can never make progress, drain hangs until the budget is
loosened.

Add an explanation to the same artifact:

```bash
cat >> /var/work/tests/artifacts/3/drain_blocked.txt <<'EOF'

Explanation: PDB web-pdb sets minAvailable: 3, equal to the number of Deployment web
replicas. The budget doesn't allow evicting a single pod, so the eviction API responds
429, and kubectl drain hangs/times out - this is the symptom of a too strict PDB, not a
cluster error.
EOF
cat /var/work/tests/artifacts/3/drain_blocked.txt
```

## Task 4. Fix: loosen the PDB and retry drain

First bring the node back into service (drain already cordoned it):

```bash
kubectl uncordon "$NODE"
```

Loosen the budget: now one replica out of three can be evicted (`minAvailable: 2`):

```bash
kubectl patch pdb web-pdb -n eks-131 --type merge -p '{"spec":{"minAvailable":2}}'
kubectl get pdb web-pdb -n eks-131
```

Retry draining the same node - now the budget allows evicting one pod, drain succeeds:

```bash
mkdir -p /var/work/tests/artifacts/4
kubectl drain "$NODE" --ignore-daemonsets --delete-emptydir-data --timeout=120s \
  > /var/work/tests/artifacts/4/drain_ok.txt 2>&1
echo "drain exit code: $?" >> /var/work/tests/artifacts/4/drain_ok.txt

echo "--- pdb status after drain ---" >> /var/work/tests/artifacts/4/drain_ok.txt
kubectl get pdb web-pdb -n eks-131 >> /var/work/tests/artifacts/4/drain_ok.txt
cat /var/work/tests/artifacts/4/drain_ok.txt
```

Bring the node back into service and wait for all 3 replicas to be ready again (the
replacement landed on another node):

```bash
kubectl uncordon "$NODE"
kubectl rollout status deployment/web -n eks-131
```

## Task 5. unhealthyPodEvictionPolicy: AlwaysAllow

By default a PDB uses the `IfHealthyBudget` policy: an unhealthy (not `Ready`) pod can
only be evicted if the budget wouldn't be violated anyway. If the application is broken
and a pod is stuck in `CrashLoopBackOff`, that pod blocks the budget calculation itself and
can permanently block drain. `AlwaysAllow` removes that blocker: unhealthy pods are always
evictable, healthy ones remain protected by the budget.

```bash
kubectl patch pdb web-pdb -n eks-131 --type merge \
  -p '{"spec":{"unhealthyPodEvictionPolicy":"AlwaysAllow"}}'

kubectl get pdb web-pdb -n eks-131 -o jsonpath='{.spec.unhealthyPodEvictionPolicy}'
echo
```

Save an explanation to the artifact:

```bash
mkdir -p /var/work/tests/artifacts/5
cat > /var/work/tests/artifacts/5/unhealthy_policy.txt <<'EOF'
unhealthyPodEvictionPolicy: AlwaysAllow added to web-pdb.

By default (IfHealthyBudget) an unhealthy pod is evicted only if currentHealthy doesn't
drop below desiredHealthy, so a pod in CrashLoopBackOff counts itself as part of the
budget and can permanently block drain, even though the application is already dead.

AlwaysAllow allows evicting an unhealthy pod regardless of the budget: a broken pod in
CrashLoopBackOff no longer holds up drain, while healthy replicas stay protected by the PDB.
EOF
cat /var/work/tests/artifacts/5/unhealthy_policy.txt
```

## Task 6. Rolling update: matchLabelKeys keeps old pods out of the way

Update the Deployment so a new revision appears (a new `pod-template-hash`): add an
environment variable. Old and new pods share the label `app: web`, but `matchLabelKeys:
[pod-template-hash]` in `topologySpreadConstraints` makes the skew count only within its
own revision, so new pods aren't blocked by old replicas.

```bash
mkdir -p /var/work/tests/artifacts/6
kubectl set env deployment/web -n eks-131 RELEASE=v2

kubectl rollout status deployment/web -n eks-131 --timeout=180s \
  | tee /var/work/tests/artifacts/6/rollout.txt
```

Check that there are no stuck `Pending` pods and the update really applied:

```bash
kubectl get pods -n eks-131 -l app=web -o wide
kubectl get deploy web -n eks-131 \
  -o jsonpath='{.status.readyReplicas}/{.status.updatedReplicas}'
echo
```

Without `matchLabelKeys: [pod-template-hash]`, both old and new pods would count toward
the skew - they share the label `app: web`. With it, the scheduler adds the revision label
to the selector and counts the distribution only within its own revision.

A fair caveat, worth checking yourself rather than taking on faith. On this test bed the
rollout succeeds even without `matchLabelKeys` - verified by experiment: a second
Deployment with the same topology but without this field, with `maxUnavailable: 0` and
`maxSurge: 1`, updated in the same amount of time, `Pending` lasted less than five seconds
and was ordinary scheduler wait time, not a skew block. The reason is simple: three
replicas across two zones give a 2-plus-1 spread, and the extra pod always fits into the
zone with fewer pods, and if nodes lack room, Karpenter brings up another one.

Where the difference becomes real: a static fleet with no spare capacity, more than two
zones, and an unevenly spread old revision. Then the skew counted across both revisions at
once leaves the new pod no allowed zone, and it waits for an old replica to leave - on a
large fleet this turns into a slow rollout with confusing `Pending` pods. That's why
`matchLabelKeys` is set up in advance, not after an incident. The result actually checked
now is that the new revision stayed spread across zones within `maxSkew: 1`:

```bash
HASH=$(kubectl get po -n eks-131 -l app=web \
  -o jsonpath='{.items[0].metadata.labels.pod-template-hash}')
for n in $(kubectl get po -n eks-131 -l app=web,pod-template-hash="$HASH" \
    -o jsonpath='{.items[*].spec.nodeName}'); do
  kubectl get node "$n" -o jsonpath='{.metadata.labels.topology\.kubernetes\.io/zone}{"\n"}'
done | sort | uniq -c
```
