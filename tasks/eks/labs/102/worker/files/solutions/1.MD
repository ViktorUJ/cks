# Lab 102 - reference solution (cluster access: IAM, RBAC, access entries)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster. The worker role has `eks:*` (enough for all access entry/access policy commands)
plus narrow `iam:CreateRole/GetRole/DeleteRole/PutRolePolicy` and `sts:AssumeRole`
permissions, scoped to roles named like `*-test-*` - enough to create a test role and
actually assume it, without touching other labs' permissions.

## Choosing the second principal

The cluster is already created by the `eks_v2_control_plane` module in
`authenticationMode = API` mode (v21 `terraform-aws-modules/eks/aws` with
`enable_cluster_creator_admin_permissions = true`). The worker role already has its own
access entry with `AmazonEKSClusterAdminPolicy` (`terraform/modules/eks_v2_work_pc/iam.tf`) -
that confirms API access entries are enabled and working in the cluster.

The tasks in this lab need a **second** IAM principal that doesn't yet have cluster access.
The Karpenter node role won't do: the `terraform-aws-modules/eks/aws//modules/karpenter`
submodule automatically creates an `EC2_LINUX` access entry for it
(`create_access_entry = true` by default), and one IAM principal can't be in two access
entries at once. So the lab creates a separate test role via the AWS CLI right on the
worker, trusted only by the worker role itself (`sts:AssumeRole` is allowed exclusively for
the worker role's ARN, no one else).

## Task 1. Inventory: authenticationMode

```bash
mkdir -p /var/work/tests/artifacts/1
CLUSTER=$(aws eks list-clusters --query 'clusters[0]' --output text)
aws eks describe-cluster --name "$CLUSTER" --query 'cluster.accessConfig' \
  > /var/work/tests/artifacts/1/accessconfig.json
cat /var/work/tests/artifacts/1/accessconfig.json
```

Expected output looks like:

```json
{
    "authenticationMode": "API",
    "bootstrapClusterCreatorAdminPermissions": true
}
```

`authenticationMode` equals `API` - the cluster has no `aws-auth` ConfigMap, all principal
mappings go through access entries.

## Task 2. Test IAM role as the second principal

Get the worker role's ARN and account id (we'll allow it to assume the test role):

```bash
WORKER_ARN=$(aws sts get-caller-identity --query Arn --output text)
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
echo "$WORKER_ARN"
```

`get-caller-identity` on an EC2-profile instance shows the **session** ARN
(`assumed-role/.../i-...`), not the role's own ARN. The trust policy and access entry need
the role ARN, so we assemble it from the session:

```bash
ROLE_NAME=$(echo "$WORKER_ARN" | sed -E 's#.*assumed-role/([^/]+)/.*#\1#')
ROLE_ARN="arn:aws:iam::${ACCOUNT_ID}:role/${ROLE_NAME}"
echo "$ROLE_ARN"
```

Create the test role. The name must contain `-test-`, otherwise the worker can't create or
assume it (its IAM policy is scoped to that substring):

```bash
TEST_ROLE_NAME="eks-task102-test-viewer"

cat > /tmp/trust.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Principal": { "AWS": "${ROLE_ARN}" }
    }
  ]
}
EOF

aws iam create-role --role-name "$TEST_ROLE_NAME" \
  --assume-role-policy-document file:///tmp/trust.json

TEST_ROLE_ARN=$(aws iam get-role --role-name "$TEST_ROLE_NAME" \
  --query 'Role.Arn' --output text)

mkdir -p /var/work/tests/artifacts/2
echo "$TEST_ROLE_ARN" > /var/work/tests/artifacts/2/test_role_arn.txt
cat /var/work/tests/artifacts/2/test_role_arn.txt
```

The role doesn't need any IAM permissions inside besides assume - all its real permissions
are granted by the cluster through the access entry and access policy/RBAC, not IAM.

## Task 3. Access entry for the test role, viewers group

```bash
CLUSTER=$(aws eks list-clusters --query 'clusters[0]' --output text)

aws eks create-access-entry --cluster-name "$CLUSTER" \
  --principal-arn "$TEST_ROLE_ARN" \
  --kubernetes-groups viewers \
  --type STANDARD

aws eks describe-access-entry --cluster-name "$CLUSTER" \
  --principal-arn "$TEST_ROLE_ARN"
```

We don't set `username` - EKS fills it in on its own, as the documentation recommends. The
principal is now known to the cluster and lands in the Kubernetes group `viewers`, but has
no permissions yet: the entry itself grants no permissions, it only provides a subject for
RBAC.

## Task 4. ClusterRole and ClusterRoleBinding for the viewers group

Classic RBAC on top of the access entry, no access policy involved:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: viewers-pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list"]
EOF

cat <<'EOF' | kubectl apply -f -
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: viewers-pod-reader
subjects:
- kind: Group
  name: viewers
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: viewers-pod-reader
  apiGroup: rbac.authorization.k8s.io
EOF

kubectl get clusterrole viewers-pod-reader -o yaml
kubectl get clusterrolebinding viewers-pod-reader -o yaml
```

The `viewers` group can now read pods in all namespaces, and nothing else.

## Task 5. Manual permission check via assume-role

This is a step the student performs by hand - the automated check only verifies the
resulting artifact, not the assume-role itself (temporary credentials aren't needed inside
`tests.bats`).

Get temporary credentials for the test role and a separate kubeconfig under an alias:

```bash
CREDS=$(aws sts assume-role --role-arn "$TEST_ROLE_ARN" \
  --role-session-name test-viewer-session)

export AWS_ACCESS_KEY_ID=$(echo "$CREDS" | python3 -c \
  'import json,sys;print(json.load(sys.stdin)["Credentials"]["AccessKeyId"])')
export AWS_SECRET_ACCESS_KEY=$(echo "$CREDS" | python3 -c \
  'import json,sys;print(json.load(sys.stdin)["Credentials"]["SecretAccessKey"])')
export AWS_SESSION_TOKEN=$(echo "$CREDS" | python3 -c \
  'import json,sys;print(json.load(sys.stdin)["Credentials"]["SessionToken"])')

aws eks update-kubeconfig --name "$CLUSTER" --region eu-central-1 \
  --alias test-viewer --kubeconfig /tmp/test-viewer.kubeconfig

kubectl --kubeconfig /tmp/test-viewer.kubeconfig get pods -A
kubectl --kubeconfig /tmp/test-viewer.kubeconfig create namespace test
```

Expected result: `get pods -A` succeeds (only read access is granted by the RBAC binding on
the `viewers` group), while `create namespace test` fails with `Forbidden` - the `viewers`
RBAC doesn't include permissions on `namespaces`. Switch back to the worker's own
permissions:

```bash
unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN
```

Save the manual check's result as an artifact:

```bash
mkdir -p /var/work/tests/artifacts/5
cat > /var/work/tests/artifacts/5/rbac_check.txt <<'EOF'
kubectl --kubeconfig /tmp/test-viewer.kubeconfig get pods -A
  -> worked: the viewers-pod-reader RBAC binding grants get/list on pods.

kubectl --kubeconfig /tmp/test-viewer.kubeconfig create namespace test
  -> Forbidden: the viewers group has no permission to create a namespace,
     the access entry provided a subject, but RBAC didn't allow this action.
EOF
cat /var/work/tests/artifacts/5/rbac_check.txt
```

## Task 6. AmazonEKSViewPolicy access policy on top of the access entry

```bash
aws eks associate-access-policy --cluster-name "$CLUSTER" \
  --principal-arn "$TEST_ROLE_ARN" \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSViewPolicy \
  --access-scope type=cluster

aws eks list-associated-access-policies --cluster-name "$CLUSTER" \
  --principal-arn "$TEST_ROLE_ARN"
```

The test role now has two independent sources of permissions: the RBAC `viewers` group
(get/list on pods) and the `AmazonEKSViewPolicy` access policy (read access to most cluster
resources, excluding secrets). Note: `kubectl --kubeconfig /tmp/test-viewer.kubeconfig
auth can-i --list` won't show the permissions coming from the access policy - it isn't
expressed as RBAC objects, the only way to see it is `list-associated-access-policies`.

## Task 7. Diagnostics: Unauthorized vs. Forbidden

Show the difference with real commands. Create another role **without** an access entry -
it'll be unknown to the cluster:

```bash
NOBODY_ROLE_NAME="eks-task102-test-nobody"
aws iam create-role --role-name "$NOBODY_ROLE_NAME" \
  --assume-role-policy-document file:///tmp/trust.json
NOBODY_ARN=$(aws iam get-role --role-name "$NOBODY_ROLE_NAME" --query 'Role.Arn' --output text)

CREDS2=$(aws sts assume-role --role-arn "$NOBODY_ARN" --role-session-name nobody-session)
export AWS_ACCESS_KEY_ID=$(echo "$CREDS2" | python3 -c \
  'import json,sys;print(json.load(sys.stdin)["Credentials"]["AccessKeyId"])')
export AWS_SECRET_ACCESS_KEY=$(echo "$CREDS2" | python3 -c \
  'import json,sys;print(json.load(sys.stdin)["Credentials"]["SecretAccessKey"])')
export AWS_SESSION_TOKEN=$(echo "$CREDS2" | python3 -c \
  'import json,sys;print(json.load(sys.stdin)["Credentials"]["SessionToken"])')

aws eks update-kubeconfig --name "$CLUSTER" --region eu-central-1 \
  --alias test-nobody --kubeconfig /tmp/test-nobody.kubeconfig

kubectl --kubeconfig /tmp/test-nobody.kubeconfig get pods -A
# error: You must be logged in to the server (Unauthorized)

unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN
aws iam delete-role --role-name "$NOBODY_ROLE_NAME"
```

Compare this with the attempt to create a namespace using the test role from task 5
(`test-viewer.kubeconfig`) - there the cluster knows the principal, but RBAC doesn't allow
the action, i.e. `Forbidden`. The difference boils down to one thing: `Unauthorized` means
the cluster found no access entry for that ARN at all (`aws eks list-access-entries` won't
show that ARN), `Forbidden` means an access entry exists, but RBAC/access policy don't allow
that action.

```bash
aws eks list-access-entries --cluster-name "$CLUSTER"
```

Save the explanation as an artifact:

```bash
mkdir -p /var/work/tests/artifacts/7
cat > /var/work/tests/artifacts/7/unauthorized_vs_forbidden.txt <<'EOF'
Unauthorized (401): the eks-task102-test-nobody role has no access entry in the cluster.
kubectl get pods -A with its kubeconfig responds "You must be logged in to the server
(Unauthorized)" - it never got to RBAC, authentication itself failed. Verification:
aws eks list-access-entries --cluster-name <cluster> does not contain its ARN.

Forbidden (403): the eks-task102-test-viewer role has an access entry (viewers group) and
can read pods, but kubectl create namespace test with the same role responds Forbidden -
the cluster recognized the principal, but the viewers group's RBAC doesn't allow creating
a namespace.
EOF
cat /var/work/tests/artifacts/7/unauthorized_vs_forbidden.txt
```

## Task 8. Deleting and restoring the access entry

Remove the access entry and confirm access is gone, then re-create the entry (the cluster
stays in a working state for grading):

```bash
aws eks delete-access-entry --cluster-name "$CLUSTER" --principal-arn "$TEST_ROLE_ARN"

CREDS=$(aws sts assume-role --role-arn "$TEST_ROLE_ARN" --role-session-name test-viewer-2)
export AWS_ACCESS_KEY_ID=$(echo "$CREDS" | python3 -c \
  'import json,sys;print(json.load(sys.stdin)["Credentials"]["AccessKeyId"])')
export AWS_SECRET_ACCESS_KEY=$(echo "$CREDS" | python3 -c \
  'import json,sys;print(json.load(sys.stdin)["Credentials"]["SecretAccessKey"])')
export AWS_SESSION_TOKEN=$(echo "$CREDS" | python3 -c \
  'import json,sys;print(json.load(sys.stdin)["Credentials"]["SessionToken"])')

kubectl --kubeconfig /tmp/test-viewer.kubeconfig get pods -A
# error: You must be logged in to the server (Unauthorized)

unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN

aws eks create-access-entry --cluster-name "$CLUSTER" \
  --principal-arn "$TEST_ROLE_ARN" \
  --kubernetes-groups viewers --type STANDARD

aws eks describe-access-entry --cluster-name "$CLUSTER" --principal-arn "$TEST_ROLE_ARN"
```

`delete-access-entry` removes all its access policy associations along with the entry - the
policy from task 6 (`AmazonEKSViewPolicy`) doesn't come back on its own once the entry is
deleted. Restore it explicitly, so the environment ends up back in the state it was in after
task 6:

```bash
aws eks associate-access-policy --cluster-name "$CLUSTER" \
  --principal-arn "$TEST_ROLE_ARN" \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSViewPolicy \
  --access-scope type=cluster

aws eks list-associated-access-policies --cluster-name "$CLUSTER" --principal-arn "$TEST_ROLE_ARN"
```

Save the delete/restore cycle's result as an artifact:

```bash
mkdir -p /var/work/tests/artifacts/8
cat > /var/work/tests/artifacts/8/delete_recreate.txt <<'EOF'
aws eks delete-access-entry --cluster-name <cluster> --principal-arn <test_role_arn>
kubectl --kubeconfig /tmp/test-viewer.kubeconfig get pods -A
  -> error: You must be logged in to the server (Unauthorized): the deleted access entry
     made the principal unknown to the cluster immediately.

aws eks create-access-entry --cluster-name <cluster> --principal-arn <test_role_arn> \
  --kubernetes-groups viewers --type STANDARD
  -> access restored, the RBAC binding on the viewers group was never changed and works again.
EOF
cat /var/work/tests/artifacts/8/delete_recreate.txt
```
