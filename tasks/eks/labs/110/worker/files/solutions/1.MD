# Lab 110 - reference solution (VPC CNI network policy: default deny, label, egress)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster (kubeconfig was built via `aws eks update-kubeconfig` when the machine booted).
`enableNetworkPolicy` is already enabled on the `vpc-cni` add-on via Terraform, so the
`aws-network-policy-agent` agent in `aws-node` is present on the nodes even before you
start the tasks.

## Task 1. Namespace `eks-110`

```bash
kubectl create namespace eks-110
```

## Task 2. Checking that the enforcer is enabled

We check both facts: the agent container in the DaemonSet `aws-node` and the add-on
configuration flag.

```bash
mkdir -p /var/work/tests/artifacts/2

{
  echo "--- kubectl describe daemonset aws-node ---"
  kubectl describe daemonset aws-node -n kube-system | grep -A2 aws-network-policy-agent
  echo
  echo "--- aws eks describe-addon vpc-cni ---"
  CLUSTER=$(kubectl config view --minify -o jsonpath='{.clusters[0].name}' | sed 's|.*/||')
  aws eks describe-addon --cluster-name "$CLUSTER" --addon-name vpc-cni \
    --query "addon.configurationValues" --output text
} > /var/work/tests/artifacts/2/enforcer.txt

cat /var/work/tests/artifacts/2/enforcer.txt
```

The output should contain the container `aws-network-policy-agent` in `aws-node` and a
line like `enableNetworkPolicy":"true"` in the add-on configuration. This confirms that the
control plane and the node agent actually enforce `NetworkPolicy` objects, not just accept
them as an API object.

## Task 3. Symptom before any policy: connectivity is allowed by default

We create `api` (the server) and `client` (for `kubectl exec curl`), plus a Service for
`api`:

```bash
kubectl create deployment api --image=viktoruj/ping_pong:latest --replicas=2 -n eks-110
kubectl rollout status deployment/api -n eks-110

kubectl expose deployment api -n eks-110 --port=8080 --target-port=8080

kubectl create deployment client --image=curlimages/curl:latest -n eks-110 \
  -- sleep 3600
kubectl rollout status deployment/client -n eks-110
```

We check connectivity: `client` should be able to reach `api` by the Service name.

```bash
mkdir -p /var/work/tests/artifacts/3
CLIENT=$(kubectl get po -n eks-110 -l app=client -o jsonpath='{.items[0].metadata.name}')

kubectl exec "$CLIENT" -n eks-110 -- \
  curl -s -o /dev/null -w "HTTP_CODE=%{http_code}\n" --connect-timeout 3 --max-time 5 \
  http://api.eks-110.svc.cluster.local:8080 \
  > /var/work/tests/artifacts/3/connectivity_before.txt

cat /var/work/tests/artifacts/3/connectivity_before.txt
```

The file should contain `HTTP_CODE=200`: without any policies, VPC CNI allows all
east-west traffic - no `NetworkPolicy` object has been created in the cluster yet.

## Task 4. Default deny ingress

We deny all inbound traffic into namespace `eks-110`:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: eks-110
spec:
  podSelector: {}
  policyTypes: ["Ingress"]
EOF
```

We check that `client` can no longer reach `api` (waiting for the timeout so we don't
hang):

```bash
mkdir -p /var/work/tests/artifacts/4
kubectl exec "$CLIENT" -n eks-110 -- \
  curl -s -o /dev/null -w "HTTP_CODE=%{http_code}\n" --connect-timeout 3 --max-time 5 \
  http://api.eks-110.svc.cluster.local:8080 \
  > /var/work/tests/artifacts/4/connectivity_denied.txt

cat /var/work/tests/artifacts/4/connectivity_denied.txt
```

The file should show `HTTP_CODE=000` (connection not established) - `podSelector: {}`
means "every pod in the namespace", and `policyTypes: ["Ingress"]` without an `ingress`
section means "deny all inbound traffic". This is a classic default deny, enforced by the
`aws-network-policy-agent` agent via eBPF.

## Task 5. Allowing by label: `app: frontend` -> `app: api`

We add a policy that allows inbound traffic to pods `app: api` only from pods labeled
`app: frontend`, on port `8080`:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-api
  namespace: eks-110
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080
EOF
```

We create a client with the right label (`frontend`) and a client without it
(`client-other`), so we can compare the outcome:

```bash
kubectl create deployment frontend --image=curlimages/curl:latest -n eks-110 \
  -- sleep 3600
kubectl rollout status deployment/frontend -n eks-110

kubectl create deployment client-other --image=curlimages/curl:latest -n eks-110 \
  -- sleep 3600
kubectl rollout status deployment/client-other -n eks-110
```

`kubectl create deployment` sets the label `app: <name>` automatically, so `frontend`
already has `app: frontend`, while `client-other` gets `app: client-other` (which does not
match the rule).

We check both cases:

```bash
mkdir -p /var/work/tests/artifacts/5
FRONTEND=$(kubectl get po -n eks-110 -l app=frontend -o jsonpath='{.items[0].metadata.name}')
OTHER=$(kubectl get po -n eks-110 -l app=client-other -o jsonpath='{.items[0].metadata.name}')

kubectl exec "$FRONTEND" -n eks-110 -- \
  curl -s -o /dev/null -w "HTTP_CODE=%{http_code}\n" --connect-timeout 3 --max-time 5 \
  http://api.eks-110.svc.cluster.local:8080 \
  > /var/work/tests/artifacts/5/allowed_frontend.txt

kubectl exec "$OTHER" -n eks-110 -- \
  curl -s -o /dev/null -w "HTTP_CODE=%{http_code}\n" --connect-timeout 3 --max-time 5 \
  http://api.eks-110.svc.cluster.local:8080 \
  > /var/work/tests/artifacts/5/blocked_other.txt

cat /var/work/tests/artifacts/5/allowed_frontend.txt
cat /var/work/tests/artifacts/5/blocked_other.txt
```

`allowed_frontend.txt` should show `HTTP_CODE=200` (the label matched the `podSelector`
rule in `ingress.from`), while `blocked_other.txt` should show `HTTP_CODE=000` (the same
`default-deny-ingress` from task 4 still applies to every pod for which there is no
explicit allow rule).

## Task 6. Egress with a DNS exception

We restrict outbound traffic from `frontend`: allow only traffic to pods `app: api` and to
DNS (`kube-system`, ports `53` UDP/TCP). Everything else (any external address) is blocked.

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: restrict-egress
  namespace: eks-110
spec:
  podSelector:
    matchLabels:
      app: frontend
  policyTypes: ["Egress"]
  egress:
    - to:
        - podSelector:
            matchLabels:
              app: api
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53
EOF
```

We check that resolving the name `api` and accessing it still work (both DNS and the
allowed egress to the `api` pod are needed):

```bash
mkdir -p /var/work/tests/artifacts/6
kubectl exec "$FRONTEND" -n eks-110 -- \
  curl -s -o /dev/null -w "HTTP_CODE=%{http_code}\n" --connect-timeout 3 --max-time 5 \
  http://api.eks-110.svc.cluster.local:8080 \
  > /var/work/tests/artifacts/6/egress_dns_api.txt

cat /var/work/tests/artifacts/6/egress_dns_api.txt
```

`HTTP_CODE=200` confirms that the `to.podSelector: app: api` entry in the policy allows
traffic to `api`, and the exception on port `53` in `kube-system` lets `frontend` resolve
the name.

Now we check that an arbitrary external address (not covered by the allowed rules) is
blocked:

```bash
kubectl exec "$FRONTEND" -n eks-110 -- \
  curl -s -o /dev/null -w "HTTP_CODE=%{http_code}\n" --connect-timeout 3 --max-time 5 \
  http://1.1.1.1 \
  > /var/work/tests/artifacts/6/egress_external_blocked.txt

cat /var/work/tests/artifacts/6/egress_external_blocked.txt
```

`HTTP_CODE=000` confirms the deny: `restrict-egress` defines the complete list of allowed
destinations for `app: frontend`, everything else is denied (including the internet and
any other pod in the cluster besides `api`).
