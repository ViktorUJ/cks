# Lab 105 - reference solution (secrets: KMS envelope encryption, External Secrets)

All commands run on the worker machine over SSH. kubectl is already configured for the
cluster, and terraform has already created a Secrets Manager secret and an IRSA role for
the ESO controller - their names and ARNs are in the hint file
`/home/ubuntu/lab105_hints.txt`.

```bash
cat ~/lab105_hints.txt
```

Variables from the hint file for the commands below:

```bash
export SECRET_NAME=$(grep '^secret_name' ~/lab105_hints.txt | awk '{print $3}')
export ROLE_ARN=$(grep '^role_arn' ~/lab105_hints.txt | awk '{print $3}')
export CLUSTER_NAME=$(grep '^cluster_name' ~/lab105_hints.txt | awk '{print $3}')
```

## Task 1. Namespace `eks-105`

```bash
kubectl create namespace eks-105
```

## Task 2. Layer 1: checking KMS envelope encryption

Starting with Kubernetes 1.28, EKS encrypts all API objects (including `Secret`) with an
AWS-owned key by default, with no action needed on your part. Check the cluster's
encryption configuration:

```bash
mkdir -p /var/work/tests/artifacts/2
aws eks describe-cluster --name "${CLUSTER_NAME}" --query 'cluster.encryptionConfig' \
  > /var/work/tests/artifacts/2/encryption_config.txt
cat /var/work/tests/artifacts/2/encryption_config.txt
```

The output's list item contains `"resources": ["secrets"]` - this confirms that layer 1
(envelope encryption of secrets in etcd) is enabled. If you need your own customer managed
key (CMK) instead of the AWS owned key, that's a separate `aws eks
associate-encryption-config` command - but while you can turn on your own CMK, you can't
turn encryption off (it's an irreversible operation), so here we stay on the default AWS
key.

## Task 3. Installing External Secrets Operator via Helm

The `role_arn` role was already created by terraform with a trust policy that trusts
exactly the `external-secrets` SA in the `external-secrets` namespace (chapter 16, IRSA).
Install ESO via Helm and immediately bind the role with an annotation on the
ServiceAccount:

```bash
helm repo add external-secrets https://charts.external-secrets.io
helm repo update

helm install external-secrets external-secrets/external-secrets \
  --namespace external-secrets --create-namespace \
  --set serviceAccount.annotations."eks\.amazonaws\.com/role-arn"="${ROLE_ARN}"

kubectl rollout status deployment/external-secrets -n external-secrets
kubectl get pods -n external-secrets
```

Confirm the annotation landed on the controller's SA:

```bash
kubectl get sa external-secrets -n external-secrets -o yaml | grep -A1 annotations
```

## Task 4. SecretStore and ExternalSecret

Create a `SecretStore` (namespace-scoped - isolation per team, chapter 18.5), then an
`ExternalSecret` referencing the demo secret from terraform:

```bash
cat <<EOF | kubectl apply -f -
apiVersion: external-secrets.io/v1
kind: SecretStore
metadata:
  name: aws-sm
  namespace: eks-105
spec:
  provider:
    aws:
      service: SecretsManager
      region: eu-central-1
EOF

cat <<EOF | kubectl apply -f -
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: db-credentials
  namespace: eks-105
spec:
  refreshInterval: 1m
  secretStoreRef:
    name: aws-sm
    kind: SecretStore
  target:
    name: db-credentials
  data:
    - secretKey: password
      remoteRef:
        key: ${SECRET_NAME}
        property: password
EOF
```

Wait for the sync and check the native `Secret`:

```bash
kubectl wait --for=jsonpath='{.status.conditions[0].reason}'=SecretSynced \
  externalsecret/db-credentials -n eks-105 --timeout=120s

kubectl get externalsecret db-credentials -n eks-105
kubectl get secret db-credentials -n eks-105 -o jsonpath='{.data.password}' | base64 -d
echo
```

The value should match the password terraform put into Secrets Manager (`S3cr3tPass123`).
`refreshInterval: 1m` is chosen small on purpose - in task 6 we need to see a quick
resync after manually changing the secret in AWS.

## Task 5. Pod with a volume: resilient sync path

Mount the `Secret` as a volume (volumeMount), not through env - this is exactly what
chapter 18.5 recommends for values that need to update without recreating the pod (kubelet
itself updates the files in the volume when the `Secret` changes):

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: vol-reader
  namespace: eks-105
spec:
  containers:
  - name: app
    image: amazon/aws-cli:2.15.0
    command: ["sleep", "3600"]
    volumeMounts:
    - name: db-creds
      mountPath: /etc/db-creds
      readOnly: true
  volumes:
  - name: db-creds
    secret:
      secretName: db-credentials
EOF

kubectl wait --for=condition=Ready pod/vol-reader -n eks-105 --timeout=120s
```

Read the value from the file in the volume:

```bash
mkdir -p /var/work/tests/artifacts/5
kubectl exec vol-reader -n eks-105 -- cat /etc/db-creds/password \
  > /var/work/tests/artifacts/5/volume_password.txt
echo >> /var/work/tests/artifacts/5/volume_password.txt
cat /var/work/tests/artifacts/5/volume_password.txt
```

## Task 6. Pod with env: the stale-value symptom

Create a second pod that reads the same `Secret`, but through an environment variable:

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: env-reader
  namespace: eks-105
spec:
  containers:
  - name: app
    image: amazon/aws-cli:2.15.0
    command: ["sleep", "3600"]
    env:
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: db-credentials
          key: password
EOF

kubectl wait --for=condition=Ready pod/env-reader -n eks-105 --timeout=120s
kubectl exec env-reader -n eks-105 -- printenv DB_PASSWORD
```

Change the secret's value directly in Secrets Manager (not through Kubernetes):

```bash
aws secretsmanager put-secret-value --secret-id "${SECRET_NAME}" \
  --secret-string '{"username":"appuser","password":"RotatedPass456"}'
```

Wait for `refreshInterval` (set to `1m` in task 4) plus a margin and check that ESO has
resynced the native `Secret`:

```bash
sleep 90
kubectl get secret db-credentials -n eks-105 -o jsonpath='{.data.password}' | base64 -d
echo
```

The value in the `Secret` is already new (`RotatedPass456`) - ESO did its job. Now look at
the env pod that was created before the rotation:

```bash
kubectl exec env-reader -n eks-105 -- printenv DB_PASSWORD
```

The pod still shows the old value (`S3cr3tPass123`). The reason: a container's environment
variables are fixed at process start, so an update to the `Secret` in etcd doesn't affect
them - the pod has to be recreated (`kubectl rollout restart` for a Deployment, or a manual
delete and create for a standalone Pod) to pick up the new value through env. This isn't a
bug in ESO, it's a property of how env works in Kubernetes - unlike a volume, which kubelet
updates on disk without recreating the pod (task 5).

Record the observation as an artifact:

```bash
mkdir -p /var/work/tests/artifacts/7
cat > /var/work/tests/artifacts/7/rotation.txt <<'EOF'
After put-secret-value in Secrets Manager and the ExternalSecret resync, the native
Secret db-credentials in etcd was updated with the new password value - ESO worked as
expected.

The env-reader pod reads the password through env (secretKeyRef), and a container's
environment variables are fixed once at process start. The env value doesn't update
after the Secret changes without recreating the pod - this isn't an ESO failure, it's a
property of env in Kubernetes. The vol-reader pod (task 5) reads the same Secret through
a volumeMount - kubelet updates that volume on disk automatically, without recreating
the pod.
EOF
cat /var/work/tests/artifacts/7/rotation.txt
```
