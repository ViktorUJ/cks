# Lab 126 - reference solution (security groups for pods)

All commands run on the worker machine over SSH, same as in the rest of the course's
labs: the worker role got permissions to create a security group, add rules to it, and
attach the `AmazonEKSVPCResourceController` policy to the cluster role (see the README,
"Infrastructure" section).

Variables shared across the solution:

```bash
export KUBECONFIG=/home/ubuntu/.kube/config
CLUSTER=$(kubectl config current-context | awk -F/ '{print $NF}')
REGION=eu-central-1
VPC_ID=$(aws eks describe-cluster --name "$CLUSTER" --query 'cluster.resourcesVpcConfig.vpcId' --output text)
echo "cluster=$CLUSTER vpc=$VPC_ID"
```

## Task 1. Namespace `eks-126`

```bash
kubectl create namespace eks-126
```

## Task 2. Checking the prerequisites

Find the control plane role name and check the attached policies (on the worker):

```bash
ROLE_ARN=$(aws eks describe-cluster --name "$CLUSTER" --query 'cluster.roleArn' --output text)
ROLE_NAME=$(echo "$ROLE_ARN" | sed 's|.*/||')
echo "cluster role: $ROLE_NAME"
aws iam list-attached-role-policies --role-name "$ROLE_NAME"
```

By default it isn't there (the role only has `AmazonEKSClusterPolicy` and the encryption
policy), so we attach it:

```bash
aws iam attach-role-policy \
  --role-name "$ROLE_NAME" \
  --policy-arn arn:aws:iam::aws:policy/AmazonEKSVPCResourceController
```

The policy goes on the **control plane** role (the cluster), not the Karpenter node role -
it's the one that allows EKS to create/delete branch ENIs and manage their IPs.

We check the three VPC CNI variables - all already set by terraform through the
`configuration` of the `vpc-cni` addon:

```bash
kubectl describe daemonset aws-node -n kube-system \
  | grep -E 'ENABLE_POD_ENI|POD_SECURITY_GROUP_ENFORCING_MODE|DISABLE_TCP_EARLY_DEMUX'
```

Expected output: `ENABLE_POD_ENI: true`, `POD_SECURITY_GROUP_ENFORCING_MODE: strict`,
`DISABLE_TCP_EARLY_DEMUX: true`. The first turns on the trunk interface, the second keeps
the pod SG rule check active for traffic from the node (in `standard` mode it isn't, and
the symptom in task 4 wouldn't appear), the third lets `kubelet` open a TCP connection to
a pod on a branch ENI.

Save both confirmations:

```bash
mkdir -p /var/work/tests/artifacts/2
{
  echo "cluster role: $ROLE_NAME"
  aws iam list-attached-role-policies --role-name "$ROLE_NAME"
  echo "---"
  kubectl describe daemonset aws-node -n kube-system | grep ENABLE_POD_ENI
} > /var/work/tests/artifacts/2/prereqs.txt
cat /var/work/tests/artifacts/2/prereqs.txt
```

## Task 3. An incomplete security group and SecurityGroupPolicy

Create the SG in the lab's VPC. Important: do NOT set the tag `karpenter.sh/discovery`,
otherwise the EC2NodeClass would pick it up as a node SG:

```bash
SG_ID=$(aws ec2 create-security-group \
  --group-name eks-task126-secured-pod-sg \
  --description "security group for secured-app pods (lab 126, intentionally incomplete)" \
  --vpc-id "$VPC_ID" \
  --query 'GroupId' --output text)
echo "$SG_ID"
```

We don't add any `authorize-security-group-ingress` or `egress` yet: a fresh SG only has
the AWS-default allow-all egress and zero inbound rules - exactly the state that produces
the symptom.

Create the `SecurityGroupPolicy`:

```bash
mkdir -p /var/work/tests/artifacts/3
echo -n "$SG_ID" > /var/work/tests/artifacts/3/sg_id.txt

cat <<EOF | kubectl apply -f -
apiVersion: vpcresources.k8s.aws/v1beta1
kind: SecurityGroupPolicy
metadata:
  name: secured-sgp
  namespace: eks-126
spec:
  podSelector:
    matchLabels:
      app: secured
  securityGroups:
    groupIds:
      - ${SG_ID}
EOF

kubectl get securitygrouppolicy secured-sgp -n eks-126 -o yaml
```

## Task 4. The symptom: Running, but never Ready

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: secured-app
  namespace: eks-126
spec:
  replicas: 1
  selector:
    matchLabels:
      app: secured
  template:
    metadata:
      labels:
        app: secured
    spec:
      nodeSelector:
        work_type: nitro
      containers:
      - name: app
        image: viktoruj/ping_pong:latest
        ports:
        - containerPort: 8080
        readinessProbe:
          httpGet:
            path: /
            port: 8080
          periodSeconds: 5
          failureThreshold: 3
EOF

kubectl rollout status deployment/secured-app -n eks-126 --timeout=180s || true
kubectl get pod -n eks-126 -l app=secured
```

The pod hangs at `0/1 Ready`, even though the phase is `Running` - the branch ENI got
created, but the pod's SG doesn't let the kubelet probe through. Save the diagnostics:

```bash
mkdir -p /var/work/tests/artifacts/4
POD=$(kubectl get pod -n eks-126 -l app=secured -o jsonpath='{.items[0].metadata.name}')
kubectl describe pod "$POD" -n eks-126 > /var/work/tests/artifacts/4/pod_not_ready.txt
grep -i 'readiness probe failed\|unhealthy' /var/work/tests/artifacts/4/pod_not_ready.txt
```

The event looks like this (verified on the test bench):

```
Warning  Unhealthy  49s (x33 over 5m44s)  kubelet  Readiness probe failed:
Get "http://10.10.16.177:8080/": context deadline exceeded
```

We confirm the pod really is on a branch ENI, not the node's ENI:

```bash
kubectl get pod "$POD" -n eks-126 \
  -o jsonpath='{.metadata.annotations.vpc\.amazonaws\.com/pod-eni}{"\n"}'
kubectl get pod "$POD" -n eks-126 -o jsonpath='{.spec.containers[0].resources.limits}{"\n"}'
aws ec2 describe-network-interfaces --filters "Name=group-id,Values=$SG_ID" \
  --query 'NetworkInterfaces[].[NetworkInterfaceId,InterfaceType,Status,PrivateIpAddress]' \
  --output text
```

The annotation will contain `eniId`, `vlanId` and an `associationID` like
`trunk-assoc-...`, the limits will show `vpc.amazonaws.com/pod-eni: 1`, and the interface
type will be `branch` with the same IP as the pod.

## Task 5. Fixing the probes: an inbound rule from the node SG

Find the Karpenter node SG through the node where `secured-app` is running (on the
worker):

```bash
NODE=$(kubectl get pod "$POD" -n eks-126 -o jsonpath='{.spec.nodeName}')
INSTANCE_ID=$(kubectl get node "$NODE" -o jsonpath='{.spec.providerID}' | sed 's|.*/||')
NODE_SG=$(aws ec2 describe-instances --instance-ids "$INSTANCE_ID" \
  --query 'Reservations[0].Instances[0].SecurityGroups[0].GroupId' --output text)
echo "node=$NODE instance=$INSTANCE_ID node_sg=$NODE_SG"
```

Add an inbound rule to the pod's SG:

```bash
aws ec2 authorize-security-group-ingress \
  --group-id "$SG_ID" \
  --protocol tcp --port 8080 \
  --source-group "$NODE_SG"
```

Wait for the probe to pass and save the result:

```bash
sleep 15
kubectl get pod -n eks-126 -l app=secured
mkdir -p /var/work/tests/artifacts/5
kubectl get pod "$POD" -n eks-126 > /var/work/tests/artifacts/5/pod_ready.txt
cat /var/work/tests/artifacts/5/pod_ready.txt
```

`READY` should now show `1/1` - kubelet can now reach the pod's branch ENI on the probe
port.

## Task 6. Diagnosing and fixing DNS

Check resolution from within `secured-app`. The `viktoruj/ping_pong:latest` image has no
shell utilities for DNS (built from `scratch`), so we use a separate diagnostic pod with
the same label `app: secured`, so that `secured-sgp` applies to it too:

```bash
kubectl run dns-probe -n eks-126 --image=busybox --restart=Never \
  --labels='app=secured' \
  --overrides='{"spec":{"nodeSelector":{"work_type":"nitro"}}}' \
  -- sleep 3600
kubectl wait --for=condition=Ready pod/dns-probe -n eks-126 --timeout=120s || true

mkdir -p /var/work/tests/artifacts/6
kubectl exec dns-probe -n eks-126 -- nslookup kubernetes.default.svc.cluster.local \
  > /var/work/tests/artifacts/6/dns_before.txt 2>&1 || true
cat /var/work/tests/artifacts/6/dns_before.txt
```

The output is `;; connection timed out; no servers could be reached`. It's important to
name the cause correctly: egress isn't the issue here, a fresh SG has the default
allow-all egress rule, and the request leaves fine. The packet is dropped on the inbound
side of the receiving party, which has no rule for our SG. CoreDNS in this lab runs on
Fargate and sits behind the cluster primary security group:

```bash
CLUSTER_PRIMARY_SG=$(aws eks describe-cluster --name "$CLUSTER" \
  --query 'cluster.resourcesVpcConfig.clusterSecurityGroupId' --output text)
echo "cluster primary sg (CoreDNS on Fargate): $CLUSTER_PRIMARY_SG"
```

We add an inbound `53` TCP and UDP to the cluster primary SG, with the source being our
pod's SG. This one rule is enough, since a security group is stateful: the reply to an
allowed inbound request goes back without a separate rule.

```bash
aws ec2 authorize-security-group-ingress --group-id "$CLUSTER_PRIMARY_SG" \
  --ip-permissions \
    "IpProtocol=tcp,FromPort=53,ToPort=53,UserIdGroupPairs=[{GroupId=$SG_ID}]" \
    "IpProtocol=udp,FromPort=53,ToPort=53,UserIdGroupPairs=[{GroupId=$SG_ID}]"
```

We check resolution again:

```bash
sleep 5
kubectl exec dns-probe -n eks-126 -- nslookup kubernetes.default.svc.cluster.local \
  > /var/work/tests/artifacts/6/dns_after.txt 2>&1
cat /var/work/tests/artifacts/6/dns_after.txt
```

Now the second step, following least privilege. The pod SG's default allow-all egress
means "the pod is allowed anything outbound" - for a pod with its own security group,
that's exactly what we were trying to avoid. We narrow egress down to `53` and confirm
DNS keeps working:

```bash
aws ec2 revoke-security-group-egress --group-id "$SG_ID" \
  --protocol -1 --port all --cidr 0.0.0.0/0
aws ec2 authorize-security-group-egress --group-id "$SG_ID" \
  --ip-permissions \
    "IpProtocol=tcp,FromPort=53,ToPort=53,UserIdGroupPairs=[{GroupId=$CLUSTER_PRIMARY_SG}]" \
    "IpProtocol=udp,FromPort=53,ToPort=53,UserIdGroupPairs=[{GroupId=$CLUSTER_PRIMARY_SG}]"

kubectl delete pod dns-probe -n eks-126 --ignore-not-found
kubectl run dns-probe -n eks-126 --image=busybox --restart=Never --labels='app=secured' \
  --overrides='{"spec":{"nodeSelector":{"work_type":"nitro"}}}' \
  --command -- sh -c 'nslookup kubernetes.default.svc.cluster.local'
sleep 45
kubectl logs dns-probe -n eks-126 | tee -a /var/work/tests/artifacts/6/dns_after.txt
```

Build the artifact:

```bash
cat > /var/work/tests/artifacts/6/dns_fix.txt <<EOF
Before the fix (dns_before.txt): nslookup to kubernetes.default failed with
";; connection timed out; no servers could be reached".

The cause is NOT egress: a fresh security group ${SG_ID} has the default allow-all
egress rule, and the request from the pod leaves fine. The packet is dropped on the
INBOUND side of the receiving party - the cluster primary security group
${CLUSTER_PRIMARY_SG}, behind which CoreDNS on Fargate runs, has no inbound rule for our
SG. The rule is needed exactly there, and one is enough: a security group is stateful,
the reply to an allowed inbound request goes back on its own.

Fix: inbound 53 TCP and UDP on ${CLUSTER_PRIMARY_SG} with source-group ${SG_ID}.
After that, nslookup resolves kubernetes.default.svc.cluster.local (dns_after.txt).

Second step: the default allow-all egress was removed from the pod's SG, replaced with
an explicit egress 53 TCP and UDP to ${CLUSTER_PRIMARY_SG}. DNS keeps working - this shows
that egress on the source side and inbound on the receiving side are two independent
rules, and allowing the pod all outbound traffic isn't required for DNS.
EOF
cat /var/work/tests/artifacts/6/dns_fix.txt
```

## Task 7. Trap: one node, different security groups

Run an experiment: two pods with DIFFERENT security groups on the same node. Set up a
second SG and a second `SecurityGroupPolicy` for the label `app: other`:

```bash
mkdir -p /var/work/tests/artifacts/7
SG2=$(aws ec2 create-security-group \
  --group-name eks-task126-other-pod-sg \
  --description "second pod sg for the same-node experiment (lab 126)" \
  --vpc-id "$VPC_ID" --query 'GroupId' --output text)
echo "second pod sg: $SG2"

cat <<EOF | kubectl apply -f -
apiVersion: vpcresources.k8s.aws/v1beta1
kind: SecurityGroupPolicy
metadata:
  name: other-sgp
  namespace: eks-126
spec:
  podSelector:
    matchLabels:
      app: other
  securityGroups:
    groupIds:
      - ${SG2}
EOF
```

We find the Deployment's pod (that one specifically, not the diagnostic pods - they also
carry the label `app: secured`) and start a pod with a different SG next to it:

```bash
APP_POD=$(kubectl get pod -n eks-126 -l app=secured \
  -o jsonpath='{range .items[?(@.metadata.ownerReferences[0].kind=="ReplicaSet")]}{.metadata.name}{"\n"}{end}' \
  | head -1)
APP_IP=$(kubectl get pod "$APP_POD" -n eks-126 -o jsonpath='{.status.podIP}')
APP_NODE=$(kubectl get pod "$APP_POD" -n eks-126 -o jsonpath='{.spec.nodeName}')
echo "secured-app=$APP_POD ip=$APP_IP node=$APP_NODE"

kubectl delete pod othersg -n eks-126 --ignore-not-found --wait=true
kubectl run othersg -n eks-126 --image=busybox --restart=Never --labels='app=other' \
  --overrides="{\"spec\":{\"nodeName\":\"$APP_NODE\"}}" \
  --command -- sh -c "wget -T 10 -qO- http://$APP_IP:8080/ ; echo RC=\$?"
sleep 55
kubectl logs othersg -n eks-126 | tee /var/work/tests/artifacts/7/before.txt
```

The result is `wget: download timed out`: the pod has its own SG, the neighbor has its
own, and there's no rule allowing traffic between them. Add the rule and repeat:

```bash
aws ec2 authorize-security-group-ingress --group-id "$SG_ID" \
  --protocol tcp --port 8080 --source-group "$SG2"

kubectl delete pod othersg -n eks-126 --ignore-not-found --wait=true
kubectl run othersg -n eks-126 --image=busybox --restart=Never --labels='app=other' \
  --overrides="{\"spec\":{\"nodeName\":\"$APP_NODE\"}}" \
  --command -- sh -c "wget -T 10 -qO- http://$APP_IP:8080/ ; echo RC=\$?"
sleep 55
kubectl logs othersg -n eks-126 | tee /var/work/tests/artifacts/7/after.txt
```

Now the request goes through (`RC=0`). This means that in `strict` mode, the pod's SG
rules apply even within a single node - both pods have their own branch ENIs, and it's
the rule that decides the outcome. Build the artifact:

```bash
{
  echo "=== Deployment's pod with SecurityGroupPolicy secured-sgp (branch ENI) ==="
  kubectl get pod "$APP_POD" -n eks-126 -o wide
  echo
  echo "=== pod with a DIFFERENT security group (other-sgp), same node ==="
  kubectl get pod othersg -n eks-126 -o wide
  echo
  echo "=== before the rule ==="
  cat /var/work/tests/artifacts/7/before.txt
  echo "=== after the inbound 8080 rule from the second SG ==="
  cat /var/work/tests/artifacts/7/after.txt
  echo
  echo "=== where CoreDNS is ==="
  kubectl get pods -n kube-system -l k8s-app=kube-dns -o wide
  cat <<'TXT'

Conclusion from the experiment. Our POD_SECURITY_GROUP_ENFORCING_MODE is strict, and in
it the pod's security group rules apply even to traffic within a single node: two pods
with different SGs on the same node first failed to connect (download timed out), and
after adding an inbound rule they connected. So the diagnosis here is the ordinary one -
look at the rules, not the topology.

The contrast worth knowing (AWS documentation, standard mode): in standard mode, the
pod's SG rules are NOT applied to traffic between pods and services on the same node,
including kubelet and nodeLocalDNS, and pods with different security groups on the same
node don't communicate at all, because they sit in different subnets with routing
disabled between them. There, the same situation can't be fixed with a rule, only by
spreading pods across nodes. That's also exactly why standard doesn't reproduce the
symptom from tasks 4 and 5: the kubelet probe bypasses SG rules, and readiness passes
even with a security group that has not a single inbound rule.
TXT
} > /var/work/tests/artifacts/7/same_node_trap.txt
cat /var/work/tests/artifacts/7/same_node_trap.txt
```
