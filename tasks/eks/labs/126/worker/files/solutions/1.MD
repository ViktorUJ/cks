# Лаба 126 - эталонное решение (security groups for pods)

Часть команд выполняется на рабочей машине (worker) по SSH - всё, что читает
Kubernetes и AWS API (`kubectl`, `aws ec2 describe-*`, `aws eks describe-*`). Команды,
которые создают или меняют security group и IAM-политики
(`create-security-group`, `authorize-security-group-*`, `attach-role-policy`),
выполняются **с вашей локальной машины** тем же профилем AWS CLI, которым вы
разворачивали лабу - у роли worker нет прав на эти действия (см. README, раздел
«Инфраструктура»). Ниже такие блоки помечены отдельно.

Переменные, общие для решения (выполнить на worker):

```bash
export KUBECONFIG=/home/ubuntu/.kube/config
CLUSTER=$(aws eks list-clusters --query 'clusters[0]' --output text)
REGION=eu-central-1
VPC_ID=$(aws eks describe-cluster --name "$CLUSTER" --query 'cluster.resourcesVpcConfig.vpcId' --output text)
echo "cluster=$CLUSTER vpc=$VPC_ID"
```

## Задание 2. Проверка предпосылок

Узнаём имя роли control plane и проверяем присоединённые политики (на worker):

```bash
ROLE_ARN=$(aws eks describe-cluster --name "$CLUSTER" --query 'cluster.roleArn' --output text)
ROLE_NAME=$(echo "$ROLE_ARN" | sed 's|.*/||')
echo "cluster role: $ROLE_NAME"
aws iam list-attached-role-policies --role-name "$ROLE_NAME"
```

Если `AmazonEKSVPCResourceController` в списке нет, присоединяем её (**с локальной
машины**, роль worker не имеет прав `iam:AttachRolePolicy` на произвольные роли):

```bash
aws iam attach-role-policy \
  --role-name "$ROLE_NAME" \
  --policy-arn arn:aws:iam::aws:policy/AmazonEKSVPCResourceController
```

Политика идёт на роль **control plane** (кластера), а не на роль ноды Karpenter -
именно она разрешает EKS создавать/удалять branch ENI и управлять их IP.

Проверяем `ENABLE_POD_ENI` (на worker, уже включено terraform через `configuration`
аддона `vpc-cni`):

```bash
kubectl describe daemonset aws-node -n kube-system | grep ENABLE_POD_ENI
```

Сохраняем оба подтверждения:

```bash
mkdir -p /var/work/tests/artifacts/2
{
  echo "cluster role: $ROLE_NAME"
  aws iam list-attached-role-policies --role-name "$ROLE_NAME"
  echo "---"
  kubectl describe daemonset aws-node -n kube-system | grep ENABLE_POD_ENI
} > /var/work/tests/artifacts/2/prereqs.txt
cat /var/work/tests/artifacts/2/prereqs.txt
```

## Задание 3. Неполная security group и SecurityGroupPolicy

Создаём SG в VPC лабы **с локальной машины** (роль worker не может создавать security
group). Важно: НЕ ставим тег `karpenter.sh/discovery`, иначе EC2NodeClass подберёт эту
SG как SG нод:

```bash
SG_ID=$(aws ec2 create-security-group \
  --region eu-central-1 \
  --group-name eks-task126-secured-pod-sg \
  --description "security group for secured-app pods (lab 126, intentionally incomplete)" \
  --vpc-id <VPC_ID из задания 1 (aws eks describe-cluster на worker)> \
  --query 'GroupId' --output text)
echo "$SG_ID"
```

Никаких `authorize-security-group-ingress`/`egress` пока не добавляем - это намеренно
неполная SG (только AWS-дефолтный allow-all egress, без единого inbound-правила и без
egress на `53`).

На worker создаём `SecurityGroupPolicy`:

```bash
mkdir -p /var/work/tests/artifacts/3
echo "$SG_ID" > /var/work/tests/artifacts/3/sg_id.txt

cat <<EOF | kubectl apply -f -
apiVersion: vpcresources.k8s.aws/v1beta1
kind: SecurityGroupPolicy
metadata:
  name: secured-sgp
  namespace: eks-126
spec:
  podSelector:
    matchLabels:
      app: secured
  securityGroups:
    groupIds:
      - ${SG_ID}
EOF

kubectl get securitygrouppolicy secured-sgp -n eks-126 -o yaml
```

## Задание 5. Починка проб: правило inbound от SG нод

Находим SG нод Karpenter через ноду, на которой сидит `secured-app` (на worker):

```bash
NODE=$(kubectl get pod "$POD" -n eks-126 -o jsonpath='{.spec.nodeName}')
INSTANCE_ID=$(kubectl get node "$NODE" -o jsonpath='{.spec.providerID}' | sed 's|.*/||')
NODE_SG=$(aws ec2 describe-instances --instance-ids "$INSTANCE_ID" \
  --query 'Reservations[0].Instances[0].SecurityGroups[0].GroupId' --output text)
echo "node=$NODE instance=$INSTANCE_ID node_sg=$NODE_SG"
```

Добавляем inbound-правило в SG пода (**с локальной машины**):

```bash
aws ec2 authorize-security-group-ingress \
  --region eu-central-1 \
  --group-id "$SG_ID" \
  --protocol tcp --port 8080 \
  --source-group "$NODE_SG"
```

Ждём, пока проба пройдёт, и сохраняем результат (на worker):

```bash
sleep 15
kubectl get pod -n eks-126 -l app=secured
mkdir -p /var/work/tests/artifacts/5
kubectl get pod "$POD" -n eks-126 > /var/work/tests/artifacts/5/pod_ready.txt
cat /var/work/tests/artifacts/5/pod_ready.txt
```

`READY` должен показать `1/1` - kubelet теперь может достучаться до branch ENI пода на
порту пробы.

## Задание 6. Диагностика и починка DNS

Проверяем резолвинг из-под `secured-app`. У образа `viktoruj/ping_pong:latest` нет
shell-утилит для DNS (собран из `scratch`), поэтому используем отдельный
диагностический под с той же меткой `app: secured`, чтобы на него тоже действовала
`secured-sgp`:

```bash
kubectl run dns-probe -n eks-126 --image=busybox:1.36 --restart=Never \
  --overrides='{"spec":{"nodeSelector":{"work_type":"nitro"}},"metadata":{"labels":{"app":"secured"}}}' \
  -- sleep 3600
kubectl wait --for=condition=Ready pod/dns-probe -n eks-126 --timeout=60s || true

mkdir -p /var/work/tests/artifacts/6
kubectl exec dns-probe -n eks-126 -- nslookup -timeout=3 kubernetes.default.svc.cluster.local \
  > /var/work/tests/artifacts/6/dns_before.txt 2>&1 || true
cat /var/work/tests/artifacts/6/dns_before.txt
```

Запрос падает по таймауту - у SG пода нет egress на `53`. Находим, куда идёт CoreDNS
(в этой лабе он на Fargate и использует cluster primary security group control plane):

```bash
CLUSTER_PRIMARY_SG=$(aws eks describe-cluster --name "$CLUSTER" \
  --query 'cluster.resourcesVpcConfig.clusterSecurityGroupId' --output text)
echo "cluster primary sg (CoreDNS on Fargate): $CLUSTER_PRIMARY_SG"
```

Добавляем outbound `53` TCP и UDP в SG пода к cluster primary SG, и ОБРАТНОЕ inbound
`53` TCP и UDP на стороне cluster primary SG от SG пода (**с локальной машины**):

```bash
aws ec2 authorize-security-group-egress --region eu-central-1 --group-id "$SG_ID" \
  --protocol tcp --port 53 --source-group "$CLUSTER_PRIMARY_SG"
aws ec2 authorize-security-group-egress --region eu-central-1 --group-id "$SG_ID" \
  --protocol udp --port 53 --source-group "$CLUSTER_PRIMARY_SG"

aws ec2 authorize-security-group-ingress --region eu-central-1 --group-id "$CLUSTER_PRIMARY_SG" \
  --protocol tcp --port 53 --source-group "$SG_ID"
aws ec2 authorize-security-group-ingress --region eu-central-1 --group-id "$CLUSTER_PRIMARY_SG" \
  --protocol udp --port 53 --source-group "$SG_ID"
```

Egress без обратного ingress не работает: security group - stateful только в рамках
одного правила-пары. `authorize-security-group-egress` в SG пода разрешает пакетам
выйти к `$CLUSTER_PRIMARY_SG`, но ответный трафик от CoreDNS всё равно должен пройти
собственную проверку ingress на стороне `$CLUSTER_PRIMARY_SG` - без нашего ingress-
правила там пакет с ответом отбрасывается ещё до того, как stateful-механизм SG свяжет
его с исходящим запросом.

Проверяем резолвинг снова (на worker):

```bash
sleep 5
kubectl exec dns-probe -n eks-126 -- nslookup -timeout=3 kubernetes.default.svc.cluster.local \
  > /var/work/tests/artifacts/6/dns_after.txt 2>&1
cat /var/work/tests/artifacts/6/dns_after.txt

cat > /var/work/tests/artifacts/6/dns_fix.txt <<EOF
До починки (dns_before.txt): запрос nslookup к kubernetes.default падал по таймауту -
у SG пода (${SG_ID}) не было egress на порт 53, ни TCP, ни UDP.

Починка: добавлен egress 53 TCP+UDP из SG пода к cluster primary SG (${CLUSTER_PRIMARY_SG},
на нём работает CoreDNS на Fargate), и ОБРАТНОЕ ingress-правило 53 TCP+UDP на стороне
cluster primary SG от SG пода. Один egress недостаточен: без обратного ingress-правила
на стороне CoreDNS ответный DNS-пакет отбрасывается на входе, потому что security group
проверяет правила на каждой стороне соединения независимо для разных SG.

После починки (dns_after.txt): nslookup успешно резолвит kubernetes.default.svc.cluster.local.
EOF
cat /var/work/tests/artifacts/6/dns_fix.txt
```

## Задание 7. Ловушка: одна нода, разные security group

```bash
mkdir -p /var/work/tests/artifacts/7

kubectl get pod -n eks-126 -l app=secured -o wide > /var/work/tests/artifacts/7/same_node_trap.txt
echo "---" >> /var/work/tests/artifacts/7/same_node_trap.txt
kubectl get pods -n kube-system -l k8s-app=kube-dns -o wide >> /var/work/tests/artifacts/7/same_node_trap.txt

cat >> /var/work/tests/artifacts/7/same_node_trap.txt <<'EOF'
---
В этой лабе CoreDNS работает на Fargate, а secured-app - на EC2-ноде Karpenter, поэтому
физически это разные ноды и правила из задания 6 работают предсказуемо.

Важная ловушка (документирована AWS): pod security group правила не применяются к
трафику между подами на одной ноде, в том числе между подом и kubelet или nodeLocalDNS.
Если бы CoreDNS оказался на EC2-ноде Karpenter, и Kubernetes запланировал его на ТУ ЖЕ
ноду, что и secured-app, DNS не заработал бы даже после правильной починки правил из
задания 6. Причина не в security group: под с одной SG и под/сервис с другой SG на
одной ноде получают адреса из разных внутренних подсетей ветвления ENI, а маршрутизация
между этими подсетями на уровне ноды отключена. Починка в такой ситуации - не менять SG,
а гарантировать, что под с security group и то, с чем он должен общаться в обход своей
SG (kubelet, DNS-кэш ноды), не оказываются на одной ноде, либо явно разносить их через
anti-affinity.
EOF
cat /var/work/tests/artifacts/7/same_node_trap.txt
```
