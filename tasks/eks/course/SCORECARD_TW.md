# EKS 成熟度矩陣：就緒度問卷

[課程目錄](README_TW.md) · [第 48 章](48/tw.md) · [詞彙表](GLOSSARY_TW.md)

這是第 48 章的實作表單：涵蓋相同的就緒度領域，但以問卷形式呈現，團隊可將其轉化為技術債清單。此處不包含新內容。

## 如何填寫

- 依序完成八個領域，不要跳過任何一項：每個領域都是運維的獨立軸向，一個軸向的弱點不能由另一個軸向的強項彌補。
- 對每個項目誠實回答：是或否。「部分完成」、「差不多」與「已設定但未驗證」均視為否。
- 由團隊共同填寫，而非由單一人員完成：網路、安全性與成本的負責人會看到不同的缺口，而「看似已就緒」恰恰會在意見交會處被揭露。
- 重點不在分數。分數僅用於判斷等級；問卷的產出是未完成事項清單，並附上負責人與期限。
- 將每個未完成項目標記為已知風險並建立任務，而不是悄悄略過以讓表單看起來全綠。
- 每季以及每次重大變更後重新填寫：版本會老化、負載會成長，昨天的「已完成」今天可能已是缺口。
- 將表單與 IaC 一同存放在儲存庫中，使其變更能在 pull request 裡被看見。

## 等級量表

問卷共有 51 個項目。每完成一項得一分。

| 等級 | 分數 | 代表意義 | 下一步行動 |
|---|---|---|---|
| 等級 1。不穩定且仰賴手動操作 | 0-20 | 只要沒有故障，叢集就能運作：許多工作透過點擊完成，復原與安全邊界尚未驗證 | 在啟用正式流量前，完成阻擋性項目及整欄「must have」 |
| 等級 2。可管理 | 21-33 | 已具備基礎：叢集由程式碼建立，存取與運算資源已經審慎規劃，但驗證與可觀測性仍仰賴個別人員 | 補齊安全性與運維：稽核、retention、警示、升級計畫 |
| 等級 3。可重複且可觀測 | 34-44 | 實務已制度化且可重複：已完成升級、備份與 restore，並可依 runbook 定位事件 | 完成「前幾週重要」優先級，為每個領域指派 ownership |
| 等級 4。自主韌性 | 45-51 | 就緒度不會在發行之間退化：已在演練中驗證 DR，成本與流量受到控制，GitOps 是事實來源 | 維持等級：每季填寫問卷、進行 game day、逐步完成「nice to have」 |

只要有任何阻擋性項目尚未完成，無論總分多高，等級都不得高於第二級。規則詳見「計分與結果處置」。

## 1. 叢集與 control plane

基礎中的基礎。若版本已不受支援，或子網路只設定在一個 AZ，其他一切都不重要。

| 完成 | 項目 | 為何重要 | 章節 |
|---|---|---|---|
| [ ] | Kubernetes 版本仍在 standard support 範圍內 | 不受支援的版本是無法透過設定消除的風險 | [38](38/tw.md) |
| [ ] | 有版本升級計畫，而非在支援期結束前一個月才反應 | 受期限壓力的升級無法保留回復窗口 | [38](38/tw.md) |
| [ ] | Endpoint access 已妥善規劃：依需求選用 public 或 private，並設定 source ranges | API 存取模式決定叢集的攻擊面 | [02](02/tw.md) |
| [ ] | 叢集子網路分布於三個 AZ，IP 規劃足以因應 Pod 成長 | 單一 AZ 是單點故障；IP 不足會停止 Pod 排程 | [06](06/tw.md) |
| [ ] | 叢集由程式碼建立（Terraform 或 eksctl），而非在主控台點擊建立 | 手動建立的叢集無法在 DR 時重建，也無法在 pull request 中審查 | [04](04/tw.md) |
| [ ] | 資源已加上標籤：團隊、環境、cost allocation | 沒有標籤便無法依團隊拆分成本與歸屬 | [43](43/tw.md) |

## 2. 運算

節點完全屬於工程師的責任範圍：韌性與帳單都在此決定。

| 完成 | 項目 | 為何重要 | 章節 |
|---|---|---|---|
| [ ] | 已有意識地選擇節點策略：Auto Mode、Karpenter 或 managed node groups | 保留預設值代表對價格與韌性的影響不明 | [09](09/tw.md) |
| [ ] | 對具容錯能力的工作負載採用 Spot 混合策略 | 負載能承受中斷時，Spot 可節省成本 | [13](13/tw.md) |
| [ ] | spot 集區中的執行個體類型已多樣化 | 未多樣化的 Spot 不是節省，而是可能一次失去全部容量的風險 | [13](13/tw.md) |
| [ ] | requests 依實際需求設定（right-sizing），而非憑感覺 | 過高的 requests 會為閒置資源付費，過低則會破壞工作負載 | [14](14/tw.md) |
| [ ] | 已設定 Karpenter disruption 與 consolidation，未忽略 drift | 沒有 consolidation，節點群會逐漸膨脹；drift 會累積與程式碼的偏差 | [12](12/tw.md) |
| [ ] | 每個節點的 Pod 密度已與 ENI 和 IP 限制協調 | 過高密度會讓 Pod 無明確原因地停在 `Pending` | [14](14/tw.md) |

## 3. 身分與安全性

最廣泛的領域，也是無聲漏洞最常見的來源。請逐項檢查。

| 完成 | 項目 | 為何重要 | 章節 |
|---|---|---|---|
| [ ] | Pod 透過 IRSA 或 Pod Identity 存取 AWS，沒有靜態金鑰 | Pod 中的長效金鑰會隨映像檔或日誌一同外洩 | [16](16/tw.md) |
| [ ] | **阻擋性。** 存取叢集的人不只 cluster creator，已建立 access entries | 只有一人能存取的叢集會隨著那個人一同失去 | [05](05/tw.md) |
| [ ] | 從 Secrets Manager 或 SSM（External Secrets、CSI）取得祕密，而非從 manifest 取得 | manifest 中的祕密會進入 git 與儲存庫的每個副本 | [18](18/tw.md) |
| [ ] | 節點與 Pod 已強化：IMDSv2、hop limit、Pod Security Admission | 從 Pod 存取節點中繼資料，等同讓 Pod 取得節點權限 | [19](19/tw.md) |
| [ ] | 在 ECR 掃描映像檔，基礎映像取自受信任來源 | 脆弱的基礎映像會立即散播至所有服務 | [20](20/tw.md) |
| [ ] | 已啟用 control plane 稽核：日誌中有 api、audit、authenticator | 稽核必須在事件前啟用，事後不會再有日誌 | [21](21/tw.md) |
| [ ] | Kyverno 或 Gatekeeper 政策可攔阻危險的 manifest 模式 | 人工審查會漏掉始終能由政策攔住的項目 | [22](22/tw.md) |

## 4. 儲存

規模不大卻很棘手的領域：EBS 預設值與未驗證的磁碟區備份會突然造成問題。

| 完成 | 項目 | 為何重要 | 章節 |
|---|---|---|---|
| [ ] | 預設 StorageClass 使用 gp3，而非過時的 gp2 | gp2 因慣性仍常是預設值，卻在效能與價格上都較差 | [23](23/tw.md) |
| [ ] | 已設定 `volumeBindingMode: WaitForFirstConsumer` | 否則磁碟區可能在錯誤的 AZ 建立，使 Pod 永遠停在 `Pending` | [23](23/tw.md) |
| [ ] | 持久磁碟區已納入備份 | 沒有備份的磁碟區，資料只存在單一副本 | [41](41/tw.md) |
| [ ] | 磁碟區快照已透過還原驗證，而非只驗證建立成功 | 未驗證的快照等同沒有快照 | [41](41/tw.md) |
| [ ] | 在遷移與工作負載排程時已考量 EBS 對 AZ 的綁定 | 原封不動遷移 manifest 會在磁碟區上失敗 | [23](23/tw.md) |
| [ ] | 已有意識地選擇共享儲存：需要 ReadWriteMany 時使用 EFS 或 FSx | EBS 不提供 ReadWriteMany，因此必須在設計階段處理此限制 | [24](24/tw.md) |

## 5. 網路與流量

此領域的錯誤可從外部看見：服務無法存取、egress 開放、流量跨越所有 AZ。

| 完成 | 項目 | 為何重要 | 章節 |
|---|---|---|---|
| [ ] | 透過 AWS Load Balancer Controller 建立負載平衡器：NLB | 手動建立的負載平衡器會與叢集狀態產生偏差 | [26](26/tw.md) |
| [ ] | Ingress 經由 ALB 運作，並已審慎選擇 target-type | target 類型決定流量路徑與 drain 時的行為 | [27](27/tw.md) |
| [ ] | TLS 憑證透過 ACM 管理，HTTPS 在負載平衡器終止 | 手動管理的憑證總會在最不方便的時候到期 | [27](27/tw.md) |
| [ ] | **阻擋性。** NetworkPolicy 使用 default-deny，Pod 間流量須明確允許 | 沒有 default-deny，遭入侵的 Pod 可以看見所有鄰居 | [30](30/tw.md) |
| [ ] | DNS 記錄由 external-dns 管理，而非在 Route 53 手動處理 | 手動記錄會在服務刪除後繼續存在並指向空處 | [29](29/tw.md) |
| [ ] | 為 AWS 服務建立 VPC endpoints，每個 AZ 都有 NAT，egress 流量受到控制 | 經由單一 NAT 的 egress 同時是單點故障與成本項目 | [31](31/tw.md) |

## 6. 可觀測性

沒有此領域，事件處理就如同盲人摸象。資料不僅必須持續送出，也必須保存足夠時間並產生警示。

| 完成 | 項目 | 為何重要 | 章節 |
|---|---|---|---|
| [ ] | metrics-server 正常運作 | 沒有它，`kubectl top` 與 HPA 都無法運作 | [33](33/tw.md) |
| [ ] | 有 metrics 後端：Prometheus 或 Container Insights | 需要具有歷史資料的 metrics，而不只「此刻」的資料 | [33](33/tw.md) |
| [ ] | 從節點與 Pod 匯出日誌 | 留在節點上的日誌會隨節點一同消失 | [34](34/tw.md) |
| [ ] | 已審慎設定日誌 retention | 沒有計畫的 retention，意味著在分析時遺失日誌或產生多餘儲存 | [34](34/tw.md) |
| [ ] | 已為關鍵症狀設定警示，而非只有儀表板 | 無人查看的儀表板無法取代警示 | [33](33/tw.md) |
| [ ] | 在呼叫鏈重要之處使用 tracing（ADOT 或 X-Ray） | 在微服務中，故障原因不在顯示症狀的服務裡 | [36](36/tw.md) |

## 7. 運維

此領域區分了「叢集今天能運作」與「叢集能撐過升級與故障」。

| 完成 | 項目 | 為何重要 | 章節 |
|---|---|---|---|
| [ ] | 有叢集與附加元件升級計畫，已清除已淘汰的 API | 已淘汰的 API 會在最不恰當的時候阻擋升級 | [37](37/tw.md) |
| [ ] | 已了解 rollback readiness：回復窗口與順序皆已確定 | 回復應預先規劃，而不是在失敗的升級期間才構想 | [39](39/tw.md) |
| [ ] | PDB 與 topology spread 可在 drain 與升級期間保護可用性 | 沒有它們，節點升級會一次移除服務的所有副本 | [40](40/tw.md) |
| [ ] | PDB 不會永久阻擋 drain（`maxUnavailable: 0` 是危險訊號） | 這種 PDB 會停止升級，看起來像卡住的 drain | [40](40/tw.md) |
| [ ] | AWS Backup 已為叢集狀態與持久磁碟區設定完成 | 只備份磁碟區無法還原叢集本身 | [41](41/tw.md) |
| [ ] | **阻擋性。** 已在 game day 實際測試 DR restore | 已設定卻從未驗證的 restore 是希望，不是備份 | [42](42/tw.md) |
| [ ] | 可依團隊與 namespace 檢視成本（OpenCost 或 Kubecost） | 看不見的成本無法最佳化，也沒有負責人 | [43](43/tw.md) |
| [ ] | GitOps 是 manifest 的事實來源（Argo CD 或 Flux） | 叢集與 git 的偏差意味著沒有人知道實際狀態 | [44](44/tw.md) |

## 8. 事件就緒度

最終領域：當一切故障時，重要的不是架構，而是定位速度。

| 完成 | 項目 | 為何重要 | 章節 |
|---|---|---|---|
| [ ] | 有節點無法加入叢集時的 runbook | 原因可能不同（IAM、SG、user data、kubelet），檢查順序可節省數小時 | [45](45/tw.md) |
| [ ] | 有網路故障 runbook：ENI、SG 與 NACL、DNS、unhealthy targets | 即使原因不同，網路故障看起來也相同 | [46](46/tw.md) |
| [ ] | 有存取問題 runbook：401 與 403 的差異、IRSA、Pod Identity、kubeconfig | 存取錯誤會同時阻礙工作與事件分析 | [47](47/tw.md) |
| [ ] | 節點上的 SSM 存取可運作，不需裸露的 SSH，且可登入節點 | 當節點已經故障時才設定節點存取為時已晚 | [45](45/tw.md) |
| [ ] | 已啟用 Control plane logging，並記錄 authenticator 與 API 日誌 | 沒有這些日誌，無法重建存取被拒的原因 | [21](21/tw.md) |
| [ ] | control plane 日誌可供分析，且不會過早刪除 | 日誌必須在分析時可用，而不是只在設定時可用 | [34](34/tw.md) |

## 計分與結果處置

計算方式如下：

- 每完成一項得一分，最高 51 分。各領域同等重要：網路不比儲存重要，一個領域的高分也不能彌補另一個領域的缺口。
- 有三個項目標記為**阻擋性**：DR restore 未經測試、叢集僅一人可存取、網路中沒有 default-deny NetworkPolicy。
- 若至少一個阻擋性項目尚未完成，無論總分為何，等級都不得高於第二級。阻擋性項目不是「扣一分」，而是正式流量的停止條件。

接著將未完成項目轉化為具有優先級的技術債清單：

| 優先級 | 應納入的項目 | 處置方式 |
|---|---|---|
| 上線前 Must have | 受支援的版本、存取權不只一人、control plane 稽核與日誌、default-deny NetworkPolicy、祕密不在 manifest 中、已測試的 restore、PDB 不阻擋升級 | 在啟用正式流量前完成：首次事件或入侵的代價高於延後上線 |
| 前幾週重要 | right-sizing requests、Spot 混合策略、日誌 retention、警示、升級計畫、VPC endpoints | 上線後立即建立任務，指派負責人與期限 |
| Nice to have | 微服務 tracing、詳細成本分攤、適用於叢集群的成熟 GitOps | 已在正式環境中迭代完成，不阻擋上線 |

技術債清單應以有負責人與期限的明確任務記錄。「以後某個時候」表示該項尚未完成，且在下次填寫時仍會出現在同一處。

接著對結果採取以下行動：

- 為各領域指派 ownership：網路、安全性與成本皆有負責人，負責確保其項目已完成且不會退化。
- 每次正式上線前填寫表單：新叢集或新的大型服務，必須在「must have」優先級完整且明確完成後才能上線。
- 將結果連結至 game day 與升級：把 DR restore 與升級計畫的驗證結果帶回表單，標記為已確認或失敗的項目，而非承諾。
- 與上一次結果比較：重要的不是總分，而是哪些項目已完成、哪些又回到未完成，以及原因為何。

## 本問卷的限制

- 它無法取代架構審查：可看見就緒度軸向，但看不見設計決策。
- 它評估的是實務是否存在，而非其品質：已啟用的稽核與有用的稽核得分相同，差異只有在事件分析時才能看出。
- 它不涵蓋應用程式部分：服務程式碼與資料結構不在表單範圍內。
- 分數無法在用途不同的叢集之間比較：非正式環境叢集不需要某些項目，該處的低分不代表有問題。
