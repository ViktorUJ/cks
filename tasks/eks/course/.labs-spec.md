# Стандарт лабораторной работы курса EKS (для авторов и сабагентов)

Рабочий файл. Каждая лаба курса собирается строго по этому стандарту. План лаб и их
привязка к главам - в `.labs-plan.tsv`. Обязательные сценарии отдельных лаб - в
`.content-notes.md`. Нумерация курсовых лаб `101+`. Существующие лабы EKS `01-04` в курс
НЕ входят и НЕ редактируются.

## Что такое курсовая лаба

Практическая работа в живом кластере EKS в аккаунте AWS читателя. Инфраструктура
разворачивается через Terragrunt одной командой, задания решаются на рабочей машине
(worker) по SSH, результат проверяется автоматически командой `check_result`. Удаление -
одной командой. Это не экзамен (экзамена по EKS нет), а отработка эксплуатации.

## Инварианты (жёсткие, как у глав)

- Только дефис `-`, длинное тире НЕ использовать НИКОГДА.
- НЕ писать «экзамен», «на экзамене», «для экзамена». Формулировка заданий -
  «продакшн-стиль»: короткая задача плюс критерии приёмки.
- Цены в долларах не приводить, говорить о структуре стоимости.
- Ссылки на главы словами: `(глава N)` или markdown-ссылкой на `../../course/NN/ru.md`
  в разделе «Цель».
- Диаграммы mermaid: не больше 8 узлов, `style` только на существующие узлы.
- Строки прозы <= 95 символов (таблицы и команды могут быть длиннее).
- Команды и флаги только существующие, проверенные по docs.aws.amazon.com и CLI reference.
- Не выдумывать поля API, версии аддонов, имена политик.

## Структура директории лабы

Каждая лаба - папка `tasks/eks/labs/<NNN>/`. Запуск: `TASK=<NNN> make run_eks_task`
(Makefile копирует содержимое папки в terragrunt-окружение). Состав повторяет рабочие
лабы EKS `02/03`:

```
<NNN>/
  env.hcl                         # регион, версии, сеть, prefix, stack_name
  README_RU.MD                    # полный текст лабы (русский, единственный пока)
  vpc/terragrunt.hcl              # vpc_v3
  ssh-keys/terragrunt.hcl         # ssh-keys
  eks_control_plane/terragrunt.hcl# eks_v2_control_plane
  eks_fargate_system/terragrunt.hcl  # eks_v2_fargate (kube-system + karpenter на Fargate)
  eks_addons/terragrunt.hcl       # eks_v2_addons (coredns, kube-proxy, vpc-cni, pod-identity)
  eks_karpenter/terragrunt.hcl    # eks_v2_karpenter (контроллер)
  eks_karpenter_default_vng/terragrunt.hcl  # eks_v2_karpenter_vng: дефолтный NodePool
  worker/terragrunt.hcl           # eks_v2_work_pc: рабочая машина, тесты, check_result
  worker/files/worker.sh          # boot-скрипт задачи (сидинг манифестов, если нужен)
  worker/files/tests.bats         # автопроверка (check_result = bats этого файла)
  worker/files/solutions/1.MD     # эталонное решение (русский)
  worker/files/tasks/*.yaml       # заготовки манифестов (если нужны студенту)
```

Дополнительные компоненты по потребности лабы (брать из рабочих лаб 02/03):
- `eks_addon_ebs_irsa/` - `eks_v2_ebs_irsa` (EBS CSI + IRSA) для сторедж-лаб (106).
- второй `eks_karpenter_*_vng/` - отдельный NodePool (мониторинг, spot, taints).

Базовый набор (vpc + ssh-keys + control_plane + fargate_system + addons + karpenter +
default_vng + worker) даёт кластер, где системные поды на Fargate, а рабочие ноды поднимает
Karpenter. Это отражает разделение вычислений из главы 9.

## Правила terragrunt (не изобретать)

- Все `terragrunt.hcl` копируются из рабочих лаб `02/03` без изменения `source` и
  `dependency`. Меняются только `inputs`, специфичные для лабы.
- `source` модулей: `../../..//modules/<name>/` - НЕ трогать.
- Ветку для URL задавать ОДНОЙ переменной в `env.hcl`, а не хардкодить в terragrunt:
  - в `env.hcl`: `git_branch = "<branch>"` и
    `raw_base_url = "https://raw.githubusercontent.com/ViktorUJ/cks/refs/heads/${local.git_branch}"`;
    `questions_list`/`solutions_scripts` тоже строить через `${local.git_branch}`.
  - в `worker/terragrunt.hcl`:
    `test_url = "${local.vars.locals.raw_base_url}/tasks/eks/labs/<NNN>/worker/files/tests.bats"`,
    `task_script_url = "${local.vars.locals.raw_base_url}/.../worker.sh"`.
  - ВАЖНО: worker тянет эти файлы по HTTP с GitHub при загрузке. Пока лаба в разработке,
    `git_branch` = рабочая ветка (например `AG-155`), и ветку надо запушить, иначе воркер
    получит `404: Not Found` вместо тестов. ПЕРЕД МЕРЖЕМ в master поменять `git_branch` на
    `master` (одна правка в `env.hcl`).
- `env.hcl`: `prefix = "eks-task<NNN>"`, `stack_name = "eks<NNN>"`, регион
  `eu-central-1`, версия control plane `1.36` (в `eks_control_plane`), `k8_version = "1.36.0"`
  (kubectl на worker). Версии аддонов под 1.36 (проверено по docs.aws.amazon.com):
  kube-proxy `v1.36.0-eksbuild.14`, coredns `v1.14.3-eksbuild.3`, vpc-cni `v1.21.1-eksbuild.1`,
  eks-pod-identity-agent `v1.3.10-eksbuild.2` (vpc-cni и pod-identity к минору k8s не привязаны).
  Если версия курса изменится - kube-proxy и coredns обязаны совпадать с минором кластера.

6. `## Инфраструктура` - таблица компонентов Terragrunt (vpc, eks, worker...).
7. `## Развёртывание` - `TASK=<NNN> make run_eks_task`, подключение по SSH,

8. `## Задания` - блоки в формате таблицы (см. ниже), сквозная нумерация.
9. `## Проверка результата` - `check_result`.
10. `## Решение` - ссылка на `worker/files/solutions/1.MD`.
11. `## Удаление` - `TASK=<NNN> make delete_eks_task`.

Принцип «от симптома» (как в главах): в каждой лабе желателен хотя бы один шаг, где инженер
намеренно вызывает симптом (под в `Pending`, ошибка планирования, отказ доступа) и объясняет
причину. Объяснение сохраняется в файл-артефакт `/var/work/tests/artifacts/<N>/...`, а тест
проверяет и симптом (состояние объекта), и ключевые слова в артефакте. Это тренирует «читать
границу ответственности», а не только механически проверять `kubectl get`.

Формат одного задания (как в лабах CKA 101, но без «экзамена»):

```
---
|        **N**        | **Короткий заголовок**                                      |
| :-----------------: | :---------------------------------------------------------- |
| Что делаем          | Постановка задачи. Точные имена объектов, namespace, образы, порты. |
| Критерии приёмки    | - пункт 1;<br/>- пункт 2. |

```

## tests.bats (автопроверка)

- Шебанг `#!/usr/bin/env bats`. Первая строка тела: `export KUBECONFIG=/home/ubuntu/.kube/config`.
- Кластер один, поэтому `--context` НЕ используем (kubeconfig от `aws eks update-kubeconfig`
  уже сделал нужный контекст текущим).
- Тест `@test "0 Init"` очищает счётчики: `echo '' > /var/work/tests/result/all` и
  то же для `/var/work/tests/result/ok`.
- Каждый содержательный тест: `echo '<вес>' >> /var/work/tests/result/all`, при успехе
  `echo '<вес>' >> /var/work/tests/result/ok`. Последняя строка теста - булево условие
  для bats (`[ "$result" == "0" ]`).
- ВАЖНО (errexit): bats выполняет тест с `set -e`, поэтому если проверка ждёт ОТСУТСТВИЯ
  объекта, присваивание обязано гаситься: `var=$(kubectl get ... 2>/dev/null || true)`. Без
  `|| true` тест падает именно в успешном случае (`kubectl get` на удалённый объект вернёт 1).
  Проверять по всем тестам, где успех означает пустое значение (`-z "$var"`).
- Идемпотентность: тесты не меняют состояние кластера без необходимости; чтение через
  `kubectl ... -o jsonpath`. Для проверки, что под НЕ на Fargate - имя ноды не начинается
  с `fargate-`. Файлы-артефакты студент кладёт в `/var/work/tests/artifacts/<N>/...`.
- `check_result` суммирует веса и печатает процент (движок в модуле worker, не трогаем).

## Удаление стенда: ресурсы, созданные контроллерами (ОБЯЗАТЕЛЬНО)

Если лаба создаёт AWS-ресурсы через контроллеры в кластере (Service типа LoadBalancer или
Ingress через AWS Load Balancer Controller, Gateway API, VPC Lattice, external-dns, Karpenter
вне NodePool из terraform), этих ресурсов НЕТ в state terraform. Порядок удаления критичен:

- сначала удалить объекты Kubernetes (Service, Ingress, Gateway, HTTPRoute) и дождаться, пока
  контроллер сам вызовет удаление в AWS (finalizer держит объект, пока ресурс не снесён);
- только потом `TASK=<NNN> make delete_eks_task`.

Если сделать наоборот, контроллер исчезает вместе с кластером, балансировщик остаётся
осиротевшим, его ENI держат подсети и security groups, и `terragrunt destroy` зависает в
`Still destroying...` на десятки минут (проверено на лабе 120: SG не удалялась, пока жил NLB).
Отдельно: правило в ЧУЖОЙ security group со ссылкой `--source-group <sg>` тоже не даёт удалить
целевую SG - если лаба просит добавить такое правило, в разделе удаления должен быть
`revoke-security-group-ingress`.

Так же ведут себя ресурсы, созданные студентом вручную через AWS CLI: IAM-роли (живут вне
региона, `destroy` их не видит, при повторном запуске лабы `create-role` даст
`EntityAlreadyExists` - проверено на лабах 102 и 121), security groups в VPC стенда (не дают
удалить VPC), VPC endpoints, правила в чужих SG.

Отдельно - ресурсы, которые создают CSI-драйверы и сервисы по объектам Kubernetes:
- динамические PVC: тома EBS и снапшоты за `VolumeSnapshot` создаёт и удаляет драйвер EBS CSI
  по факту удаления PVC. Снести кластер с живыми PVC - значит оставить тома `available`
  навсегда, они тарифицируются, и terraform о них не знает (найдено вживую: два тома от лабы
  106). PVC от `volumeClaimTemplates` не удаляются вместе со StatefulSet;
- EFS: драйвер создаёт access point на каждый PVC, лишние access points не дают удалить
  файловую систему (`FileSystemInUse`);
- AWS Backup: recovery points создаёт `start-backup-job`, и terraform НЕ МОЖЕТ удалить непустой
  vault. Удалять надо сначала вложенные точки, потом composite (`Parent recovery point cannot
  be deleted because it has child recovery points`). Restore дополнительно создаёт новый том
  EBS без тегов Kubernetes - его тоже удаляют руками (лаба 122);
- S3: объекты, записанные подами, terraform не удалит, а непустой бакет не удаляется (при
  версионировании нужны и версии, и delete markers).

Отдельный класс, найденный на лабе 128: ресурс создал КОНТРОЛЛЕР, но НЕ по объекту Kubernetes,
поэтому удаление объекта его не снимает. `Gateway` класса `amazon-vpc-lattice` уходит вместе с
сервисами VPC Lattice, а Service Network, созданная контроллером по флагу
`defaultServiceNetwork`, и её ассоциация с VPC остаются в `ACTIVE`. Ассоциация держит VPC, и
`destroy` встаёт на сети. Удалять надо руками и по порядку: сначала
`delete-service-network-vpc-association`, дождаться исчезновения ассоциации, потом
`delete-service-network`. Права на это у воркера есть (`vpc-lattice:DeleteServiceNetwork`,
`DeleteServiceNetworkVpcAssociation`). Проверять в любой лабе, где контроллер получает имя
AWS-ресурса флагом установки, а не из объекта Kubernetes.

Ещё один тихий остаток - target groups. Если снести кластер раньше, чем LBC уберёт `Ingress`,
`Service` типа LoadBalancer или `Gateway`, балансировщик может уйти, а target group останется
(найдены осиротевшие TG от лаб 108 и 120). Денег они не стоят и `destroy` не блокируют, но
копятся и расходуют квоту региона, поэтому в разделе удаления полезно проверять не только
`describe-load-balancers`, но и `describe-target-groups`.

Отдельный класс - осиротевшие ENI. Если удалять стенд с ЖИВОЙ нагрузкой, Karpenter-нода
терминируется вместе с кластером, а вторичный ENI от VPC CNI (тег
`eks:eni:owner=amazon-vpc-cni`) остаётся в состоянии `available` и держит security group нод:
`destroy` зависает на `module.eks.aws_security_group.node[0]: Still destroying...` (проверено
на лабе 121). То же с `branch` ENI при security groups for pods. Поэтому лабы, где Karpenter
поднимает ноды, обязаны в разделе удаления сначала снимать нагрузку и ждать, пока EC2-ноды
уйдут (`kubectl get nodes | grep -v fargate` в цикле).

ЕСЛИ `run-all destroy` УПАЛ НА СЕРЕДИНЕ. Повторный запуск `make delete_eks_task` может даже не
начаться: terragrunt читает конфиги всех модулей, а у уже уничтоженных модулей нет outputs, и
зависимые конфиги падают с `... is a dependency of ... but detected no outputs`. Это не поломка
стенда, а особенность `run-all`. Лечится добиванием остатков по одному модулю, в обратном
порядке зависимостей, из каталога окружения (Makefile удаляет его после неудачного прогона,
поэтому каталог сначала пересоздают копией лабы):

```bash
mkdir -p terraform/environments/eks-labs
cp -r tasks/eks/labs/<NNN>/* terraform/environments/eks-labs/
export TF_VAR_STACK_TASK=<NNN> TF_VAR_STACK_NAME=eks-labs TF_VAR_USER_ID= TF_VAR_ENV_ID=
# порядок: сначала то, что зависит от кластера, потом кластер, потом сеть
cd terraform/environments/eks-labs/eks_fargate_system && terragrunt destroy -auto-approve
cd ../eks_control_plane && terragrunt destroy -auto-approve
cd ../vpc && terragrunt destroy -auto-approve
```

Значения `TF_VAR_USER_ID` и `TF_VAR_ENV_ID` должны совпадать с теми, что были при создании
(они входят в имя кластера: `eks<NNN>-<user>-<env>`). Проверено на лабе 122: так добиваются
остатки после падения на Fargate-профиле. Структурная альтернатива - добавить `mock_outputs`
с `mock_outputs_allowed_terraform_commands = ["destroy"]` в блоки `dependency`, тогда
`run-all destroy` станет перезапускаемым.

Транзиентная ошибка на destroy, не связанная с утечками: EKS сериализует изменения кластера,
поэтому пока идёт одно обновление (например удаление аддона), следующая операция отвечает
`409 ResourceInUseException ... currently has an update in progress`. Порядок зависимостей в
лабах при этом ПРАВИЛЬНЫЙ (`eks_addons` и `eks_addon_ebs_irsa` зависят от `eks_fargate_system`,
значит на destroy идут раньше него), но `DeleteAddon` возвращается до того, как кластер выйдет
из состояния UPDATING, и удаление Fargate-профиля попадает в это окно. Лечится не правкой
графа, а ретраем: в корневом `terraform/environments/terragrunt.hcl` заданы `retryable_errors`
на эти сообщения плюс `retry_max_attempts`/`retry_sleep_interval_sec`. Повторный запуск
`make delete_eks_task` тоже безопасен и идемпотентен.

Поэтому раздел `## Удаление` обязан содержать: блок-предупреждение, команды предварительной
очистки с ожиданием (`kubectl wait --for=delete ...`, ожидание исчезновения EC2-нод и ENI),
удаление созданных вручную IAM-ролей, SG и правил, и краткий рецепт разбора, если destroy
всё же зависает (найти ENI по `--filters Name=group-id` и по `Name=status,Values=available`,
найти и удалить осиротевший LB, посмотреть, какие SG ссылаются на целевую через
`Name=ip-permission.group-id`).

## Привязка к главам и маркер 🧪 (ОБЯЗАТЕЛЬНО, критерий готовности)

Лаба НЕ считается готовой, пока не привязана к курсу. Как только лаба рабочая:
1. В `.labs-plan.tsv` статус лабы `todo -> ready`.
2. В каждой главе из привязки: раздел `## Практика` заменить с «лабы пока нет» на ссылку
   на лабу (`../../labs/<NNN>/README_RU.MD`) с пометкой, что проверяется `check_result`.
3. В `README_RU.md` курса, в оглавлении, к строкам этих глав добавить значок `🧪`.
4. В `docs/labs.MD`, раздел EKS labs, добавить строку с лабой (ссылка на `README_RU.MD`).

Значок 🧪 ставится ТОЛЬКО у главы, чья курсовая лаба уже существует, и ТОЛЬКО в оглавлении
`README_RU.md`. В тексте самой главы (раздел `## Практика`) значок НЕ ставить: строка
начинается словами «Лаба курса к этой теме: ...». Причина - эмодзи в теле главы у части
читателей рендерится мусорным глифом. Проверка: `grep -c "🧪" <глава>/ru.md` = 0 у всех глав.
