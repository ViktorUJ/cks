# EKS コースのアーキテクチャ判断（ADR）

[コース目次](README_JP.md) · [用語集](GLOSSARY_JP.md)

## 使い方

ADR（Architecture Decision Record）は、単一の判断について、なぜそれを選んだか、
どのような選択肢があり、選択に何を支払うかを記す短い記録です。文書化そのものが目的ではなく、
1 年後に同じ議論を繰り返さず、新しくチームに加わった人が結果だけでなく理由を理解できるようにすることが目的です。

以下のテンプレートにはすでにコースの内容が記入されています。選択肢、その利点とコストは各章から
引用したものであり、ここで作り出したものではありません。ただし、**コンテキスト、ステータス、日付、判断そのものはエンジニアが**プロジェクトに合わせて記入します。
コースは、あなたのクラスタ群、コンプライアンス要件、プラットフォームチームの有無を知りません。

「却下した選択肢」は「悪い」ことを意味しません。コース内のほぼすべての分岐では両方の選択肢に有効性があり、
異なる前提条件では却下した方が正しくなります。そのために「見直し条件」欄があります。

## ADR-01. コンピューティング: EKS Auto Mode 対独自の Karpenter スタック

ステータス: _エンジニアが記入_
日付: _エンジニアが記入_

**コンテキスト。** 選択前に答えること:

- セキュリティ上、ノードイメージ（認証済み AMI、独自 bootstrap）が必要か。
- デバッグのため、または DaemonSet のノードエージェントのためにノードへのアクセスが必要か。
- VPC CNI 以外と、NodePool だけでなく Karpenter コントローラー自体の制御が必要か。
- コストはどれほど重要か。EC2 に上乗せされる管理料金を許容できるか。
- ノードを運用する準備ができたチームがいるか、それとも本当に運用を最小化することが目標か。

**検討した選択肢。**

| 選択肢 | 得られるもの | 支払うもの | 適する場合 |
|---|---|---|---|
| EKS Auto Mode | appliance としてのノード: Bottlerocket、SELinux enforcing、read-only root、最長 21 日のローテーション、組み込みの Karpenter、IPAM、network policy、EBS CSI、ELB、Pod Identity | EC2 に上乗せされる管理料金（Reserved および Savings Plans の割引対象外）、SSH と SSM はなし、デフォルトの NodePool と NodeClass は変更不可、別の CNI は使用不可 | ノード運用の最小化が目的で、ノードイメージとノードアクセスの要件がない |
| 独自スタック: managed node groups または self-managed と独自の Karpenter | 独自の launch template と AMI、ノードアクセス、任意の CNI、Karpenter のバージョンと設定を完全に所有 | ノード、アドオン、アップグレード、割り込み処理を自分たちで担い、EC2 にのみ支払う | Auto Mode が満たせない要件がある、または経済性が管理料金を許容しない |

**採用した判断の影響。**

- 得られるもの: クラスタごとに単一のノード運用モデルと、AWS とチームの間で予測可能な
  責任境界。
- 支払うもの: Auto Mode ではコンテナ、クラスタと VPC の設定、PVC 由来のボリューム、
  ロードバランサーは自分たちの責任として残る。独自の NodePool はデフォルトの制約を継承しないため、
  制限とインスタンスタイプを手動で設定する必要があり、そうしなければプールは上限なく拡大する。

**判断。** _自プロジェクト向けに記入_

**見直し条件。** 認証済みノードイメージの要件が発生した。sidecar として動作しないノードエージェントが
必要になった。主要 CNI として Cilium が必要になった。disruption budgets がノード寿命より長い更新を
妨げるようになった。ノード置換によるスパイクと管理料金が請求額で目立つ規模までクラスタ群が成長した。

**参照。** [第 9 章](09/jp.md): コンピューティングタイプ、9.6-9.8 節。
[第 10 章](10/jp.md): launch template と独自 AMI。[第 12 章](12/jp.md): NodePool と
 disruption。[第 43 章](43/jp.md): コストの分析。

## ADR-02. Pod アイデンティティ: IRSA 対 EKS Pod Identity

ステータス: _エンジニアが記入_
日付: _エンジニアが記入_

**コンテキスト。** 選択前に答えること:

- クラスタはいくつあり、ロールはクラスタ間で移動するか。
- Fargate または Windows ノード上のワークロードがあるか。
- 同じロールで EKS 外部（EC2、ECS、Lambda）のアイデンティティが必要か。
- クロスアカウントが必要か。必要であればどの形式か。
- 既存クラスタの platform version は何か。

**検討した選択肢。**

| 選択肢 | 得られるもの | 支払うもの | 適する場合 |
|---|---|---|---|
| IRSA | STS を介する OIDC federation、EKS 外でも動作、クロスアカウントを直接利用可能、Fargate と Windows ノードをサポート | クラスタごとに IAM OIDC provider、クラスタごとに trust policy の書き換え、session tags を手動で設定 | Fargate、Windows、EKS 外のアイデンティティ、federation によるクロスアカウント |
| EKS Pod Identity | 全クラスタで `pods.eks.amazonaws.com` 向けの単一 trust policy、アノテーションなしで EKS API の関連付けにより紐付け、session tags と ABAC が標準で利用可能 | Amazon EC2 Linux ノードのみ、Fargate、Windows、Outposts、EKS Anywhere は非対応、アドオンエージェントと最小 platform version が必要 | EC2 ノード上の新規クラスタ、ロールを再利用するクラスタ群 |

**採用した判断の影響。**

- 得られるもの: Pod に権限を付与する統一方法と、ロールがどの ServiceAccount に
  紐付いているかについての、明確な唯一の情報源。
- 支払うもの: 混在するクラスタ群では両方のモデルを維持する必要がある。同一
  ServiceAccount に両方を設定すると IRSA が優先される。これは web identity が SDK チェーンで
  コンテナプロバイダーより先にあるためで、Pod Identity の関連付けは黙って無視される。

**判断。** _自プロジェクト向けに記入_

**見直し条件。** クラスタ群に Fargate プロファイルまたは Windows ノードが追加された。session tags による
ABAC の要件が生じた。Pod Identity の制限がドキュメントで縮小された。EKS 内外のワークロードで同じロールが
必要になった。

**参照。** [第 16 章](16/jp.md): IRSA と OIDC provider。[第 17 章](17/jp.md): Pod
Identity、比較と移行順序。

## ADR-03. ネットワーク: VPC CNI 対 Cilium（chaining または完全置換）

ステータス: _エンジニアが記入_
日付: _エンジニアが記入_

**コンテキスト。** 選択前に答えること:

- L7（HTTP、gRPC、Kafka）または DNS 名に対するポリシーが必要か。誰がそれを書くのか。
- Hubble レベルの Pod 間フローの可観測性が必要か。
- VPC における実際の Pod アドレス、security groups for pods、Pod ごとの Flow Logs は重要か。
- 他の手段では IPv4 不足を解消できないか。
- CNI のアップグレードとクラスタバージョンとの互換性をチームが所有する準備ができているか。

**検討した選択肢。**

| 選択肢 | 得られるもの | 支払うもの | 適する場合 |
|---|---|---|---|
| 組み込み NetworkPolicy を備えた VPC CNI | managed addon、AWS サポート、標準アップグレード、標準の `NetworkPolicy` L3/L4 と管理用の `ClusterNetworkPolicy`、実際の VPC アドレス | L7 ルールなし、FQDN によるポリシーなし、Cilium CRD と Hubble なし | L3/L4 での分離が必要で、VPC のアドレスモデルに満足している |
| CNI chaining モードの Cilium | `CiliumNetworkPolicy`、L7 と DNS ポリシー、Hubble。その一方で IPAM と VPC 統合は VPC CNI が担当 | Cilium の独自インストールと保守、2 つ目の CRD モデル、チーム教育 | L7 または DNS ポリシー、あるいは Hubble が必要で、アドレスモデルには満足している |
| 完全置換としての Cilium（ENI IPAM または cluster-pool） | 独自の IPAM、オプションの overlay と IPv4 不足からの脱却、ClusterMesh、eBPF による kube-proxy の置換 | アップグレードと互換性は自分たちの責任、AWS サポートは限定的になる、overlay では実際の Pod アドレス、SG for pods、Flow Logs 内の Pod アドレスを失う | overlay またはマルチクラスタネットワークが必要、あるいは ENI モデルで満たせない要件がある |

**採用した判断の影響。**

- 得られるもの: AWS サポートの対象範囲と、プラットフォームチームが所有する範囲との明示的な境界。
- 支払うもの: フラグを切り替えて CNI を変更することはできない。CNI は Pod の作成時に割り当てられるため、
  移行は新しいノードプールまたは新しいクラスタを介した blue/green になる。障害診断は CNI のツールに
  移り、Pod 起動時のポリシーなしの時間枠も別途考慮する必要がある
  （`NETWORK_POLICY_ENFORCING_MODE` の `standard` モードは default allow となる）。

**判断。** _自プロジェクト向けに記入_

**見直し条件。** L7 または DNS 名によるポリシーの要件が発生した。Pod 間フローのマップが必要になった。
IPv4 不足を第 7 章の手段で解決できなくなった。複数クラスタに共通の Pod Network が必要になった。
iptables kube-proxy がボトルネックになった。

**参照。** [第 8 章](08/jp.md): 代替 CNI、移行のコスト、移行方法。
[第 6 章](06/jp.md): ENI による Pod アドレッシング。[第 7 章](07/jp.md): アドレス不足。
[第 30 章](30/jp.md): 本番環境のネットワークポリシー。

## ADR-04. ノードのオートスケーリング: Cluster Autoscaler 対 Karpenter

ステータス: _エンジニアが記入_
日付: _エンジニアが記入_

**コンテキスト。** 選択前に答えること:

- クラスタは Auto Mode か独自スタックか（Auto Mode では問いは解決済みで、Karpenter はすでに含まれる）。
- ワークロードはどれほど多様で、維持すべき node group はいくつになるか。
- トラフィック急増への迅速な反応が必要か。
- 他のクラウドのクラスタと単一ツールで統一する必要があるか。
- CA はすでに導入・調整済みか。また本当に問題になっているか。

**検討した選択肢。**

| 選択肢 | 得られるもの | 支払うもの | 適する場合 |
|---|---|---|---|
| Cluster Autoscaler | Auto Scaling group 上で動作、多数のプロバイダーで統一可能、新しい CRD なしの慣れた運用 | Pod ではなくグループレベルの反応、タイプの組み合わせは launch template で固定、ASG 層のため低速、空のノードは削除するが高密度化はしない | 単純で予測可能なクラスタ、マルチクラウド統一、稼働中のインストール |
| Karpenter | EC2 を直接呼び出し、特定の Pod に合わせてインスタンスタイプを選択、積極的な consolidation、spot 向けのタイプ分散 | 独自の CRD `NodePool` と `EC2NodeClass`、コントローラーのバージョンと設定を所有、AWS-first | EKS 上の新規クラスタ、多様なワークロード、速度と高密度パッキングの要件 |

**採用した判断の影響。**

- 得られるもの: ノードの作成と削除を担う単一のメカニズムと、クラスタ群の制限を設定する単一の場所。
- 支払うもの: 両者を同時に維持できるのは、異なるノードセット上で、一時的な移行モードとしてのみである。
  そうしなければ scale-down の判断を巡って競合する。移行は稼働中ノード上の Pod を移動するのではなく、
  新しいノードを介して行う。

**判断。** _自プロジェクト向けに記入_

**見直し条件。** node group の乱立が増えて管理不能になった。低いパッキング効率による無駄が請求額で
目立つようになった。トラフィック急増への反応が SLO に収まらなくなった。クラスタが Auto Mode に移行した。
単一ツールを要件とする他クラウドのクラスタが追加された。

**参照。** [第 11 章](11/jp.md): アプローチの比較と選択チェックリスト。
[第 12 章](12/jp.md): NodePool、consolidation、disruption budgets。
[第 13 章](13/jp.md): spot。[第 9 章](09/jp.md): Auto Mode との関係。

## ADR-05. クラスタ群の GitOps: hub-and-spoke 対分散化

ステータス: _エンジニアが記入_
日付: _エンジニアが記入_

**コンテキスト。** 選択前に答えること:

- 現在クラスタ群にいくつのクラスタがあり、今後いくつが見込まれるか。
- hub または hub との接続を失った場合に、クラスタの自律性が必要か。
- クラスタ群全体を対象とする統一された概要パネルが必要か。
- エージェントを更新するのは誰か。チームはそのバージョンの乖離に備えているか。
- クラスタ境界を越える reconciliation トラフィックのコストはいくらか。

**検討した選択肢。**

| 選択肢 | 得られるもの | 支払うもの | 適する場合 |
|---|---|---|---|
| Hub-and-spoke | hub 上の 1 つの Argo CD または Flux インスタンス、各クラスタへのエージェント配置は不要、matrix を通じた cluster と git generator を持つ ApplicationSet がアドオンセットをクラスタ群全体に展開、統一された概要 | hub は障害ドメイン: spoke 上のワークロードは動作するが、コミットの適用、self-heal、ロールバックはクラスタ群全体で停止する。ネットワーク経由の reconciliation はレイテンシ、送信トラフィック料金、接続への依存を生む | 運用の単純さと統一された概要が重視される、小規模から中規模のクラスタ群 |
| Hub のシャーディング | クラスタを application-controller レプリカ間に分散し、レプリカ数を `ARGOCD_CONTROLLER_REPLICAS` にも複製 | 依然として 1 つの障害ドメイン。hash-based 分散は不均一で、round-robin の方が均一 | クラスタ群が 1 コントローラーを超えたが、クラスタの自律性は不要 |
| 分散化 | hub は基盤とローカルエージェントのみを展開し、その後はクラスタ自身が Git から取得するため、hub を失っても自律的に動作 | エージェント数はクラスタ数と同数であり、更新と設定が必要、統一パネルはなく、エージェントのバージョンは乖離する | 大規模なクラスタ群、または自律性が厳格に求められる場合 |
| argocd-agent | 中央の 1 つの Argo CD インスタンスがすべてのクラスタの `Application` を把握するが、同期は spoke 側のエージェントが取得 | `argoproj-labs` プロジェクトであり、Argo CD コアではなく incubation 段階。トポロジーは依然として hub-and-spoke | 逆方向のフローのために incubation プロジェクトを使うことを受け入れられる |

**採用した判断の影響。**

- 得られるもの: hub が利用不能な場合にデリバリーで何が起こるかという問いへの明確な答え。
- 支払うもの: IaC と GitOps の境界はどのトポロジーでも必須である。インフラストラクチャ
  （VPC、クラスタ、node groups、IAM）は Terraform を経由し、アドオンとワークロードは GitOps を経由する。
  混在させると、Deployment の修正のためにクラスタを再作成するか、同じクラスタに存在するエージェントに関する
  鶏と卵の問題のどちらかになる。

**判断。** _自プロジェクト向けに記入_

**見直し条件。** クラスタ群が成長し、1 コントローラーでは対処できなくなった。hub を失っても reconciliation を
継続する要件が発生した。reconciliation の送信トラフィック料金が目立つようになった。argocd-agent が
incubation を終えた。

**参照。** [第 44 章](44/jp.md): クラスタ群のトポロジー、44.6 節。
[第 32 章](32/jp.md): クラスタ群。[第 4 章](04/jp.md): IaC と Terraform。
[第 31 章](31/jp.md): トラフィックコスト。[第 38 章](38/jp.md): blue/green 移行。

## ここで意図的に決めないこと

コースでは、いくつかの分岐をアーキテクチャ上のものとは見なしません。そこでは技術的な差はおおむね同等で、
企業のコンテキストが判断を決めるためです。Argo CD と Flux の選択は、ツールの性質ではなく、チームがすでに
使えるものと必要なインターフェースの問題です。独自の Prometheus と managed サービスの選択は、メトリクス収集の
アーキテクチャではなく、誰がオンコールを担当し、保存にいくらかかるかの問題です。イメージレジストリ、
シークレットツール、アカウント配置の選択も同様です。これらは組織上の境界です。本番リリース前に確認すべき
事項の一覧は、[第 48 章](48/jp.md) にまとめています。
