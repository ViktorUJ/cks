# EKS成熟度マトリクス: 準備状況アンケート

[コース目次](README_JP.md) · [第48章](48/jp.md) · [用語集](GLOSSARY_JP.md)

これは第48章に対応する実務用フォームです。同じ準備状況ドメインを、チームで実施して技術的負債のリストへ変換するアンケートとしてまとめています。ここに新しい内容はありません。

## 実施方法

- 8つのドメインを何も飛ばさず順に確認してください。各ドメインは運用の独立した軸であり、一つの軸の弱さを別の軸の強さで補うことはできません。
- 各項目には正直に、はいまたはいいえで答えてください。「一部だけ」「ほぼ」「設定済みだが未検証」は、いいえとして扱います。
- 一人ではなくチームで記入してください。ネットワーク、セキュリティ、コストの責任者にはそれぞれ異なる見落としがあり、「たぶん準備できている」は意見が交わる場所で明らかになります。
- 目的はスコアではありません。スコアはレベルを把握するためだけのもので、アンケートの成果は、未対応項目を担当者と期限付きで列挙したリストです。
- 未対応の項目はすべて、タスク付きの既知リスクとして記録してください。フォームを良く見せるために黙って飛ばしてはいけません。
- 四半期ごと、および大きな変更の後に再実施してください。バージョンは古くなり、負荷は増え、昨日の「対応済み」は今日には穴になり得ます。
- このフォームは IaC と並べてリポジトリに置き、変更が pull request で見えるようにします。

## レベル尺度

アンケートには合計51項目あります。対応済みの項目1つが1点です。

| レベル | 点数 | 意味 | 次に行うこと |
|---|---|---|---|
| レベル1. 不安定で手作業 | 0-20 | 何も壊れない間だけクラスターは動作します。多くがクリック操作で作られ、復旧とセキュリティ境界は未検証です | 本番トラフィックを有効にする前に、ブロッカー項目と「must have」列全体を対応する |
| レベル2. 管理可能 | 21-33 | 基盤はあります。クラスターはコードで作られ、アクセスとコンピューティングは意識されていますが、検証とオブザーバビリティは個人に依存しています | セキュリティと運用を仕上げる: 監査、retention、アラート、アップグレード計画 |
| レベル3. 再現可能で可観測 | 34-44 | プラクティスが定着して再現可能です。アップグレード、バックアップ、restore を実施済みで、インシデントを runbook により局所化できます | 「最初の数週間で重要」の優先度を完了し、各ドメインに ownership を割り当てる |
| レベル4. 自律的な耐障害性 | 45-51 | リリース間で準備状況が劣化しません。DR は訓練で検証され、コストとトラフィックは管理され、GitOps が信頼できる情報源です | レベルを維持する: 四半期ごとのアンケート、game day、「nice to have」の仕上げ |

ブロッカー項目が一つでも未対応の場合、合計点がいくつであってもレベルは2を超えられません。このルールは「集計と結果への対応」で説明します。

## 1. クラスターと control plane

基盤です。バージョンがサポート外だったりサブネットが一つの AZ に設定されていたりすれば、他は重要ではありません。

| 対応済み | 項目 | 重要な理由 | 章 |
|---|---|---|---|
| [ ] | Kubernetes バージョンが standard support の範囲内 | サポート外のバージョンは、設定で解消できないリスクです | [38](38/jp.md) |
| [ ] | サポート終了の1か月前に慌てるのではなく、バージョンアップ計画がある | 期限に追われたアップグレードはロールバックの余地なしに実施されます | [38](38/jp.md) |
| [ ] | Endpoint access を検討済み: public または private、用途に適した source ranges | API へのアクセスモードはクラスターの攻撃対象領域を決めます | [02](02/jp.md) |
| [ ] | クラスターのサブネットが3つの AZ にあり、IP 計画に Pod 増加の余裕がある | 単一 AZ は単一障害点であり、IP 不足は Pod のスケジューリングを止めます | [06](06/jp.md) |
| [ ] | クラスターをコンソールのクリックではなくコード（Terraform または eksctl）で作成した | 手作業のクラスターは DR 時に再作成できず、pull request でレビューもできません | [04](04/jp.md) |
| [ ] | リソースにチーム、環境、cost allocation のタグを付けた | タグがなければコストと所有権をチームごとに分解できません | [43](43/jp.md) |

## 2. コンピューティング

ノードは完全にエンジニアの責任範囲です。耐障害性も請求額もここで決まります。

| 対応済み | 項目 | 重要な理由 | 章 |
|---|---|---|---|
| [ ] | ノード戦略を意識して選択した: Auto Mode、Karpenter、または managed node groups | デフォルトのままにすると、価格と耐障害性への影響が不明確になります | [09](09/jp.md) |
| [ ] | 中断に耐えられるワークロードに Spot の混在を適用した | Spot は中断を許容できる負荷でコストを削減します | [13](13/jp.md) |
| [ ] | spot プールのインスタンスタイプを分散した | 分散しない Spot は節約ではなく、容量を一度に失うリスクです | [13](13/jp.md) |
| [ ] | requests を「勘」ではなく実測に基づいて設定した（right-sizing） | 過大な requests は使わないリソースに支払い、過小なものはワークロードを壊します | [14](14/jp.md) |
| [ ] | Karpenter の disruption と consolidation を設定し、drift を放置していない | consolidation がなければノード群が膨らみ、drift はコードとの差異を蓄積します | [12](12/jp.md) |
| [ ] | ノードあたりの Pod 密度を ENI と IP の制限に合わせた | 密度を上げすぎると、明確な理由なしに Pod が `Pending` のままになります | [14](14/jp.md) |

## 3. アイデンティティとセキュリティ

最も広いドメインであり、静かな穴の最も多い原因です。項目ごとに確認してください。

| 対応済み | 項目 | 重要な理由 | 章 |
|---|---|---|---|
| [ ] | Pod は静的キーなしに IRSA または Pod Identity を通じて AWS へアクセスする | Pod 内の長期間有効なキーは、イメージまたはログとともに漏えいします | [16](16/jp.md) |
| [ ] | **ブロッカー。** クラスターへのアクセスが cluster creator だけに限られず、access entries を設定した | 一人だけがアクセスできるクラスターは、その人とともに失われます | [05](05/jp.md) |
| [ ] | シークレットはマニフェストではなく Secrets Manager または SSM（External Secrets、CSI）から取得する | マニフェスト内のシークレットは git とリポジトリのすべてのコピーに入ります | [18](18/jp.md) |
| [ ] | ノードと Pod をハードニングした: IMDSv2、hop limit、Pod Security Admission | Pod からノードメタデータへアクセスできると、Pod はノード権限を得ます | [19](19/jp.md) |
| [ ] | ECR でイメージをスキャンし、ベースイメージを信頼できるソースから取得する | 脆弱なベースイメージはすべてのサービスへ一度に広がります | [20](20/jp.md) |
| [ ] | control plane の監査を有効化した: ログに api、audit、authenticator がある | 監査はインシデント前に有効にします。事後にはログは残っていません | [21](21/jp.md) |
| [ ] | Kyverno または Gatekeeper のポリシーで危険なマニフェストパターンを防ぐ | 人によるレビューでは、ポリシーが常に検出するものを見逃します | [22](22/jp.md) |

## 4. ストレージ

小さいながら油断できないドメインです。EBS のデフォルトと未検証のボリュームバックアップは、突然問題になります。

| 対応済み | 項目 | 重要な理由 | 章 |
|---|---|---|---|
| [ ] | デフォルトの StorageClass が旧式の gp2 ではなく gp3 である | gp2 は慣性でデフォルトに残り、性能と価格で劣ります | [23](23/jp.md) |
| [ ] | `volumeBindingMode: WaitForFirstConsumer` を設定した | 設定しないとボリュームが誤った AZ に作成され、Pod は永久に `Pending` のままになります | [23](23/jp.md) |
| [ ] | 永続ボリュームをバックアップに含める | バックアップのないボリュームとは、一つのコピーにしか存在しないデータです | [41](41/jp.md) |
| [ ] | ボリュームスナップショットを作成だけでなく復元で検証した | 未検証のスナップショットは、スナップショットがないことと同じです | [41](41/jp.md) |
| [ ] | ワークロードの移行とスケジューリングで EBS の AZ への結び付きを考慮した | マニフェストをそのまま移すと、まさにボリュームで壊れます | [23](23/jp.md) |
| [ ] | ReadWriteMany が必要な場所では EFS または FSx という共有ストレージを意識して選択した | EBS は ReadWriteMany を提供しないため、設計段階で回避策を講じます | [24](24/jp.md) |

## 5. ネットワークとトラフィック

このドメインの問題は外から見えます。サービスに到達できない、egress が開いている、全 AZ をまたいでトラフィックが流れる、といった状態です。

| 対応済み | 項目 | 重要な理由 | 章 |
|---|---|---|---|
| [ ] | AWS Load Balancer Controller を通じて NLB のロードバランサーを作成する | 手作業のロードバランサーはクラスターの状態と乖離します | [26](26/jp.md) |
| [ ] | Ingress が意図した target-type で ALB を通じて動作する | target-type はトラフィック経路と drain 時の挙動を決めます | [27](27/jp.md) |
| [ ] | ACM による TLS 証明書を使用し、ロードバランサーで HTTPS を終端する | 手作業の証明書は最も都合の悪いときに期限切れになります | [27](27/jp.md) |
| [ ] | **ブロッカー。** default-deny の NetworkPolicy があり、Pod 間トラフィックを明示的に許可する | default-deny がなければ、侵害された Pod はすべての隣接 Pod を見られます | [30](30/jp.md) |
| [ ] | DNS レコードを Route 53 で手作業ではなく external-dns により管理する | 手作業のレコードはサービス削除後も残り、空の宛先を指します | [29](29/jp.md) |
| [ ] | AWS サービス向けの VPC endpoints、AZ ごとの NAT を用意し、egress トラフィックを管理する | 単一 NAT 経由の egress は、単一障害点であると同時にコスト要因です | [31](31/jp.md) |

## 6. オブザーバビリティ

このドメインがなければ、インシデントは手探りで調査します。データは収集するだけでなく、必要な期間保持し、アラートを発生させなければなりません。

| 対応済み | 項目 | 重要な理由 | 章 |
|---|---|---|---|
| [ ] | metrics-server が動作している | これがなければ `kubectl top` も HPA も応答しません | [33](33/jp.md) |
| [ ] | Prometheus または Container Insights のメトリクスバックエンドがある | メトリクスには「今この瞬間」だけでなく履歴が必要です | [33](33/jp.md) |
| [ ] | ノードと Pod からログを外部へ送っている | ノードに残ったログは、ノードとともに消えます | [34](34/jp.md) |
| [ ] | ログの retention を意識して設定した | 計画のない retention は、調査でログを失うか、余分なストレージを使う結果になります | [34](34/jp.md) |
| [ ] | ダッシュボードだけでなく、主要な症状に対するアラートを設定した | 誰も見ないダッシュボードはアラートの代わりになりません | [33](33/jp.md) |
| [ ] | 呼び出しチェーンが重要な場所でトレーシング（ADOT または X-Ray）を導入した | マイクロサービスでは、障害原因は症状が見えるサービスにあるとは限りません | [36](36/jp.md) |

## 7. 運用

「今日クラスターが動く」と「クラスターがアップグレードと障害を乗り越える」を分けるドメインです。

| 対応済み | 項目 | 重要な理由 | 章 |
|---|---|---|---|
| [ ] | クラスターとアドオンのアップグレード計画があり、非推奨 API を除去した | 非推奨 API は最も不適切なタイミングでアップグレードを止めます | [37](37/jp.md) |
| [ ] | rollback readiness が明確で、ロールバックの猶予と順序を把握している | ロールバックは失敗したアップグレード中ではなく事前に設計します | [39](39/jp.md) |
| [ ] | PDB と topology spread が drain およびアップグレード中の可用性を守る | これらがなければ、ノードアップグレードがサービスの全レプリカを一度に停止させます | [40](40/jp.md) |
| [ ] | PDB が drain を完全にブロックしない（`maxUnavailable: 0` は危険信号） | このような PDB はアップグレードを止め、drain が停止したように見せます | [40](40/jp.md) |
| [ ] | AWS Backup がクラスター状態と永続ボリュームに設定されている | ボリュームだけのバックアップではクラスター自体を復元できません | [41](41/jp.md) |
| [ ] | **ブロッカー。** DR-restore を game day で実際にテストした | 設定済みでも一度も検証していない restore は、バックアップではなく希望です | [42](42/jp.md) |
| [ ] | コストをチームと namespace ごとに可視化している（OpenCost または Kubecost） | 見えないコストは最適化されず、所有者もいません | [43](43/jp.md) |
| [ ] | GitOps がマニフェストの信頼できる情報源である（Argo CD または Flux） | クラスターと git が乖離すると、誰も状態を把握できません | [44](44/jp.md) |

## 8. インシデント対応準備

最後のドメインです。すべてが壊れたときに重要なのはアーキテクチャではなく、局所化の速さです。

| 対応済み | 項目 | 重要な理由 | 章 |
|---|---|---|---|
| [ ] | クラスターに参加しないノード用の runbook がある | 原因はさまざまです（IAM、SG、user data、kubelet）。確認順序が時間を節約します | [45](45/jp.md) |
| [ ] | ネットワーク障害用の runbook がある: ENI、SG、NACL、DNS、unhealthy targets | 原因が異なってもネットワーク障害は同じように見えます | [46](46/jp.md) |
| [ ] | アクセス用の runbook がある: 401 と 403、IRSA と Pod Identity、kubeconfig | アクセスエラーは作業とインシデント調査の両方を妨げます | [47](47/jp.md) |
| [ ] | 裸の SSH なしにノードへ接続できる SSM アクセスが動作する | すでに壊れたノードへのアクセスを設定するのでは遅すぎます | [45](45/jp.md) |
| [ ] | control plane logging を有効化し、authenticator と API のログを書き込む | これらのログがなければ、アクセス拒否の原因を復元できません | [21](21/jp.md) |
| [ ] | control plane のログを調査でき、早すぎる時期に削除されない | ログが必要なのは設定時ではなく調査時です | [34](34/jp.md) |

## 集計と結果への対応

次のように集計します。

- 対応済みの項目1つが1点、最大51点です。ドメインは同等であり、ネットワークはストレージより重要ではなく、一つのドメインの高得点が別のドメインの穴を埋めることはありません。
- **ブロッカー**とされる項目は3つあります: DR-restore が未検証、クラスターにアクセスできるのが一人だけ、ネットワークに default-deny NetworkPolicy がないことです。
- ブロッカー項目が一つでも未対応なら、合計点にかかわらずレベルは2を超えられません。ブロッカーは「1点減点」ではなく、本番トラフィックに対する停止条件です。

次に、未対応項目を優先度付きの技術的負債リストに変換します。

| 優先度 | 含めるもの | 対応方法 |
|---|---|---|
| 本番前の Must have | サポート対象バージョン、単独でないアクセス、control plane の監査とログ、default-deny NetworkPolicy、マニフェスト外のシークレット、検証済み restore、アップグレードを妨げない PDB | 本番トラフィックを有効にする前に対応する。最初のインシデントまたは侵害は、ローンチの遅延より高くつきます |
| 最初の数週間で重要 | right-sizing requests、Spot の混在、ログ retention、アラート、アップグレード計画、VPC endpoints | ローンチ直後に担当者と期限を定めたタスクとして登録する |
| Nice to have | マイクロサービスのトレーシング、詳細なコスト配分、クラスター群向けの成熟した GitOps | ローンチを妨げず、本番ですでに反復的に仕上げる |

技術的負債のリストは、所有者と期限を明記したタスクとして作成します。「いつか後で」という表現は、項目が未対応であり、次回の確認でも同じ場所にあることを意味します。

結果に対して次に行うこと:

- ドメインに ownership を割り当てます。ネットワーク、セキュリティ、コストには、担当項目が対応済みで劣化していないことに責任を持つ担当者がいます。
- 本番リリースのたびにフォームを実施します。新しいクラスターまたは新しい主要サービスは、「must have」の優先度が完全かつ明示的に対応されるまで本番投入しません。
- 結果を game day とアップグレードに結び付けます。DR-restore とアップグレード計画の検証は、約束ではなく、確認済みまたは失敗した項目としてフォームに戻します。
- 前回の結果と比較します。重要なのは合計点ではなく、対応済みになった項目、再び未対応に戻った項目、そしてその理由です。

## このアンケートの制約

- これはアーキテクチャレビューの代わりにはなりません。準備状況の軸は見えますが、設計上の判断は見えません。
- これはプラクティスの有無を評価するもので、その品質は評価しません。有効化された監査と有用な監査は同じ点数であり、差はインシデント調査でのみ分かります。
- アプリケーション層は対象外です。サービスコードとデータスキーマはフォームの範囲外に残ります。
- スコアは目的の異なるクラスター間で比較できません。非本番クラスターでは一部の項目が不要であり、低いスコアが悪いことを意味するわけではありません。
