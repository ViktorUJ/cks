# Lab 109 - reference solution: encryption at rest for Secrets

> We work as on the exam: the `kubectl` commands are run on the work machine, and the operations on the
> node (etcd, files and the manifest of the control-plane) - on the control-plane itself: log in to it
> with `ssh control-plane`, run the commands, and exit (`exit`). This is **only a training single-node
> cluster**; in production users are not given direct access to etcd.

## 1. Record the plaintext proof before enabling encryption

`Secret.data` in the API is base64-encoded, not encrypted. The bootstrap created a safe
canary before the EncryptionConfiguration appeared. First we look at the raw etcd record with the command from the
documentation, then we save the string proof into the file `/var/work/109/plaintext-proof.txt`
on the control-plane (`/tmp/plaintext-proof.txt`), then we copy it to the work machine into
`/var/work/109/plaintext-proof.txt` (the directory is created by the bootstrap): the check reads the file on the work machine.

Log in to the control-plane and run on it (everything in this command is from the documentation, except the key in
etcd: `/registry/secrets/<namespace>/<name>`):

```bash
ssh control-plane
sudo -i
```

```bash
# on the control-plane: the raw etcd record, the hexdump -C output shows the plaintext
ETCDCTL_API=3 etcdctl \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  get /registry/secrets/encryption-109/legacy-secret | hexdump -C

# save the proof (only the value, via strings) - also on the control-plane
ETCDCTL_API=3 etcdctl \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  get /registry/secrets/encryption-109/legacy-secret --print-value-only \
  | strings > /tmp/plaintext-proof.txt
cat /tmp/plaintext-proof.txt
# cks-109-legacy-plaintext
exit   # from root
exit   # from the control-plane
```

```bash
# on the work machine: copy the proof
scp control-plane:/tmp/plaintext-proof.txt /var/work/109/plaintext-proof.txt
cat /var/work/109/plaintext-proof.txt
```

At this step the file contains no `k8s:enc:`. This is a proof of the state **before** the configuration;
after re-encryption the repeated output must become ciphertext and the marker will disappear.

## 2. Create the EncryptionConfiguration

`aescbc` is chosen only for the training mechanics of CKS. Kubernetes considers AES-CBC weak because of
the risk of padding-oracle attacks and does not recommend it as a production default. For an external key
manager use KMS v2; choose a local provider only with a current threat model
and a rotation procedure.

We generate a 32-byte AES-256 key, encode it in base64, and create the configuration on the control-plane.
`aescbc` is first: new Secrets will be written with it. `identity` last lets the API
server read the old plaintext record only until the migration. An example of the file is on the documentation page
(the link at the beginning of the solution).

```bash
ssh control-plane
sudo -i
```

```bash
# on the control-plane (root)
mkdir -m 700 /etc/kubernetes/enc
key=$(head -c 32 /dev/urandom | base64)
cat > /etc/kubernetes/enc/encryption-config.yaml <<EOF
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources:
  - secrets
  providers:
  - aescbc:
      keys:
      - name: cks-109-aescbc
        secret: ${key}
  - identity: {}
EOF
chmod 600 /etc/kubernetes/enc/encryption-config.yaml
ls -ld /etc/kubernetes/enc; ls -l /etc/kubernetes/enc
exit   # from root
exit   # from the control-plane
```

A real key must not be put into Git, a ticket, a terminal log, or Terraform state.
If the key is lost, an encrypted Secret from a snapshot becomes unreadable.

## 3. Connect the configuration to the static kube-apiserver

First we save the manifest **outside** the `/etc/kubernetes/manifests/` directory: the kubelet reads as a static
Pod every non-hidden file of this directory, including `*.bak`. A copy of the original manifest inside
the directory is a second static Pod with the same name; the kubelet may keep running exactly it
(the old configuration without `--encryption-provider-config`), and the edit of the main file will silently
not take effect, and encryption will stay switched off with an outwardly healthy API server.
On the control-plane open exactly the existing static Pod
manifest and add these elements **to the existing** `command`, `volumeMounts`, and `volumes`;
do not replace the whole file with a template.

```bash
ssh control-plane
sudo -i
```

```bash
# on the control-plane (root)
cp /etc/kubernetes/manifests/kube-apiserver.yaml /root/kube-apiserver.yaml.bak-109
vim /etc/kubernetes/manifests/kube-apiserver.yaml
```

```yaml
# container name: kube-apiserver
command:
- kube-apiserver
- --encryption-provider-config=/etc/kubernetes/enc/encryption-config.yaml
volumeMounts:
- name: encryption-config
  mountPath: /etc/kubernetes/enc
  readOnly: true

# spec.volumes
volumes:
- name: encryption-config
  hostPath:
    path: /etc/kubernetes/enc
    type: Directory
```

The kubelet will notice the change and restart the static Pod. Before continuing wait for the API
server, otherwise a YAML/path error may leave the control-plane unavailable.

```bash
# still on the control-plane: check that the flag got into the running manifest, then exit
grep -n -- '--encryption-provider-config\|encryption-config' /etc/kubernetes/manifests/kube-apiserver.yaml
exit   # from root
exit   # from the control-plane
```

```bash
# on the work machine: the API server restarts for about a minute; repeat until the command
# returns "readyz check passed" (before that there will be "connection refused")
kubectl get --raw='/readyz?verbose'
```

## 4. Rewrite the old Secrets and check the ciphertext

The configuration does not change the records that are already stored. First we create a Secret after enabling the
provider, then we rewrite all the existing Secrets through the API. In production a
protected snapshot is made before this and a controlled procedure with retry is used.

```bash
kubectl -n "$NS" create secret generic encrypted-secret \
  --from-literal=token='cks-109-fresh-ciphertext'
kubectl get secrets --all-namespaces -o json | kubectl replace -f -

kubectl -n "$NS" get secret legacy-secret -o jsonpath='{.data.token}' | base64 -d; echo
kubectl -n "$NS" get secret encrypted-secret -o jsonpath='{.data.token}' | base64 -d; echo
# cks-109-legacy-plaintext
# cks-109-fresh-ciphertext
```

We read the raw records on the control-plane, as in task 1:

```bash
ssh control-plane
sudo -i
```

```bash
# on the control-plane (root)
ETCDCTL_API=3 etcdctl \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  get /registry/secrets/encryption-109/legacy-secret | hexdump -C
ETCDCTL_API=3 etcdctl \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  get /registry/secrets/encryption-109/encrypted-secret | hexdump -C
# both records begin with k8s:enc:aescbc:v1:...
exit   # from root
exit   # from the control-plane
```

The API returns plaintext to an authorized client - this is normal and does not prove
encryption at rest. The proof here is that the raw etcd contains `k8s:enc:aescbc:v1:` for the
old and the new record and no longer contains the legacy marker.

Now the migration fallback is no longer needed. We remove `identity`, forcibly restart the
static kube-apiserver via the CRI, and check the health and the reading once more. Do this only
after a snapshot and after confirming the ciphertext of all the affected resource types.

```bash
ssh control-plane
sudo -i
```

```bash
# on the control-plane (root): remove identity and restart the static kube-apiserver
vim /etc/kubernetes/enc/encryption-config.yaml   # delete the line "- identity: {}"
crictl stop $(crictl ps --name kube-apiserver -q)
exit   # from root
exit   # from the control-plane
```

```bash
# on the work machine
until kubectl get --raw=/readyz 2>/dev/null | grep -qx ok; do sleep 2; done
kubectl -n "$NS" get secret legacy-secret encrypted-secret
```

The final state of this lab: the encrypted provider is first and the only one, `identity` is
removed. The temporary fallback must not be left as a permanent "insurance".

## 5. Restrict API access and disable token automount

Encryption at rest does not replace RBAC: a subject with `get` on a Secret will see the plaintext through the API.
We create a ServiceAccount that has access to exactly one Secret, and a diagnostic Pod without a
mounted service-account token.

```yaml
# rbac-109.yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: secret-reader
  namespace: encryption-109
automountServiceAccountToken: false
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: secret-reader-109
  namespace: encryption-109
rules:
- apiGroups: [""]
  resources: ["secrets"]
  resourceNames: ["encrypted-secret"]
  verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: secret-reader-109
  namespace: encryption-109
subjects:
- kind: ServiceAccount
  name: secret-reader
  namespace: encryption-109
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: secret-reader-109
---
apiVersion: v1
kind: Pod
metadata:
  name: secret-reader-109
  namespace: encryption-109
spec:
  serviceAccountName: secret-reader
  automountServiceAccountToken: false
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.10
```

```bash
kubectl apply -f rbac-109.yaml
kubectl wait -n "$NS" --for=condition=Ready pod/secret-reader-109 --timeout=120s
kubectl auth can-i --as=system:serviceaccount:$NS:secret-reader get secret/encrypted-secret -n "$NS"
kubectl auth can-i --as=system:serviceaccount:$NS:secret-reader list secrets -n "$NS"
kubectl auth can-i --as=system:serviceaccount:$NS:secret-reader get secret/legacy-secret -n "$NS"
# yes
# no
# no

check_result
```

`automountServiceAccountToken: false` reduces the credential surface available to the Pod, but does not
restrict the RBAC of the ServiceAccount itself if the application obtains other credentials.

## Additional: what KMS v2 looks like and the full key rotation

### KMS v2: envelope encryption without a local key in the config

The `aescbc` above is needed only for the training mechanics. In production KMS v2 connects a
supported KMS plugin through a local Unix socket in the `EncryptionConfiguration`.
For KMS v2 the API server uses an encrypted seed/DEK at the API server level and
derives the encryption keys of individual records. The plugin protects the seed through an external KEK;
this is how KMS v2 differs from the per-resource KMS v1. Etcd stores the ciphertext of resources and the
metadata needed for decryption. The KEK stays in the external KMS, and not in etcd or in Git. The scheme of the
configuration depends on the Kubernetes version and on the plugin, but in principle a provider `kms`, a
stable key name, and a socket endpoint are needed. Do not copy an example endpoint from someone else's cluster:
check the KMS v2 format and the health/ACL requirements against the documentation of your Kubernetes version.

### The full lifecycle of rotating an aescbc key

The `identity -> aescbc` transition in task 4 is a migration, and not a rotation of an already
encrypted key. Before the rotation make an encrypted etcd snapshot and save the
old key for rollback. Add the new key **first**, and temporarily leave the old one
second: the providers are read in order, and new records are written with the first key.

```yaml
- aescbc:
    keys:
    - name: cks-109-aescbc-2026-rotation
      secret: <base64-32-byte-new-key>
    - name: cks-109-aescbc
      secret: <base64-32-byte-old-key>
```

After the API server restarts, rewrite the resources and check specifically the name of the new key in the raw
ciphertext, and not only the general `k8s:enc` prefix:

```bash
# on the work machine
kubectl get secrets --all-namespaces -o json | kubectl replace -f -
ssh control-plane
sudo -i
```

```bash
# on the control-plane (root)
ETCDCTL_API=3 etcdctl \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  get /registry/secrets/encryption-109/legacy-secret --print-value-only \
  | strings | grep -F 'k8s:enc:aescbc:v1:cks-109-aescbc-2026-rotation:'
exit   # from root
exit   # from the control-plane
```

When the migration of all Secrets is confirmed, a backup is made, the API reads the data, and `/readyz`
returns `ok`, remove the old key from the list, restart the API server, and repeat the
checks. Do not remove the old key earlier: records not rewritten by the new provider will become
unreadable. For KMS v2 the order is the same: first the new primary KEK/plugin, then
re-encryption, verification, and only after the migration the withdrawal of the old KEK from service.
