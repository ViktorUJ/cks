## 1. Installing Falco with modern eBPF

We install Falco from the official APT repository (the commands from the Install page of the Falco
documentation). Modern eBPF does not require building or loading a kernel module by hand.

```bash
# terminal 1 (control-plane, root)
curl -fsSL https://falco.org/repo/falcosecurity-packages.asc | gpg --dearmor -o /usr/share/keyrings/falco-archive-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/falco-archive-keyring.gpg] https://download.falco.org/packages/deb stable main" >> /etc/apt/sources.list.d/falcosecurity.list
apt-get update -y
```

**Run the installation as a separate command:** `apt-get` flushes the terminal input buffer, so
lines pasted right after it are lost.

```bash
# terminal 1 (control-plane, root)
FALCO_FRONTEND=noninteractive FALCOCTL_ENABLED='' FALCO_DRIVER_CHOICE=modern_ebpf apt-get install -y falco
```

```bash
# terminal 1 (control-plane, root)
mkdir -p /etc/falco/config.d
cat > /etc/falco/config.d/engine-kind.yaml <<EOF
engine:
  kind: modern_ebpf
EOF
# The package installs the unit falco-modern-bpf.service, and falco.service is only an alias to it;
# `systemctl enable falco` fails on the alias, so we enable the real unit.
systemctl enable --now falco-modern-bpf
falco --version; systemctl is-active falco; grep -R modern_ebpf /etc/falco
sleep 20
```

`sleep 20` is needed because on the first start the modern eBPF probe is opened with several
retries (the journal shows several `Opening 'syscall' source` lines): until it is
open, Falco does not record events, and the shell from task 2 may go unnoticed. If there is
no alert, repeat the `exec` a few seconds later.

If the service does not start, first look at `journalctl -u falco-modern-bpf -b --no-pager`.
Do not replace the engine with a kernel module: this lab requires exactly `modern_ebpf`.

## 3. A Local Rule and a Controlled Marker

Falco already loads `/etc/falco/falco_rules.local.yaml`; we will add the rule exactly there.
`spawned_process` keeps compatibility with the Falco rules, and `container` does not allow
matching the same marker launched on the host.

```bash
# terminal 1 (control-plane, root)
cat > /etc/falco/falco_rules.local.yaml <<EOF
- rule: CKS112 Custom Shell Marker
  desc: Detect the controlled CKS lab marker in a container process command line
  condition: spawned_process and container and proc.cmdline contains "CKS112_CUSTOM_EVENT"
  output: "CKS112 custom shell marker container=%container.id pid=%proc.pid ppid=%proc.ppid user=%user.name command=%proc.cmdline"
  priority: WARNING
EOF
systemctl restart falco && systemctl is-active falco && sleep 10
```

```bash
# terminal 2
kubectl exec -n "$NS" falco-shell -- sh -c 'echo CKS112_CUSTOM_EVENT >/dev/null'
```

```bash
# terminal 1
sleep 2
journalctl -u falco-modern-bpf -b --no-pager -n 500 | grep -F 'CKS112 custom shell marker' | tail -1 > /tmp/art/3/falco-custom.log
cat /tmp/art/3/falco-custom.log
```

```bash
# terminal 2
scp control-plane:/tmp/art/3/falco-custom.log /var/work/tests/artifacts/3/
```

After every `restart falco` the solution has `sleep 10`: Falco loads the rules and the container
metadata for about 5 seconds, and events that happened earlier it will not write to the journal.

## 4. Audit: RequestResponse for ConfigMap, Metadata for Secret

We will create a policy following the rule of chapter 32: we write the full request/response only for the
non-sensitive `configmaps` in `runtime-112`; for `secrets` we take `Metadata`, so that the body of the Secret
(tokens, passwords) does not get into the journal. `None` and `omitStages` really do reduce high-volume
noise; the final catch-all `Metadata` is fallback logging, and not noise suppression. The order of the rules matters:
the specific rules go before the catch-all. The structure of the file is from the example in the documentation (the Audit
policy section).

```bash
# terminal 1 (control-plane, root)
cat > /etc/kubernetes/audit/policy.yaml <<EOF
apiVersion: audit.k8s.io/v1
kind: Policy
omitStages: ["RequestReceived"]
rules:
# 1. Noise reduction: high-volume events and health probes are not forensic evidence here.
- level: None
  resources:
  - group: ""
    resources: ["events"]
- level: None
  nonResourceURLs: ["/healthz*", "/livez*", "/readyz*", "/version"]
# 2. ConfigMap: constrained forensic RequestResponse example.
- level: RequestResponse
  namespaces: ["runtime-112"]
  resources:
  - group: ""
    resources: ["configmaps"]
# 3. Secret matters for investigation, but its body must not be logged.
- level: Metadata
  resources:
  - group: ""
    resources: ["secrets"]
# 4. Fallback logging for the rest of the API (not noise reduction).
- level: Metadata
EOF
```

Edit `/etc/kubernetes/manifests/kube-apiserver.yaml` on the control-plane (`vim`). In the `command`
of the `kube-apiserver` container add:

```yaml
- --audit-policy-file=/etc/kubernetes/audit/policy.yaml
- --audit-log-path=/var/log/kubernetes/audit/audit.log
- --audit-log-maxage=7
- --audit-log-maxbackup=3
- --audit-log-maxsize=100
```

In the `volumeMounts` of the same container add:

```yaml
- name: audit-policy
  mountPath: /etc/kubernetes/audit
  readOnly: true
- name: audit-log
  mountPath: /var/log/kubernetes/audit
```

In `spec.volumes` add:

```yaml

  hostPath:
    path: /etc/kubernetes/audit
    type: Directory
- name: audit-log
  hostPath:
    path: /var/log/kubernetes/audit
    type: DirectoryOrCreate
```

## 5. An Immutable Root Filesystem

`emptyDir` gives the application a controlled place for runtime files; the root filesystem
remains read-only. `hostPath` is not needed and is not allowed.

```bash
# terminal 2
kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: immutable-app
  namespace: runtime-112
spec:
  automountServiceAccountToken: false
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    securityContext:
      readOnlyRootFilesystem: true
    volumeMounts:
    - name: writable-tmp
      mountPath: /tmp
  volumes:
  - name: writable-tmp
    emptyDir: {}
EOF
kubectl wait -n "$NS" --for=condition=Ready pod/immutable-app --timeout=120s
```

Let us prove both properties and save the denial message:


## 6. A Minimal Containment Chain from Alert to Isolation

The audit backend is already running, so a new `kubectl exec` will leave API evidence. We start
a controlled long-lived process: the marker stays in the command line long enough to
check `/proc`. In production a suspicious process is not launched again; here it is
safe planted evidence of a one-off lab.

```bash
# terminal 1 (control-plane, root): the start time of the run (we take the time from the control-plane,
# where we will read the journal later)
START=$(date '+%Y-%m-%d %H:%M:%S')
```

```bash
# terminal 2
DIR=/var/work/tests/artifacts/6
kubectl exec -n "$NS" falco-shell -- \
  sh -c 'sleep 600; echo completed' CKS112_CUSTOM_EVENT >/tmp/cks112-incident-exec.log 2>&1 &
INCIDENT_EXEC_PID=$!
```

Next we do everything on the control-plane while the process is alive: we take the alert, and from it the container id and
the host pid (we start from the alert, and do not guess):

```bash
# terminal 1 (control-plane, root)
cd /tmp/art/6
journalctl -u falco-modern-bpf -b --since "$START" --no-pager | grep -F 'CKS112 custom shell marker' | tail -1 > falco-alert.log
cat falco-alert.log

SHORT_ID=$(sed -n 's/.*container=\([^ ]*\).*/\1/p' falco-alert.log | tail -1)
HOST_PID=$(sed -n 's/.* pid=\([0-9][0-9]*\) .*/\1/p' falco-alert.log | tail -1)
echo "SHORT_ID=$SHORT_ID HOST_PID=$HOST_PID"

CONTAINER_ID=$(crictl ps -a -q | grep "^$SHORT_ID" | head -1)
crictl inspect $CONTAINER_ID > cri-container.json
SANDBOX_ID=$(jq -r '.status.sandboxId // .status.sandboxID // .info.sandboxID // empty' cri-container.json)
crictl inspectp $SANDBOX_ID > cri-sandbox.json
printf 'container_init_pid=%s\n' "$(jq -r '.info.pid // empty' cri-container.json)" > cri-mapping.txt

cat /proc/$HOST_PID/status > proc-status.txt
tr '\0' ' ' < /proc/$HOST_PID/cmdline > proc-cmdline.txt; echo >> proc-cmdline.txt
cat /proc/$HOST_PID/cgroup > proc-cgroup.txt
ps -eo pid,ppid,user,lstart,args --forest > process-tree.txt
```

Now we correlate the API event. The modern `kubectl exec` works over WebSocket, so in the audit it is
seen as `get` (with the SPDY fallback - `create`), both variants are fine. For `pods/exec`
`Metadata` is enough: the command from the request body may contain a secret, so `RequestResponse` is not needed here.

```bash
# terminal 1 (control-plane, root)
jq -c 'select(.level == "Metadata" and (.verb == "create" or .verb == "get") and .objectRef.resource == "pods" and .objectRef.subresource == "exec" and .objectRef.namespace == "runtime-112" and .objectRef.name == "falco-shell")' /var/log/kubernetes/audit/audit.log | tail -1 > audit-exec.json
jq '{verb, level, hasRequestObject: has("requestObject")}' audit-exec.json
```

```bash
# terminal 2: fetch all the chain files and assemble the final summary
scp 'control-plane:/tmp/art/6/*' /var/work/tests/artifacts/6/

SHORT_ID=$(sed -n 's/.*container=\([^ ]*\).*/\1/p' "$DIR/falco-alert.log" | tail -1)
HOST_PID=$(sed -n 's/.* pid=\([0-9][0-9]*\) .*/\1/p' "$DIR/falco-alert.log" | tail -1)
CONTAINER_ID=$(jq -r '.status.id' "$DIR/cri-container.json")
POD=$(jq -r '.status.metadata.name' "$DIR/cri-sandbox.json")
NAMESPACE=$(jq -r '.status.metadata.namespace' "$DIR/cri-sandbox.json")
NODE=$(kubectl get pod "$POD" -n "$NAMESPACE" -o jsonpath='{.spec.nodeName}')
CONTAINER_INIT_PID=$(jq -r '.info.pid // empty' "$DIR/cri-container.json")

cat > "$DIR/evidence-summary.txt" <<EOF
alert_rule=CKS112 Custom Shell Marker
namespace=$NAMESPACE
pod=$POD
node=$NODE
runtime=containerd
container_id=$CONTAINER_ID
container_init_pid=$CONTAINER_INIT_PID
host_pid=$HOST_PID
audit_verb=$(jq -r .verb "$DIR/audit-exec.json")
audit_subresource=exec
attack_phase=Execution
technique=Container Administration Command
containment=quarantine-and-delete
EOF
cat "$DIR/evidence-summary.txt"
```

First we save the evidence, then we isolate the namespace at the network level and delete the
compromised Pod. This is a minimal containment chain, and not a full investigation:
credential revocation/rotation, the search for other workloads, and the restoration of the owner/controller are done by
a separate IR process. The last command proves a negative outcome, and does not look for a specific
error text.

```bash
# terminal 2
kubectl apply -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: incident-quarantine
  namespace: runtime-112
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
  ingress: []
  egress: []
EOF

kubectl delete pod falco-shell -n "$NS" --wait=true
wait "$INCIDENT_EXEC_PID" 2>/dev/null
kubectl exec -n "$NS" falco-shell -- sh -c 'echo CKS112_CUSTOM_EVENT' > "$DIR/post-containment-exec.log" 2>&1
printf 'pod=deleted\nnetworkpolicy=incident-quarantine\nexec_exit=%s\n' "$?" > "$DIR/containment.txt"
cat "$DIR/containment.txt"
# exec_exit=1 (not 0)
```

## Task 7. Overriding an Upstream Macro and Output to JSON/a File

The standard rule **Terminal shell in container** will also fire on a legitimate
tool. The right place for an environment-specific exception is not editing the
rule itself, but an override of the reserved upstream macro of exactly this rule:
`user_expected_terminal_shell_in_container_conditions` (by default `(never_true)`, that
is, there are no exceptions). Do not confuse it with the similarly named `user_shell_container_exclusions` -
that one belongs to the separate rule **Run shell untrusted** ("Shell spawned by untrusted
binary") and does not affect **Terminal shell in container**. Use `k8s.pod.name` and
`k8s.ns.name`, and not `container.name`: `container.name` is the name of the **container** (here
`app`), and not of the Pod, and matching by the container name almost always gives a wrong or too broad
allowlist.

```bash
# terminal 1 (control-plane, root)
cat >> /etc/falco/falco_rules.local.yaml <<EOF

- macro: user_expected_terminal_shell_in_container_conditions
  condition: (k8s.ns.name = "runtime-112" and k8s.pod.name = "ci-runner")
  override:
    condition: replace
EOF
systemctl restart falco && sleep 10
```

Create a Pod with an interactive shell under the name that is now excluded:

```bash
# terminal 2
kubectl apply -n runtime-112 -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: ci-runner
  labels:
    app: ci-runner
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sleep", "3600"]
    stdin: true
    tty: true
EOF
kubectl wait -n runtime-112 --for=condition=Ready pod/ci-runner --timeout=60s
kubectl exec -n runtime-112 -it ci-runner -- sh -c 'echo shell-open; sleep 2'
```

Separately check that `immutable-app` from task 5 (without the exception) keeps producing an alert - the override
must not quietly silence the rule altogether:

```bash
# terminal 2
kubectl exec -n runtime-112 -it immutable-app -- sh -c 'echo shell-open; sleep 2'
```

```bash
# terminal 1
journalctl -u falco-modern-bpf -b --no-pager -n 200 | grep -F 'A shell was spawned in a container with an attached terminal'
```

The standard output of the rule **Terminal shell in container** does not contain `k8s.pod.name`/
`k8s.ns.name` (you can make sure on the control-plane: `grep -A3 "rule: Terminal shell in container" /etc/falco/falco_rules.yaml`
will show an `output` without these fields). Without Pod/namespace evidence in the alert itself, reliable correlation
of a specific firing with a specific Pod is impossible - a text `grep` for the Pod name in the journal
will simply find no match. We add these fields through the same `override` mechanism, but with
`output: append` instead of `condition: replace`:

```bash
# terminal 1 (control-plane, root)
cat >> /etc/falco/falco_rules.local.yaml <<EOF

- rule: Terminal shell in container
  output: ' k8s_ns=%k8s.ns.name k8s_pod=%k8s.pod.name'
  override:
    output: append
EOF
systemctl restart falco && sleep 10
```

In `/etc/falco/config.d/` enable the JSON format and file output. Falco 0.38+ by default
picks up `config_files` from this directory; appending directly to `falco.yaml` creates
duplicate top-level keys on a repeated run and survives a package upgrade worse -
`config.d` is intended exactly for local additions:

```bash
# terminal 1 (control-plane, root)
mkdir -p /var/log/falco /etc/falco/config.d
cat > /etc/falco/config.d/cks112-output.yaml <<EOF
json_output: true
file_output:
  enabled: true
  filename: /var/log/falco/events.log
EOF
systemctl restart falco && sleep 10
```

We confirm in a structured way, via `output_fields`, and not with a text `grep` for the Pod name -
this works reliably regardless of how exactly the `output` line is formatted:

```bash
# terminal 2
kubectl exec -n runtime-112 -it immutable-app -- sh -c 'echo shell-open; sleep 2'
```

```bash
# terminal 1 (control-plane, root)
sleep 2
tail -n 20 /var/log/falco/events.log \
  | jq -c 'select(.rule == "Terminal shell in container" and .output_fields["k8s.pod.name"] == "immutable-app" and .output_fields["k8s.ns.name"] == "runtime-112")' \
  | tail -1 \
  | jq '{pod: .output_fields["k8s.pod.name"], ns: .output_fields["k8s.ns.name"]}'
# {"pod": "immutable-app", "ns": "runtime-112"}
```

## Task 9. An Integration Task: Bypassing Admission via containerd and Detecting It via Falco

This task ties Supply Chain Security (lab 111, chapter 26) to the Runtime Security of this
lab: an admission check (Kyverno) does not see a container if it is created directly through
containerd, bypassing the kube-apiserver. Falco, unlike an admission controller, works at
the level of kernel syscalls and sees **all** containers on the node regardless of how they were
started.

**It is important not to confuse this with lab 111**: there the policy checks a cryptographic signature
(Cosign). Here the policy checks only a registry/repository allowlist - a simpler
admission control without a signature/attestor. The general principle is the same for both: admission works
only on the API admission path.

The lab-owned local registry names are prepared by the bootstrap (not the public Docker Hub - the controlled
abuse fixture of this task must be safe and lab-owned, and must not depend on the availability of an external
registry at the time of the check). They are in `/etc/cks112/registry.env` on the control-plane; source
them in both terminals:

```bash
# terminal 1 (control-plane, root)
source /etc/cks112/registry.env
echo "CKS112_REGISTRY=$CKS112_REGISTRY CKS112_TRUSTED_REPO=$CKS112_TRUSTED_REPO"
START_TS=$(date '+%Y-%m-%d %H:%M:%S')     # the start of the run
install-kyverno
```

```bash
# terminal 2
scp control-plane:/etc/cks112/registry.env /tmp/cks112-registry.env
source /tmp/cks112-registry.env
echo "CKS112_REGISTRY=$CKS112_REGISTRY CKS112_TRUSTED_REPO=$CKS112_TRUSTED_REPO"
```

(`install-kyverno` is the same Kyverno version as in lab 111.)

We create a native `ValidatingPolicy` with an allowlist for the trusted registry. We use the Kyverno CEL
Image library (`image(...).registry()`/`.repository()`) for an exact comparison, and not
`startsWith` - otherwise `${CKS112_TRUSTED_REPO}-evil` would also pass the policy, because its
image string simply starts with the allowed substring. The denial message contains the
unique marker `CKS112_TRUSTED_REPO_POLICY`, so that BATS can later tell exactly this
policy apart from any other admission webhook/policy in the cluster:

```bash
# terminal 2
kubectl apply -f - <<YAML
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: require-trusted-registry-runtime-112
spec:
  matchConstraints:
    resourceRules:
    - apiGroups: [""]
      apiVersions: ["v1"]
      resources: ["pods", "pods/ephemeralcontainers"]
      operations: ["CREATE", "UPDATE"]
  matchConditions:
  - name: only-runtime-112
    expression: "object.metadata.namespace == 'runtime-112'"
  validations:
  - expression: >
      object.spec.containers.all(c,
        image(c.image).registry() == '${CKS112_REGISTRY}' &&
        image(c.image).repository() == '${CKS112_TRUSTED_REPO}') &&
      (!has(object.spec.initContainers) || object.spec.initContainers.all(c,
        image(c.image).registry() == '${CKS112_REGISTRY}' &&
        image(c.image).repository() == '${CKS112_TRUSTED_REPO}')) &&
      (!has(object.spec.ephemeralContainers) || object.spec.ephemeralContainers.all(c,
        image(c.image).registry() == '${CKS112_REGISTRY}' &&
        image(c.image).repository() == '${CKS112_TRUSTED_REPO}'))
    message: "CKS112_TRUSTED_REPO_POLICY: only ${CKS112_TRUSTED_IMAGE} is allowed in runtime-112"
  validationActions: [Deny]
YAML
```

We confirm the admission denial for an image outside the allowlist:

```bash
# terminal 2 (wait about 10 seconds after creating the policy)
kubectl apply -n runtime-112 -f - > /var/work/tests/artifacts/9/admission-deny.txt 2>&1 <<YAML
apiVersion: v1
kind: Pod
metadata:
  name: blocked-attempt
spec:
  containers:
  - name: app
    image: ${CKS112_UNTRUSTED_IMAGE}
    imagePullPolicy: IfNotPresent
    command: ["sleep", "60"]
YAML
cat /var/work/tests/artifacts/9/admission-deny.txt
# Error from server: ... CKS112_TRUSTED_REPO_POLICY: only ... is allowed in runtime-112
```

Now we model a path that the admission controller does not see: a container is created directly
in the container runtime through the CRI, bypassing the kube-apiserver entirely. For this the control-plane has
the helper `cks112-run <image> <id> '<command>'` (a wrapper over `crictl runp/create/start`) and
`cks112-rm <id>` for cleanup. Why not `ctr run`: containers created through `ctr` are not
known to the CRI, and for them Falco always writes `container.image.repository = <NA>` - the trusted and
untrusted images would be indistinguishable. A container created through the CRI is seen by Falco with its image.
Each run gets one unique suffix `$RUN_ID`, and all the IDs it creates use
this suffix, so a repeated run will not collide with the leftovers of a previous attempt:

```bash
# terminal 1 (control-plane, root)
RUN_ID="$(date +%s%N)"
BYPASS_1="cks112-bypass-1-$RUN_ID"
OBSERVE_REPO="cks112-observe-repo-$RUN_ID"
PROBE_ALLOWED="cks112-probe-allowed-$RUN_ID"
BYPASS_2="cks112-bypass-2-$RUN_ID"
PREFIX_TRAP="cks112-prefix-trap-$RUN_ID"

# CKS112_UNTRUSTED_IMAGE is already in the local containerd store after the bootstrap - no pull is needed.
cks112-run $CKS112_UNTRUSTED_IMAGE $BYPASS_1 'echo CKS112_CTR_BYPASS; sleep 5'
```

> `container.id != host` is mandatory: the command `cks112-run ... 'echo CKS112_CTR_BYPASS'` itself
> runs on the host, and its command line contains the marker. Without this condition the rule
> would fire on the host launch process (its repository is empty, that is, not equal to the trusted one),
> and even the trusted image would give a false alert.
>
> For an image Falco shows not the tag with which the container was started, but the alphabetically first
> image name (an image can have several names). Therefore the names of the lab images use
> the registry host `cks112.local:5000`, which sorts before `docker.io`.

Before writing the exact condition, we determine the REAL observed value of
`%container.image.repository` for the trusted image on this containerd/Falco stack -
we do not assume it in advance. Different container runtime/Falco versions may form
this field differently (with the registry hostname or without it), so the only reliable
way is to run the trusted container with a temporary observe rule and see what
Falco actually writes:

```bash
# terminal 1 (control-plane, root)
cat >> /etc/falco/falco_rules.local.yaml <<EOF

- rule: CKS112 Observe Trusted Repository Value
  desc: Temporary rule to capture the exact observed container.image.repository string for the trusted image
  condition: spawned_process and container.id != host and proc.cmdline contains "CKS112_OBSERVE_REPO"
  output: "CKS112 observed repository=%container.image.repository tag=%container.image.tag"
  priority: INFORMATIONAL
EOF
systemctl restart falco && sleep 10

# CKS112_TRUSTED_IMAGE is already local after the bootstrap - no pull is needed.
cks112-run $CKS112_TRUSTED_IMAGE $OBSERVE_REPO 'echo CKS112_OBSERVE_REPO; sleep 5'
sleep 3
TRUSTED_REPO=$(journalctl -u falco-modern-bpf -b --no-pager -n 50 | grep -oP 'CKS112 observed repository=\K[^ ]+' | tail -1)
echo "TRUSTED_REPO=$TRUSTED_REPO"
cks112-rm $OBSERVE_REPO
```

Save the value `$TRUSTED_REPO` (for example `cks112/trusted` or
`cks112.local:5000/cks112/trusted` - exactly what your Falco/containerd
version actually printed) as evidence, so that the condition below is verifiably tied to the observed value,
and not to an assumption:

```bash
# terminal 1
echo "$TRUSTED_REPO" > /tmp/art/9/observed-trusted-repo.txt
cat /tmp/art/9/observed-trusted-repo.txt
```

Now we add the final rule after the temporary observe rule (`>>`, without
overwriting the file, so as not to lose the rules from tasks 3 and 7). The condition uses an **exact**
comparison with the observed `$TRUSTED_REPO`, and not a `startswith`/prefix check:
`not container.image.repository startswith "$TRUSTED_REPO"` would let through (not notice)
a repository like `<TRUSTED_REPO>-evil`, because its name simply STARTS with the allowed
substring - that is, Falco would consider it part of the allowlist, although in reality it is outside the permitted
repository. This is the same trap that the Kyverno policy above avoids through `==`, and not
`startsWith`; the admission condition and the Falco condition must check the same repository
property in the same (exact) way and with the same observed value, otherwise they are
not equivalent as a security control:

```bash
# terminal 1 (control-plane, root)
cat >> /etc/falco/falco_rules.local.yaml <<EOF

- rule: CKS112 Runtime Bypass of Admission
  desc: Process spawned in a container whose image is outside the runtime-112 trusted registry allowlist, indicating a container started outside kube-apiserver/admission (e.g. via ctr/crictl directly)
  condition: >
    spawned_process and
    container.id != host and
    proc.cmdline contains "CKS112_CTR_BYPASS" and
    container.image.repository != "$TRUSTED_REPO"
  output: >
    CKS112 runtime bypass of admission detected
    (command=%proc.cmdline container_id=%container.id
    repo=%container.image.repository tag=%container.image.tag
    pid=%proc.pid ppid=%proc.ppid user=%user.name)
  priority: CRITICAL
  tags: [cks112, supply_chain, admission_bypass]
EOF
systemctl restart falco && sleep 10
```

Before repeating the bypass with the untrusted image, we check both controlled cases to
prove that the comparison is really exact, and not prefix-based. First the trusted image - for
it there must be no alert (a negative control):

```bash
# terminal 1 (control-plane, root)
cks112-run $CKS112_TRUSTED_IMAGE $PROBE_ALLOWED 'echo CKS112_CTR_BYPASS; sleep 5'
sleep 3
journalctl -u falco-modern-bpf --since "$START_TS" --no-pager | grep -F 'CKS112 runtime bypass of admission' | grep -F 'CKS112_CTR_BYPASS' > /tmp/art/9/probe-trusted.log
wc -l < /tmp/art/9/probe-trusted.log        # 0: there is no alert for the allowed repository
cks112-rm $PROBE_ALLOWED
```

We remove the first container/task before the repetition, so as not to leave a "hanging" process, and
start the second one with a new unique ID - for it the alert is required:

```bash
# terminal 1 (control-plane, root)
cks112-rm $BYPASS_1

cks112-run $CKS112_UNTRUSTED_IMAGE $BYPASS_2 'echo CKS112_CTR_BYPASS; sleep 5'
sleep 3
journalctl -u falco-modern-bpf --since "$START_TS" --no-pager | grep 'CKS112 runtime bypass of admission' > /tmp/art/9/falco-bypass-attempt.log
cp /tmp/art/9/falco-bypass-attempt.log /tmp/art/9/probe-alpine.log
cks112-rm $BYPASS_2
```

Finally, we prove the prefix trap itself: a repository built as `${TRUSTED_REPO}-evil`
STARTS with the same substring as the allowed `$TRUSTED_REPO`, but is not exactly equal to it.
If the Falco condition used `startswith` (as in an earlier, incorrect version
of this rule), this image would pass UNNOTICED - which is exactly why the corrected `!=`
condition must catch it. The prefix-trap image is prepared by the bootstrap (`$CKS112_PREFIX_IMAGE`,
a separate digest):

```bash
# terminal 1 (control-plane, root)
cks112-run $CKS112_PREFIX_IMAGE $PREFIX_TRAP 'sleep 2; echo CKS112_CTR_BYPASS; sleep 6'
sleep 3
journalctl -u falco-modern-bpf --since "$START_TS" --no-pager | grep -F 'CKS112 runtime bypass of admission' | grep -F "${TRUSTED_REPO}-evil" > /tmp/art/9/probe-prefix.log
cat /tmp/art/9/probe-prefix.log >> /tmp/art/9/falco-bypass-attempt.log
cks112-rm $PREFIX_TRAP
```

```bash
# terminal 2: fetch the task 9 files
scp 'control-plane:/tmp/art/9/*' /var/work/tests/artifacts/9/
```

> **The structure of the evidence files of task 9.** `falco-bypass-attempt.log` is the main
> combined artifact that the automatic acceptance check examines (it contains both alerts:
> untrusted and prefix-trap, but must not contain an alert for the trusted repo). In addition,
> each probe writes its own file for manual diagnostics: `probe-trusted.log` (must be
> empty - this is the negative control), `probe-alpine.log`, and `probe-prefix.log`.

The key takeaway of this task: a registry allowlist at admission and Falco at runtime are not
interchangeable layers, but complementary ones. Admission stops the path through the Kubernetes
API, but knows nothing about processes started directly through the container runtime on the node;
Falco cannot **block** the creation of such a container in advance, but sees it after it
starts, regardless of which API (or the absence of one) was used. The same principle
applies to signature verification in lab 111 - the only difference is that there the policy
checks a signature, and here simply the registry/repository. An additional takeaway from the
prefix-trap check above: the Falco condition and the Kyverno CEL policy must use the SAME
comparison semantics (`==`/`!=`, and not `startsWith`/prefix), otherwise they stop being
equivalent security controls, even if both formally check "the same" repository.

## 10. Detecting Access to `/dev/mem` via a File/Device-Open Condition

Tasks 3, 7, and 9 built the condition around `spawned_process`/`proc.cmdline` - detection
by the LAUNCH of a process and its arguments. Here a fundamentally different class of Falco
condition is used: detection by the OPENING of a specific file/device, regardless of which
process does it and with which command-line arguments.

The Deployment `mem-scanner` (2 replicas) has already been deployed by the bootstrap; both replicas periodically
open `/dev/mem` from inside the container. The path `/dev/mem` inside the container is a synthetic
safe fixture (the backing device is in fact the host `/dev/null`, and not the real physical
memory of the host); for a Falco condition on the file name (`fd.name = /dev/mem`) this is indistinguishable -
the `open`/`openat`/`openat2` system call itself is detected. Add the rule on the
`control-plane`:

```bash
# terminal 1 (control-plane, root)
cat >> /etc/falco/falco_rules.local.yaml <<EOF
- rule: CKS112 Container access to /dev/mem
  desc: Detect an open of /dev/mem from a container process
  condition: >
    evt.type in (open, openat, openat2) and
    fd.name = /dev/mem and
    container.id != host
  output: >
    CKS112 Container access to /dev/mem
    (container_id=%container.id k8s_pod=%k8s.pod.name k8s_ns=%k8s.ns.name
    proc=%proc.name pid=%proc.pid user=%user.name)
  priority: CRITICAL
  tags: [container, mitre_privilege_escalation, mitre_defense_evasion]
EOF
systemctl restart falco && sleep 10
```

Wait for the next periodic cycle of `mem-scanner` (every ~15 seconds) and find the
trigger. Take the Pod identifier FROM the alert itself (`k8s_pod=`), and do not guess in advance
which of the two replicas is guilty - this is the same fundamental rule "start from the
alert" as in task 6:

```bash
# terminal 1 (control-plane, root)
journalctl -u falco-modern-bpf -b --no-pager -n 500 | grep -F 'CKS112 Container access to /dev/mem' | tail -1 > /tmp/art/10/falco-devmem.log
cat /tmp/art/10/falco-devmem.log
exit   # from root
exit   # from the control-plane
```

```bash
# terminal 2
scp control-plane:/tmp/art/10/falco-devmem.log /var/work/tests/artifacts/10/
```

Having made sure that the detection is confirmed by Falco itself (and not by the Pod manifest), save the Pod
named in the alert, and make sure that it really belongs to the ReplicaSet of the Deployment
`mem-scanner` before scaling:

```bash
# terminal 2
ALERT_POD=$(sed -n 's/.*k8s_pod=\([^ ]*\).*/\1/p' /var/work/tests/artifacts/10/falco-devmem.log | tail -1)
echo "$ALERT_POD"
kubectl get pod "$ALERT_POD" -n runtime-112 -o json > /var/work/tests/artifacts/10/detected-pod.json
```

Then we stop the workload:

```bash
# terminal 2
kubectl scale deployment mem-scanner -n runtime-112 --replicas=0
kubectl get deployment mem-scanner -n runtime-112 -o json > /var/work/tests/artifacts/10/scaled-down.json
jq '.spec.replicas' /var/work/tests/artifacts/10/scaled-down.json
# expected: 0
```

`container.id != host` in the condition is not a decorative detail: without it the rule would fire
on legitimate system processes of the node as well (for example, memory diagnostic tools)
launched outside containers, creating noisy false positives on every node of the cluster.

At the end run `check_result`.
