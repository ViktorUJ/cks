## 1. Minimal `auditor` access to Pods only

On the exam, writing the full YAML of a typical RBAC object by hand is a waste of time:
`kubectl create` generates the ServiceAccount/Role/RoleBinding with one command each:

```bash
k create sa auditor -n security-104
k create role pod-observer -n security-104 --resource=pods --verb=get,list,watch
k create rolebinding auditor-pod-observer -n security-104 \
  --role=pod-observer --serviceaccount=security-104:auditor

k auth can-i list pods -n security-104 \
  --as=system:serviceaccount:security-104:auditor
k auth can-i delete secrets -n security-104 \
  --as=system:serviceaccount:security-104:auditor # must be no
```

## 2. Projected ServiceAccount token

A TokenRequest volume issues a short-lived token; the regular automount is disabled.
We do not pin `audience: kubernetes.default.svc`: for kubeadm this is not necessarily the
value accepted by the API server. If `audience` is omitted, the kubelet uses the default
API server identifier. A separate audience may be specified only after checking
`--api-audiences` (or the default from `--service-account-issuer`) on the control-plane.
`expirationSeconds` must be in the range `600`-`3600` inclusive - the Kubernetes API
rejects as invalid any value below `600` seconds for a `serviceAccountToken`
projected source, regardless of what is written in the manifest.

You do not need to recall the exact syntax of `projected.sources[].serviceAccountToken` from memory on the exam -
on `kubernetes.io/docs` it is in the section Concepts → Storage →
[Projected Volumes](https://kubernetes.io/docs/concepts/storage/projected-volumes/), under the
heading **"serviceAccountToken projected volumes"** (there is a ready example of a Pod with this
volume - take the structure from there rather than writing it from scratch). `kubectl run` cannot add
such a volume through flags - we generate a Pod skeleton via `--dry-run=client -o yaml` and
add in `vim` only the needed fields copied from the example in the documentation:

```bash
k create sa api-client -n security-104
k run token-client -n security-104 --image=busybox:1.36 --command --dry-run=client -o yaml \
  -- sh -c "sleep 3600" > token-client.yaml
vim token-client.yaml
```

```yaml
# Add to the Pod spec (containers/image/command are already generated by kubectl run):
spec:
  serviceAccountName: api-client              # add
  automountServiceAccountToken: false         # add
  containers:
  - name: token-client
    volumeMounts:                             # add
    - name: api-token                         # add
      mountPath: /var/run/secrets/tokens       # add
      readOnly: true                          # add
    ...
  volumes:                                    # add
  - name: api-token                           # add
    projected:                                # add
      sources:                                # add
      - serviceAccountToken:                  # add
          path: api-token                     # add
          expirationSeconds: 3600             # add
```

```bash
k apply -f token-client.yaml
k wait -n security-104 --for=condition=Ready po/token-client --timeout=120s
k exec -n security-104 token-client -- \
  ls -l /var/run/secrets/tokens/api-token
# the file is there - if the manifest matches the example from the documentation, the kubelet issued it

k auth can-i delete secrets -n security-104 \
  --as=system:serviceaccount:security-104:api-client
# no
```

We check not only the presence of the file but also that the mounted projected token
really authenticates as the expected ServiceAccount, by sending it to a `TokenReview`:

```bash
TOKEN=$(k exec -n security-104 token-client -- cat /var/run/secrets/tokens/api-token)

k create -o jsonpath='{.status.authenticated}{" "}{.status.user.username}{"\n"}' -f - <<EOF
apiVersion: authentication.k8s.io/v1
kind: TokenReview
spec:
  token: $TOKEN
EOF
# true system:serviceaccount:security-104:api-client
```

For the lab this check is mandatory: the presence of a file alone does not prove
that the projected token is valid and authenticates as the expected ServiceAccount. `TokenReview`
must return `authenticated: true` and the username
`system:serviceaccount:security-104:api-client`.

On the exam you do not need to run a separate `TokenReview` unless the task requires it:
there it is enough to quickly create a correct projected token volume and check the result in the
way the specific task needs. Here `TokenReview` is a training verification check
that at the same time matches the acceptance criterion of the lab.

## 3. A Pod without an API token

We disable automounting on both the ServiceAccount and the Pod: this protects against later
changes to the template or to the ServiceAccount.

`kubectl create serviceaccount` has no flag for `automountServiceAccountToken` - we create
it and patch it right away:

```bash
k create sa no-token-sa -n security-104
k patch sa no-token-sa -n security-104 -p '{"automountServiceAccountToken":false}'
k run no-token -n security-104 --image=busybox:1.36 --command --dry-run=client -o yaml \
  -- sh -c "sleep 3600" > no-token.yaml
vim no-token.yaml
```

```yaml
# Add to the Pod spec:
spec:
  serviceAccountName: no-token-sa       # add
  automountServiceAccountToken: false   # add
  containers:
  - name: no-token
    ...
```

```bash
k apply -f no-token.yaml
k wait -n security-104 --for=condition=Ready po/no-token --timeout=60s
k get po no-token -n security-104 -o jsonpath='{.spec.automountServiceAccountToken}'

# We confirm at the runtime level, not only at the level of the YAML specification: there is really
# no token file in the container.
k exec -n security-104 no-token -- \
  test ! -e /var/run/secrets/kubernetes.io/serviceaccount/token
echo "exit code: $?"
# exit code: 0 - the file is absent, the exec itself worked successfully
```

Do not separately mount a legacy `Secret` with `type: kubernetes.io/service-account-token` either -
even with automount switched off, such a Secret can be mounted manually via
`volumes[].secret`, and then the Pod is formally "without a token" by the automount field, but in fact
still has a valid API token inside the container.

## 5. Disabling anonymous-auth

A plain `--anonymous-auth=false` is not suitable here: kubeadm `release-1.36` generates the
kube-apiserver static Pod with HTTPS liveness/readiness/startup probes on `/livez` and
`/readyz`, and kubelet HTTP probes do not pass client credentials - when anonymous
access is fully disabled these requests will get `401`, and the kubelet will start considering kube-apiserver
unhealthy (which in turn also breaks task 9, which depends on a stably working API
server). Instead we use an `AuthenticationConfiguration` with `anonymous.conditions`
that restrict anonymous access to only three health paths. On the exam do not prefix
every command with `sudo` - become root once (`sudo -i`), it is faster:

```bash
ssh control-plane
sudo -i
cat > /etc/kubernetes/authentication-config.yaml <<'EOF'
apiVersion: apiserver.config.k8s.io/v1
kind: AuthenticationConfiguration
jwt: []
anonymous:
  enabled: true
  conditions:
  - path: /livez
  - path: /readyz
  - path: /healthz
EOF
```

We edit the static manifest: we remove `--anonymous-auth=true` completely (it must not be left
next to `--authentication-config` - kube-apiserver refuses to start if both are set),
add `--authentication-config`, and also a `hostPath` volume/volumeMount for the new
configuration file - kube-apiserver reads `authentication-config.yaml` from the node's file
system, so the file must be visible inside the container through a volumeMount, and not
just lie on the host:

```bash
cp /etc/kubernetes/manifests/kube-apiserver.yaml ~/5-api.yaml
vim /etc/kubernetes/manifests/kube-apiserver.yaml
# In the command array:
# - remove the line "- --anonymous-auth=true"
# - add a line with the same indentation as the other arguments:
#   - --authentication-config=/etc/kubernetes/authentication-config.yaml
# In the container's volumeMounts (the same indentation as the neighboring items):
#   - mountPath: /etc/kubernetes/authentication-config.yaml
#     name: authentication-config
#     readOnly: true
# In the Pod's volumes (the same indentation as the neighboring items):
#   - hostPath:
#       path: /etc/kubernetes/authentication-config.yaml
#       type: File
#     name: authentication-config
systemctl restart kubelet
exit
exit
```

`systemctl restart kubelet` forces an immediate rebuild of the static Pod - on the exam this is
faster than waiting for the kubelet to notice the file change itself (usually seconds, but not
guaranteed to be instant):

```bash
k get po -n kube-system -l component=kube-apiserver
# STATUS must become Running - if not yet, wait a couple of seconds and repeat
```

Check all three behaviors: `/version` rejects anonymous requests, while `/livez`/`/readyz`
accept them:

```bash
SERVER=$(k config view --minify -o jsonpath='{.clusters[0].cluster.server}')
curl -k -o /dev/null -s -w '%{http_code}\n' "$SERVER/version" # 401 - anonymous access is closed
curl -k -o /dev/null -s -w '%{http_code}\n' "$SERVER/livez"   # 200 - the health probe works
curl -k -o /dev/null -s -w '%{http_code}\n' "$SERVER/readyz"  # 200 - the health probe works
```

An authenticated request to `/readyz` (through the already configured kubectl context)
keeps working exactly the same - `AuthenticationConfiguration.anonymous.conditions`
only WIDENS access for anonymous requests to specific paths, but does not narrow access
for already authenticated clients:

```bash
k get --raw=/readyz # ok
```

Authentication without restrictive authorization is pointless - check that the
`--authorization-mode` on the static Pod is still `Node,RBAC` and does not contain `AlwaysAllow`
(kubeadm sets this by default, but it is worth making sure nothing changed the flag):

```bash
k get po -n kube-system -l component=kube-apiserver \
  -o jsonpath='{.items[0].spec.containers[0].command}' | tr ',' '\n' | grep authorization-mode
# --authorization-mode=Node,RBAC
```

Separately we audit the ClusterRoleBindings whose subjects point to the anonymous user
or group - the cluster deliberately contains one such lab-owned binding:

```bash
k get clusterrolebinding -o json | jq -r \
  '.items[] | select([.subjects[]? | select(.name == "system:anonymous" or .name == "system:unauthenticated")] | length > 0) | .metadata.name'
# system:public-info-viewer
# lab104-unintended-anonymous-access
```

`system:public-info-viewer` is a standard kubeadm binding: it also targets
`system:unauthenticated`, but its ClusterRole allows a read-only `GET` only to the
non-resource URLs `/livez`, `/readyz`, `/healthz`, `/version`, `/version/`, and not to regular
Kubernetes resources - this is default Kubernetes RBAC, a required part of the bootstrap; do not touch
it. This is not the same thing as the `anonymous.conditions` of this same task: that list
restricts on which paths a request gets an anonymous identity at the authentication stage at all
(there only `/livez`/`/readyz`/`/healthz`) - `/version` returns `401` anonymously
precisely because the anonymous identity is not assigned there, and not because
`system:public-info-viewer` lacks permissions there. `lab104-unintended-anonymous-access` is
an intentional lab-owned finding: its ClusterRole `lab104-anonymous-debug-access` gives
a full-fledged RBAC `get`/`list` on `pods`/`secrets`/`configmaps` cluster-wide, that is, ANY
anonymous request can read them. We delete both objects, as in tasks 4/7:

```bash
k delete clusterrolebinding lab104-unintended-anonymous-access
k delete clusterrole lab104-anonymous-debug-access
```

We confirm the revocation with a negative control on behalf of exactly the unauthenticated identity
(`system:anonymous` + the group `system:unauthenticated`, and nothing else) via
`SubjectAccessReview` - it is created by the admin context, so the list of groups does not have to be
artificially extended:

```bash
for R in pods secrets configmaps; do
  for NS in $(k get ns -o jsonpath='{.items[*].metadata.name}'); do
    ALLOWED=$(k create -o jsonpath='{.status.allowed}' -f - <<EOF
apiVersion: authorization.k8s.io/v1
kind: SubjectAccessReview
spec:
  user: system:anonymous
  groups: ["system:unauthenticated"]
  resourceAttributes:
    namespace: $NS
    resource: $R
    verb: get
EOF
    )
    printf '%-12s %-24s %s\n' "$R" "$NS" "$ALLOWED"
  done
done
# false is expected for every row
```

Do not add `--as-group=system:authenticated` to `can-i --as=system:anonymous`: a real
unauthenticated request does not belong to that group, and the check would stop reflecting the
true anonymous identity. We check each namespace separately, because a
RoleBinding is valid only in its own namespace: the absence of a cluster-wide binding does not
prove the absence of a local one, and the acceptance criterion requires that there be no access in any namespace.

At the end run `check_result`.

## 6. A Secret leak via env into `/proc/1/environ`: moving to a volume

`app-vulnerable` receives `db-creds` via `envFrom`, so the value ends up in the
environment of the container's PID 1 process. Anyone who has the right to `kubectl exec` into this
Pod can read the secret directly from `/proc`, without calling the Kubernetes API and without RBAC
on `get secrets`:

```bash
mkdir -p /var/work/tests/artifacts/6
k exec -n security-104 app-vulnerable -- cat /proc/1/environ \
  | tr '\0' '\n' | grep DB_PASSWORD | tee /var/work/tests/artifacts/6/env-leak-before.txt
```

We save exactly the line `DB_PASSWORD=<real value>` from the process environment, and not
just the word `DB_PASSWORD` without a value - the checker itself will compare it with the actual value
from the Secret `db-creds`; you do not need to compute and compare the value yourself separately.

We recreate the Pod with the same name: we remove `envFrom`, mount the same Secret as the volume
`db-creds-vol` at `/etc/secrets`, read-only, with `defaultMode: 0400` (`256` in decimal, as
shown by `kubectl get pod -o json`). `0400` is read-only for the file owner
inside the container only; the application process itself must still run under this UID, otherwise
it will not be able to read the file.

Most Pod fields (including `volumes`) are immutable, so the Pod must be deleted and created again with the same name. Again it is cheaper to
generate a skeleton via `--dry-run` and add the volume in `vim` than to write the whole YAML:

```bash
k run app-vulnerable -n security-104 --image=busybox:1.36 --command --dry-run=client -o yaml \
  -- sh -c "sleep 3600" > app-vulnerable-fixed.yaml
vim app-vulnerable-fixed.yaml
```

```yaml
# Add to the Pod spec:
spec:
  automountServiceAccountToken: false     # add
  containers:
  - name: app-vulnerable
    volumeMounts:                         # add
    - name: db-creds-vol                  # add
      mountPath: /etc/secrets             # add
      readOnly: true                      # add
    ...
  volumes:                                # add
  - name: db-creds-vol                    # add
    secret:                               # add
      secretName: db-creds                # add
      defaultMode: 0400                   # add
```

```bash
k delete pod app-vulnerable -n security-104
k apply -f app-vulnerable-fixed.yaml
k wait -n security-104 --for=condition=Ready po/app-vulnerable --timeout=120s
```

We confirm the three final properties, and not only "the secret is not in the environment": the file
permissions are exactly `400` (and not merely that somewhere the substring `400` occurs), and, more importantly, the application
can still REALLY read the secret value - otherwise the hardening could silently
break the very functionality of the application:

```bash
k exec -n security-104 app-vulnerable -- cat /proc/1/environ | tr '\0' '\n' | grep DB_PASSWORD
# nothing found - this is expected

k exec -n security-104 app-vulnerable -- stat -L -c '%a' /etc/secrets/DB_PASSWORD \
  | tee /var/work/tests/artifacts/6/secret-file-mode.txt
# 400 - exactly this value, and not arbitrary text containing "400" somewhere. The -L flag is
# required: the secret volume is mounted via a chain of symlinks ("..data"), and without -L
# stat will show the mode of the symlink itself (always 777 on Linux), not of the real file.

# Positive control: the application process must really be able to read the secret value.
k exec -n security-104 app-vulnerable -- cat /etc/secrets/DB_PASSWORD
# must match the value that was in env-leak-before.txt before the fix
```

`defaultMode: 0400` protects against reading by other UIDs in this same Pod (for example, by a neighboring
sidecar container without the needed UID), but it does not replace encryption at rest in etcd and does not prevent
a process running under the expected UID from reading the file itself - the mount allows exactly that.
Also make sure that `db-creds` is not mounted in a SECOND way at the same time
(for example, also via a `projected` volume) - exactly one volume that
mounts this Secret must remain.

At the end run `check_result`.

## 7. Auditing and revoking hidden RBAC privilege escalation paths

`build-agent-hidden-privesc` does not contain the wildcard `*`, but `impersonate`/`bind`/`escalate`/
CSR approval are a separate category of dangerous verbs: they do not widen the list of visible
resources, but give the ability to **act on behalf of someone else** or to **grant yourself
additional permissions**. In this version of the fixture the ClusterRole also contains the base
`create`/`update` on `clusterroles`/`clusterrolebindings` - without them `bind`/`escalate`
would be incomplete escalation primitives (RBAC requires EITHER that you already have the permissions from the role, or
that you explicitly have `escalate`/`bind` IN THE CONTEXT of an attempt to actually create/update a Role/Binding).
We find all ClusterRoleBindings whose ClusterRoles allow any of the dangerous verbs. We go not
from the ClusterRoles (there are dozens in the cluster, including the standard `system:*`) but from the
ClusterRoleBindings - `kubectl get clusterrolebinding` already shows by default the column
`ROLE` (format `ClusterRole/<name>`), and `-o wide` adds `USERS`/`GROUPS`/
`SERVICEACCOUNTS` as well - neither custom-columns nor YAML are needed:

```bash
mkdir -p /var/work/tests/artifacts/7
k get clusterrolebinding -o wide | grep -v system:
# build-agent-hidden-privesc   ClusterRole/build-agent-hidden-privesc   ...   security-104/build-agent
```

For each candidate we look at its ClusterRole in a human-readable form, without `jq`/`grep` over YAML -
`kubectl describe` prints the verbs as a table itself, and you immediately see `impersonate`/`bind`/
`escalate` and the separate rule on `certificatesigningrequests/approval`:

```bash
k describe clusterrole build-agent-hidden-privesc
# The Verbs in the PolicyRule table will show impersonate / bind / escalate / update
# (on certificatesigningrequests/approval) - you can see by eye that the role is dangerous
```

We save the name of the ClusterRoleBinding (not the ClusterRole - they may not match; in this lab
they coincided by chance) to the artifact:

```bash
echo build-agent-hidden-privesc > /var/work/tests/artifacts/7/dangerous-bindings-before.txt
cat /var/work/tests/artifacts/7/dangerous-bindings-before.txt
```

`build-agent-hidden-privesc` must be in the final file (as the name of the ClusterRoleBinding,
not of the ClusterRole). We delete exactly this ClusterRoleBinding (and the ClusterRole, so that the template does not
remain for reuse), without touching the `system:*` bindings, which give the
core Kubernetes components the necessary `impersonate`/CSR access:

```bash
k delete clusterrolebinding build-agent-hidden-privesc
k delete clusterrole build-agent-hidden-privesc
```

We confirm the revocation of ALL the declared dangerous permissions, and not only some of them. Two subtleties:
the fixture gives `impersonate` on all three resource types at once (`users`/`groups`/`serviceaccounts`) -
checking only `users` does not prove the revocation of the other two; and the `TYPE/NAME` in `kubectl auth
can-i` is a resourceName, not a subresource (`kubectl auth can-i --help` itself shows
the example "jobs.batch/bar" - a check of an object literally named `bar`), so for
`certificatesigningrequests/approval` you need the separate flag `--subresource=approval`, and not
a slash:

```bash
k auth can-i impersonate users --as=system:serviceaccount:security-104:build-agent
k auth can-i impersonate groups --as=system:serviceaccount:security-104:build-agent
k auth can-i impersonate serviceaccounts -n security-104 --as=system:serviceaccount:security-104:build-agent
k auth can-i bind clusterroles --as=system:serviceaccount:security-104:build-agent
k auth can-i escalate clusterroles --as=system:serviceaccount:security-104:build-agent
k auth can-i update certificatesigningrequests --subresource=approval --as=system:serviceaccount:security-104:build-agent
k auth can-i approve signers/kubernetes.io/kube-apiserver-client --as=system:serviceaccount:security-104:build-agent
# no / no / no / no / no / no / no
```

At the end run `check_result`.

## 8. Namespace-level baseline: the `default` SA without automount

Task 3 disabled automount in a targeted way, for a specific Pod and its own SA. Here
you need a systemic baseline: we fix the `default` SA of the namespace **before** any
Pods are created in it, so that no new workload gets a token by default, even if the developer
forgets the explicit field in the manifest.

The ServiceAccount `default` is created by a separate controller asynchronously after the
Namespace appears - `kubectl wait` can wait precisely for the appearance of an object (`--for=create`), not
only for its condition, so neither a manual retry nor a home-made loop is needed:

```bash
k create namespace security-104-baseline
k wait -n security-104-baseline --for=create sa/default --timeout=30s

k -n security-104-baseline patch sa default \
  -p '{"automountServiceAccountToken":false}'
k -n security-104-baseline get sa default \
  -o jsonpath='{.automountServiceAccountToken}{"\n"}'
# false
```

We create a Pod that sets **neither** `serviceAccountName` nor `automountServiceAccountToken` -
this is the most frequent case in reality, when the developer simply does not think about the SA. The field
`automountServiceAccountToken` must be ABSENT from the Pod spec - an explicit `false`
would prove only a targeted setting of the Pod itself (as in task 3), and not that the
namespace-level baseline really works.

Here not even `--dry-run` is needed - since not a single SA/automount field is added to the Pod,
`kubectl run` without flags creates exactly what is needed, directly:

```bash
k run implicit-default-sa -n security-104-baseline --image=busybox:1.36 --command -- sh -c "sleep 3600"
k wait -n security-104-baseline --for=condition=Ready po/implicit-default-sa --timeout=60s
k get po implicit-default-sa -n security-104-baseline -o jsonpath='{.spec.serviceAccountName}{"\n"}'
# default

k get po implicit-default-sa -n security-104-baseline \
  -o jsonpath='{.spec.automountServiceAccountToken}{"\n"}'
# empty output - the field is absent from the spec, and is not set to false

k exec -n security-104-baseline implicit-default-sa -- \
  test ! -e /var/run/secrets/kubernetes.io/serviceaccount/token
echo "exit code: $?"
# exit code: 0 - the file is absent, and the exec itself worked successfully (unlike a trivial
# "cat" of a non-existent file, which also exits with a non-zero code, but for a different
# reason - test ! -e performs exactly the check that is needed, and its own success
# must be required separately, rather than simply "any error = no file")
```

The SA value works only if the Pod does not override it itself. If the same namespace
later needs a Pod with API access, add `automountServiceAccountToken: true` explicitly in the
specific manifest after checking that the access is really needed - do not change the baseline of the
`default` SA back to `true` for the whole namespace. Also do not manually mount an old
(legacy) `Secret` with `type: kubernetes.io/service-account-token` via `volumes[].secret` -
that would give the Pod a valid API token regardless of the automount settings.

At the end run `check_result`.

## 9. Integration task: detecting a dangerous RBAC change → audit log → containment

Tasks 1-8 closed the specific privilege escalation paths available to `build-agent` itself
(wildcard, impersonate/bind/escalate, automount). Here a different layer of protection is needed -
the detection of a **dangerous RBAC grant issued by an administrator** (by mistake, through
compromised automation, or maliciously), and not only a current snapshot of RBAC.
We connect to the control-plane and prepare a minimal audit backend:

```bash
ssh control-plane
sudo -i
mkdir -p /etc/kubernetes/audit /var/log/kubernetes/audit
cat > /etc/kubernetes/audit/policy.yaml <<'EOF'
apiVersion: audit.k8s.io/v1
kind: Policy
omitStages:
- RequestReceived
rules:
- level: RequestResponse
  resources:
  - group: "rbac.authorization.k8s.io"
    resources: ["clusterroles", "clusterrolebindings"]
- level: Metadata
EOF
```

The RBAC rule is first - the more specific rule must come before the general
catch-all, otherwise `Metadata` intercepts the event first. `omitStages: [RequestReceived]`
at the level of the whole policy removes the extra record made before the request is processed - it has no
`requestObject`/`responseStatus`, and the checker filters such records out anyway (`stage ==
"ResponseComplete"`), and with a catch-all `Metadata` rule for ALL the other requests of the cluster
this stage would double the volume of audit.log for no benefit.

We edit the static manifest: we add `--audit-policy-file`/`--audit-log-path` and the hostPath
volume/volumeMount for the policy and log directories - by the same technique as in task 5 for
`authentication-config.yaml`:

```bash
cp /etc/kubernetes/manifests/kube-apiserver.yaml ~/9-api.yaml
vim /etc/kubernetes/manifests/kube-apiserver.yaml
# In the command array add lines with the same indentation as the other arguments:
#   - --audit-policy-file=/etc/kubernetes/audit/policy.yaml
#   - --audit-log-path=/var/log/kubernetes/audit/audit.log
# In the container's volumeMounts (the same indentation as the neighboring items):
#   - mountPath: /etc/kubernetes/audit
#     name: audit-policy
#     readOnly: true
#   - mountPath: /var/log/kubernetes/audit
#     name: audit-log
# In the Pod's volumes (the same indentation as the neighboring items):
#   - hostPath:
#       path: /etc/kubernetes/audit
#       type: Directory
#     name: audit-policy
#   - hostPath:
#       path: /var/log/kubernetes/audit
#       type: DirectoryOrCreate
#     name: audit-log
systemctl restart kubelet
exit
exit
```

`systemctl restart kubelet` forces an immediate rebuild of the static Pod - as in
task 5, this is faster than waiting for the kubelet to notice the file change itself:

```bash
k get po -n kube-system -l component=kube-apiserver
# STATUS must become Running - if not yet, wait a couple of seconds and repeat
```

We return to the work machine (as the administrator `cluster1-admin`) and create the
dangerous binding - this is **not** an escalation attempt by `build-agent` (it no longer has
real paths to this after task 7), but a modeled administrator action
that the audit log must catch as reproducible evidence of who exactly
did it and to whom exactly the permissions were granted:

```bash
k create clusterrolebinding incident-simulated-escalation \
  --clusterrole=cluster-admin \
  --serviceaccount=security-104:build-agent
```

First we simply verify by eye that the audit rule really works and the event got into
the log - on the exam it is usually exactly this check that is needed, and not a ready artifact:

```bash
ssh control-plane
sudo cat /var/log/kubernetes/audit/audit.log | jq . | grep -A 30 incident-simulated-escalation
exit
```

`jq .` prints each log record in a human-readable form (one field per line); `grep -A 30`
shows the found line with the name and 30 lines AFTER it - this is enough to see
`stage`, `user.username` (the real initiator), `requestObject.roleRef`,
`requestObject.subjects` by eye, without any special jq syntax.

That is enough for the real exam, but this lab additionally requires an artifact file with
the event - not because the checker needs more than knowing that the rule works (it itself, independently,
reads `audit.log` on the control-plane over SSH), but to check a separate skill:
extracting and saving the REAL record as forensic evidence, and not retelling it
in your own words (the checker compares the `auditID` of your file with the `auditID` of the real record in the log).
`/var/work/tests/artifacts/9/` is a path on the WORK machine, not on the control-plane, so
we save from the work machine via `ssh control-plane "..."`, using the same combination of grep over plain
substrings (the event name + `ResponseComplete`, so as not to hit an intermediate
`ResponseStarted` record of the same request):

```bash
mkdir -p /var/work/tests/artifacts/9
ssh control-plane "sudo cat /var/log/kubernetes/audit/audit.log" \
  | grep incident-simulated-escalation | grep ResponseComplete \
  | tail -n1 > /var/work/tests/artifacts/9/audit-escalation-event.json
```

We save the event **in full**, as it really lies in the audit log (including `auditID`) - we do not
rewrite it or assemble the JSON by hand, otherwise the artifact will not match the real
record in the log during verification.

Containment: we delete the binding and confirm that the access is really revoked, and not that the
object has simply become unreadable. `can-i` without `-n`/`-A` checks only the current namespace
of the kubeconfig context, not the whole cluster - for a namespaced RoleBinding in `security-104`
(unlike the already deleted cluster-wide ClusterRoleBinding) this changes the result,
so we specify the namespace explicitly:

```bash
k delete clusterrolebinding incident-simulated-escalation
k auth can-i '*' '*' -n security-104 --as=system:serviceaccount:security-104:build-agent \
  | tee /var/work/tests/artifacts/9/containment-result.txt
# no
```

The difference from task 7: there we found and revoked an **already existing** hidden path through
static analysis of RBAC objects, belonging to the workload itself (`build-agent`). Here the
source of truth is an **event in time** (the audit log), which proves who exactly
(the field `user.username` - the real initiator of the request, in this case the administrator, and not
`build-agent`) granted the dangerous permissions and to whom exactly - this is what is needed for a real
incident, when the object itself could already have been deleted after use, while `build-agent` in the
event appears only as the recipient of the permissions, and not as the author of the request.

At the end run `check_result`.

## 12. Client certificate user via CSR + namespaced RBAC

We generate a private key and a CSR with `CN=john` - RBAC for a certificate-based user
is bound via `kind: User`, not `ServiceAccount`, and a `User` has no API
object of its own: its identity is determined entirely by the CN in the client certificate
matching the `name` in the binding.

```bash
mkdir -p /var/work/tests/artifacts/12
openssl genrsa -out /var/work/tests/artifacts/12/john.key 2048
openssl req -new -key /var/work/tests/artifacts/12/john.key \
  -out /tmp/john.csr -subj "/CN=john"
```

We submit it as a Kubernetes `CertificateSigningRequest` with the same signer that is already
used in task 7 for CSR approval (`kubernetes.io/kube-apiserver-client` is
the correct signer precisely for a client-auth certificate that will authenticate
requests to the API server):

```bash
cat > john-csr.yaml <<EOF
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: john-csr
spec:
  request: $(base64 -w0 /tmp/john.csr)
  signerName: kubernetes.io/kube-apiserver-client
  usages: ["client auth"]
EOF
k apply -f john-csr.yaml
k certificate approve john-csr
k get csr john-csr -o jsonpath='{.status.certificate}' \
  | base64 -d > /var/work/tests/artifacts/12/john.crt
```

We check that the certificate is really signed by this cluster, and not only that the field
`status.certificate` is non-empty:

```bash
openssl verify -CAfile <(ssh control-plane sudo cat /etc/kubernetes/pki/ca.crt) \
  /var/work/tests/artifacts/12/john.crt
# /var/work/tests/artifacts/12/john.crt: OK
openssl x509 -in /var/work/tests/artifacts/12/john.crt -noout -subject
# subject=CN = john
```

RBAC: a Role in `development`, a RoleBinding to `kind: User, name: john` - `--user=john` in
`kubectl create rolebinding` sets `kind: User` itself, you do not need to write YAML:

```bash
k create role john-pod-access -n development --resource=pods --verb=create,list,get
k create rolebinding john-pod-access-binding -n development \
  --role=john-pod-access --user=john

k auth can-i create pods -n development --as=john  # yes
k auth can-i list pods -n development --as=john    # yes
k auth can-i get pods -n development --as=john     # yes
k auth can-i delete pods -n development --as=john  # no
k auth can-i create pods -n security-104 --as=john # no
```

`--as=john` proves only the RBAC logic (impersonation, available to any admin
regardless of whether a real certificate was issued). Separately we prove that the
ISSUED certificate is really accepted by the API server via a real TLS client-auth
request:

```bash
SERVER=$(k config view --minify -o jsonpath='{.clusters[0].cluster.server}')
ssh control-plane sudo cat /etc/kubernetes/pki/ca.crt > /tmp/cluster-ca.crt
curl -s -o /dev/null -w '%{http_code}\n' --cacert /tmp/cluster-ca.crt \
  --cert /var/work/tests/artifacts/12/john.crt --key /var/work/tests/artifacts/12/john.key \
  "$SERVER/api/v1/namespaces/development/pods"     # 200
curl -s -o /dev/null -w '%{http_code}\n' --cacert /tmp/cluster-ca.crt \
  --cert /var/work/tests/artifacts/12/john.crt --key /var/work/tests/artifacts/12/john.key \
  "$SERVER/api/v1/namespaces/security-104/pods"     # 403
```

The same proof, but through the familiar `kubectl` and not `curl` - we build a separate
kubeconfig for John from the already issued certificate (`set-credentials` with `--client-certificate`/
`--client-key`, and not `--token`, because the identity here is specifically a client-cert, not a
ServiceAccount token):

```bash
k config set-cluster cluster1 --server="$SERVER" \
  --certificate-authority=/tmp/cluster-ca.crt --embed-certs=true \
  --kubeconfig=/var/work/tests/artifacts/12/john.kubeconfig
k config set-credentials john \
  --client-certificate=/var/work/tests/artifacts/12/john.crt \
  --client-key=/var/work/tests/artifacts/12/john.key --embed-certs=true \
  --kubeconfig=/var/work/tests/artifacts/12/john.kubeconfig
k config set-context john@cluster1 --cluster=cluster1 --user=john \
  --kubeconfig=/var/work/tests/artifacts/12/john.kubeconfig
k config use-context john@cluster1 \
  --kubeconfig=/var/work/tests/artifacts/12/john.kubeconfig

k --kubeconfig=/var/work/tests/artifacts/12/john.kubeconfig get pods -n development
# works - RBAC lets it through

k --kubeconfig=/var/work/tests/artifacts/12/john.kubeconfig get pods -n security-104
# Error from server (Forbidden) - the same 403 as in the curl check above

k --kubeconfig=/var/work/tests/artifacts/12/john.kubeconfig auth whoami
# Username: john - confirms that the kubeconfig really authenticates as
# john, and not merely happens to give the needed response codes
```

At the end run `check_result`.
