# Lab 101 - NetworkPolicy: default-deny, იზოლაცია და EC2 IMDS

## აღწერა

`NetworkPolicy` მუშაობს როგორც allow-list: default-deny-ის შემდეგ საჭირო ნაკადები უბრუნდება მხოლოდ აშკარა წესებით. წესების იძულებით გამოყენებას უზრუნველყოფს Calico. ამ ლაბორატორიის worker არის EC2 instance, რომელსაც Terraform მართავს; მისი Instance Metadata Service (IMDS) ხელმისაწვდომია მისამართზე `http://169.254.169.254/`. Terraform აშკარად რთავს HTTP endpoint-ს, ტოვებს IMDSv1 GET-ს დასაშვებად უსაფრთხო probe-სთვის და ადგენს response hop limit-ს `2`-ზე, რათა default-deny-მდე ჩვეულებრივმა Pod-მა შეძლოს IMDS-ის ქსელური მისაწვდომობის დადასტურება.

ლაბორატორია ამოწმებს მხოლოდ IMDS endpoint-ის ქსელურ მისაწვდომობას, metadata-ს ან credentials-ის წაკითხვის გარეშე. ნებისმიერი რეალურად მიღებული HTTP status `1xx–5xx` ნიშნავს, რომ TCP/HTTP გზა IMDS-მდე არსებობს. `HTTPCODE:000` transport error/timeout-თან ერთად ნიშნავს HTTP-პასუხის არარსებობას. კონკრეტული HTTP status დამოკიდებულია EC2 metadata options-ზე: თუ token usage არის `required`, GET ვალიდური IMDSv2 token-ის გარეშე იღებს `401`-ს; თუ IMDSv1 დაშვებულია, tokenless GET განიხილება როგორც IMDSv1-მოთხოვნა და შეიძლება მიიღოს ჩვეულებრივი HTTP response.

**ნარჩენი რისკი.** worker EC2-ს მიმაგრებული აქვს IAM instance profile, და tokenless IMDSv1 GET `latest/meta-data/iam/security-credentials/<role>`-ზე რეალურად აბრუნებს დროებით AWS credentials-ს (AccessKeyId/SecretAccessKey/SessionToken) - ეს არ არის ჰიპოთეტური რისკი, არამედ მიმდინარე გარემოს ფაქტობრივი ქცევა. თავად როლი შეზღუდულია თითქმის ნულოვანი უფლებებით (least privilege: ის ვერც კი კითხულობს საკუთარ IAM-როლს `iam:GetRole`-ის გავლით), ამიტომ გაჟონვის პრაქტიკული ღირებულება თავდამსხმელისთვის მინიმალურია, მაგრამ სტუდენტმა აშკარად უნდა გააცნობიეროს, რომ production-ში იგივე კონფიგურაციის (`HttpTokens=optional`, IMDSv1 დაშვებულია) დროს ეს იგივე ბრძანება დააბრუნებდა სამუშაო როლის რეალურ credentials-ს რეალური უფლებებით. ლაბორატორია განზრახ ამრავლებს ამ anti-pattern-ს 02.1 თავიდან (IMDSv1 allowed, response hop limit `2`) probe-ის და ამ სისუსტის NetworkPolicy-ით პოვნის სწავლების მიზნით; production-ში გამოიყენეთ `HttpTokens=required` (IMDSv2 only) და `HttpPutResponseHopLimit=1`.

## განთავსება

მართვის მანქანაზე გაუშვით გარემო:

```bash
TASK=101 make run_cks_task
```

წარმატებული განთავსების შემდეგ Terraform გამოიტანს SSH-ბრძანებას worker-თან დასაკავშირებლად. ის იქნება ფორმატში:

```
worker_pc_ssh = "ssh ubuntu@<IP> password=<PASSWORD>"
```

მაგალითად:

```
18:53:06.019 STDOUT [worker] terraform: worker_pc_ssh = "ssh ubuntu@18.193.110.150 password= fq0J9RuZWN"
```

დასაკავშირებლად გამოიყენეთ მხოლოდ მისამართი ბრძანებიდან:

```bash
ssh ubuntu@<IP>
```

როცა SSH პაროლს მოგთხოვთ, შეიყვანეთ მნიშვნელობა, რომელიც Terraform-მა აჩვენა `password=`-ის შემდეგ.

**runtime-შემოწმებებისთვის** გამოიყენეთ დროებითი დიაგნოსტიკური Pod იმავე labels-ით, რაც შემოწმებადი identity-ს აქვს. HTTP-შემოწმებებისთვის გჭირდებათ curl-ით image (`curlimages/curl:8.11.1`); DNS-ისთვის - nslookup-ით image (`busybox`). შემოწმების შემდეგ წაშალეთ დროებითი Pod-ები და დროებითი policy.

იმუშავეთ worker-ზე. დაწყებამდე დარწმუნდით, რომ namespaces სუფთაა (ყოველი შემთხვევისთვის):

```bash
kubectl delete namespace cks-101 cks-101-legacy imds-control --ignore-not-found --wait=true
printf 'EC2 IMDS target: %s\n' 'http://169.254.169.254/'
time_left
```

თითოეული ეტაპი თვითონ შეამოწმეთ თქვენს რესურსებზე; `check_result` გაუშვით დავალებების შესრულების შემდეგ, ხოლო ეტალონური ამოხსნა გახსენით მხოლოდ საკუთარი მცდელობის შემდეგ ან სირთულის შემთხვევაში.

## მიზანი

მინიმალური ingress/egress allow-list-ის გამართვა, image digest-ის დაფიქსირება, AND selector-ის სემანტიკისა და IMDS-ისთვის ზუსტი `ipBlock.except`-ის დამტკიცება, და შემდეგ ჩვეულებრივი Pod-ის შედარება `hostNetwork`-თან, წინასწარ უნივერსალური შედეგის დაშვების გარეშე.
