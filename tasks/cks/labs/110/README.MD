# Lab 110 - gVisor RuntimeClass, Cilium WireGuard, and Istio mTLS

## Goal

In this CKS lab you build three independent layers of workload protection: the sandboxed runtime
**gVisor** via `runsc`, Cilium WireGuard inter-node encryption, and Istio service-to-service
mTLS. At the end you will not only see the settings but prove them with observable
results: the difference in the gVisor kernel view, WireGuard packets without an HTTP marker, and the different
result of a call from the mesh and from a plaintext client outside the mesh.

## Self-check before you start

<details>
<summary>1. How does the gVisor userspace kernel fundamentally differ from the guest kernel of a virtual machine?</summary>

gVisor (`runsc`) implements its own subset of Linux syscalls IN USERSPACE, intercepting the container's system calls and handling them itself, without passing them directly to the host kernel - the container process sees a different "kernel" (a different `uname -r`, different behavior of some syscalls). A guest kernel (for example, Kata Containers) runs a FULL Linux kernel inside a lightweight VM - stronger isolation, but with the overhead of full virtualization that gVisor does not have.
</details>

<details>
<summary>2. What exactly does a WireGuard peer authenticate, and why is this NOT the same as the identity of a ServiceAccount?</summary>

WireGuard authenticates the cluster NODES through cryptographic keys generated by Cilium for each node - encryption happens at the level of the node-to-node tunnel. This protects the traffic BETWEEN nodes from eavesdropping at the network level, but has nothing to do with the identity of a specific Pod/ServiceAccount inside this traffic - Cilium WireGuard does not check "who" the sender is at the application level, only "which node".
</details>

<details>
<summary>3. Why does a successful `curl` with code 200 inside the mesh NOT prove that a plaintext client was really blocked?</summary>

A successful response INSIDE the mesh proves only that the mTLS connection between the two sidecars works - this is a positive control. To prove that STRICT really blocks NON-mesh traffic, a separate negative control is needed: a client WITHOUT a sidecar trying to reach the same service and getting a denial. One successful test is not enough - both are needed: allowed for the mesh identity, denied for plaintext.
</details>

## Infrastructure

Terragrunt creates Kubernetes `1.36.0` in `eu-central-1`:

| Component | Purpose |
|---|---|
| `k8s-1` control-plane | a regular containerd workload node, Cilium, and `tcpdump` for capturing the inter-node packet |
| `k8s-1` worker `gvisor` | a separate node with containerd, `runsc` installed, and the CRI handler `runsc` |
| CNI | **Cilium** (installed via the Cilium CLI with the Helm release `cilium`); WireGuard is deliberately switched off until task 4 |
| `worker` | a work machine with `kubectl`, `cilium`, `istioctl`, `check_result`, and SSH aliases to the nodes |

The matrix verified on 2026-08-31 (check it before each build): Kubernetes in the lab is
`1.36.0`; the Cilium data plane is a supported lab build whose compatibility with
Kubernetes `1.36` must be confirmed against the current requirements matrix; Cilium CLI `0.19.7`
(compatible with Cilium `1.17+`); Istio `1.30.4` (the `1.30` branch officially supports Kubernetes
`1.32–1.36`). The exam version does not determine the compatibility of the lab tooling here; according to the LF
it is currently `v1.34` and is checked separately before the exam.

After bootstrap, two workload placement labels are available:

```text
lab.cks.io/role=control-plane
sandbox.runtime/gvisor=true,lab.cks.io/role=gvisor
```

The control-plane is available for regular Pods without tolerations. The gVisor node is additionally tainted with
`sandbox.runtime/gvisor=true:NoSchedule`: only the Pods that tolerate this taint get onto it
(Pods with `RuntimeClass gvisor` get the needed toleration from `scheduling.tolerations` of the class).

The namespaces `sandbox-110` and `market` already exist. `market` has the label
`istio-injection=enabled` set in advance; the Istio control plane is not installed. To access the
sandbox node from the worker, use the alias `k8s110_node_gvisor`, for the control-plane -
`k8s110_controlPlane_1`.

## Tasks

| **1** | **Configure the containerd runtime and create a RuntimeClass for runsc** |
| :---: | :--- |
| What to do | • On `k8s110_node_gvisor` the `runsc` binary is already installed, but the bootstrap deliberately removed from `/etc/containerd/config.toml` the section `[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runsc]` with `runtime_type = "io.containerd.runsc.v1"` - this is a typical exam situation with a broken config.toml.<br/>• Restore this section (a backup is available at `/etc/containerd/config.toml.bak`, or add it manually) and run `sudo systemctl restart containerd`.<br/>• Create a `RuntimeClass` `gvisor` with the exact `handler: runsc`.<br/>• In `scheduling` set a `nodeSelector` `sandbox.runtime/gvisor: "true"`, so that a Pod with this class never lands on a regular node, and `tolerations` for the taint of the gVisor node (`sandbox.runtime/gvisor=true:NoSchedule`), otherwise the Pod will not get there. |
| Acceptance criteria | • On the node, `containerd` is active and `config.toml` contains a working section `runtimes.runsc` with `runtime_type = "io.containerd.runsc.v1"`<br/>• `kubectl get runtimeclass gvisor` exists, the handler equals `runsc`, and `scheduling` has a `nodeSelector` and `tolerations` for the taint of the gVisor node<br/>• `/var/work/tests/artifacts/1/runsc-runtime.txt` contains the exact line `RuntimeClass gvisor: handler runsc` |

<details>
<summary>💡 Hint for task 1</summary>

The backup `/etc/containerd/config.toml.bak` is the fastest way to restore, but check its content before copying it back (`diff` with the current file), to understand what exactly is missing. After restoring the `runtimes.runsc` section, be sure to `systemctl restart containerd` - simply editing the file does not apply the changes to an already running process.
</details>

| **4** | **Enable Cilium transparent encryption** |
| :---: | :--- |
| What to do | • First record the versions of Kubernetes, the Cilium agent, and the Cilium CLI in `/var/work/tests/artifacts/4/tool-versions.txt` and make sure that the data plane supports Kubernetes `1.36`.<br/>• Enable WireGuard in the existing Helm release created by `cilium install`: `cilium upgrade --version 1.20.1 --set encryption.enabled=true --set encryption.type=wireguard --wait`.<br/>• Restart the agents (`kubectl -n kube-system rollout restart daemonset/cilium`): Helm changes only the ConfigMap, and the DaemonSet template stays the same.<br/>• Check `cilium-config` (`enable-wireguard: "true"`) and the readiness of both Cilium agents.<br/>• A direct ConfigMap patch is acceptable only as a short-term training baseline probe with a mandatory confirmed rollback. | Acceptance criteria | • The version evidence exists and matches the real image of the DaemonSet `kube-system/cilium`<br/>• The Cilium agents (DaemonSet) are fully Ready<br/>• The status shows WireGuard and does not show IPsec at the same time<br/>• The debuginfo JSON contains peer/allowed-IP (or remote-node) evidence for the inter-node state<br/>• The ConfigMap `kube-system/cilium-config` contains `enable-wireguard: "true"` as the applied effective configuration from the Helm values<br/>• The setting survives a restart of one agent Pod (the checker restarts the Pod and rechecks the status) |

<details>
<summary>💡 Hint for task 4</summary>

Use the Helm values of the existing release `cilium` as the long-term source of truth for enabling WireGuard, and not ephemeral commands - a change made outside the Helm values may not survive an agent restart or an update of the Helm release, and the test specifically checks that the setting survives a restart. `cilium-dbg` is called INSIDE the agent Pod via `kubectl exec`, and not as a separate local binary on the worker. `cilium-dbg status` has NO flag `--all-encryption` - for detailed peer/allowed-IP evidence use `cilium-dbg debuginfo --output json`.
</details>

| **5** | **Prove the absence of plaintext between nodes** |
| :---: | :--- |
| What to do | • Build a BEFORE/AFTER baseline proof for one and the same inter-node flow.<br/>• **Baseline (WireGuard off):** on the control-plane run `tcpdump` on the IP of the remote node (`host <remote-node-ip>`, without a preliminary filter by `udp port 51871`); temporarily disable WireGuard (`enable-wireguard: "false"` in `cilium-config`, `rollout restart daemonset/cilium`); perform the request `runc-baseline -> gvisor-echo`; save this baseline capture and make sure that the plaintext `CKS110-WIREGUARD-MARKER` is visible in it.<br/>• **After (WireGuard on):** restore `enable-wireguard: "true"`, wait for Ready, and repeat THE SAME request with THE SAME capture scope (`host <remote-node-ip>`, without a port filter).<br/>• The capture is taken on the control-plane (into a file on the node), then copied with `scp` to the work machine as `/var/work/tests/artifacts/5/wireguard-tcpdump.txt`: it must now show only WireGuard UDP/`51871`, without the plaintext marker. |
| Acceptance criteria | • The final (post-change) capture for the same peer/interface scope contains UDP/`51871`, but does **not** contain `CKS110-WIREGUARD-MARKER`<br/>• A call between different nodes successfully receives the marker in the HTTP response<br/>• The checker itself repeats the post-change capture for the same peer/interface scope (not limiting itself in advance to only `udp port 51871`), and also itself temporarily disables and restores WireGuard to obtain its own baseline confirmation that the same flow in the plaintext state really exposes the marker on the wire |

<details>
<summary>💡 Hint for task 5</summary>

Capture the traffic on the REAL physical network interface of the node (for example `eth0`), and not on a virtual Pod/veth interface or on the internal Cilium interface `cilium_wg0` - by the design of the WireGuard tunnel, `cilium_wg0` carries ALREADY DECRYPTED traffic (that is its purpose), so a capture on `any` will see the marker there even with encryption working properly on the physical NIC. Determine the specific physical interface via `ip route get <remote-node-ip>` and use that interface. If the capture goes "inside" the Pod path before the WireGuard encryption, you will see plaintext HTTP regardless of whether node-to-node encryption is enabled. Run `tcpdump` IN THE BACKGROUND BEFORE you perform the HTTP request, not after. A capture filter ONLY by `udp port 51871` excludes the plaintext TCP from the result in advance and therefore does NOT prove its absence - use `host <remote-node-ip>` without a port filter, so that one and the same scope can really show the difference before/after enabling WireGuard. The checker runs its own `tcpdump` simultaneously with its own request (including the baseline probe with a temporary WireGuard disable and a verified subsequent restore) - your artifact is useful for learning, but is not the only proof: if encryption does not really work at the time of checking, the checker's live capture will detect this independently of the content of your file.
</details>

| **6** | **Istio PeerAuthentication STRICT** |
| :---: | :--- |
| What to do | • Install the pinned Istio `1.30.4` from the prepared `istioctl` (the minimal profile is sufficient) and record the version of the control plane.<br/>• In `market` create a `market-api` Deployment and a Service `market-api`: the application listens on `8080`, name the service port `http`. `market-api` must run on the gVisor node: `nodeSelector` `lab.cks.io/role: gvisor` and a toleration for its taint (`sandbox.runtime/gvisor=true:NoSchedule`).<br/>• Create an injected Deployment `market-client` in `market` and a plaintext Pod `mesh-outside` in `default`; all three workloads must be Running - **without** `PeerAuthentication` STRICT.<br/>• **Baseline:** the same outside plaintext request to `market-api` must get HTTP 200 (mTLS is not required yet); save this baseline response separately.<br/>• Apply the `PeerAuthentication` `market-strict` in the namespace `market` with `mtls.mode: STRICT` and repeat THE SAME outside request: the plaintext client without a sidecar must not get a successful application response, while the in-mesh request must get HTTP 200.<br/>• Save the status/headers/exit code in `artifacts/6/market-inside.txt` and `market-outside.txt` (append the line `exit_code=<curl exit code>` to the end of both files); do not match a specific socket error string. |
| Acceptance criteria | • The namespace keeps `istio-injection=enabled`<br/>• `PeerAuthentication market-strict` has `STRICT`<br/>• Inside the mesh there is HTTP 200, and the plaintext call from outside the mesh does not get a successful HTTP response (curl fails, no 2xx, the `exit_code` in the file is non-zero) - regardless of the exact error text<br/>• Both pieces of evidence are saved, `market-inside.txt` contains `exit_code=0`<br/>• Do not replace the plaintext client with a sidecar: it is exactly the absence of a sidecar that proves the STRICT denial.<br/>• The checker additionally repeats BEFORE/AFTER itself: it temporarily switches the same policy to `PERMISSIVE`, repeats the same plaintext request, and requires 200 - this proves that the previous denial was caused exactly by STRICT mTLS, and not by an independent DNS/network problem<br/>• Then the checker restores `STRICT` |

<details>
<summary>💡 Hint for task 6</summary>

The Service port MUST be named exactly `http` (not `market-api` or anything else) - Istio uses the named port convention to determine the protocol and handle the traffic correctly through the sidecar. `market-client` is created AFTER the namespace received `istio-injection=enabled` - if the Deployment was created BEFORE this label, the sidecar will not be added automatically, and you will have to recreate the Pod (not the Deployment) for injection.
</details>
