## 1. Restore the containerd runtime and create the RuntimeClass

The node `k8s110_node_gvisor` has already been delivered as a dedicated pool with `runsc` installed, but the
bootstrap deliberately removed the `runsc` runtime section from `/etc/containerd/config.toml` -
a typical exam situation where the binary is there but containerd does not know about it.

```bash
ssh k8s110_node_gvisor
sudo -i
```

```bash
# on the gVisor node (root): the binary is there, containerd is active, there is no runsc section in the config
runsc --version
systemctl is-active containerd
grep runsc /etc/containerd/config.toml

# append the runsc section (the runtime_type value must be exact) and restart containerd
cat >> /etc/containerd/config.toml <<EOF
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runsc]
  runtime_type = "io.containerd.runsc.v1"
EOF
systemctl restart containerd
systemctl is-active containerd
grep -A1 runtimes.runsc /etc/containerd/config.toml
exit   # from root
exit   # from the gVisor node
```

The kubelet does not need to be restarted: the kubelet passes the handler name from the `RuntimeClass` to
containerd each time a Pod is created, and not when the kubelet starts.

```yaml
# runtimeclass-gvisor.yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor
handler: runsc
scheduling:
  nodeSelector:
    sandbox.runtime/gvisor: "true"
  tolerations:
  - key: sandbox.runtime/gvisor
    operator: Equal
    value: "true"
    effect: NoSchedule
```

```bash
kubectl apply -f runtimeclass-gvisor.yaml
kubectl get runtimeclass gvisor -o yaml
printf 'RuntimeClass gvisor: handler runsc\n' \
  > /var/work/tests/artifacts/1/runsc-runtime.txt
```

`scheduling.nodeSelector` is an important boundary: the scheduler will not assign a `runsc` workload to the
control-plane, where there is no such handler. The gVisor node is, at the same time, tainted with
`sandbox.runtime/gvisor=true:NoSchedule` (`kubectl describe node <gvisor-node> | grep Taints`):
no Pod except those that tolerate it will get onto it. The `scheduling.tolerations` in the RuntimeClass
are automatically added to all Pods with this class, so `gvisor-sandbox` gets there,
and the others do not.

## 2. Start a sandboxed Pod and a Service

`busybox httpd` gives both a shell for `uname` and a small HTTP endpoint for the
inter-node WireGuard experiment. `runtimeClassName` is applied to the Pod, and not to the container.

The `nodeSelector` and `tolerations` in the Pod are set explicitly: this way it is visible which node it lands on and why.
This is the same as described in the `scheduling` of the `RuntimeClass` itself. If you do not specify them in the Pod,
nothing breaks: when a Pod with `runtimeClassName` is created, Kubernetes itself **adds** to it the
`nodeSelector` and `tolerations` from `RuntimeClass.scheduling` (check: `kubectl -n sandbox-110 get
pod gvisor-sandbox -o jsonpath='{.spec.nodeSelector}'`). But then this is not visible in the manifest, and without
`scheduling` in the RuntimeClass the Pod could land on a node without `runsc` and fail to start.

```yaml
# gvisor-sandbox.yaml
apiVersion: v1
kind: Pod
metadata:
  name: gvisor-sandbox
  namespace: sandbox-110
  labels:
    app: gvisor-echo
spec:
  runtimeClassName: gvisor
  nodeSelector:
    sandbox.runtime/gvisor: "true"
  tolerations:
  - key: sandbox.runtime/gvisor
    operator: Equal
    value: "true"
    effect: NoSchedule
  automountServiceAccountToken: false
  containers:
  - name: app
    image: busybox:1.36
    command:
    - sh
    - -ec
    - |
      mkdir -p /www
      printf 'CKS110-WIREGUARD-MARKER\n' >/www/index.html
      exec httpd -f -p 8080 -h /www
    ports:
    - containerPort: 8080
      name: http
---
apiVersion: v1
kind: Service
metadata:
  name: gvisor-echo
  namespace: sandbox-110
spec:
  selector:
    app: gvisor-echo
  ports:
  - name: http
    port: 8080
    targetPort: 8080
```

```bash
kubectl apply -f gvisor-sandbox.yaml
kubectl wait -n sandbox-110 --for=condition=Ready pod/gvisor-sandbox --timeout=180s
{
  printf 'gvisor uname -r: '
  kubectl exec -n sandbox-110 gvisor-sandbox -- uname -r
  printf '\n--- gvisor dmesg ---\n'
  kubectl exec -n sandbox-110 gvisor-sandbox -- dmesg 2>&1 || true
} > /var/work/tests/artifacts/2/gvisor-kernel.txt
cat /var/work/tests/artifacts/2/gvisor-kernel.txt
kubectl get pod -n sandbox-110 gvisor-sandbox -o wide
```

The gVisor Sentry shows the workload a synthetic kernel view; `dmesg` prints not the
kernel log of the node but a short synthetic log that begins with the line `Starting gVisor...` (this is exactly what the
checker expects). This is expected and is not a reason to give the container extra privileges.

## 3. A regular runc Pod for comparison

The absence of `runtimeClassName` leaves the default handler `runc`. The selector deliberately
places this Pod on the control-plane, so the following tasks generate inter-node
traffic.

```yaml
# runc-baseline.yaml
apiVersion: v1
kind: Pod
metadata:
  name: runc-baseline
  namespace: sandbox-110
spec:
  nodeSelector:
    lab.cks.io/role: control-plane
  automountServiceAccountToken: false
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
```

```bash
kubectl apply -f runc-baseline.yaml
kubectl wait -n sandbox-110 --for=condition=Ready pod/runc-baseline --timeout=180s
{
  printf 'gvisor uname -r: '
  kubectl exec -n sandbox-110 gvisor-sandbox -- uname -r
  printf 'runc uname -r: '
  kubectl exec -n sandbox-110 runc-baseline -- uname -r
} > /var/work/tests/artifacts/3/runtime-comparison.txt
cat /var/work/tests/artifacts/3/runtime-comparison.txt
```

A regular `runc` container sees the host kernel release, while the gVisor workload sees the Sentry view.
This is an additional execution boundary, and not a replacement for `SecurityContext`, seccomp, or
image checking.

## 4. Enable Cilium WireGuard

Cilium manages the WireGuard keys and peers itself. We enable one encryption backend - we do not
add IPsec. Important: the **client** `cilium` CLI (installed on the worker) has no
`encrypt enable` subcommand; WireGuard is enabled through the Cilium configuration, and not by a
runtime command. First we record the versions and check the agent against the requirements matrix:

```bash
agent=$(kubectl -n kube-system get pods -l k8s-app=cilium -o jsonpath='{.items[0].metadata.name}')
{
  printf 'Kubernetes='
  kubectl version -o json | jq -r '.serverVersion.gitVersion'
  printf 'Cilium agent='
  kubectl -n kube-system get pod "$agent" -o jsonpath='{.spec.containers[?(@.name=="cilium-agent")].image}'
  printf '\n'
  cilium version --client
  printf 'Cilium CLI=v0.19.7\n'
  printf 'Cilium data plane=verify current supported lab build against Kubernetes 1.36 requirements matrix\n'
  printf 'Istio=1.30.4\n'
} > /var/work/tests/artifacts/4/tool-versions.txt
cat /var/work/tests/artifacts/4/tool-versions.txt
```

The cluster was deployed with the `cilium install` command, which installs Cilium **via Helm**.
The long-term source of truth is the Helm values of the release `cilium`; we use the pinned Cilium CLI upgrade and afterwards check the live ConfigMap and the agents:

```bash
cilium upgrade --version 1.20.1 \
  --set encryption.enabled=true --set encryption.type=wireguard --wait
# Helm changes only the ConfigMap: the DaemonSet template does not change, so the agents do not
# restart themselves and keep working without WireGuard - restart them explicitly.
kubectl -n kube-system rollout restart daemonset/cilium
kubectl -n kube-system rollout status daemonset/cilium --timeout=180s
test "$(kubectl -n kube-system get cm cilium-config -o jsonpath='{.data.enable-wireguard}')" = true
cilium status --wait
```

We read the encryption status from the agent via `cilium-dbg`: this is an in-pod debug CLI shipped with the Cilium agent. The local `cilium` CLI remains an install/cluster-level tool and does not replace it inside the Pod. `cilium-dbg status` has NO flag `--all-encryption` (in 1.20.x only `--all-addresses`, `--all-clusters`, `--all-controllers`, `--all-health`, `--all-nodes`, `--all-redirects`, `--verbose` are available) - we get the detailed peer/allowed-IP/remote-node evidence via `cilium-dbg debuginfo --output json`, and not via a non-existent flag.

```bash
agent=$(kubectl -n kube-system get pods -l k8s-app=cilium -o jsonpath='{.items[0].metadata.name}')
{
  printf '$ cilium-dbg encrypt status
'
  kubectl -n kube-system exec "$agent" -- cilium-dbg encrypt status
  printf '$ cilium-dbg debuginfo --output json
'
  kubectl -n kube-system exec "$agent" -- cilium-dbg debuginfo --output json
} > /var/work/tests/artifacts/4/cilium-encrypt-status.txt
cat /var/work/tests/artifacts/4/cilium-encrypt-status.txt
grep -Eqi 'peer|allowed[ -]?ip|remote node' /var/work/tests/artifacts/4/cilium-encrypt-status.txt
```

## 5. Capturing an inter-node WireGuard packet

WireGuard uses UDP/51871 by default. A filter ONLY by `udp port 51871` excludes the plaintext TCP
from the result in advance and therefore does NOT prove its absence - instead
we use one and the same capture scope (`host <remote-node-ip>`, without a port filter) and compare
BEFORE/AFTER enabling WireGuard for one and the same inter-node flow.

A capture on `any` is NOT a correct point of observation of the on-wire state: `any` also sees the internal
Cilium interface `cilium_wg0`, through which, by the design of the tunnel, ALREADY DECRYPTED
traffic passes. You need to capture on the physical egress interface toward the remote node (not `any`, `cilium_*`,
`lxc*`, `veth*`).

Two terminals are needed: **terminal 1** - the control-plane (runs `tcpdump`), **terminal 2** -
the work machine (requests and `kubectl`).

```bash
# terminal 2 (work machine): the IP of the node with the gVisor Pod is the "remote" node for the control-plane
gvisor_node=$(kubectl get pod gvisor-sandbox -n sandbox-110 -o jsonpath='{.spec.nodeName}')
remote_ip=$(kubectl get node "$gvisor_node" -o jsonpath='{.status.addresses[?(@.type=="InternalIP")].address}')
echo "remote_ip=$remote_ip"
```

```bash
# terminal 1: log in to the control-plane and find out the physical interface toward remote_ip
ssh k8s110_controlPlane_1
sudo -i
```

```bash
# terminal 1 (control-plane, root): enter the value of remote_ip from terminal 2
remote_ip=10.110.2.172
ip route get $remote_ip
# 10.110.2.172 dev ens5 src 10.110.1.x   <- the interface (ens5), not any / cilium_* / lxc* / veth*
```

**Baseline: WireGuard off.** We temporarily disable WireGuard and run the request with the capture scope
`host <remote-node-ip>`. At the end be sure to restore `enable-wireguard: "true"`.

```bash
# terminal 2
kubectl -n kube-system patch cm cilium-config --type merge -p '{"data":{"enable-wireguard":"false"}}'
kubectl -n kube-system rollout restart daemonset/cilium
kubectl -n kube-system rollout status daemonset/cilium --timeout=180s
```

```bash
# terminal 1 (control-plane, root): capture for 20 seconds, then immediately run the request in terminal 2
timeout 20 tcpdump -nni ens5 host $remote_ip -A > /tmp/wireguard-baseline.txt
```

```bash
# terminal 2: while the capture is running (the first ~15 seconds)
kubectl exec -n sandbox-110 runc-baseline -- \
  wget -qO- --timeout=10 http://gvisor-echo.sandbox-110.svc.cluster.local:8080
```

```bash
# terminal 1 (after the capture ends): the plaintext marker is visible, WireGuard is off
grep CKS110-WIREGUARD-MARKER /tmp/wireguard-baseline.txt
```

**After: WireGuard on.** We restore WireGuard and repeat THE SAME request with THE SAME capture
scope: now WireGuard UDP/51871 must be visible and there must be no marker.

```bash
# terminal 2
kubectl -n kube-system patch cm cilium-config --type merge -p '{"data":{"enable-wireguard":"true"}}'
kubectl -n kube-system rollout restart daemonset/cilium
kubectl -n kube-system rollout status daemonset/cilium --timeout=180s
```

```bash
# terminal 1 (control-plane, root): capture for 20 seconds
timeout 20 tcpdump -nni ens5 host $remote_ip -A > /tmp/wireguard-tcpdump.txt
```

```bash
# terminal 2: while the capture is running
kubectl exec -n sandbox-110 runc-baseline -- \
  wget -qO- --timeout=10 http://gvisor-echo.sandbox-110.svc.cluster.local:8080
```

```bash
# terminal 1 (after the capture ends)
grep -E 'UDP' /tmp/wireguard-tcpdump.txt | head -3      # 51871 > 51871: UDP
grep -c CKS110-WIREGUARD-MARKER /tmp/wireguard-tcpdump.txt   # 0
exit   # from root
exit   # from the control-plane
```

```bash
# terminal 2: fetch the capture for the check
scp k8s110_controlPlane_1:/tmp/wireguard-tcpdump.txt /var/work/tests/artifacts/5/wireguard-tcpdump.txt
```

Do not draw conclusions from a `tcpdump` in the Pod netns: there the traffic before the Cilium encryption point may still be
plaintext. The proof here is the transition from a visible marker (WireGuard off) to its
absence (WireGuard on) with ONE AND THE SAME capture scope.

## 6. Istio and PeerAuthentication STRICT

We install only the Istio control plane in the minimal profile. The namespace was prepared with
`istio-injection=enabled`, so the workloads in `market` get an Envoy sidecar on
creation. `market-api` is placed on the gVisor worker, the client - on the control-plane, which
also makes the request inter-node.

```bash
istioctl install --set profile=minimal -y
kubectl -n istio-system rollout status deployment/istiod --timeout=180s
kubectl get namespace market --show-labels
```

```yaml
# market-workloads.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: market-api
  namespace: market
spec:
  replicas: 1
  selector:
    matchLabels: {app: market-api}
  template:
    metadata:
      labels: {app: market-api}
    spec:
      nodeSelector:
        lab.cks.io/role: gvisor
      tolerations:
      - key: sandbox.runtime/gvisor
        operator: Equal
        value: "true"
        effect: NoSchedule
      automountServiceAccountToken: false
      containers:
      - name: app
        image: busybox:1.36
        command: ["sh", "-ec", "mkdir -p /www; printf 'market-110\\n' >/www/index.html; exec httpd -f -p 8080 -h /www"]
        ports:
        - containerPort: 8080
          name: http
        readinessProbe:
          httpGet:
            path: /
            port: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: market-api
  namespace: market
spec:
  selector: {app: market-api}
  ports:
  - name: http
    port: 80
    targetPort: 8080
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: market-client
  namespace: market
spec:
  replicas: 1
  selector:
    matchLabels: {app: market-client}
  template:
    metadata:
      labels: {app: market-client}
    spec:
      nodeSelector:
        lab.cks.io/role: control-plane
      automountServiceAccountToken: false
      containers:
      - name: app
        image: curlimages/curl:8.11.0
        command: ["sh", "-c", "sleep 3600"]
---
apiVersion: v1
kind: Pod
metadata:
  name: mesh-outside
  namespace: default
spec:
  nodeSelector:
    lab.cks.io/role: control-plane
  automountServiceAccountToken: false
  containers:
  - name: app
    image: curlimages/curl:8.11.0
    command: ["sh", "-c", "sleep 3600"]
```

```bash
kubectl apply -f market-workloads.yaml
kubectl rollout status -n market deployment/market-api --timeout=180s
kubectl rollout status -n market deployment/market-client --timeout=180s
kubectl wait -n default --for=condition=Ready pod/mesh-outside --timeout=180s
kubectl get pods -n market

# Baseline (STRICT is not applied yet): a plaintext client outside the mesh must get 200 -
# this proves that connectivity works in principle and that any subsequent denial will be
# caused exactly by STRICT mTLS, and not by an independent DNS/network problem.
kubectl exec -n default mesh-outside -- \
  curl -sv --max-time 10 http://market-api.market.svc.cluster.local \
  > /var/work/tests/artifacts/6/market-outside-baseline.txt 2>&1
echo "exit_code=$?" >> /var/work/tests/artifacts/6/market-outside-baseline.txt
cat /var/work/tests/artifacts/6/market-outside-baseline.txt
# we expect: HTTP/1.1 200 OK and exit_code=0 at the end
```

```yaml
# market-strict.yaml
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: market-strict
  namespace: market
spec:
  mtls:
    mode: STRICT
```

```bash
kubectl apply -f market-strict.yaml
kubectl get peerauthentication -n market market-strict -o yaml

# a request from inside the mesh (a client with a sidecar)
kubectl exec -n market deploy/market-client -- \
  curl -si --max-time 10 http://market-api \
  > /var/work/tests/artifacts/6/market-inside.txt 2>&1
echo "exit_code=$?" >> /var/work/tests/artifacts/6/market-inside.txt
cat /var/work/tests/artifacts/6/market-inside.txt
# we expect: HTTP/1.1 200 OK and exit_code=0 at the end

# the same request from outside the mesh (plaintext, without a sidecar)
kubectl exec -n default mesh-outside -- \
  curl -sv --max-time 10 http://market-api.market.svc.cluster.local \
  > /var/work/tests/artifacts/6/market-outside.txt 2>&1
echo "exit_code=$?" >> /var/work/tests/artifacts/6/market-outside.txt
cat /var/work/tests/artifacts/6/market-outside.txt
# we expect: Recv failure: Connection reset by peer and exit_code=56 at the end (not 0)
```

`PeerAuthentication` controls the inbound server mode. The internal client gets a
certificate and uses mTLS automatically; the Pod in `default` has no sidecar and sends
plaintext, so the Envoy server resets the connection under `STRICT`. At the end, run the check:

```bash
check_result
```
