# Lab 108 - reference solution: Kyverno admission policies

> All the commands are run on the work machine. The context is already configured; the namespace
> `policy-108` is created by the startup script. First install Kyverno and wait for the
> webhook: otherwise the subsequent CEL-based policies will not check admission requests.

```bash
export KUBECONFIG=/home/ubuntu/.kube/config
export CTX=cluster1-admin@cluster1
kubectl config use-context "$CTX"
```

## 1. Install Kyverno

A pinned installer is prepared on the worker: it installs the Kyverno Helm chart
`3.9.0` (Kyverno `1.19`) in the namespace `kyverno`. You can look at it before running it.

```bash
cat /usr/local/bin/install-kyverno
install-kyverno
kubectl get pods -n kyverno
kubectl get crd validatingpolicies.policies.kyverno.io
kubectl get crd mutatingpolicies.policies.kyverno.io
```

Wait until at least one Deployment in `kyverno` has `AVAILABLE > 0`.

> **Migration note.** The old examples of `kyverno.io/v1` `Policy`/`ClusterPolicy` remain
> useful only when maintaining existing clusters. In Kyverno `1.19` they are deprecated,
> and removal is planned in `1.20`. The new policies in this lab use
> `policies.kyverno.io/v1`.

## 2. Forbid the `latest` tag

Create a `ValidatingPolicy` in `Deny` mode. The rule checks all three container lists -
`containers`, `initContainers`, and `ephemeralContainers`: otherwise a forbidden image can easily be
slipped in through an init or ephemeral container, while the Pod itself still passes admission.

```yaml
# deny-latest-tag.yaml
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: deny-latest-tag
spec:
  validationActions: [Deny]
  matchConstraints:
    resourceRules:
    - apiGroups: [""]
      apiVersions: [v1]
      operations: [CREATE, UPDATE]
      resources: [pods, pods/ephemeralcontainers]
  matchConditions:
  - name: policy-108-only
    expression: request.namespace == 'policy-108'
  variables:
  - name: images
    expression: >-
      object.spec.containers.map(c, c.image)
      + object.spec.?initContainers.orValue([]).map(c, c.image)
      + object.spec.?ephemeralContainers.orValue([]).map(c, c.image)
  validations:
  - message: Images must use an explicit non-latest tag or a digest.
    expression: >-
      variables.images.all(image,
        image.contains('@') ||
        (image.matches('^(?:.*/)?[^/:]+:[^/]+$') && !image.endsWith(':latest')))
```

```bash
kubectl apply -f deny-latest-tag.yaml
```

The task allows TWO forms of an image reference - a non-latest tag OR a digest. Check
explicitly that the digest form passes (and not only that a versioned tag passes) - otherwise it is easy to
write a policy that accidentally rejects ALL digest references:

```bash
kubectl apply --dry-run=server -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: digest-pinned-ok
  namespace: policy-108
spec:
  securityContext:
    runAsNonRoot: true
  containers:
  - name: app
    image: registry.k8s.io/pause@sha256:5a92cb1de40c9c50e1c72e83bf35b9b32ce88e0d1b93f5e2727d97a44c176f56
EOF
# expected: success (no admission error)
```

Make sure that the tag handling takes the colon in the registry port into account: `registry.example:5000/app`
contains no image tag and must be rejected as an implicit latest. A digest must
be accepted in the other container lists too - for example, in `initContainers` and via
`kubectl debug --image=...` for `ephemeralContainers`.

## 3. Require `runAsNonRoot`

The policy requires the value in the Pod-level `securityContext` to be exactly `true`; an implicit
value and `false` do not pass. Additionally, `runAsUser: 0` at the
Pod level and the container-level overrides `runAsNonRoot: false` / `runAsUser: 0` in all
three container lists are forbidden, otherwise the container-level securityContext could override the
Pod-level `runAsNonRoot: true` and start a root process.

```yaml
# require-run-as-non-root.yaml
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: require-run-as-non-root
spec:
  validationActions: [Deny]
  matchConstraints:
    resourceRules:
    - apiGroups: [""]
      apiVersions: [v1]
      operations: [CREATE, UPDATE]
      resources: [pods, pods/ephemeralcontainers]
  matchConditions:
  - name: policy-108-only
    expression: request.namespace == 'policy-108'
  validations:
  - message: Pod and every container must have an effective non-root security context.
    expression: >-
      has(object.spec.securityContext) &&
      object.spec.securityContext.?runAsNonRoot.orValue(false) &&
      object.spec.securityContext.?runAsUser.orValue(1) != 0 &&
      object.spec.containers.all(c,
        !has(c.securityContext) ||
        (c.securityContext.?runAsNonRoot.orValue(true) &&
         c.securityContext.?runAsUser.orValue(1) != 0)) &&
      object.spec.?initContainers.orValue([]).all(c,
        !has(c.securityContext) ||
        (c.securityContext.?runAsNonRoot.orValue(true) &&
         c.securityContext.?runAsUser.orValue(1) != 0)) &&
      object.spec.?ephemeralContainers.orValue([]).all(c,
        !has(c.securityContext) ||
        (c.securityContext.?runAsNonRoot.orValue(true) &&
         c.securityContext.?runAsUser.orValue(1) != 0))
```

```bash
kubectl apply -f require-run-as-non-root.yaml
```

## 4. Allow only approved registries

`registry.k8s.io` and the dedicated organizational path `ghcr.io/cks-lab` are allowed. The CEL expression
combines all three container lists and applies one allowlist to each image.

```yaml
# allow-approved-registries.yaml
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: allow-approved-registries
spec:
  validationActions: [Deny]
  matchConstraints:
    resourceRules:
    - apiGroups: [""]
      apiVersions: [v1]
      operations: [CREATE, UPDATE]
      resources: [pods, pods/ephemeralcontainers]
  matchConditions:
  - name: policy-108-only
    expression: request.namespace == 'policy-108'
  variables:
  - name: images
    expression: >-
      object.spec.containers.map(c, c.image)
      + object.spec.?initContainers.orValue([]).map(c, c.image)
      + object.spec.?ephemeralContainers.orValue([]).map(c, c.image)
  validations:
  - message: Images must come from registry.k8s.io or ghcr.io/cks-lab.
    expression: >-
      variables.images.all(image,
        image.startsWith('registry.k8s.io/') ||
        image.startsWith('ghcr.io/cks-lab/'))
```

```bash
kubectl apply -f allow-approved-registries.yaml
```

A check without creating a Pod and without an image pull. `docker.io` is only ONE specific
untrusted value; check that the policy is really an ALLOWLIST (it forbids ANY
registry except the two allowed ones), and not just a denylist of `docker.io` by a literal string -
otherwise an unqualified image, another third-party registry, or a host with a similar spelling will easily
slip through.

The positive controls must cover both allowed prefixes (`registry.k8s.io/` and
`ghcr.io/cks-lab/`) in `containers`, `initContainers`, and `ephemeralContainers`; do not
limit one of the registries to regular containers only:

```bash
kubectl apply --dry-run=server -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: rejected-registry
  namespace: policy-108
spec:
  securityContext:
    runAsNonRoot: true
  containers:
  - name: app
    image: docker.io/library/busybox:1.36
EOF

kubectl apply --dry-run=server -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: rejected-unqualified-registry
  namespace: policy-108
spec:
  securityContext:
    runAsNonRoot: true
  containers:
  - name: app
    image: busybox:1.36
EOF

kubectl apply --dry-run=server -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: rejected-quay-registry
  namespace: policy-108
spec:
  securityContext:
    runAsNonRoot: true
  containers:
  - name: app
    image: quay.io/prometheus/busybox:v0.24.0
EOF

kubectl apply --dry-run=server -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: rejected-lookalike-registry
  namespace: policy-108
spec:
  securityContext:
    runAsNonRoot: true
  containers:
  - name: app
    image: registry.k8s.io.evil.example/pause:3.10
EOF
```

All four must be rejected. The first Pod below violates the rule with its main
container, the second - only with `initContainers`; both must be rejected:

```bash
kubectl apply --dry-run=server -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: rejected-registry-main
  namespace: policy-108
spec:
  securityContext:
    runAsNonRoot: true
  containers:
  - name: app
    image: docker.io/library/busybox:1.36
EOF

kubectl apply --dry-run=server -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: rejected-init-registry
  namespace: policy-108
spec:
  securityContext:
    runAsNonRoot: true
  initContainers:
  - name: init
    image: docker.io/library/busybox:1.36
  containers:
  - name: app
    image: registry.k8s.io/pause:3.10
EOF
```

Both commands must end with an admission policy error. For an explicit bypass attempt via
`ephemeralContainers` create an allowed Pod, then run `kubectl debug` first with
`docker.io/library/busybox:1.36` (a denial is expected), then with
`registry.k8s.io/e2e-test-images/busybox:1.36-1` (success is expected). It is exactly
`pods/ephemeralcontainers` in `matchConstraints` that protects the subresource update.

## 5. Optional: mutation of a label

This `MutatingPolicy` does not reject a Pod but adds a label via the CEL
`ApplyConfiguration` - and only if the label is not set yet. The task specifically requires
defaulting semantics ("if it is missing"): a Pod that already carries this label with a DIFFERENT
value (for example, from another owner/tool) must not get it
forcibly overwritten.

```yaml
# add-kyverno-managed-label.yaml
apiVersion: policies.kyverno.io/v1
kind: MutatingPolicy
metadata:
  name: add-kyverno-managed-label
spec:
  matchConstraints:
    resourceRules:
    - apiGroups: [""]
      apiVersions: [v1]
      operations: [CREATE]
      resources: [pods]
  matchConditions:
  - name: policy-108-only
    expression: request.namespace == 'policy-108'
  mutations:
  - patchType: ApplyConfiguration
    applyConfiguration:
      expression: >-
        has(object.metadata.labels) &&
        'security.cks.io/managed-by' in object.metadata.labels
        ? Object{}
        : Object{
            metadata: Object.metadata{
              labels: {"security.cks.io/managed-by": "kyverno"}
            }
          }
```

```bash
kubectl apply -f add-kyverno-managed-label.yaml
kubectl apply --dry-run=server -o json -f - <<'EOF' \
  | jq -r '.metadata.labels["security.cks.io/managed-by"]'
apiVersion: v1
kind: Pod
metadata:
  name: mutation-check
  namespace: policy-108
spec:
  securityContext:
    runAsNonRoot: true
  containers:
  - name: app
    image: registry.k8s.io/pause:3.10
EOF
# expected: kyverno

kubectl apply --dry-run=server -o json -f - <<'EOF' \
  | jq -r '.metadata.labels["security.cks.io/managed-by"]'
apiVersion: v1
kind: Pod
metadata:
  name: mutation-check-existing-label
  namespace: policy-108
  labels:
    security.cks.io/managed-by: external
spec:
  securityContext:
    runAsNonRoot: true
  containers:
  - name: app
    image: registry.k8s.io/pause:3.10
EOF
# expected: external (the mutation does NOT overwrite a value that is already set)
```

Run `check_result`. Task 5 is shown in the check, but it is optional: the absence of the
mutation policy does not affect passing tasks 1–4, 6, and 7.

## 6. ImagePolicyWebhook: an external backend

Unlike tasks 1-5, here the decision about an image is made by an external HTTPS backend through the
`ImageReview` API, and not by a CEL expression inside Kyverno. The upstream documentation of
ImagePolicyWebhook explicitly requires the backend connection to use TLS ("It is
required that the backend communicate over TLS"), so we use a self-signed
certificate, and not HTTP.

The backend is already prepared on the work machine:

```bash
cat /opt/image-policy-backend/server.py
```

Create the namespace and a ConfigMap with the backend code:

```bash
kubectl create namespace image-policy --dry-run=client -o yaml | kubectl apply -f -
kubectl create configmap image-policy-backend-src -n image-policy \
  --from-file=server.py=/opt/image-policy-backend/server.py \
  --dry-run=client -o yaml | kubectl apply -f -
```

Create the Service **before** the Deployment - the `ClusterIP` is needed for the correct SAN in the
certificate:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Service
metadata:
  name: image-policy-backend
  namespace: image-policy
spec:
  selector:
    app: image-policy-backend
  ports:
  - port: 8443
    targetPort: 8443
EOF

BACKEND_IP=$(kubectl get service image-policy-backend -n image-policy -o jsonpath='{.spec.clusterIP}')
echo "$BACKEND_IP"
```

Issue a self-signed certificate with this `ClusterIP` in the SAN and save it into a Secret:

```bash
workdir=$(mktemp -d)
openssl req -x509 -nodes -newkey rsa:2048 -days 3 \
  -keyout "$workdir/tls.key" -out "$workdir/tls.crt" \
  -subj "/CN=image-policy-backend" \
  -addext "subjectAltName=IP:${BACKEND_IP}"

kubectl create secret tls image-policy-backend-tls -n image-policy \
  --cert="$workdir/tls.crt" --key="$workdir/tls.key" \
  --dry-run=client -o yaml | kubectl apply -f -
```

Create the Deployment, mounting both the code and the certificate:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: image-policy-backend
  namespace: image-policy
spec:
  replicas: 1
  selector:
    matchLabels:
      app: image-policy-backend
  template:
    metadata:
      labels:
        app: image-policy-backend
    spec:
      containers:
      - name: backend
        image: python:3.12-slim
        command: ["python3", "/opt/image-policy/server.py"]
        ports:
        - containerPort: 8443
        volumeMounts:
        - name: src
          mountPath: /opt/image-policy
        - name: tls
          mountPath: /opt/image-policy/tls
          readOnly: true
      volumes:
      - name: src
        configMap:
          name: image-policy-backend-src
      - name: tls
        secret:
          secretName: image-policy-backend-tls
EOF

kubectl rollout status deployment/image-policy-backend -n image-policy --timeout=90s
```

Copy the CA certificate (here it is self-signed, so the server certificate is its
own CA) to the `control-plane`, so that kube-apiserver can verify the chain when
connecting to the backend, and log in to the node:

```bash
CP=$(kubectl get nodes -l node-role.kubernetes.io/control-plane -o jsonpath='{.items[0].metadata.name}')
scp "$workdir/tls.crt" "$CP":/tmp/image-policy-ca.crt
rm -rf "$workdir"
echo "$BACKEND_IP"     # will be needed on the node
ssh "$CP"
sudo -i
```

On the `control-plane` create the admission config and the kubeconfig for the backend. The paths are on the disk of the **control-plane
itself**:

```bash
# on the control-plane (root)
mkdir /etc/kubernetes/image-policy
mv /tmp/image-policy-ca.crt /etc/kubernetes/image-policy/ca.crt

cat > /etc/kubernetes/image-policy/admission-config.yaml <<EOF
apiVersion: apiserver.config.k8s.io/v1
kind: AdmissionConfiguration
plugins:
- name: ImagePolicyWebhook
  configuration:
    imagePolicy:
      kubeConfigFile: /etc/kubernetes/image-policy/kubeconfig
      allowTTL: 30
      denyTTL: 30
      retryBackoff: 500
      defaultAllow: false
EOF

BACKEND_IP=10.111.15.20     # enter the ClusterIP that "echo $BACKEND_IP" printed
cat > /etc/kubernetes/image-policy/kubeconfig <<EOF
apiVersion: v1
kind: Config
clusters:
- name: image-policy-backend
  cluster:
    certificate-authority: /etc/kubernetes/image-policy/ca.crt
    server: https://${BACKEND_IP}:8443/imagepolicy
users:
- name: kube-apiserver
contexts:
- name: image-policy
  context:
    cluster: image-policy-backend
    user: kube-apiserver
current-context: image-policy
EOF
```

Edit the static manifest **on the `control-plane`** (you are already in a root shell). Do not replace the
existing `--enable-admission-plugins` entirely - append `ImagePolicyWebhook` to the current
value (usually `NodeRestriction` is already there), add `--admission-control-config-file` and
`--runtime-config`, and mount the new directory as a hostPath:

```bash
# on the control-plane (root)
vim /etc/kubernetes/manifests/kube-apiserver.yaml
```

```yaml
# a fragment of /etc/kubernetes/manifests/kube-apiserver.yaml on the control-plane
spec:
  containers:
  - name: kube-apiserver
    command:
    - kube-apiserver
    - --enable-admission-plugins=NodeRestriction,ImagePolicyWebhook   # append to the existing list
    - --admission-control-config-file=/etc/kubernetes/image-policy/admission-config.yaml
    - --runtime-config=imagepolicy.k8s.io/v1alpha1=true               # append if runtime-config was already set
    volumeMounts:
    - name: image-policy
      mountPath: /etc/kubernetes/image-policy
      readOnly: true
  volumes:
  - name: image-policy
    hostPath:
      path: /etc/kubernetes/image-policy
      type: DirectoryOrCreate
```

After saving, leave the node; the kubelet will pick up the static Pod change itself:

```bash
exit   # from root
exit   # from the control-plane
```

Wait for the API to recover:

```bash
until kubectl get --raw=/readyz 2>/dev/null | grep -q '^ok$'; do sleep 5; done
```

Check both cases:

```bash
kubectl run webhook-latest-must-fail --image=nginx:latest
# Error from server (Forbidden): pods "webhook-latest-must-fail" is forbidden:
# image policy webhook backend denied one or more images: Images using latest tag are not allowed

kubectl run webhook-pinned-ok --image=nginx:1.27.3
kubectl get pod webhook-pinned-ok
# STATUS: Running
```

`ImagePolicyWebhook` uses the backend from `/opt/image-policy-backend/server.py`:
in `default` and the other namespaces (except `policy-108`) it forbids explicit/implicit
latest; `policy-108` is fully controlled by the three Kyverno policies of tasks 2–4.
This is a lab isolation of the mechanisms, and not a universal production pattern.
The user annotation `alpha.image-policy.k8s.io/break-glass` does NOT grant permission:
forwarding annotations in ImageReview is not an authentication check.

`defaultAllow: false` means fail-closed: if the backend is unavailable, new Pods/images
are forbidden, and not allowed. Check this explicitly - but do NOT scale
`image-policy-backend` down to 0 replicas: `ImagePolicyWebhook` is a cluster-wide admission
plugin without a namespace exception in our configuration, so it checks the Pod of the backend
itself as well. If you temporarily remove all the replicas and then try to bring them
back, the creation of the NEW backend Pod will ITSELF go through the same (at that moment
unavailable) ImagePolicyWebhook and be rejected under a correct `defaultAllow: false` -
you get a deadlock from which `kubectl rollout status` will not exit. Instead,
detach the Service from the backend by changing the `selector` to a non-existent value - this
neither creates nor deletes a single Pod, it only temporarily removes the `Endpoints`:

```bash
kubectl get service image-policy-backend -n image-policy -o jsonpath='{.spec.selector}'
# save this value to restore it later

kubectl patch service image-policy-backend -n image-policy \
  -p '{"spec":{"selector":{"app":"image-policy-backend-detached-for-probe"}}}'
kubectl get endpoints image-policy-backend -n image-policy -w
# Ctrl+C when ENDPOINTS becomes empty

kubectl run webhook-should-fail-closed --image="nginx:fail-closed-check-$(date +%s%N)"
# expected: Forbidden - the backend is unavailable, defaultAllow:false forbids admission
# (we use a tag not seen YET, and not just a date in seconds, so as not to run into the
# TTL cache of the backend response for the same tag from a previous attempt)

kubectl patch service image-policy-backend -n image-policy \
  -p '{"spec":{"selector":{"app":"image-policy-backend"}}}'
kubectl get endpoints image-policy-backend -n image-policy -w
# Ctrl+C when ENDPOINTS appears again - this is the very same Pod as before the probe, no
# rebuild/recreation was required
```

This is the same fundamental fail-closed design choice described in [chapter 26 of the course](../../../../../course/26/README.md) for the
production configuration of ImagePolicyWebhook.

## 7. Gatekeeper: complete the Rego blocklist in the ConstraintTemplate

Gatekeeper and the starting (incomplete) `ConstraintTemplate`/`Constraint` are already deployed
by the cluster bootstrap in the separate namespace `gatekeeper-108` - this is a separate, third
admission engine in this lab (after Kyverno and ImagePolicyWebhook), which specifically tests the
OPA/Rego skill. `gatekeeper-108` is isolated from the Kyverno tasks 1-5 (`policy-108`)
on purpose: otherwise the same test Pod could be rejected by both Kyverno and
Gatekeeper at once, and the source of the denial would be ambiguous. Look at the current Rego:

```bash
kubectl get constrainttemplate k8sblockedregistries -o yaml
```

`spec.targets[].rego` declares the blocked registries through separate facts:

```rego
blocked_registry("untrusted-registry.example")
blocked_registry("docker-fake.test")
```

`very-bad-registry.test` is not among them - this is exactly the line to add. The `Constraint
deny-bad-registries` is already completely correct and does not use `spec.parameters` at all -
you do not need to edit it; the fix belongs SPECIFICALLY in the Rego inside the
`ConstraintTemplate`, not in the Constraint. Edit the template (for example `kubectl edit
constrainttemplate k8sblockedregistries`, or `get -o yaml` → edit → `apply -f -`),
adding a new line without deleting the existing ones:

```rego
blocked_registry("untrusted-registry.example")
blocked_registry("docker-fake.test")
blocked_registry("very-bad-registry.test")
```

Check all three outcomes with a server-side dry-run, without creating a persistent Pod: the new
registry must be denied, the old (already blocked) one must stay denied (no
regression), and the trusted one must pass:

```bash
kubectl apply --dry-run=server -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: gatekeeper-new-bad-check
  namespace: gatekeeper-108
spec:
  containers:
  - name: app
    image: very-bad-registry.test/malicious/app:1.0
EOF
# expected: Error from server ... admission webhook "validation.gatekeeper.sh" denied
# the request: [deny-bad-registries] image registry very-bad-registry.test is blocked
# by k8sblockedregistries

kubectl apply --dry-run=server -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: gatekeeper-old-bad-check
  namespace: gatekeeper-108
spec:
  containers:
  - name: app
    image: untrusted-registry.example/app:1
EOF
# expected: also Error from server ... - the old rule must not be lost

kubectl apply --dry-run=server -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: gatekeeper-trusted-check
  namespace: gatekeeper-108
spec:
  containers:
  - name: app
    image: registry.k8s.io/pause:3.10
EOF
# expected: success (no admission error)
```

Make sure that the denial really came from Gatekeeper (`validation.gatekeeper.sh`), and
not from one of the Kyverno `ValidatingPolicy` objects of tasks 2-4 - the error message explicitly
names the webhook and the name of your Constraint. Do not solve the task via `Constraint.spec.parameters` -
in this version of the policy the Constraint does not use them at all.

Run `check_result`.
