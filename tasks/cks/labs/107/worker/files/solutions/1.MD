# Lab 107 - reference solution: Pod Security Admission and a read-only root filesystem

> Run the commands on the work machine. The context `cluster1-admin@cluster1` is already
> configured. The namespaces `psa-restricted-107`, `psa-observe-107`, and `psa-controller-107` are created by the startup
> script, but deliberately have no PSA labels.

## 1. Enforcing restricted and verifying the denial

PSA applies the Pod Security Standards based on the namespace labels. We pin the version of the
standard so that the behavior does not change with a future Kubernetes upgrade:

```bash
kubectl label namespace psa-restricted-107 \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=v1.36
```

We check admission without saving the dangerous object. `hostNetwork` is forbidden by the
`restricted` level, so the command must fail with the error `violates PodSecurity`:

```bash
kubectl apply --dry-run=server -f - <<'YAML'
apiVersion: v1
kind: Pod
metadata:
  name: rejected-by-restricted
  namespace: psa-restricted-107
spec:
  hostNetwork: true
  containers:
  - name: unsafe
    image: busybox:1.36
    command: ["sh", "-c", "sleep 5"]
YAML
```

## 2 and 5. A hardened Pod and a writable emptyDir

Create the Pod immediately in its final safe form. The `restricted` level requires
non-root, seccomp, forbidding escalation, and dropping capabilities. A read-only root filesystem
reduces the consequences of a write into the container; the application is left only with `/tmp` in an
`emptyDir`.

```yaml
# restricted-app.yaml
apiVersion: v1
kind: Pod
metadata:
  name: restricted-app
  namespace: psa-restricted-107
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    securityContext:
      privileged: false
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
      seccompProfile:
        type: RuntimeDefault
    volumeMounts:
    - name: writable-tmp
      mountPath: /tmp
  volumes:
  - name: writable-tmp
    emptyDir:
      medium: Memory
```

```bash
kubectl apply -f restricted-app.yaml
kubectl get pod restricted-app -n psa-restricted-107
```

Prove both outcomes with a live call, and not only by reading the YAML: the container runs under
`runAsUser: 1000` with a read-only root, so a write outside `/tmp` must end with a filesystem
error, while a write to the mounted `emptyDir` must succeed:

```bash
kubectl exec -n psa-restricted-107 restricted-app -- sh -c 'touch /root-write-test.txt'
# touch: /root-write-test.txt: Read-only file system

kubectl exec -n psa-restricted-107 restricted-app -- sh -c 'echo probe > /tmp/test.txt && cat /tmp/test.txt'
# probe
```

If `restricted-app` has already been created without a read-only filesystem, the Pod field cannot be changed;
delete it and create it again (if you are doing this already after task 6, add to `spec`
the field `automountServiceAccountToken: false` - otherwise the policy from task 6 will reject the Pod):

```bash
kubectl delete pod restricted-app -n psa-restricted-107
kubectl apply -f restricted-app.yaml
```

## 3. Audit and warn for baseline

These modes do not forbid the request. `warn` returns a warning to the client, and `audit`
adds the annotation `pod-security.kubernetes.io/audit-violations` to the API server
audit event. For a gradual rollout, do not set
`enforce` in the observation namespace:

```bash
kubectl label namespace psa-observe-107 \
  pod-security.kubernetes.io/audit=baseline \
  pod-security.kubernetes.io/audit-version=v1.36 \
  pod-security.kubernetes.io/warn=baseline \
  pod-security.kubernetes.io/warn-version=v1.36
```

> **A caveat about the version.** `v1.36` is pinned for Kubernetes 1.36.0 in this training
> infrastructure. As of 2026-09-06 the official CKS exam targets `v1.35`; this is a
> forward-looking example, and when preparing for the exam use `*-version=v1.35`.

> **The limit of the audit proof.** The lab does not configure an audit-log sink, so
> `pod-security.kubernetes.io/audit-violations` cannot be extracted with a `kubectl` command.
> The actually verifiable result below is the PSA Warning and a successful admission; the audit
> annotation is explained, but is not a verifiable artifact of this infrastructure.

## 4. Make sure that warn/audit do not block the Pod

This Pod violates baseline because of `hostNetwork`, but is accepted, because the namespace
has no `enforce`. `kubectl apply` will print a PSA warning; do not ignore it when
migrating a production workload.

```yaml
# baseline-audit-sample.yaml
apiVersion: v1
kind: Pod
metadata:
  name: baseline-audit-sample
  namespace: psa-observe-107
spec:
  hostNetwork: true
  containers:
  - name: legacy
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
```

```bash
kubectl apply -f baseline-audit-sample.yaml
kubectl get pod baseline-audit-sample -n psa-observe-107
kubectl get namespace psa-restricted-107 --show-labels
kubectl get namespace psa-observe-107 --show-labels
```

## 6. Native ValidatingAdmissionPolicy without Kyverno/Gatekeeper

PSA `restricted` already requires `allowPrivilegeEscalation: false` and `capabilities.drop`
containing `ALL` - task 2 shows exactly this, and this is a built-in part of the Pod Security
Standard, not a gap. But PSS `restricted` **does not check** `automountServiceAccountToken`:
a Pod can silently receive a mounted ServiceAccount token and fully pass PSA. For
this separate control, which PSS genuinely does not cover, a custom `ValidatingAdmissionPolicy` is exactly the right tool.

```yaml
# require-no-automount-token.yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: require-no-automount-token
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - apiGroups: [""]
      apiVersions: ["v1"]
      operations: ["CREATE", "UPDATE"]
      resources: ["pods"]
  validations:
  - expression: >-
      has(object.spec.automountServiceAccountToken) &&
      object.spec.automountServiceAccountToken == false
    message: "spec.automountServiceAccountToken must be explicitly set to false"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: require-no-automount-token-binding
spec:
  policyName: require-no-automount-token
  validationActions: [Deny]
  matchResources:
    namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: psa-restricted-107
```

```bash
kubectl apply -f require-no-automount-token.yaml
kubectl get validatingadmissionpolicy,validatingadmissionpolicybinding
```

Prove all three states via a server-side dry-run, without saving a persistent Pod. A Pod without
the field must get a DENY from the exact policy + binding pair, `false` must pass, and
`true` must get a DENY from the same pair. The first Pod
fully complies with PSA `restricted` (non-root, seccomp, `allowPrivilegeEscalation:
false`, `capabilities.drop: ["ALL"]`) - PSA itself would have accepted it, so the denial must
come from the new policy and not from `violates PodSecurity`:

```bash
kubectl apply --dry-run=server -f - <<'YAML'
apiVersion: v1
kind: Pod
metadata:
  name: vap-unsafe-check
  namespace: psa-restricted-107
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 5"]
    securityContext:
      privileged: false
      allowPrivilegeEscalation: false
      capabilities:
        drop: ["ALL"]
      seccompProfile:
        type: RuntimeDefault
YAML
# Error from server: ... ValidatingAdmissionPolicy 'require-no-automount-token'
# with binding 'require-no-automount-token-binding' denied request: ...
```

The same Pod with `automountServiceAccountToken: false` added must pass:

```bash
kubectl apply --dry-run=server -f - <<'YAML'
apiVersion: v1
kind: Pod
metadata:
  name: vap-safe-check
  namespace: psa-restricted-107
spec:
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 5"]
    securityContext:
      privileged: false
      allowPrivilegeEscalation: false
      capabilities:
        drop: ["ALL"]
      seccompProfile:
        type: RuntimeDefault
YAML
```

The explicit value `true` must also be rejected by the same policy and binding:

```bash
kubectl apply --dry-run=server -f - <<'YAML'
apiVersion: v1
kind: Pod
metadata:
  name: vap-explicit-true-check
  namespace: psa-restricted-107
spec:
  automountServiceAccountToken: true
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 5"]
    securityContext:
      privileged: false
      allowPrivilegeEscalation: false
      capabilities:
        drop: ["ALL"]
      seccompProfile:
        type: RuntimeDefault
YAML
# Error from server: ... ValidatingAdmissionPolicy 'require-no-automount-token'
# with binding 'require-no-automount-token-binding' denied request: ...
```

`Binding.matchResources.namespaceSelector` restricts the policy to `psa-restricted-107` only:
Pods in other namespaces (for example `psa-observe-107`) are not checked by this rule and
do not get an extra Deny.

## 7. Controller-driven admission denial

First a simple, non-hardened Deployment - PSA does not enforce yet, everything passes:

```bash
kubectl -n psa-controller-107 create deployment controller-app --image=busybox:1.36 -- sh -c "sleep 3600"
kubectl -n psa-controller-107 rollout status deployment/controller-app
```

We enable enforce - the existing Pod is not touched:

```bash
kubectl label namespace psa-controller-107 \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=v1.36
kubectl -n psa-controller-107 get pod
# controller-app-xxxx is still Running - PSA does not act on already existing objects
```

We delete the Pod - the ReplicaSet tries to create a replacement and gets a denial:

```bash
kubectl -n psa-controller-107 delete pod -l app=controller-app
kubectl -n psa-controller-107 get events --sort-by=.lastTimestamp | tail -5
# ... FailedCreate ... violates PodSecurity "restricted:v1.36": ...
kubectl -n psa-controller-107 get deploy controller-app
# controller-app   0/1     1            0           ...   <- READY 0/1, AVAILABLE 0
```

We fix the template - we add the same hardening fields as in task 2:

```bash
kubectl -n psa-controller-107 edit deployment controller-app
```

In `spec.template.spec` replace the line `securityContext: {}` with the block below, and in the container `busybox`
(the container name is `busybox`, created by `kubectl create deployment`) add its own `securityContext`:

```yaml
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        seccompProfile:
          type: RuntimeDefault
      containers:
      - name: busybox
        securityContext:
          allowPrivilegeEscalation: false
          capabilities:
            drop: ["ALL"]
```

Save and wait for the rollout:

```bash
kubectl -n psa-controller-107 rollout status deployment/controller-app
```
