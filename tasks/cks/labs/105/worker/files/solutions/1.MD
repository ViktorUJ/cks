# Lab 105 - reference solution: OS System Hardening and Docker

> How to work: log in to the node once via `ssh` and run the commands directly on it (under
> `sudo -i`, so as not to write `sudo` before every command) - this is faster than sending
> each command with a separate `ssh`, and this is exactly how you should work on the exam. Look up the name of the
> control-plane node with `kubectl get no`:
>
> ```bash
> kubectl get no
> ssh <node-name-from-the-output>
> sudo -i
> ```
>
> Checks and artifacts: the checker reads the artifacts from the **work machine** (`worker`), in
> `/var/work/tests/artifacts/<number>/`, so after the edits on the node we exit (`exit`, `exit`) and
> save the artifact with a short command from `worker`. For that, set the node name once:
>
> ```bash
> CP=<node-name-from-the-output>
> mkdir -p /var/work/tests/artifacts/{1,2,3,4,5,6,7,9,10}
> ```
>
> The artifacts are needed only for checking the lab: they do not exist on the exam, where the commands on the
> node and a quick check of the result are enough. The commands save the output to a file (`>`), and we look at the content
> separately via `cat <file>` - the expected result is given in the `# ...` comments under the block.
>
> For the Docker host we log in the same way: `ssh docker-host`, then `sudo -i`.

## 1. Disable an unnecessary systemd service

The service `cks-lab105-unused.service` is not needed for Kubernetes and increases the attack
surface. We stop it and forbid autostart.

On the control-plane:

```bash
ssh "$CP"
sudo -i
systemctl disable --now cks-lab105-unused.service
systemctl is-enabled cks-lab105-unused.service   # disabled
systemctl is-active cks-lab105-unused.service    # inactive
exit
exit
```

The artifact (on `worker`):

```bash
ssh "$CP" 'systemctl is-enabled cks-lab105-unused.service; systemctl is-active cks-lab105-unused.service' \
  | xargs > /var/work/tests/artifacts/1/service.txt
# disabled inactive
```

## 2. Close the unnecessary TCP/8080

Port 8080 is deliberately opened by the service `cks-lab105-port.service`; it is needed neither by the
control-plane nor by the kubelet. We stop and disable the service - both actions are mandatory,
otherwise the listener will return after a reboot, even if the port is closed now.

On the control-plane:

```bash
ssh "$CP"
sudo -i
systemctl disable --now cks-lab105-port.service

exit
exit
```

The artifacts (on `worker`):

```bash
ssh "$CP" 'systemctl is-enabled cks-lab105-port.service; systemctl is-active cks-lab105-port.service' \
```

## 3. Restricting incoming traffic with UFW

First we determine the topology and the needed sources. This is a single-node control-plane
that also runs the workload. The worker needs SSH and API access; the Pod CIDR and the node
itself - API access. There are no inter-node kubelet/CNI flows here. We do not open `22`/`6443` to
`Anywhere`.

On `worker` we look at the needed values by eye:

```bash
kubectl get no -o wide                                      # INTERNAL-IP of the node
kubectl get no "$CP" -o jsonpath='{.spec.podCIDR}{"\n"}'    # Pod CIDR
hostname -I                                                 # IP of the worker
```

We record them in the preflight (substitute your own values; the `role=` line is required):

```bash
WORKER_IP=<worker-ip>; NODE_IP=<node-internal-ip>; POD_CIDR=<pod-cidr>
printf 'role=control-plane,workload\nworker_ip=%s\nnode_ip=%s\npod_cidr=%s\n' \
  "$WORKER_IP" "$NODE_IP" "$POD_CIDR" > /var/work/tests/artifacts/3/preflight.txt
```

Baseline BEFORE UFW: we check that TCP/10250 (kubelet HTTPS) is really reachable now - without
this the "blocked" after UFW proves nothing, the port could have been unreachable for another
reason (security group, routing). The checker separately compares against its own baseline, but your
record is needed too:

```bash
curl -ks -o /dev/null -w '%{http_code}\n' --max-time 3 "https://$NODE_IP:10250/healthz"
# 401 - the port is reachable (any 1xx-5xx, including 401/403, is fine)
echo 'baseline kubelet 10250: CURL_EXIT=0 HTTPCODE=401' >> /var/work/tests/artifacts/3/preflight.txt
```

If the baseline is unreachable (curl returned `000`) - first fix the connectivity, otherwise the result
after UFW will be unconvincing.

We configure the UFW rules on the node. First we allow the recovery and the needed sources, and only
then change the default. The values `WORKER_IP`/`NODE_IP`/`POD_CIDR` are taken from `preflight.txt`
(substitute your own):

```bash
ssh "$CP"
sudo -i
WORKER_IP=<worker_ip>; NODE_IP=<node_ip>; POD_CIDR=<pod_cidr>
ufw allow from "$WORKER_IP" to any port 22 proto tcp comment 'CKS105 worker SSH recovery'
ufw allow from "$WORKER_IP" to any port 6443 proto tcp comment 'CKS105 worker API'
ufw allow from "$NODE_IP" to any port 6443 proto tcp comment 'CKS105 node API'
ufw allow from "$POD_CIDR" to any port 6443 proto tcp comment 'CKS105 Pod API'
ufw allow in on lo comment 'CKS105 loopback'
ufw default allow outgoing
ufw default deny incoming
ufw --force enable
ufw status verbose
exit
exit
```

The artifacts (on `worker`). `ufw show added` is a normalized representation of the rules that
you actually added (NOT guaranteed to be the original form/order of the commands - UFW normalizes them on
display). The check compares exactly this list with the expected allowlist - save it
too, it is the most reliable evidence of the exact allow-set. Manage the firewall only via `ufw` -
do NOT edit `/etc/ufw/before*.rules` or `/etc/ufw/after*.rules` by hand, these are
framework files with the common default rules, not a place for source-scoped rules; the checker
compares their hash with the checker-owned bootstrap baseline and will notice a direct edit.

```bash
ssh "$CP" 'sudo ufw status verbose; sudo ufw status' \
  > /var/work/tests/artifacts/3/ufw.txt
ssh "$CP" 'sudo ufw show added' \
  >> /var/work/tests/artifacts/3/ufw.txt

cat > /var/work/tests/artifacts/3/recovery.txt <<'EOF'
# Run from a still open SSH/console session if the API is lost:
sudo ufw disable
sudo ufw status verbose
# fix the too narrow allow rules, check the source IP/CIDR
sudo ufw --force enable
# If the rules are completely broken, only via the console/recovery channel:
sudo ufw --force reset
EOF
```

We check that the cluster is healthy (from `worker`):

```bash
kubectl get --raw=/readyz
kubectl get nodes
kubectl rollout status deployment/health-probe -n cks-105-health --timeout=60s
# The workload inside the cluster must still resolve DNS and reach the API server
# (UFW must not break Pod -> CoreDNS and Pod -> API traffic):
kubectl exec -n cks-105-health deploy/health-probe -- nslookup kubernetes.default   # must return the Address of the kubernetes Service
kubectl exec -n cks-105-health deploy/health-probe -- curl -ks -o /dev/null -w '%{http_code}\n' --max-time 5 https://kubernetes.default.svc/readyz   # any code except 000

# The undesired worker -> kubelet flow must not produce an HTTP response.
curl -ksS -o /dev/null -w 'kubelet_http=%{http_code}\n' --connect-timeout 2 --max-time 3 \
  "https://${NODE_IP}:10250/healthz"
# kubelet_http=000 - a transport deny
```

The mandatory full E2E retest AFTER `ufw reload` - it proves that the ruleset survives a
reload, and does not only work in memory right after `ufw enable`. Without this step you can
accidentally get a false PASS right after enable:

```bash
ssh "$CP" 'sudo ufw reload'
sleep 2
kubectl get --raw=/readyz
kubectl get nodes
kubectl get pods -n kube-system -l k8s-app=calico-node
# We repeat the same two workload checks after the reload:
kubectl exec -n cks-105-health deploy/health-probe -- nslookup kubernetes.default
kubectl exec -n cks-105-health deploy/health-probe -- curl -ks -o /dev/null -w '%{http_code}\n' --max-time 5 https://kubernetes.default.svc/readyz
# The same contract as before the reload: the worker still does not reach the kubelet.
curl -ksS -o /dev/null -w 'kubelet_http=%{http_code}\n' --connect-timeout 2 --max-time 3 \
  "https://${NODE_IP}:10250/healthz"
# kubelet_http=000
```

The declared vs effective check: `ufw show added` is a declarative list reconstructed
from the `### tuple ###` metadata that ufw itself writes to `user.rules` when a rule is added
through the CLI. The real kernel state after `ufw reload` is what
`ufw show user-rules` shows. Compare not only the COUNT of lines but also their CONTENT
(source/port/proto): `ufw-user-input` must show the loopback (all, lo) and three tcp
dpt:22/6443 rules with the exact source addresses, and `ufw6-user-input` - EXACTLY one line, the same
loopback ACCEPT for v6 (`ufw allow in on lo` is an interface rule without an explicit IP,
so ufw always creates both a v4 and a v6 version). Any OTHER/additional line there is
an outside bypass:

```bash
ssh "$CP" 'sudo ufw show user-rules'
```

The output must contain `Status: active`, `Default: deny (incoming)`, and the source-scoped rules -
both in `ufw status verbose` and in the declarative list `ufw show added`. Do not close the
original SSH session until `/readyz`, nodes, calico-node, the workload (including the Pod DNS before and
after the reload) and both negative `10250` checks (before and after `ufw reload`, with the same
CURL_EXIT/HTTPCODE contract) have given the expected result.

## 4. Protect the administrator kubeconfig

`/etc/kubernetes/admin.conf` contains the cluster-admin credential. It must be readable
only by root.

On the control-plane:

```bash

sudo -i
chown root:root /etc/kubernetes/admin.conf && chmod 600 /etc/kubernetes/admin.conf
stat -c '%U %G %a' /etc/kubernetes/admin.conf   # root root 600
exit
exit
```

The artifact (on `worker`):

```bash
ssh "$CP" "stat -c '%U %G %a' /etc/kubernetes/admin.conf" \
  > /var/work/tests/artifacts/4/admin-conf.txt
```

## 5. Forbid direct root login over SSH

We change the configuration, check the syntax before the reload, and apply without breaking the current
session.

On the control-plane:

```bash
ssh "$CP"
sudo -i
sed -i -E 's/^[[:space:]]*PermitRootLogin[[:space:]]+.*/PermitRootLogin no/' /etc/ssh/sshd_config
grep -qE '^[[:space:]]*PermitRootLogin[[:space:]]+' /etc/ssh/sshd_config || echo 'PermitRootLogin no' >> /etc/ssh/sshd_config
sshd -t && systemctl reload ssh
```

The current session is not broken by `reload ssh`. But during the restart of sshd a new
connection to the control-plane may get `Connection refused` for 1-2 seconds - this is
normal and does not mean that the configuration is broken (it was already checked by `sshd -t`), just
repeat the command.

`sshd -T` without a connection context does not apply `Match` blocks at all - the `sshd(8)` man page
explicitly says that `Match` in test mode is applied only when `-C` is passed. Therefore
we check via `-C`, simulating a real root connection from the worker (the addresses are taken from
`preflight.txt` of task 3):

```bash
sshd -T -C 'user=root,addr=<worker_ip>,laddr=<node_ip>,lport=22' | grep -i permitrootlogin
# permitrootlogin no
exit
exit
```

The artifact (on `worker`, after a pause of a couple of seconds):

```bash
# WORKER_IP and NODE_IP - the same values as in task 3
ssh "$CP" "sudo sshd -T -C 'user=root,addr=${WORKER_IP},laddr=${NODE_IP},lport=22' | awk '\$1 == \"permitrootlogin\" {print \"PermitRootLogin \" \$2}'" \
  > /var/work/tests/artifacts/5/sshd.txt
# PermitRootLogin no
```

## 6. Close insecure access to the Docker daemon on `docker-host`

TCP/2375 has no TLS and no authentication: access to it is practically equal to root access to
the host. We delete the training systemd override with the TCP listener, set the owner of the unix socket
via a socket override, and remove `developer` from the `docker` group.

We apply the changes via a full `daemon-reload` + restart of **both** units - this is a
mandatory step, and not just "reread the config": without a real restart you can accidentally
"pass" the check if Docker simply stopped responding (then TCP/2375 is closed not because
`-H tcp://` was removed, but because the daemon is not running at all).

On `docker-host`:

```bash
ssh docker-host
sudo -i
rm -f /etc/systemd/system/docker.service.d/10-cks-lab105-tcp.conf
install -d -m 0755 /etc/systemd/system/docker.socket.d
printf '[Socket]\nSocketGroup=root\nSocketMode=0660\n' > /etc/systemd/system/docker.socket.d/10-cks-lab105-socket.conf
gpasswd -d developer docker || true
systemctl daemon-reload
systemctl restart docker.socket
systemctl restart docker.service
chown root:root /var/run/docker.sock && chmod 660 /var/run/docker.sock
```

Positive control: after the restart Docker REALLY WORKS (it is not just not listening on 2375 - it
must function fully through the unix socket):

```bash
systemctl is-active docker.service docker.socket   # active / active
docker version && docker info >/dev/null
```

The persistent config check - the effective unit contains no `-H tcp://`, and the socket override really
sets the needed values (and does not merely temporarily match them):

```bash
systemctl cat docker.service | grep -c "H tcp://"   # 0
systemctl cat docker.socket                          # ... SocketGroup=root ... SocketMode=0660 ...
```

The contract of the task is wider than port 2375: the Docker API must not listen on TCP on any port, and
`docker.socket` must not contain a TCP `ListenStream`:

```bash
ss -ltnp | grep -E 'dockerd|docker\.socket'    # empty output
systemctl cat docker.socket | grep ListenStream # only /run/docker.sock (and an empty reset)
stat -c '%U %G %a' /var/run/docker.sock         # root root 660
sudo -u developer docker ps                     # permission denied
exit
exit
```

The artifacts (on `worker`):

```bash
# port 2375 has already been checked on docker-host (`ss -ltnp | grep dockerd` - empty), we record the result:
echo 'tcp/2375: closed' > /var/work/tests/artifacts/6/docker-tcp.txt
ssh docker-host "sudo stat -c '%U %G %a' /var/run/docker.sock" \
  > /var/work/tests/artifacts/6/docker-socket.txt
ssh docker-host 'if sudo -u developer docker ps >/dev/null 2>&1; then echo "developer docker ps: allowed"; else echo "developer docker ps: denied"; fi' \
  > /var/work/tests/artifacts/6/developer-access.txt
# tcp/2375: closed
# root root 660
# developer docker ps: denied
```

After completing all the steps, run `check_result`.

## 7. Forbid loading the `sctp` module

`sctp` is loaded, but it is needed neither by kubeadm, nor by containerd, nor by Calico on this node. We try to
unload the already loaded module, then in any case we block reloading both via
`blacklist` and via the `install` override. Both directives act at the level of
`modprobe` (alias resolution and an explicit `modprobe sctp`) and eliminate the usual loading path;
they do not replace kernel-level enforcement (`insmod` inserts a module directly through a syscall
and does not read `modprobe.d`, and `modprobe --ignore-install` can bypass `install` given equal
root access) - for this lab what matters is to eliminate the expected autoload path, and not to
model a defense against a user who already has root on the node.

**`modprobe -r sctp` may fail on an already live cluster** - this is expected and is not
a student's error. Kernel protocol modules (including `sctp`) get a persistent
per-network-namespace reference (`try_module_get` in the pernet initialization) for every netns
that already existed at the moment the module was loaded - Pods are already running on this node
(calico, coredns, kube-system), so `sctp` may stay in the `in use` state with a
non-zero refcount and an EMPTY `/sys/module/sctp/holders` (that is, it is held not by another module -
there is nothing to unload recursively). This cannot be fixed without stopping all these Pods, which is not
part of the task. What matters, and is exactly what is checked, is what is under the student's control:
the module cannot be loaded AGAIN.

On the control-plane:

```bash
ssh "$CP"
sudo -i
modprobe -r sctp || true
printf 'blacklist sctp\ninstall sctp /bin/true\n' > /etc/modprobe.d/60-cks-sctp.conf
lsmod | grep sctp                       # may be either empty or non-empty - both options are acceptable
modprobe --show-config | grep sctp      # install sctp /bin/true and blacklist sctp
exit
exit
```

The artifact (on `worker`): the current state (`absent` or `present`) and the override in the effective
modprobe config:

```bash
ssh "$CP" '
{
  if lsmod | grep -q sctp; then echo "lsmod: present"; else echo "lsmod: absent"; fi
  modprobe --show-config | grep sctp
}' > /var/work/tests/artifacts/7/sctp.txt
# lsmod: absent   (or lsmod: present - both options are acceptable, see above)
# install sctp /bin/true
```

## 8. `protectKernelDefaults` and safe sysctls

First we fix the sysctls - `protectKernelDefaults: true` makes the kubelet **fail at
startup** if the current kernel values do not match its expectations, so the sysctls
must be applied before the kubelet restart.

On the control-plane:

```bash
ssh "$CP"
sudo -i
printf 'kernel.unprivileged_bpf_disabled = 1\nvm.overcommit_memory = 1\n' > /etc/sysctl.d/99-kubernetes.conf
sysctl --system
sysctl kernel.unprivileged_bpf_disabled vm.overcommit_memory
```

Now we enable `protectKernelDefaults` in the kubelet configuration and restart the service:

```bash
grep -q '^protectKernelDefaults:' /var/lib/kubelet/config.yaml \
  && sed -i 's/^protectKernelDefaults:.*/protectKernelDefaults: true/' /var/lib/kubelet/config.yaml \
  || echo 'protectKernelDefaults: true' >> /var/lib/kubelet/config.yaml
systemctl restart kubelet
systemctl is-active kubelet     # active
exit
exit
```

The node must stay `Ready` (from `worker`):

```bash
kubectl get no
```

If the kubelet does not come up after this step - check precisely the order: the sysctls must
be applied (`sysctl --system`), and not only written to a file, before the kubelet
checks them at startup.

`find` will show both the system SUID binaries (`sudo`, `passwd`, `mount` - we do not touch them) and the
training `/usr/local/bin/cks-lab105-suid-tool`, which is not needed by any Kubernetes
component on this node.

`/var/lib/containerd` is excluded from the output: its overlayfs snapshot paths are the content of

```bash
ssh "$CP" "sudo find / -xdev -perm -4000 -type f 2>/dev/null | grep -v '^/var/lib/containerd/'" \
```

## 10. Disable core dumps and protect SUID processes

A core dump may contain secrets and keys from the process memory at the moment of the crash - it must be
forbidden both for regular and for SUID processes. We add `fs.suid_dumpable` to the same
file `/etc/sysctl.d/99-kubernetes.conf` that was already created in task 8 - we do not create a separate
conflicting config.

On Ubuntu `ulimit -c 0` and `fs.suid_dumpable=0` **do not guarantee** the absence of a core dump:
`man 5 core` explicitly documents that `RLIMIT_CORE` is ignored by the kernel if
`kernel.core_pattern` directs the dump to a userspace handler through a pipe (`|program`).
Ubuntu is configured exactly like that by default - the crash is intercepted by Apport and saved to
`/var/lib/apport/coredump/` REGARDLESS of the process `ulimit -c`. The only reliable
way is to override `kernel.core_pattern` itself with a deliberately non-working handler.

We also restrict the size of core dumps at the level of process limits - this is a mechanism separate from
`suid_dumpable`/`core_pattern` (a soft limit for regular crashes with classic
file-based writing, should it ever be restored).

On the control-plane:

```bash
ssh "$CP"
sudo -i
printf 'fs.suid_dumpable = 0\nkernel.core_pattern = |/bin/false\n' >> /etc/sysctl.d/99-kubernetes.conf
sysctl --system
sysctl -n fs.suid_dumpable; cat /proc/sys/kernel/core_pattern   # 0 / |/bin/false
printf '* hard core 0\n* soft core 0\n' >> /etc/security/limits.conf
```

`limits.conf` is applied to new login sessions through PAM, and not to already open shells -
we check specifically in a new session:

```bash
su - ubuntu -c 'ulimit -c'      # 0
exit
exit
```

The artifact `coredump.txt` (on `worker`). It includes a controlled crash probe: we confirm that
after a real `SIGSEGV` no NEW retained core dump appears - neither in the standard
current directory nor via Apport:

```bash
ssh "$CP" "sysctl -n fs.suid_dumpable; cat /proc/sys/kernel/core_pattern; sudo su - ubuntu -c 'ulimit -c'" \
  > /var/work/tests/artifacts/10/coredump.txt
ssh "$CP" "cat /etc/sysctl.d/99-kubernetes.conf; cat /etc/security/limits.conf" \
  >> /var/work/tests/artifacts/10/coredump.txt
ssh "$CP" '
before_count=$(sudo find /var/lib/apport/coredump /var/crash -type f 2>/dev/null | wc -l)
sh -c "kill -SEGV \$\$" || true
sleep 2
after_count=$(sudo find /var/lib/apport/coredump /var/crash -type f 2>/dev/null | wc -l)
if [ "$after_count" -le "$before_count" ]; then
  echo "crash-probe: no new retained core dump"
else
  echo "crash-probe: NEW core dump appeared after SIGSEGV"
fi
' >> /var/work/tests/artifacts/10/coredump.txt
# crash-probe: no new retained core dump
```

After completing all the steps, run `check_result`.
