# Lab 106 - reference solution: AppArmor and seccomp

> Run the Kubernetes commands (`kubectl`) on the work machine (`worker`). Do everything that concerns
> the node itself (AppArmor, kubelet, `crictl`) **directly on the node**: log in via `ssh` once
> and become root (`sudo -i`) - this is faster than sending each command with a separate
> `ssh control-plane '...'`, and this is exactly how you need to work on the exam. The namespace
> `security-106` is created in task 3.
>
> ```bash
> ssh control-plane
> sudo -i
> # ... commands on the node ...
> exit   # from root
> exit   # from the node back to the worker
> ```
>
> The check reads the artifacts from the **work machine** (`/var/work/tests/artifacts/<number>/`), and they are
> needed only for the lab - they do not exist on the exam. We save them with a short command from `worker`
> (`> file`) and look at the content separately via `cat <file>`.

## 1. Transferring and loading the AppArmor profile

The profile lies only on the work machine. We copy it to the node (from `worker`), then on the node
we put it in place and load it into the kernel. The file already contains the `complain` flag, so a single
`apparmor_parser -r` is enough for the initial load (without `aa-complain`, which, like
`aa-enforce`, parses all the files in `/etc/apparmor.d/` and would fail on the still broken
`k8s-106-broken-profile` from task 9):

```bash
# on worker
scp /opt/lab106-fixtures/k8s-106-deny-write control-plane:/tmp/k8s-106-deny-write

# on the node
ssh control-plane
sudo -i
mv /tmp/k8s-106-deny-write /etc/apparmor.d/k8s-106-deny-write
apparmor_parser -r /etc/apparmor.d/k8s-106-deny-write
aa-status --pretty-json | grep k8s-106-deny-write
# expected: "k8s-106-deny-write":	"complain",
```

## 2. Switching the AppArmor profile to enforce

The profile is currently in `complain` mode (it was loaded with this flag in task 1). We stay on the node
(as root) and switch the existing profile itself to enforcing mode:

```bash
sed -i 's/, complain,/,/' /etc/apparmor.d/k8s-106-deny-write
apparmor_parser -r /etc/apparmor.d/k8s-106-deny-write
aa-status --pretty-json | grep k8s-106-deny-write
# expected: "k8s-106-deny-write":	"enforce",
# A regular 'aa-status | grep ...' will not show the profile mode: in the text output the profiles are
# grouped under headings ('N profiles are in enforce mode.'), the names have no suffix.
# To check a specific profile use 'aa-status --pretty-json' (or '--json').
exit
exit
```

Do not use `aa-enforce`/`aa-complain` and other profile-modifying tools from the
`apparmor-utils` package, written in Python, for THIS profile until task 9 is done:
internally they call `apparmor.read_profiles()`, which at startup parses
**all** the files in `/etc/apparmor.d/`, including the not yet loaded and deliberately
broken `/etc/apparmor.d/k8s-106-broken-profile` from task 9 - and they fail with a
parser error on an UNRELATED file, without even trying to get to your profile. `apparmor_parser`
(a binary, not a Python wrapper), called directly with ONE specific file, parses
only it and is not subject to this problem - this is exactly why we edit the profile flag
(removing `complain` from `flags=(...)`) by hand via `sed`, and then reload exactly
this file via `apparmor_parser -r`.

`aa-status` is a separate tool for viewing state, not for modifying profiles, so this restriction does not
apply to it. The mode of a specific profile is shown by `aa-status --pretty-json` (verified on
the lab node, apparmor 3.0.4; `--json` gives the same on one line, for example
`aa-status --json | jq -r '.profiles["k8s-106-deny-write"]'`). The alternative is the kernel file
`grep -F 'k8s-106-deny-write' /sys/kernel/security/apparmor/profiles`: there the format is
`name (enforce|complain)`.

## 3. A Pod with Localhost AppArmor and a write denial

We create the namespace and the Pod. `emptyDir` guarantees the presence of `/work`; the profile allows
the process to start but forbids writing in this directory. The node selector ties the Pod to
the node on which the profile is really loaded.

```yaml
# apparmor-writer.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: security-106
---
apiVersion: v1
kind: Pod
metadata:
  name: apparmor-writer
  namespace: security-106
spec:
  nodeSelector:
    security.cks.io/localhost-profiles-106: "true"
  automountServiceAccountToken: false
  securityContext:
    appArmorProfile:
      type: Localhost
      localhostProfile: k8s-106-deny-write
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    volumeMounts:
    - name: work
      mountPath: /work
  volumes:
  - name: work
    emptyDir: {}
```

```bash
# on worker
kubectl apply -f apparmor-writer.yaml
kubectl get pod -n security-106 apparmor-writer
# wait for STATUS Running (repeat get), then run exec

# Evidence: the profile is really assigned to the PID 1 process, and not only written in the Pod YAML.
kubectl exec -n security-106 apparmor-writer -- cat /proc/1/attr/current
# k8s-106-deny-write (enforce)

# A positive control BEFORE the denial: an allowed read operation on exactly the same /work
# where the denial will be checked - without this step the write denial could not be told apart
# from a completely non-working mount/mountPath (in which case even reading would be unavailable).
kubectl exec -n security-106 apparmor-writer -- sh -c 'ls /work'

# A negative control: the denial must be exactly an AppArmor write denial.
kubectl exec -n security-106 apparmor-writer -- \
  sh -c 'printf blocked >/work/cks-106-denied.txt'
# a non-zero code is expected: Permission denied / Operation not permitted
```

A non-zero exit code and the text 'permission denied' by themselves do NOT prove that it was exactly
this AppArmor rule that fired - an ordinary DAC/filesystem error would look identical from the
point of view of the shell. Tie the denial to exactly this profile through the kernel audit log; we look at it
on the node right after the attempt above:

```bash
# on the node
ssh control-plane
sudo -i
journalctl -k --no-pager -n 500 | grep -F 'apparmor="DENIED"' | grep -F 'profile="k8s-106-deny-write"' | grep -F 'cks-106-denied.txt'
# a record of the form is expected: ... apparmor="DENIED" ... profile="k8s-106-deny-write" name=".../cks-106-denied.txt" ... denied_mask="c" ... (mknod: file creation; for a write to an existing file it will be "w")
exit
exit
```

If `/proc/1/attr/current` is unavailable in the specific runtime, record that and rely
on the assignment of the Localhost profile together with the kernel `apparmor="DENIED"` for this profile;
a non-zero code alone without this evidence is insufficient, since it can also be produced by a mount or a regular
Unix permission.

## 4. RuntimeDefault for a regular Pod

`RuntimeDefault` is a portable baseline that selects the standard
containerd/runtime profile. The field is set explicitly at the Pod level.

```yaml
# runtime-default.yaml
apiVersion: v1
kind: Pod
metadata:
  name: runtime-default
  namespace: security-106
spec:
  nodeSelector:
    security.cks.io/localhost-profiles-106: "true"
  automountServiceAccountToken: false
  securityContext:
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
```

```bash
# on worker
kubectl apply -f runtime-default.yaml
kubectl get pod -n security-106 runtime-default
kubectl exec -n security-106 runtime-default -- grep '^Seccomp:' /proc/1/status
# Seccomp: 2
```

## 5–6. Localhost seccomp and the proof of blocking `unshare`

The file lies only on the work machine, in `/opt/lab106-fixtures/cks-106-deny-unshare.json`.
We copy it to the node (from `worker`) and put it into the kubelet seccomp root (on the node):

```bash
# on worker
scp /opt/lab106-fixtures/cks-106-deny-unshare.json control-plane:/tmp/cks-106-deny-unshare.json

# on the node
ssh control-plane
sudo -i
mkdir -p /var/lib/kubelet/seccomp/profiles
mv /tmp/cks-106-deny-unshare.json /var/lib/kubelet/seccomp/profiles/cks-106-deny-unshare.json
jq empty /var/lib/kubelet/seccomp/profiles/cks-106-deny-unshare.json && echo valid
exit
exit
```

In the API we specify the path relative to the seccomp root: `profiles/cks-106-deny-unshare.json`.

`SYS_ADMIN` here is a deliberate, dangerous exception only for the lab (the control check without seccomp is done by the checker). Without a custom
filter, `unshare -n` with this capability may succeed; seccomp must return `EPERM`.
This is not a hardened combination. `allowPrivilegeEscalation: false` enables `no_new_privs`, but
does not take away capabilities already granted to the process, so we do not use this field as
a "compensation" for `SYS_ADMIN`. In production such a capability is removed unless there is a proven
need. In Kubernetes a capability is written as `SYS_ADMIN`, without the `CAP_` prefix.

We use `unshare -n` (network namespace, `CLONE_NEWNET`), and NOT `unshare -m` (mount
namespace). Both operations require the same `CAP_SYS_ADMIN`, but BusyBox `unshare -m`
after a successful `unshare(2)` additionally performs an independent `mount(2)` syscall
for forced private propagation - and containerd's default AppArmor profile (`RuntimeDefault`,
which this Pod gets, since no explicit `appArmorProfile` is set here) contains
`deny mount,` without any conditions on flags, regardless of capabilities/seccomp. Therefore
`unshare -m true` can fail with `EPERM` because of AppArmor even if seccomp does not
restrict `unshare` at all - such a probe would mix two different security controls. `unshare -n`
calls only the `unshare(2)` syscall itself, without a side-effect `mount()`.

```yaml
# localhost-seccomp.yaml
apiVersion: v1
kind: Pod
metadata:
  name: localhost-seccomp
  namespace: security-106
spec:
  nodeSelector:
    security.cks.io/localhost-profiles-106: "true"
  automountServiceAccountToken: false
  securityContext:
    seccompProfile:
      type: Localhost
      localhostProfile: profiles/cks-106-deny-unshare.json
  containers:
  - name: app
    image: busybox:1.36
    command:
    - sh
    - -ec
    - |
      if unshare -n true 2>/tmp/unshare.err; then
        echo 'unshare unexpectedly succeeded' >/tmp/unshare-result
        exit 1
      fi
      grep -Eqi 'operation not permitted|permission denied' /tmp/unshare.err
      echo 'unshare denied by seccomp' >/tmp/unshare-result
      exec sleep 3600
    securityContext:
      capabilities:
        add: ["SYS_ADMIN"]
```

```bash
# on worker
kubectl apply -f localhost-seccomp.yaml
kubectl get pod -n security-106 localhost-seccomp
kubectl exec -n security-106 localhost-seccomp -- cat /tmp/unshare-result
# unshare denied by seccomp

kubectl exec -n security-106 localhost-seccomp -- grep '^Seccomp:' /proc/1/status
# Seccomp: 2

kubectl exec -n security-106 localhost-seccomp -- unshare -n true
# a non-zero code is expected: Operation not permitted / Permission denied
```

## 7. User namespaces: `hostUsers: false` and `uid_map`

`hostUsers: false` asks the kubelet to allocate a separate user namespace for the Pod: root (UID 0)
inside the container is mapped to an unprivileged range of host UIDs. We do not set
`runAsUser`, so that the process really starts as UID 0 **inside** the namespace - it is exactly this
case that shows the translation, and not the absence of privileges from the very beginning.

```yaml
# userns-probe.yaml
apiVersion: v1
kind: Pod
metadata:
  name: userns-probe
  namespace: security-106
spec:
  hostUsers: false
  nodeSelector:
    security.cks.io/localhost-profiles-106: "true"
  automountServiceAccountToken: false
  containers:
  - name: app
    image: busybox:1.36
    command: ["sleep", "3600"]
```

```bash
# on worker
kubectl apply -f userns-probe.yaml
kubectl get pod -n security-106 userns-probe
mkdir -p /var/work/tests/artifacts/6

kubectl exec -n security-106 userns-probe -- id > /var/work/tests/artifacts/6/userns.txt
cat /var/work/tests/artifacts/6/userns.txt
# uid=0(root) gid=0(root) groups=0(root)
```

The host PID of the container neither matches the PID inside the container nor is directly visible via
`kubectl`. We take the container ID on the worker, and get the PID via `crictl inspect` on the node
where the Pod is actually running:

```bash
# on worker
kubectl get pod userns-probe -n security-106 -o jsonpath='{.status.containerStatuses[0].containerID}'
# containerd://<ID> - copy <ID> without the prefix containerd://

# on the node
ssh control-plane
sudo -i
crictl inspect <ID> | jq -r '.info.pid'
# for example: 15205 - this is the <host PID>
```

`/proc/<host PID>/uid_map` on the node describes the translation: three numbers - `<container-uid-start>
<host-uid-start> <length>`. For `hostUsers: false` the first line must start with `0`
(container UID 0), but host-uid-start must be **non-zero** - that is the
unprivileged host range, and `length` is the standard per-Pod block of `65536` UIDs.

```bash
# on the node (as root)
cat /proc/<host PID>/uid_map
# 0 1349844992 65536   (host-uid-start is different for each Pod, the main thing is that it is not 0)
exit
exit
```

We save the `uid_map` line into the artifact (on `worker`):

```bash
ssh control-plane "sudo cat /proc/<host PID>/uid_map" >> /var/work/tests/artifacts/6/userns.txt
```

If `host-uid-start` equals `0` - the user namespace was not applied (for example, because of an
incompatible containerd/runc or the absence of `hostUsers: false` in the Pod that was actually applied) -
this is not hardening but ordinary root on the host. For comparison: a regular Pod without
`hostUsers: false` also has a file `/proc/<host-PID>/uid_map`, but the process stays in the
host (initial) user namespace. So the mapping starts with UID 0 -> host UID 0 (usually
a line of the form `0 0 4294967295`, for example `cat /proc/1/uid_map` on the node), and not with an
unprivileged per-Pod host UID. For `userns-probe` with `hostUsers: false` we expect the
opposite: `0 <non-zero-host-uid> <per-pod-range>`.

## 8. `seccompDefault: true` on the kubelet

All the previous Pods explicitly set `seccompProfile`. Here we check the node-level baseline:
if a developer forgets this field, the kubelet must itself apply `RuntimeDefault`, and not
leave the process `Unconfined`. We edit the kubelet configuration on the node:

```bash
# on the node
ssh control-plane
sudo -i
grep -q '^seccompDefault:' /var/lib/kubelet/config.yaml \
  && sed -i 's/^seccompDefault:.*/seccompDefault: true/' /var/lib/kubelet/config.yaml \
  || echo 'seccompDefault: true' >> /var/lib/kubelet/config.yaml
systemctl restart kubelet
systemctl is-active kubelet     # active
exit
exit
```

```bash
# on worker: the Node name in the API is not the alias 'control-plane' from /etc/hosts, but the real name of the node (ip-10-...)
kubectl get nodes     # Ready
```

We create a Pod without a single mention of `seccompProfile` - neither at the Pod nor at the container level:

```yaml
# no-seccomp-field.yaml
apiVersion: v1
kind: Pod
metadata:
  name: no-seccomp-field
  namespace: security-106
spec:
  nodeSelector:
    security.cks.io/localhost-profiles-106: "true"
  containers:
  - name: app
    image: busybox:1.36
    command: ["sleep", "3600"]
```

```bash
# on worker
kubectl apply -f no-seccomp-field.yaml
kubectl get pod -n security-106 no-seccomp-field
kubectl exec -n security-106 no-seccomp-field -- grep '^Seccomp:' /proc/1/status
# Seccomp: 2  -- the kubelet applied RuntimeDefault itself, without a field in the manifest

# Check yourself via the REALLY APPLIED kubelet configuration, not via the text of the file on
# disk - a drop-in or a command-line flag could override the value without
# changing config.yaml itself:
NODE=$(kubectl get nodes -o jsonpath='{.items[0].metadata.name}')
kubectl get --raw "/api/v1/nodes/${NODE}/proxy/configz" | jq '.kubeletconfig.seccompDefault'
# true
```

Without `seccompDefault: true` the same manifest would give `Seccomp: 0` (`Unconfined`) - this is easy to
check by rolling back the flag and recreating the Pod, if you need to see the difference.

## 9. Debugging a broken AppArmor profile

`/etc/apparmor.d/k8s-106-broken-profile` is already on disk, but was never loaded: it lacks
a comma after the rule `deny /work/** w`. First we find the error without loading into the
kernel. `-p`/`--preprocess` is NOT suitable here - it is preprocessing (it expands
`#include` to stdout), and not a safe dry-run/syntax-check. We use `-Q`/`--skip-kernel-load`
(full compilation/check without loading into the kernel) or `-d`/`--debug`
(once - only a syntax check).

The artifact `apparmor-debug.txt` must contain the **original** parser error, so
we save it before the fix (on `worker`):

```bash
mkdir -p /var/work/tests/artifacts/8
ssh control-plane 'sudo apparmor_parser -Q /etc/apparmor.d/k8s-106-broken-profile' \
  > /var/work/tests/artifacts/8/apparmor-debug.txt 2>&1
cat /var/work/tests/artifacts/8/apparmor-debug.txt
# ... syntax error, unexpected TOK_CLOSE, expecting TOK_END_OF_RULE
```

We use `sudo` for the compile-only check `-Q` as well: on the lab node (apparmor 3.0.4, Ubuntu)
without privileges the parser tries on every run to set up the policy cache in
`/var/cache/apparmor` and fails with "Failed setting up policy cache (/var/cache/apparmor):
Permission denied" BEFORE checking the syntax - you will get a misleading permissions error instead of
the real syntax error, and `apparmor-debug.txt` will not contain the needed text
"syntax error". Verified on the node itself, including on a deliberately broken profile.
The alternative without `sudo` is to add `-K`/`--skip-cache` (`apparmor_parser -Q -K ...`): without
caching the parser gets as far as parsing the profile. `sudo` is chosen in this lab for a consistent
workflow with the subsequent `-r`, which requires privileges in any case.

We fix it on the node: an AppArmor rule must end with a comma. Then we load the fixed
profile into the kernel - exactly `-r -v` (reload + verbose), and not `-Q`/`-p`, which
load nothing:

```bash
# on the node
ssh control-plane
sudo -i
sed -i 's/^\(\s*deny \/work\/\*\* w\)$/\1,/' /etc/apparmor.d/k8s-106-broken-profile
tail -5 /etc/apparmor.d/k8s-106-broken-profile
apparmor_parser -r -v /etc/apparmor.d/k8s-106-broken-profile
aa-status --pretty-json | grep k8s-106-broken-profile
# expected: "k8s-106-broken-profile":	"enforce",
```

The final check that the file is now valid without errors:

```bash
apparmor_parser -Q /etc/apparmor.d/k8s-106-broken-profile
echo "exit: $?"
# exit: 0
exit
exit
```

Now on `worker` append the load confirmation AFTER the fix to the same artifact:

```bash
ssh control-plane 'sudo aa-status --pretty-json' | grep k8s-106-broken-profile >> /var/work/tests/artifacts/8/apparmor-debug.txt
cat /var/work/tests/artifacts/8/apparmor-debug.txt
```

At the end run (on `worker`):

```bash
check_result
```
