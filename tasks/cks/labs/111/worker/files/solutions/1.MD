# Lab 111 - reference solution

All the commands are run on the worker. These are regular commands of the tools (trivy, kubesec,
kube-linter, hadolint, podman, syft, bom, cosign) that exist on the exam; there are no scripts, and where
several results need to be compared, this is done by eye from the output. First set the common
variables:

```bash
export ROOT=/home/ubuntu/cks-111 ART=/var/work/tests/artifacts BASE_TAG=nginx:1.27.3-alpine
cd $ROOT
# The tag is mutable: we learn the manifest digest from Trivy once and then use tag@digest.
trivy image --format json $BASE_TAG > /tmp/cks-111-base.json
export IMAGE=$BASE_TAG@$(jq -r '.Metadata.RepoDigests[0]' /tmp/cks-111-base.json | cut -d@ -f2)
echo $IMAGE
```

## 0. Preparation: podman and the registry

For building and publishing images `podman` is used (it is in the list of exam tools;
rootless, works as `ubuntu`). The registry has already been brought up by the bootstrap: it is `registry:2` on the control-plane
(`<node IP>:5000`, plain HTTP inside the VPC, data on the local PV of the node). Podman on the worker is configured
for it as an insecure registry (`/etc/containers/registries.conf.d/cks111.conf`), and so is containerd on the
node, so the flag `--tls-verify=false` is not needed. The lab images have been downloaded in advance into a local
cache used by Trivy and Syft, so repeated scans do not run into the Docker Hub limit.

The registry address:

```bash
export REGISTRY="$(cat /etc/cks111/registry)"     # <IP control-plane>:5000
curl -fsS "http://$REGISTRY/v2/" && echo " registry ok: $REGISTRY"
podman --version
```

We leave the cosign key password empty so that the commands do not wait for input:

```bash
export COSIGN_PASSWORD=""
```

The registry works over HTTP: we take the digest of a published image from `podman push --digestfile`, and
check the existence of the manifest with a request to `/v2/`. `cosign` itself uses HTTP for addresses of
private networks; for Kyverno `credentials.allowInsecureRegistry: true` is set in the policy. `bom` reads
images only from a registry, so it still calls Docker Hub; if you see
`TOOMANYREQUESTS`, wait or run `podman login docker.io` under your own account.

## 3. Fix the Dockerfile

Do not add a secret into an image layer and do not use a floating tag: use `$IMAGE`, in which the tag is supplemented with the manifest digest. `USER 101` is a property of the future hardened image.

```bash
cat > "$ROOT/Dockerfile" <<EOF
FROM $IMAGE
ARG CKS_SIGNATURE_TEST=signed
LABEL cks.signature-test=\$CKS_SIGNATURE_TEST
COPY --chown=101:101 . /usr/share/nginx/html
USER 101
CMD ["nginx", "-g", "daemon off;"]
EOF
mkdir -p "$ART/3"
hadolint "$ROOT/Dockerfile" > "$ART/3/hadolint-after.txt"
# A clean Dockerfile gives an EMPTY hadolint output (return code 0) - an empty file is expected and correct here.
grep -nE '^(FROM|COPY|USER)' "$ROOT/Dockerfile"
```

`ARG CKS_SIGNATURE_TEST`/`LABEL cks.signature-test` do not change any of the
security properties checked here (base image, non-root, absence of a secret) - this is the only point of
a controlled difference that in task 9c guarantees a different manifest digest without
revisiting the rest of the Dockerfile.

Build and **publish** the image to a registry that Kubernetes can reach; a local image ID/DiffID alone is not suitable for digest pinning. Substitute your repository, then obtain the registry manifest digest and form the immutable reference:

```bash
export HARDENED_TAG="$REGISTRY/catalog:1.0"
podman build -t "$HARDENED_TAG" "$ROOT"
podman push --digestfile /tmp/cks-111-hardened.digest "$HARDENED_TAG"
export HARDENED_DIGEST=$(cat /tmp/cks-111-hardened.digest)
export HARDENED_IMAGE="${HARDENED_TAG%:*}@${HARDENED_DIGEST}"
printf '%s\n' "$HARDENED_IMAGE"   # <IP>:5000/catalog@sha256:<manifest-digest>
```

## 4. Fix the Deployment

`readOnlyRootFilesystem` requires writable runtime paths for nginx. `emptyDir` provides them point-wise; the init container (also a hardened image with `USER 101`) copies the default config into a separate writable config volume. `$HARDENED_IMAGE` is the built and digest-pinned reference from task 3, and not the upstream image.

```bash
cat > "$ROOT/deployment.yaml" <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog
  namespace: cks-111
spec:
  replicas: 1
  selector:
    matchLabels: {app: catalog}
  template:
    metadata:
      labels: {app: catalog}
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        runAsUser: 101
        runAsGroup: 101
        fsGroup: 101
        seccompProfile: {type: RuntimeDefault}
      initContainers:
      - name: prepare-nginx-config
        image: $HARDENED_IMAGE
        command: ["sh", "-c", "cp /etc/nginx/conf.d/default.conf /work/default.conf"]
        securityContext:
          allowPrivilegeEscalation: false
          capabilities: {drop: ["ALL"]}
        volumeMounts: [{name: nginx-config, mountPath: /work}]
      containers:
      - name: catalog
        image: $HARDENED_IMAGE
        ports: [{containerPort: 80, name: http}]
        readinessProbe: {httpGet: {path: /, port: http}}
        securityContext:
          allowPrivilegeEscalation: false
          readOnlyRootFilesystem: true
          capabilities: {drop: ["ALL"]}
        resources:
          requests: {cpu: 100m, memory: 64Mi}
          limits: {cpu: 250m, memory: 128Mi}
        volumeMounts:
        - {name: nginx-tmp, mountPath: /tmp}
        - {name: nginx-run, mountPath: /var/run}
        - {name: nginx-cache, mountPath: /var/cache/nginx}
        - {name: nginx-config, mountPath: /etc/nginx/conf.d}
      volumes:
      - {name: nginx-tmp, emptyDir: {medium: Memory}}
      - {name: nginx-run, emptyDir: {}}
      - {name: nginx-cache, emptyDir: {}}
      - {name: nginx-config, emptyDir: {}}
---
apiVersion: v1
kind: Service
metadata: {name: catalog, namespace: cks-111}
spec:
  selector: {app: catalog}
  ports: [{name: http, port: 80, targetPort: http}]
EOF
mkdir -p "$ART/4"
kubesec scan "$ROOT/deployment.yaml" > "$ART/4/kubesec-after.json" || true
kube-linter lint "$ROOT/deployment.yaml" --format json > "$ART/4/kube-linter-after.json" || true
jq type "$ART/4/kubesec-after.json" "$ART/4/kube-linter-after.json"
kubectl apply -f "$ROOT/deployment.yaml"
kubectl rollout status deployment/catalog -n cks-111 --timeout=180s
kubectl wait --for=condition=Available deployment/catalog -n cks-111 --timeout=180s
kubectl run catalog-http-smoke -n cks-111 --rm -i --restart=Never --image=curlimages/curl:8.11.0 --   curl -fsS --max-time 10 http://catalog
```

## 7. CycloneDX SBOM (Syft) and keyless Cosign

Syft can do both SPDX and CycloneDX; here we take CycloneDX (`bom` already gave SPDX in task 6).
We verify the public Distroless image and its expected Google workload identity; do not
use `--insecure-ignore-tlog` or skipping the certificate identity.

```bash
mkdir -p "$ART/7"
# For a reference of the form tag@digest Syft writes only the tag into metadata.component.version; a reference
# without a tag ("nginx@sha256:...") gives version = the manifest digest, which is what is checked.
syft "nginx@${IMAGE#*@}" -o "cyclonedx-json=$ART/7/syft.cdx.json"
```

After `syft` wait for it to finish and paste the further commands separately: `syft` (like `apt-get`)
flushes the terminal input buffer, and lines pasted right after it are lost.

```bash
jq -r '.metadata.component.version' "$ART/7/syft.cdx.json"   # sha256:<manifest-digest>
cosign verify \
  --certificate-oidc-issuer https://accounts.google.com \
  --certificate-identity keyless@distroless.iam.gserviceaccount.com \
  gcr.io/distroless/static-debian13:nonroot > $ART/7/cosign-verify.txt 2>&1
echo "exit code: $?"      # 0 = the signature is verified

# gcr.io/distroless/static:nonroot (without the suffix -debian13) is considered deprecated and is no longer
# updated according to the official Distroless README - we use the current
# supported tag gcr.io/distroless/static-debian13:nonroot. The success of cosign verify is
# determined by the exit code, and not by the literal string "Verified OK" - there is no such string in the
# real cosign output (a successful output starts with the line "Verification for <image> --"
# and a list of the checks performed). cosign writes its progress to stderr, so 2>&1
# is mandatory - otherwise the artifact will stay empty.
printf '\nreference=gcr.io/distroless/static-debian13:nonroot\n' >> $ART/7/cosign-verify.txt
jq '.bomFormat, (.components | length)' $ART/7/syft.cdx.json
```

## 9a. Kyverno and an `ImageValidatingPolicy` on a trusted signature

Install Kyverno in the same way as in lab 108 and wait for the admission controller to be ready.

```bash
sudo install-kyverno
```

Paste the following commands after the installation finishes (the installer flushes the input buffer):

```bash
kubectl -n kyverno get deployment kyverno-admission-controller
kubectl -n kyverno wait --for=condition=Available deployment/kyverno-admission-controller --timeout=180s
```

Generate a training key pair OUTSIDE `$ROOT` - this directory is reused as the
Docker build context in task 9c (`COPY . /usr/share/nginx/html` in the Dockerfile copies
ALL of the content of the build context), so a `cosign.key` left inside `$ROOT` will get
inside the filesystem of the published image as a leak of the private signing key into the registry. Sign
exactly the `$HARDENED_IMAGE` from tasks 3/4, and not the upstream `nginx`. Do not carry this
`cosign.key` over into a production CI.

```bash
export KEYDIR=/home/ubuntu/.cks111-cosign
mkdir -p $KEYDIR $ART/9a $ART/9b $ART/9c
cd $KEYDIR && cosign generate-key-pair && cd $ROOT

# cosign sign writes its progress to stderr, so 2>&1 is mandatory - otherwise the artifact will stay empty.
cosign sign --key $KEYDIR/cosign.key --yes $HARDENED_IMAGE > $ART/9a/cosign-sign.txt 2>&1
cosign verify --key $KEYDIR/cosign.pub $HARDENED_IMAGE > $ART/9a/cosign-verify.txt 2>&1
cat $ART/9a/cosign-verify.txt | head -3
```

Create an `ImageValidatingPolicy` that references the public key with which
`$HARDENED_IMAGE` was just signed. `matchImageReferences` restricts the policy to exactly the repository
of your image: for OCI references the separate delimiters `:` (tag) and `@` (digest) are needed,
otherwise the prefix `${HARDENED_REPO}*` would capture, for example, another repository with the same beginning
of the name. This prevents the policy from blocking the other Pods of the cluster.

```bash
export HARDENED_REPO="${HARDENED_IMAGE%@*}"
cat > "$ROOT/require-signed-catalog-images.yaml" <<EOF
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: require-signed-catalog-images
spec:
  failurePolicy: Fail
  validationActions: [Deny]
  credentials:
    allowInsecureRegistry: true   # the lab registry works over HTTP
  matchConstraints:
    resourceRules:
    - apiGroups: [""]
      apiVersions: ["v1"]
      operations: ["CREATE", "UPDATE"]
      resources: ["pods", "pods/ephemeralcontainers"]
  matchImageReferences:
  - glob: "${HARDENED_REPO}:*"
  - glob: "${HARDENED_REPO}@*"
  attestors:
  - name: catalogReleaseKey
    cosign:
      key:
        data: |-
$(sed 's/^/          /' "$KEYDIR/cosign.pub")
  validations:
  - message: "catalog image must have a valid release signature"
    expression: >-
      (images.containers + images.?initContainers.orValue([]) +
      images.?ephemeralContainers.orValue([])).map(image,
        verifyImageSignatures(image, [attestors.catalogReleaseKey]) > 0).all(ok, ok)
EOF
kubectl apply -f "$ROOT/require-signed-catalog-images.yaml"
kubectl get imagevalidatingpolicy require-signed-catalog-images -o yaml
```

At the end run `check_result` (partially, test 9a).

## 9b. Fresh signed ALLOW: a new Pod after the policy is created

A repeated `kubectl apply` of the already existing Deployment `catalog` **does not prove**
the post-policy admission: if the template has not changed, Kubernetes does not create a new
ReplicaSet/Pod, and the observed `Running` may be the same Pod that existed even before
`require-signed-catalog-images`. To prove exactly a fresh admission, we create a **new**
object that did not exist before this moment:

```bash
POLICY_CREATED=$(kubectl get imagevalidatingpolicy require-signed-catalog-images \
  -o jsonpath='{.metadata.creationTimestamp}')

# Right after the policy is created, the first call of the Kyverno webhook (checking the signature in the registry) may
# hit a 10 s timeout (`failed calling webhook ... context deadline exceeded`): with
# failurePolicy=Fail the Pod is then not created. Just repeat the command after a few seconds.
kubectl run signed-admission-check -n cks-111 --image=$HARDENED_IMAGE --restart=Never --command -- sleep 3600
kubectl wait --for=condition=Ready pod/signed-admission-check -n cks-111 --timeout=60s

kubectl get pod signed-admission-check -n cks-111 -o json \
  | jq --arg policy "$POLICY_CREATED" '{
      creationTimestamp: .metadata.creationTimestamp,
      policyCreationTimestamp: $policy,
      createdAfterPolicy: (.metadata.creationTimestamp >= $policy),
      image: .spec.containers[0].image,
      phase: .status.phase,
      ready: ([.status.conditions[]? | select(.type == "Ready") | .status] | any(. == "True"))
    }' > "$ART/9b/signed-admission-check.json"
cat "$ART/9b/signed-admission-check.json"
```

The criterion (`creationTimestamp` has a precision of 1 s, so the comparison is non-strict): `createdAfterPolicy == true` and `ready == true`. This - and only this - proves
that exactly **this** policy admitted exactly **this**, previously non-existent Pod with a
signed image, and not that an old Pod simply keeps running.

At the end run `check_result` (partially, test 9b).

## 9c. Signature-specific DENY: an unsigned digest in the same repository

The unsigned candidate must exist in the **same** repository as the signed
`$HARDENED_IMAGE` - otherwise admission may refuse because of `manifest unknown` or a
registry lookup error, and not because of the absence of a signature, and the denial will not prove the claimed
security property. We build and publish a second, deliberately unsigned tag in the same
repository - and **necessarily** with content different from `$HARDENED_IMAGE`: if you build
the same `Dockerfile`/context unchanged, a reproducible/cached build may give the **same**
manifest digest as the already signed image, and then `cosign verify` on the "unsigned" tag
will unexpectedly pass - because it physically points to the already signed artifact. Therefore
we introduce a controlled difference via `ARG`/`LABEL` that is guaranteed to change the digest:

```bash
export UNSIGNED_TAG="${HARDENED_TAG%:*}:unsigned-1"
podman build --build-arg CKS_SIGNATURE_TEST=unsigned-1 -t "$UNSIGNED_TAG" "$ROOT"
podman push --digestfile /tmp/cks-111-unsigned.digest "$UNSIGNED_TAG"
export UNSIGNED_DIGEST=$(cat /tmp/cks-111-unsigned.digest)
export UNSIGNED_IMAGE="${HARDENED_REPO}@${UNSIGNED_DIGEST}"
export HARDENED_DIGEST="${HARDENED_IMAGE#*@}"

# A mandatory check: the unsigned candidate must be a physically different artifact,
# and not the same digest as the already signed HARDENED_IMAGE.
[ "$UNSIGNED_DIGEST" != "$HARDENED_DIGEST" ] && echo "digests differ: OK"
printf 'hardened_digest=%s\nunsigned_digest=%s\nunsigned_image=%s\ndistinct=true\n' \
  "$HARDENED_DIGEST" "$UNSIGNED_DIGEST" "$UNSIGNED_IMAGE" > "$ART/9c/digest-comparison.txt"
cat "$ART/9c/digest-comparison.txt"
```

The `$ROOT/Dockerfile` from task 3 must accept this build-arg (for example,
`ARG CKS_SIGNATURE_TEST=signed` and `LABEL cks.signature-test=$CKS_SIGNATURE_TEST` next to the
existing instructions) - then the built image differs from `$HARDENED_IMAGE` by exactly
one safe label, without touching the security properties checked in tasks 3-4.

We explicitly prove that this digest exists and is pullable before checking the policy -
otherwise the denial will prove nothing. This is self-check evidence for you: the checker for task 9c
does not trust text files as the only proof - it itself resolves
`unsigned_image` from `digest-comparison.txt`, itself checks the absence of a signature, and itself
creates a new Pod with this image, so writing these files by hand without a real
working admission control is not enough for PASS.

```bash
curl -fsSI -H 'Accept: application/vnd.oci.image.manifest.v1+json, application/vnd.oci.image.index.v1+json, application/vnd.docker.distribution.manifest.v2+json' \
  "http://$REGISTRY/v2/catalog/manifests/$UNSIGNED_DIGEST" > "$ART/9c/unsigned-exists.txt"
cat "$ART/9c/unsigned-exists.txt"        # HTTP/1.1 200 OK and docker-content-digest: $UNSIGNED_DIGEST
```

We explicitly prove the absence of a valid signature by the same key - **before** trying to create the
Pod, so that the denial is predictably specific to the signature and not to something else:

```bash
cosign verify --key "$KEYDIR/cosign.pub" "$UNSIGNED_IMAGE" > "$ART/9c/unsigned-not-signed.txt" 2>&1
cat "$ART/9c/unsigned-not-signed.txt"     # error: no matching signatures
```

Only now we try to create the Pod and confirm that the denial refers exactly to the policy/
signature, and not to a generic admission error:

```bash
kubectl run catalog-unsigned-probe -n cks-111 --image="$UNSIGNED_IMAGE" --restart=Never > "$ART/9c/admission-deny.txt" 2>&1
cat "$ART/9c/admission-deny.txt"        # ... catalog image must have a valid release signature
kubectl get pod catalog-unsigned-probe -n cks-111       # NotFound: the Pod is not created
```

The difference from a naive check: if instead we had taken a digest from another repository
(for example, the digest of the upstream `nginx` from task 1), admission might have refused for a completely
different reason (`manifest unknown`, no pull access) - and such a denial would look
like "the policy works", although in fact the signature check was never reached.
