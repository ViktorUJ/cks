# Lab 102 - short solution

We use `k` instead of `kubectl` (the alias is already available on the exam). The context `cluster1-admin@cluster1` is already selected.

## 1. Namespace and training Pods

```bash
k create ns cks-102
k -n cks-102 run backend --image=nginx:1.27-alpine -l app=backend --port=80
k -n cks-102 expose pod backend --port=80
k -n cks-102 run frontend --image=curlimages/curl:8.10.1 -l role=frontend --command -- sleep 3600
k -n cks-102 run client --image=curlimages/curl:8.10.1 -l role=untrusted --command -- sleep 3600
k -n cks-102 wait --for=condition=Ready pod/backend pod/frontend pod/client --timeout=120s
sleep 5
```

## 2. CiliumNetworkPolicy L3/L4

Check BEFORE the policy - both Pods must actually reach the backend:

```bash
k -n cks-102 exec frontend -- curl -sS -o /dev/null -w 'frontend HTTP:%{http_code}\n' -m5 http://backend/
k -n cks-102 exec client -- curl -sS -o /dev/null -w 'client HTTP:%{http_code}\n' -m5 http://backend/
```

```
frontend HTTP:200
client HTTP:200
```

The policy: selects `backend`, allows ingress only from `role=frontend` on TCP/80.

```bash
k apply -f - <<EOF
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: backend-policy
  namespace: cks-102
spec:
  endpointSelector:
    matchLabels:
      app: backend
  ingress:
    - fromEndpoints:
        - matchLabels:
            role: frontend
      toPorts:
        - ports:
            - port: "80"
              protocol: TCP
EOF
```

Check AFTER the policy:

```bash
k -n cks-102 exec frontend -- curl -sS -o /dev/null -w 'frontend HTTP:%{http_code}\n' -m5 http://backend/
k -n cks-102 exec client -- curl -sS -o /dev/null -w 'client HTTP:%{http_code}\n' -m5 http://backend/
```

```
frontend HTTP:200
client HTTP:000
curl: (28) Connection timed out after 5000 milliseconds
```

`client` -> a transport-level deny (`000` and a timeout), not just "not 200".

## 3. L7 restriction: only GET /

Check BEFORE (while the L4-only policy is still in effect) - GET and POST must both actually reach the backend:

```bash
k -n cks-102 exec frontend -- curl -sS -o /dev/null -w 'GET HTTP:%{http_code}\n' -m5 http://backend/
k -n cks-102 exec frontend -- curl -sS -X POST -o /dev/null -w 'POST HTTP:%{http_code}\n' -m5 http://backend/
```

```
GET HTTP:200
POST HTTP:405
```

Replace the rule (do not add a second broad L4 rule next to it - otherwise the L7 filter will not work):

```bash
k apply -f - <<EOF
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: backend-policy
  namespace: cks-102
spec:
  endpointSelector:
    matchLabels:
      app: backend
  ingress:
    - fromEndpoints:
        - matchLabels:
            role: frontend
      toPorts:
        - ports:
            - port: "80"
              protocol: TCP
          rules:
            http:
              - method: GET
                path: "/"
EOF
```

Check AFTER:

```bash
k -n cks-102 exec frontend -- curl -sS -o /dev/null -w 'GET HTTP:%{http_code}\n' -m5 http://backend/
k -n cks-102 exec frontend -- curl -sS -X POST -o /dev/null -w 'POST HTTP:%{http_code}\n' -m5 http://backend/
```

```
GET HTTP:200
POST HTTP:403
```

The POST is rejected by Cilium's Envoy proxy at L7 (`403`), not by a transport deny.

## 4. DNS-aware egress via toFQDNs

`allowed.cks102.test`/`blocked.cks102.test` is a lab-owned fixture that resolves to
`198.18.0.10`/`198.18.0.20` (synthetic IPs outside the Kubernetes address space, a separate
network namespace on the control-plane node, and NOT a ClusterIP: Cilium's `toFQDNs` does not apply the
allow rule to an IP inside the cluster), brought up and written into CoreDNS already at bootstrap:
unlike `example.com`, these names are always available and do not depend on the Internet. Check BEFORE the
policy - DNS and both control endpoints must be really reachable (`-k` because of the self-signed
certificate of the fixture):

```bash
k -n cks-102 exec frontend -- nslookup allowed.cks102.test
k -n cks-102 exec frontend -- curl -sSk -o /dev/null -w 'allowed:443 HTTP:%{http_code}\n' -m10 https://allowed.cks102.test/
k -n cks-102 exec frontend -- curl -sS -o /dev/null -w 'allowed:80 HTTP:%{http_code}\n' -m5 http://allowed.cks102.test:80/
k -n cks-102 exec frontend -- curl -sSk -o /dev/null -w 'blocked:443 HTTP:%{http_code}\n' -m10 https://blocked.cks102.test/
```

```
allowed.cks102.test has address ...
allowed:443 HTTP:200
allowed:80 HTTP:200
blocked:443 HTTP:200
```

Three egress rules in one object: (1) DNS to `kube-dns` via `rules.dns` - without it Cilium will not build the FQDN-to-IP mapping; (2) internal `backend` on TCP/80 - without it the default-deny egress will block the flow already allowed in tasks 2-3; (3) `toFQDNs` only to `allowed.cks102.test:443`.

```bash
k apply -f - <<EOF
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: frontend-fqdn
  namespace: cks-102
spec:
  endpointSelector:
    matchLabels:
      role: frontend
  egress:
    - toEndpoints:
        - matchLabels:
            k8s:io.kubernetes.pod.namespace: kube-system
            k8s:k8s-app: kube-dns
      toPorts:
        - ports:
            - port: "53"
              protocol: ANY
          rules:
            dns:
              - matchPattern: "*"
    - toEndpoints:
        - matchLabels:
            app: backend
      toPorts:
        - ports:
            - port: "80"
              protocol: TCP
    - toFQDNs:
        - matchName: allowed.cks102.test
      toPorts:
        - ports:
            - port: "443"
              protocol: TCP
EOF
```

Check AFTER (wait a couple of seconds, the FQDN mapping is not instantaneous) and make sure that the backend from tasks 2-3 has not regressed:

```bash
k -n cks-102 exec frontend -- curl -sSk -o /dev/null -w 'allowed:443 HTTP:%{http_code}\n' -m10 https://allowed.cks102.test/
k -n cks-102 exec frontend -- curl -sS -o /dev/null -w 'allowed:80 HTTP:%{http_code}\n' -m5 http://allowed.cks102.test:80/
k -n cks-102 exec frontend -- curl -sSk -o /dev/null -w 'blocked:443 HTTP:%{http_code}\n' -m10 https://blocked.cks102.test/
k -n cks-102 exec frontend -- curl -sS -o /dev/null -w 'GET HTTP:%{http_code}\n' -m5 http://backend/
k -n cks-102 exec frontend -- curl -sS -X POST -o /dev/null -w 'POST HTTP:%{http_code}\n' -m5 http://backend/
```

```
allowed:443 HTTP:200
allowed:80 HTTP:000
blocked:443 HTTP:000
GET HTTP:200
POST HTTP:403
```

HTTPS to `allowed.cks102.test` stays `200`; `allowed.cks102.test:80` and `blocked.cks102.test:443` hang/time out (`000`); backend GET/POST are as in tasks 2-3, no regression.

## 5. Observation via Hubble

The Relay is already enabled by worker.sh. Open the port-forward and the observation, and generate a GET and a POST:

```bash
cilium hubble port-forward &
sleep 3
hubble observe --from-pod cks-102/frontend --to-pod cks-102/backend --protocol http --follow &
sleep 2

k -n cks-102 exec frontend -- curl -sS http://backend/ -o /dev/null
k -n cks-102 exec frontend -- curl -sS -X POST http://backend/ -o /dev/null
sleep 3
```

```
cks-102/frontend:xxxxx -> cks-102/backend:80 http-request FORWARDED (HTTP/1.1 GET http://backend/)
cks-102/frontend:xxxxx -> cks-102/backend:80 http-request DROPPED (HTTP/1.1 POST http://backend/)
```

You should see exactly two flows: `GET /` with the verdict `FORWARDED` and `POST /` with the verdict `DROPPED`. If they are missing, `hubble observe` was not running while the requests were made; repeat.

## 6. Composite L7 policy: public/private path scopes

A second, independent backend with two path scopes. We replace the nginx config completely
(`default.conf`), so that `location` returns `200` for a specific prefix and `404` for
everything else - without it there is no way to tell "allowed" from "denied" by the HTTP code.

```bash
k create ns production
k create ns finance

k create configmap portal-nginx-conf -n production --from-literal=default.conf='
server {
  listen 80;
  location /public/ { return 200 "public ok\n"; }
  location /private/ { return 200 "private ok\n"; }
  location / { return 404; }
}
'

k apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: portal
  namespace: production
  labels:
    app: portal
spec:
  containers:
  - name: nginx
    image: nginx:1.27-alpine
    ports:
    - containerPort: 80
    volumeMounts:
    - name: conf
      mountPath: /etc/nginx/conf.d/default.conf
      subPath: default.conf
  volumes:
  - name: conf
    configMap:
      name: portal-nginx-conf
EOF
k expose pod portal -n production --port=80
k -n finance run finance-client --image=curlimages/curl:8.10.1 --command -- sleep 3600
k -n production wait --for=condition=Ready pod/portal --timeout=60s
k -n finance wait --for=condition=Ready pod/finance-client --timeout=60s
```

Baseline BEFORE the policy - both paths from both namespaces must really return `200`:

```bash
k -n finance exec finance-client -- curl -sS -o /dev/null -w 'public:%{http_code}\n' -m5 http://portal.production/public/
k -n finance exec finance-client -- curl -sS -o /dev/null -w 'private:%{http_code}\n' -m5 http://portal.production/private/
k -n cks-102 exec client -- curl -sS -o /dev/null -w 'public:%{http_code}\n' -m5 http://portal.production/public/
k -n cks-102 exec client -- curl -sS -o /dev/null -w 'private:%{http_code}\n' -m5 http://portal.production/private/
```

```
public:200
private:200
public:200
private:200
```

The policy: two ingress rules on the same port. **An important Cilium trap**: `fromEndpoints:
[{}]` (an empty selector) in a namespaced `CiliumNetworkPolicy` does NOT mean "any identity in the
whole cluster" - Cilium implicitly adds a restriction to the namespace of the policy ITSELF to any
`fromEndpoints` selector without an explicit namespace label, including an empty `{}`. That is, `{}`
here in practice matches only the endpoints in the namespace `production`, not `finance`/`cks-102`
- a live check confirms this: with a literal `{}` the external client gets a transport
timeout on BOTH paths (the rule is not applied to its namespace at all), and `finance` gets
`403` on `/public/*` (it matches only rule 2, which allows only `/private/*`).
To actually match any identity regardless of namespace, you need `matchExpressions` with
`operator: Exists` on the reserved label `k8s:io.kubernetes.pod.namespace` (the mere presence of
this label is true for absolutely any Pod, regardless of the value) - this, and not an empty
`{}`, gives cross-namespace acceptance for rule 1:

```bash
k apply -f - <<EOF
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: portal-policy
  namespace: production
spec:
  endpointSelector:
    matchLabels:
      app: portal
  ingress:
    - fromEndpoints:
        - matchExpressions:
            - key: k8s:io.kubernetes.pod.namespace
              operator: Exists
      toPorts:
        - ports:
            - port: "80"
              protocol: TCP
          rules:
            http:
              - method: GET
                path: "/public/.*"
    - fromEndpoints:
        - matchLabels:
            k8s:io.kubernetes.pod.namespace: finance
      toPorts:
        - ports:
            - port: "80"
              protocol: TCP
          rules:
            http:
              - method: GET
                path: "/private/.*"
EOF
sleep 3
```

With this selector rule 1 really matches ABSOLUTELY any identity (including
`finance`), so the final allow-set for `finance` is the union of `/public/*` (rule 1)
and `/private/*` (rule 2, which matches only `finance`). For any other namespace
only rule 1 applies.

Check AFTER the policy:

```bash
k -n finance exec finance-client -- curl -sS -o /dev/null -w 'public:%{http_code}\n' -m5 http://portal.production/public/
k -n finance exec finance-client -- curl -sS -o /dev/null -w 'private:%{http_code}\n' -m5 http://portal.production/private/
k -n cks-102 exec client -- curl -sS -o /dev/null -w 'public:%{http_code}\n' -m5 http://portal.production/public/
k -n cks-102 exec client -- curl -sS -o /dev/null -w 'private:%{http_code}\n' -m5 http://portal.production/private/
```

```
public:200
private:200
public:200
private:403
```

`finance-client` -> both paths `200`. `cks-102/client` (any other namespace) -> `/public/*`
is still `200`, while `/private/*` is `403` (an Envoy L7 deny, not the transport-level `000`: rule 1
has already allowed the TCP connect itself for all identities).
