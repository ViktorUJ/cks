# Lab 113 - Reference Solution: kubeadm minor upgrade

> Work as you would in the exam: `kubectl` on the work machine, and the operations on a node (apt, kubeadm,
> kubelet) on the node itself: log in to it with `ssh <node>`, switch to root (`sudo -i`),
> run the commands, and exit (`exit`, `exit`). The starting version of the cluster is `1.35.x`, the target is
> `1.36.x`. We take the node names (`<cp-name>`, `<worker-name>`) from `kubectl get no`; in the exam they are different; in this lab the ssh aliases are: `k8s113_controlPlane_1` and `k8s113_node_worker1`.

On the Ubuntu nodes `needrestart` is configured in "list only" mode (without an OK/Cancel dialog), so
`apt-get install` does not stop on questions.

Instead of `1.36.x` in the commands, substitute the real patch from `apt-cache madison kubeadm` and from the
output of `kubeadm upgrade plan`.

```bash
export KUBECONFIG=/home/ubuntu/.kube/config
kubectl config use-context cluster1-admin@cluster1
mkdir -p /var/work/tests/artifacts/{1,2,4}
kubectl get no
```

In the `kubectl get no` output, note the node names (`ip-10-...`): you will need them for `drain` and `uncordon`. Below
`<cp-name>` is the name of the control-plane, `<worker-name>` is the name of the worker node.

## Step 0. Start the Availability Polling in Parallel (Task 4)

Before the upgrade open a separate session (`tmux`) on the work machine and leave the polling loop of the
Deployment `canary` running for the whole time of the following steps:

```bash
while true; do
  if available=$(kubectl get deployment canary -n upgrade-113 -o jsonpath='{.status.availableReplicas}' 2>/dev/null); then
    echo "$(date +%s) available=${available:-0}"
  else
    echo "$(date +%s) available=api-unreachable"
  fi >> /var/work/tests/artifacts/4/canary-availability.log
  sleep 5
done
```

## 1. Upgrading the Control-Plane

```bash
ssh <cp-name>
sudo -i
```

```bash
# on the control-plane (root): current versions
kubeadm version -o short; kubelet --version

# switch the repository to the next minor: in the file replace v1.35 with v1.36
vim /etc/apt/sources.list.d/kubernetes.list
# deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.36/deb/ /

apt update
apt-cache madison kubeadm | head -3
```

Upgrade kubeadm (the real patch instead of `x`). **Run this command separately:** `apt-get`
flushes the terminal input buffer, so lines pasted right after it are lost.

```bash
# on the control-plane (root)
apt-mark unhold kubeadm && apt-get update && apt-get install -y kubeadm='1.36.x-*' && apt-mark hold kubeadm
```

```bash
# on the control-plane (root)
kubeadm version -o short
kubeadm upgrade plan
```

Take the specific version from the output of `plan` and run the upgrade, saving the **full** output:

```bash
# on the control-plane (root)
kubeadm upgrade apply v1.36.x -y > /tmp/kubeadm-upgrade-apply.txt 2>&1
tail -3 /tmp/kubeadm-upgrade-apply.txt
# [upgrade] SUCCESS! A control plane node of your cluster was upgraded to "v1.36.x".
exit   # from root
exit   # from the control-plane
```

```bash
# on the work machine: fetch the output for the check
scp <cp-name>:/tmp/kubeadm-upgrade-apply.txt /var/work/tests/artifacts/1/kubeadm-upgrade-apply.txt
```

Only now, AFTER a successful `kubeadm upgrade apply`, drain the node and upgrade kubelet/kubectl:

```bash
# on the work machine
kubectl drain <cp-name> --ignore-daemonsets --delete-emptydir-data
```

```bash
ssh <cp-name>
sudo -i
```

```bash
# on the control-plane (root)
apt-mark unhold kubelet kubectl && apt-get update && apt-get install -y kubelet='1.36.x-*' kubectl='1.36.x-*' && apt-mark hold kubelet kubectl
```

```bash
# on the control-plane (root)
systemctl daemon-reload
systemctl restart kubelet
kubelet --version
exit   # from root
exit   # from the control-plane
```

```bash
# on the work machine
kubectl uncordon <cp-name>
kubectl get nodes
```

## 2. Upgrading the Worker Node

Start only after the control-plane is `Ready` on `1.36.x` (version skew policy:
the kubelet of a worker node cannot be newer than the control-plane). Wait until `canary` is `2/2` again:

```bash
# on the work machine: repeat until AVAILABLE becomes 2
kubectl get deployment canary -n upgrade-113
```

```bash
ssh <worker-name>
sudo -i
```

```bash
# on the worker (root): the same repository as on the control-plane
vim /etc/apt/sources.list.d/kubernetes.list     # v1.35 -> v1.36
apt update
```

```bash
# on the worker (root)
apt-mark unhold kubeadm && apt-get update && apt-get install -y kubeadm='1.36.x-*' && apt-mark hold kubeadm
```

```bash
# on the worker (root)
# on a worker node (and additional control-plane nodes) upgrade node is run instead of apply
kubeadm upgrade node > /tmp/kubeadm-upgrade-node.txt 2>&1
tail -3 /tmp/kubeadm-upgrade-node.txt
exit   # from root
exit   # from the worker
```

```bash
# on the work machine
scp <worker-name>:/tmp/kubeadm-upgrade-node.txt /var/work/tests/artifacts/2/kubeadm-upgrade-node.txt
kubectl drain <worker-name> --ignore-daemonsets --delete-emptydir-data
```

```bash
ssh <worker-name>
sudo -i
```

```bash
# on the worker (root)
apt-mark unhold kubelet kubectl && apt-get update && apt-get install -y kubelet='1.36.x-*' kubectl='1.36.x-*' && apt-mark hold kubelet kubectl
```

```bash

systemctl restart kubelet
```

## 3. Checking the Upgrade Order

Task 3 does not require separate commands: the order is proven by the checker-owned monitor
(`/var/lib/cks-lab113-checker/upgrade-monitor.log` on the work machine), which has been recording continuously
since the bootstrap. If you followed the steps in order (first all of section 1, then section 2), the
log has a line where the control-plane is already on `v1.36.x`, `Ready` and schedulable, while the worker is still on
`v1.35.x`.

## 4. Checking the Absence of Downtime

> During `kubeadm upgrade apply` on the only control-plane the API server restarts for a few seconds,
> and `kubectl` in the polling loop does not respond. Such lines are recorded as
> `available=api-unreachable` and do not count toward the minimum: API unavailability is not a
> `canary` outage. Whether there was any downtime is determined by the checker's independent monitor (Pod Ready and containers via `crictl`).

Stop the polling loop from Step 0 (`Ctrl+C` in its session) and check that the minimum of `available`
over the run never dropped to 0:

```bash
grep -oE 'available=[0-9]+' /var/work/tests/artifacts/4/canary-availability.log | sort -u
kubectl get deployment canary -n upgrade-113
```

Both `canary` replicas are spread across different nodes (required `podAntiAffinity`) and protected by a
`PodDisruptionBudget` with `minAvailable: 1`, so a correct sequential drain (first
one node, then the other, after the uncordon) does not drop `available` below `1`.

## Final Check

```bash
kubectl get nodes
check_result
```

Both nodes must be `Ready` on `v1.36.x`, and neither may be `SchedulingDisabled`.
