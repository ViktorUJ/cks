# Lab 123 — reference solution (installing a CNI from scratch + low-level networking)

The cluster is brought up **without a CNI**: `kubectl get nodes` → all nodes `NotReady`, the
Pods in `netlab` hang in `Pending`/`ContainerCreating`, CoreDNS does not come up. As long as
there is no network plugin — there is no Pod network.

Connecting to the nodes: `ssh k8s1_controlPlane_1`, `ssh k8s1_node_node_1`.

## Task 1. Install the CNI by hand

The official kubeadm step is "Installing a Pod network add-on"
([kubeadm documentation](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/create-cluster-kubeadm/#pod-network),
[list of addons](https://kubernetes.io/docs/concepts/cluster-administration/addons/)).
We install Calico ([Calico quickstart](https://docs.tigera.io/calico/latest/getting-started/kubernetes/quickstart)):

```bash
# pick a manifest version compatible with k8s 1.35 (see docs.tigera.io)
kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.28.2/manifests/calico.yaml

# watch the network come up
kubectl -n kube-system get pods -l k8s-app=calico-node -w
kubectl get nodes -w        # the nodes move to Ready
```

After the CNI is installed:
- the nodes become `Ready`;
- CoreDNS comes up (`kubectl -n kube-system get deploy coredns`);
- the `netprobe` Pods in `netlab` spread across the two nodes and move to `Running`.

> If you want Calico's address pool to match `--pod-network-cidr=10.0.0.0/16`,
> set `CALICO_IPV4POOL_CIDR=10.0.0.0/16` in the manifest before `apply` (it does not affect
> passing the lab).

## Tasks 2-3 (validated automatically)

As soon as the CNI works, CoreDNS and `netprobe` (2 Pods on different nodes) come up on their
own — that is the confirmation of a working Pod network, including **across nodes**.

## Task 4. Low-level networking report → `net-lowlevel.txt`

Collect the facts on the control plane node:

```bash
ssh k8s1_controlPlane_1

# the CNI config that the plugin dropped in
sudo ls /etc/cni/net.d
# e.g.: 10-calico.conflist

# the default route device
ip route show default
# default via 10.10.1.1 dev ens5 ...   -> dev = ens5
```

On the work machine:

```bash
mkdir -p /home/ubuntu/answers
cat > /home/ubuntu/answers/net-lowlevel.txt <<EOF
cni_conf=10-calico.conflist
default_route_dev=ens5
EOF
```

> Substitute your own values from the output above.

## A look at network namespaces and routes (low level)

It is useful to understand how the CNI connects a Pod to the node network. On a node that has
a Pod:

```bash
# find the containers and their network namespaces
sudo crictl ps
sudo crictl inspectp <pod-id> | grep -i netns    # path to the Pod's network namespace

# list the network namespaces
ip netns list
# enter the netns of the Pod's process and look at its network
PID=$(sudo crictl inspect <container-id> | jq '.info.pid')
sudo nsenter -t $PID -n ip addr        # the Pod's eth0 interface and its IP
sudo nsenter -t $PID -n ip route       # the Pod's default route

# veth pairs on the host (one end in the Pod, the other on the node)
ip -o link | grep -E 'cali|veth'
# routes to the Pod networks (Calico adds routes to the other nodes)
ip route | grep -E '10\.|192\.168'
```

The idea: the CNI creates a separate **network namespace** for the Pod, connects it to the host
with a veth pair, hands out an IP from the pool and writes **routes** to the Pod networks on the
other nodes — that is how the Kubernetes "flat network" works.

Documentation: [Cluster Networking](https://kubernetes.io/docs/concepts/cluster-administration/networking/),
[Network Plugins (CNI)](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/network-plugins/).
