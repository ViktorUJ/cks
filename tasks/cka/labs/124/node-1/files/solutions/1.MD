# Lab 124 — reference solution (HA control plane out of 3 nodes)

You are given a cluster with a single control plane `cp1`, initialized with
`--control-plane-endpoint` and `--upload-certs`, with a CNI installed. You need to join
**two** control-plane nodes `cp2` and `cp3` (the prerequisites and packages are already in
place on them) in order to get an odd etcd quorum (3 nodes).

Official documentation:
[Creating Highly Available clusters with kubeadm](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/high-availability/),
[kubeadm join](https://kubernetes.io/docs/reference/setup-tools/kubeadm/kubeadm-join/).

## Step 1. Get the certificate-key and the join command (on `cp1`)

```bash
# 1. Upload the control plane certificates into a secret and get the certificate-key
sudo kubeadm init phase upload-certs --upload-certs
# ... prints: <certificate-key>

# 2. Get the basic join command (token + discovery-hash)
sudo kubeadm token create --print-join-command
# kubeadm join <endpoint>:6443 --token ... --discovery-token-ca-cert-hash sha256:...
```

Assemble the command for a control-plane node by adding `--control-plane` and
`--certificate-key`.

## Step 2. Join cp2 (task 1)

```bash
ssh cp2
sudo kubeadm join <endpoint>:6443 \
  --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash> \
  --control-plane \
  --certificate-key <certificate-key>
exit
```

## Step 3. Join cp3 (task 2)

The same way. If more than ~2 hours have passed since step 1, the `certificate-key` has
expired — repeat `upload-certs`; if the token has expired (~24 h) — run
`kubeadm token create` again.

```bash
ssh cp3
sudo kubeadm join <endpoint>:6443 \
  --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash> \
  --control-plane \
  --certificate-key <certificate-key>
exit
```

Check on `cp1`:

```bash
kubectl get nodes -l node-role.kubernetes.io/control-plane   # 3 nodes
kubectl get nodes                                            # all Ready
```

## Step 4. Check the etcd quorum (task 3)

With a stacked topology every control-plane node brings up its own static pod `etcd-*`:

```bash
kubectl -n kube-system get pods -l component=etcd -o wide
# etcd-cp1   Running
# etcd-cp2   Running
# etcd-cp3   Running

# the number of etcd members directly (with the certificates, chapter 37):
sudo ETCDCTL_API=3 etcdctl member list \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
# 3 lines — three members of the etcd cluster
```

## Why exactly 3

3 etcd members have a quorum of 2 and survive the loss of **one** node. 2 members survive
**zero** failures (quorum 2 out of 2) — that is worse than a single node. That is why HA is
built on an odd number: 3 (the standard) or 5 (survives two failures). An even number is
not beneficial (chapter 35A).
