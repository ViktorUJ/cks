# Lab 117 — reference solution (troubleshooting the control plane and nodes)

Connecting to the nodes from the work machine:

```bash
ssh k8s1_controlPlane_1     # control plane
ssh k8s1_node_node_1        # worker (see the name in /etc/hosts)
```

## Task 1. Fix kube-apiserver (debugging via crictl)

`kubectl` does not work (`connection refused`) — the API server has crashed. The only way to
figure it out is debugging at the container-runtime level with `crictl`.

```bash
ssh k8s1_controlPlane_1
sudo -i

# list the containers — looking for kube-apiserver in the Exited state
crictl ps -a | grep kube-apiserver
# CONTAINER   IMAGE   CREATED   STATE    NAME                ATTEMPT
# abc123...   ...     ...       Exited   kube-apiserver      5

# read the logs of the crashed container
crictl logs <container-id>
# Error: unknown flag: --invalid-nonexistent-flag

# fix the manifest — delete the line with the broken flag
vi /etc/kubernetes/manifests/kube-apiserver.yaml
# delete the line:    - --invalid-nonexistent-flag=true
```

> **Alternative:** `grep -n "invalid" /etc/kubernetes/manifests/kube-apiserver.yaml`
> to find the line, then `sed -i '/--invalid-nonexistent-flag/d' /etc/kubernetes/manifests/kube-apiserver.yaml`.

kubelet recreates the static pod after the manifest is edited. Wait ~30 s:

```bash
# on the control plane
crictl ps | grep kube-apiserver    # should be Running
exit
```

```bash
# on the worker PC — verify
kubectl get --raw='/healthz'       # ok
```

## Task 2. Fix kube-scheduler

```bash
# symptom: new pods are not scheduled
kubectl get pod sched-check -n default            # Pending
kubectl -n kube-system get pods -l component=kube-scheduler   # ImagePullBackOff

# look at the reason
kubectl -n kube-system describe pod -l component=kube-scheduler   # bad image tag v0.0.0-broken

# fix the static pod on the control plane node
ssh k8s1_controlPlane_1
sudo vi /etc/kubernetes/manifests/kube-scheduler.yaml
#   image: registry.k8s.io/kube-scheduler:v0.0.0-broken
# ->image: registry.k8s.io/kube-scheduler:v1.35.2   (version = cluster version)
```

kubelet recreates the static pod itself after the manifest is edited.
In ~30-60 s the scheduler comes up and `sched-check` moves to Running.

> The exact image version can be taken from a working component:
> `kubectl -n kube-system get pod -l component=kube-apiserver -o jsonpath='{.items[0].spec.containers[0].image}'`

## Task 3. Fix the worker node (NotReady)

```bash
kubectl get nodes                     # worker is NotReady
kubectl describe node <worker>        # kubelet does not report status

ssh k8s1_node_node_1
sudo systemctl status kubelet         # activating/failed
sudo journalctl -u kubelet -n 10      # failed to load kubelet config file ... NONEXISTENT-config.yaml

# remove the broken drop-in (it replaced the path to the config)
sudo rm /etc/systemd/system/kubelet.service.d/99-broken.conf
sudo systemctl daemon-reload
sudo systemctl restart kubelet
sudo systemctl status kubelet         # active (running)
```

In ~30 s the node returns to Ready.

## Task 4. Fix the broken static pod on the control plane

```bash
kubectl get pods -n default           # staticweb-<cp> in ImagePullBackOff
kubectl describe pod staticweb-<cp> -n default   # image viktoruj/ping_pong:doesnotexist999

ssh k8s1_controlPlane_1
sudo vi /etc/kubernetes/manifests/staticweb.yaml
#   image: viktoruj/ping_pong:doesnotexist999  ->  image: viktoruj/ping_pong:latest
```

kubelet recreates the static pod, and the mirror pod `staticweb-<cp>` moves to Running.
