# Lab 112 — reference solution (etcd: snapshots and restore)

All etcd actions happen on the control plane node (`ssh k8s1_controlPlane_1`, `sudo -i`).
`etcdctl` is already installed; the certificates are in `/etc/kubernetes/pki/etcd/`.

It is convenient to set the common etcd connection parameters once:

```bash
# on the control plane, as root
export ETCDCTL_API=3
export EP="--endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key"
```

## Task 1. Take snapshot S1 (baseline state) and copy it to the worker

```bash
# on the control plane
etcdctl $EP snapshot save /root/etcd-snapshot-1.db
etcdctl snapshot status /root/etcd-snapshot-1.db --write-out=table
```

Copy the snapshot to the work machine (for validation):

```bash
# from worker PC
scp k8s1_controlPlane_1:/root/etcd-snapshot-1.db \
  /var/work/tests/artifacts/etcd/etcd-snapshot-1.db
```

(if `scp` cannot pick the file up from `/root`, copy it into `/tmp` on the control plane and
grant permissions: `cp /root/etcd-snapshot-1.db /tmp/ && chmod 644 /tmp/etcd-snapshot-1.db`,
then `scp` from `/tmp`.)

## Task 2. Make changes in the cluster

We create "marker resources" — they are what will later show the difference between the
snapshots. The commands are run on the work machine (that is where `kubectl` is configured).

```bash
# on worker PC
kubectl create namespace snapshot-demo
kubectl -n snapshot-demo create configmap demo-config --from-literal=app=v1
kubectl -n snapshot-demo create deployment demo-web \
  --image=viktoruj/ping_pong --replicas=2

kubectl get ns snapshot-demo
kubectl -n snapshot-demo get cm,deploy
```

## Task 3. Take snapshot S2 (after the changes)

```bash
# on the control plane
etcdctl $EP snapshot save /root/etcd-snapshot-2.db
etcdctl snapshot status /root/etcd-snapshot-2.db --write-out=table
```

```bash
# from worker PC
scp k8s1_controlPlane_1:/root/etcd-snapshot-2.db \
  /var/work/tests/artifacts/etcd/etcd-snapshot-2.db
```

The difference: `etcd-snapshot-1.db` was taken **before** `snapshot-demo` was created, and
`etcd-snapshot-2.db` — **after**. So S2 contains the namespace `snapshot-demo` and its
resources, while S1 does not.

## Task 4. Restore S1 and confirm the extra resources are gone

We restore the very first snapshot — the cluster must return to the state **before**
`snapshot-demo` was created.

The restore order (the "stop the static Pods → restore into `/var/lib/etcd` → bring the
static Pods back up" method):

```bash
# on the control plane, as root
# 1. look up the node name and the addresses in the current etcd manifest — needed for the restore
grep -E -- '--name=|--initial-cluster=|--initial-advertise-peer-urls=' \
  /etc/kubernetes/manifests/etcd.yaml
# example output:
#   - --name=ip-10-10-1-17
#   - --initial-advertise-peer-urls=https://10.10.1.17:2380
#   - --initial-cluster=ip-10-10-1-17=https://10.10.1.17:2380

# 2. stop all control plane static Pods (kubelet will shut down their containers)
mkdir -p /etc/kubernetes/manifests-stopped
mv /etc/kubernetes/manifests/*.yaml /etc/kubernetes/manifests-stopped/
# wait until the etcd/apiserver containers disappear
crictl ps

# 3. move the current data away and restore snapshot S1 into /var/lib/etcd
mv /var/lib/etcd /var/lib/etcd.bak
etcdctl snapshot restore /root/etcd-snapshot-1.db \
  --data-dir=/var/lib/etcd \
  --name=ip-10-10-1-17 \
  --initial-cluster=ip-10-10-1-17=https://10.10.1.17:2380 \
  --initial-advertise-peer-urls=https://10.10.1.17:2380

# 4. put the manifests back — kubelet brings the control plane up on the restored data
mv /etc/kubernetes/manifests-stopped/*.yaml /etc/kubernetes/manifests/
```

> **Important about `--name` (etcd 3.6+).** During a restore you must pass `--name`,
> `--initial-cluster` and `--initial-advertise-peer-urls` **exactly the same** as in the etcd
> manifest. Otherwise the restored member will not match the one the static Pod starts with,
> and etcd will crash with the `member unknown` panic. The values come from step 1.

Check that the cluster came up and `snapshot-demo` is **gone**:

```bash
# from worker PC (wait ~1 minute for the API to come up)
kubectl get --raw='/healthz'          # ok
kubectl get ns snapshot-demo          # NotFound — no extra resources
kubectl get pods -n kube-system
```

## Task 5. Restore the cluster from S2

Now we restore the second snapshot — `snapshot-demo` and its resources must come back. The
procedure is the same, the snapshot is `/root/etcd-snapshot-2.db`.

```bash
# on the control plane, as root
mv /etc/kubernetes/manifests/*.yaml /etc/kubernetes/manifests-stopped/
crictl ps                                    # wait for the containers to stop

rm -rf /var/lib/etcd
etcdctl snapshot restore /root/etcd-snapshot-2.db \
  --data-dir=/var/lib/etcd \
  --name=ip-10-10-1-17 \
  --initial-cluster=ip-10-10-1-17=https://10.10.1.17:2380 \
  --initial-advertise-peer-urls=https://10.10.1.17:2380

mv /etc/kubernetes/manifests-stopped/*.yaml /etc/kubernetes/manifests/
```

Check that the cluster is healthy and `snapshot-demo` is **back**:

```bash
# from worker PC
kubectl get --raw='/healthz'                 # ok
kubectl get ns snapshot-demo                 # Active
kubectl -n snapshot-demo get cm,deploy       # demo-config and demo-web are in place
kubectl get pods -n kube-system
```

Bottom line: a snapshot is a complete image of the cluster state at the moment it was taken.
Restoring from S1 rolls the cluster back to the "empty" state, restoring from S2 brings the
created resources back.
