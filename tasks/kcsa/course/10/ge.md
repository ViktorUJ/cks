# თავი 10. ავთენტიფიკაცია და ავტორიზაცია

> **რა არის შემდეგ.** 07-09 თავებში ჩვენ ვიცავდით კლასტერის კომპონენტებს, სამუშაო კვანძებს, `Pod`-ებსა და ქსელურ საზღვრებს. ახლა განვიხილავთ Kubernetes API-სკენ მოთხოვნის გზას: ჯერ კლასტერი ადგენს ვინაობას, შემდეგ კი წყვეტს, ნებადართულია თუ არა მისთვის მოქმედება. ეს არის KCSA-ს **Kubernetes Security Fundamentals** დომენი, რომლის წონაა 22%.

## 10.1 ვინ მიმართავს API-ს: მომხმარებლები და `ServiceAccount`

Kubernetes API-სადმი ყოველი მოთხოვნა გადის ავთენტიფიკაციას, ანუ authentication-ს. მისი ამოცანაა უპასუხოს კითხვას „ვინ არის ეს?“. წარმატებული ავთენტიფიკაციის შემდეგ API Server მომხმარებლის სახელსა და ჯგუფებს გადასცემს შემდეგ ეტაპს, ავტორიზაციას.

ჩვეულებრივი მომხმარებელი, მაგალითად ინჟინერი ან კლასტერის გარეთ არსებული CI-სისტემა, არ არის Kubernetes-ის `User` ობიექტი. Kubernetes ასეთ ვინაობას იღებს კონფიგურირებული ავთენტიფიკაციის მექანიზმიდან. `ServiceAccount` არის Kubernetes API-ს ობიექტი, რომელიც პირველ რიგში განკუთვნილია `Pod`-ში მიმდინარე პროცესებისთვის. მისი სრული სახელი შეიცავს namespace-ს: `system:serviceaccount:shop:catalog`.

| მეთოდი | როდის გამოიყენება | მნიშვნელოვანი შეზღუდვა |
|---|---|---|
| კლიენტის TLS სერტიფიკატი | ადმინისტრატორი, კლასტერის კომპონენტი ან ავტომატიზაცია | საჭიროა დახურული გასაღებისა და სერტიფიკატის მოქმედების ვადის დაცვა. |
| Bearer token | ავტომატიზაცია ან ინტეგრაცია | ტოკენი გადასცემს მფლობელის უფლებამოსილებებს, ამიტომ ის არ უნდა მოხვდეს კოდში ან ჟურნალებში. |
| `ServiceAccount` ტოკენი | `Pod`-ის შიგნით მიმდინარე პროცესი მიმართავს API-ს | უფლებები განისაზღვრება RBAC-ით და არა მხოლოდ ტოკენის არსებობით. |
| OIDC | ვინაობის გარე მომწოდებელი, მაგალითად კორპორაციული SSO | API Server უნდა ენდობოდეს issuer-ს და ამოწმებდეს ტოკენის claims-ს. |
| Authentication webhook | გარე სერვისი ადასტურებს კლიენტის credential-ს | ეს არის authentication integration და არა admission webhook ან authorizer. |
| Bootstrap token | დანიშნულებით შეზღუდული token კვანძის საწყისი მიერთებისთვის | საჭიროა bootstrap/TLS bootstrap-ისთვის და არა როგორც ხანგრძლივად მოქმედი application identity. |

ანონიმური ავთენტიფიკაციის ჩართვისას ანონიმური მოთხოვნა ხდება მომხმარებელი `system:anonymous` და ჯგუფი `system:unauthenticated`. ეს არ არის API-სთან ჩვეულებრივი წვდომისთვის მოსახერხებელი რეჟიმი. დაცულ კონფიგურაციაში ანონიმურ წვდომას თიშავენ ან აძლევენ მხოლოდ განზრახ გახსნილ, უსაფრთხო საბოლოო წერტილებზე წვდომას.

ავთენტიფიკაცია თავისთავად წვდომას არ იძლევა. სერტიფიკატი, ტოკენი ან OIDC-ვინაობა მხოლოდ სუბიექტს ასახელებს. იმას, თუ რისი გაკეთება შეუძლია ამ სუბიექტს, ავტორიზაცია განსაზღვრავს.

## 10.2 `ServiceAccount` ტოკენები და `default` ანგარიშის რისკი

ყოველი `Namespace` შეიცავს `ServiceAccount`-ს სახელით `default`. თუ `Pod`-ის სპეციფიკაციაში `serviceAccountName` მითითებული არ არის, Kubernetes სწორედ მას ანიჭებს. ეს არ ნიშნავს, რომ `default` ავტომატურად იღებს ფართო უფლებებს: რისკი ჩნდება, როდესაც მოხერხებულობისთვის მას `RoleBinding` ან `ClusterRoleBinding` მიენიჭა.

თანამედროვე Kubernetes, მათ შორის v1.36, ჩვეულებრივ `Pod`-ს TokenRequest მექანიზმის მეშვეობით პროეცირებულ bound token-ს აძლევს. ასეთი ტოკენი დაკავშირებულია `ServiceAccount`-თან და კონკრეტულ `Pod`-თან, აქვს შეზღუდული მოქმედების ვადა და kubelet მას ავტომატურად აახლებს. `ServiceAccount` ტოკენიანი ხანგრძლივად მოქმედი Secret არ უნდა შეიქმნას დასაბუთებული მიზეზის გარეშე.

თუ აპლიკაციას Kubernetes API არ სჭირდება, ტოკენიც არ არის საჭირო. მის დამონტაჟებას თიშავენ `Pod`-ში ან თავად `ServiceAccount`-ში:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: web
  namespace: shop
automountServiceAccountToken: false
---
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: shop
spec:
  serviceAccountName: web
  automountServiceAccountToken: false
  containers:
    - name: web
      image: nginx:1.30.4
```

კონტეინერის კომპრომეტირებისას დამონტაჟებული ტოკენის წაკითხვა და მისი მოქმედების პერიოდში კლასტერის გარედან გამოყენება შესაძლებელია. ამიტომ თითოეული `Pod`-ისთვის ირჩევენ ცალკე `ServiceAccount`-ს მინიმალური უფლებებით, ხოლო `default`-ს აპლიკაციების საერთო ანგარიშად არ იყენებენ. automount-ის გამორთვა RBAC-ს არ აუქმებს, მაგრამ საიდუმლოს აშორებს იმ პოდის ფაილური სისტემიდან, რომელსაც API არ სჭირდება.

## 10.3 ავტორიზაცია: RBAC და სხვა authorizer-ები

ავტორიზაცია პასუხობს კითხვას „შეუძლია თუ არა უკვე ავთენტიფიცირებულ სუბიექტს ამ მოქმედების შესრულება?“. API Server აფასებს მომხმარებლის ან ჯგუფის, `verb`-ის, რესურსის, namespace-ის, ზოგჯერ კი ობიექტის სახელისა და API-ს ბილიკის კომბინაციას.

Kubernetes-ში შეიძლება რამდენიმე authorizer იყოს ჩართული. ისინი მოწმდება კონფიგურირებული თანმიმდევრობით: პირველი, რომელიც დააბრუნებს `Allow`-ს ან `Deny`-ს, გადაწყვეტილებას დაუყოვნებლივ ასრულებს; მხოლოდ მაშინ, თუ ყველამ `NoOpinion` დააბრუნა, მოთხოვნა ნაგულისხმევად იკრძალება. კლასტერების უმეტესობისთვის ძირითადი და რეკომენდებული მექანიზმია RBAC.

| მექანიზმი | დანიშნულება | პრაქტიკული მნიშვნელობა |
|---|---|---|
| RBAC | წესები `Role`, `ClusterRole` და მიბმებში | ჩვეულებრივი არჩევანი მართვადი და შემოწმებადი წვდომისთვის. |
| Node | ზღუდავს kubelet-ის მოქმედებებს კვანძის სახელით | გამოიყენება კვანძების ვინაობებისთვის და არა მომხმარებლების RBAC-ის ნაცვლად. |
| Webhook | მიმართავს ავტორიზაციის გარე სერვისს | გამოდგება, როდესაც გადაწყვეტილება გარე სისტემაზეა დამოკიდებული. |
| ABAC | მოთხოვნას ადარებს პოლიტიკების სტატიკურ ფაილს | ახალი პროექტებისთვის მოძველებული მიდგომა, რომლის აუდიტი და მხარდაჭერა რთულია. |

არ აგერიოთ RBAC და authentication. `RoleBinding` ვინაობას არ ადასტურებს და ტოკენს არ ქმნის. ის უკვე ცნობილ სუბიექტს ნებართვების ნაკრებთან აკავშირებს. ანალოგიურად, `NetworkPolicy` ზღუდავს ქსელურ კავშირებს, მაგრამ არ ცვლის API Server-ის გადაწყვეტილებას რესურსზე უფლებების შესახებ.

### Node authorizer და `NodeRestriction`: მეზობელი, მაგრამ განსხვავებული ფენები

**Node authorizer** არის სპეციალური authorizer kubelet/node identity-სთვის `system:node:<nodeName>` ჯგუფიდან `system:nodes`. ის ზღუდავს, რომელი API-ოპერაციების შესრულება შეუძლია kubelet-ს თავისი კვანძისა და მასზე დანიშნული `Pod`-ების მიმართ, მათ შორის მისთვის საჭირო `Secret`, `ConfigMap` და ტომების შესახებ ინფორმაციისთვის. ეს არის **authorization**.

**`NodeRestriction`** არის validating admission plugin. ის დამატებით ზღუდავს, რომელი `Node` ობიექტებისა და დაკავშირებული `Pod`-ების შეცვლა შეუძლია kubelet-ს: სწორად იდენტიფიცირებულ kubelet-ს არ უნდა შეეძლოს სხვისი Node/Pod-ის შეცვლა ან დაცული labels-ის თვითნებურად დაყენება. ეს არის **admission** და არა authorizer.

> **არ აგერიოთ.** Node authorizer პასუხობს კითხვას „ნებადართულია თუ არა node identity-სთვის ეს API-მოქმედება?“. `NodeRestriction` პასუხობს კითხვას „დასაშვებია თუ არა ობიექტის ეს ცვლილება ავტორიზაციის შემდეგაც?“. ორივე მექანიზმი მნიშვნელოვანია kubelet-ის least privilege-ისთვის, მაგრამ არ ცვლის მომხმარებლების RBAC-ს, TLS-ს ან კვანძის დაცვას.

## 10.4 RBAC: როლები, მიბმები და მინიმალური უფლებამოსილებები

`Role` წესებს მხოლოდ ერთ `Namespace`-ში აღწერს. `ClusterRole` აღწერს მთელი კლასტერის დონის წესებს ან შეიძლება ერთ namespace-ს `RoleBinding`-ის მეშვეობით მიებას. `RoleBinding` თავის namespace-ში მოქმედებს, ხოლო `ClusterRoleBinding` მთელ კლასტერზე ვრცელდება.

RBAC უფლებამოსილებები ადიტიურია: რამდენიმე მიბმა ერთმანეთს ემატება, ხოლო ცალკე წესი „აკრძალვა“ არ არსებობს. ამიტომ უმცირესი პრივილეგიების პრინციპი ნიშნავს მხოლოდ საჭირო `apiGroups`, `resources` და `verbs`-ის მინიჭებას, ასევე მოქმედების უმცირესი სფეროს არჩევას.

ქვემოთ მოცემული `Role` აპლიკაციას namespace `shop`-ში მხოლოდ ერთი `ConfigMap`-ის წაკითხვის უფლებას აძლევს. ეს ვიწრო წესის მაგალითია და არა ყველა ამოცანის შაბლონი.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: read-site-config
  namespace: shop
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["site-config"]
    verbs: ["get"]
```

მოსალოდნელი ნებართვის შემოწმება შესაძლებელია ბრძანებით `kubectl auth can-i`. მაგალითად, ადმინისტრატორს შეუძლია შეამოწმოს მოქმედება კონკრეტული ანგარიშისთვის:

```bash
kubectl auth can-i get configmap/site-config -n shop \
  --as=system:serviceaccount:shop:web
```

ბრძანება სასარგებლოა შემოწმებისთვის, მაგრამ არ ცვლის მანიფესტებისა და ფაქტობრივი მიბმების მიმოხილვას. განსაკუთრებულ ყურადღებას მოითხოვს `get`, `list` და `watch` უფლებები `secrets`-ზე, ასევე `create`, `update`, `patch` და `delete` სამუშაო დატვირთვებისთვის. RBAC-რესურსებზე წვდომამ, `bind`, `escalate` და `impersonate` უფლებებმა შეიძლება დამატებითი უფლებების მინიჭება ან გამოყენება გახადოს შესაძლებელი. `cluster-admin`, `verbs: ["*"]` და `resources: ["*"]` უსაფრთხო საწყისი ვარიანტი არ არის.

ეს სპეციალური authorization checks სხვადასხვა ამოცანას წყვეტს:

- `bind` ეხება `RoleBinding` / `ClusterRoleBinding`-ის შექმნას ან შეცვლას. ჩვეულებრივ, caller უკვე უნდა ფლობდეს შესაბამის scope-ზე მისაბმელ `Role`/`ClusterRole`-ში შემავალ permissions-ს. კონკრეტულ როლზე `bind`-ის აშკარა ნებართვა binding-ის შესრულების საშუალებას იძლევა მაშინაც კი, როდესაც თავად caller ამ permissions-ის სრულ ნაკრებს არ ფლობს.

- `escalate` ეხება არა binding-ს, არამედ `Role` / `ClusterRole`-ის შექმნას ან შეცვლას. ჩვეულებრივ, caller ვერ ჩაწერს როლში permissions-ს, რომლებსაც თავად არ ფლობს. `escalate`-ის აშკარა ნებართვა ამ დაცვის გამონაკლისია.

- classic `impersonate` იძლევა მოთხოვნების მითითებული user/group/ServiceAccount-ის ან სხვა მხარდაჭერილი identity attribute-ის სახელით გაგზავნის უფლებას. ეს ცალკე შესაძლებლობაა და მისი აღრევა `bind`-თან ან `escalate`-თან არ შეიძლება.

Kubernetes v1.36-ში ასევე ხელმისაწვდომია beta-მექანიზმი `ConstrainedImpersonation`, enabled by default. ის ამატებს `impersonate:*` და `impersonate-on:*` ოჯახების უფრო ვიწრო verbs-ს, რათა შეიზღუდოს არა მხოლოდ identity, არამედ მისი სახელით შესრულებული მოქმედებებიც. არსებული RBAC rules classic `impersonate`-ით მუშაობას აგრძელებს; API Server-ს შეუძლია გამოიყენოს constrained checks და საჭიროების შემთხვევაში classic `impersonate`-ზე fallback შეასრულოს.

`pods`-ზე `create` ნებართვა ცალკე ყურადღებას იმსახურებს: თავად `Pod`-ის შექმნის შესაძლებლობა შეიძლება სუბიექტის გავლენის გაზრდისკენ გადადგმულ ნაბიჯად იქცეს, მაშინაც კი, თუ ამ სუბიექტს სამიზნე მონაცემებზე პირდაპირი წვდომა არ აქვს. მსჯელობის ჯაჭვი ასეთია: სუბიექტს აქვს `Pod`-ის შექმნის უფლება → ახალ `Pod`-ს შეუძლია მიუთითოს namespace-ში ხელმისაწვდომი ნებისმიერი `ServiceAccount`-ის `serviceAccountName`, თუ ცალკე აშკარა აკრძალვა არ არის კონფიგურირებული → არჩეული `ServiceAccount`-ის ან დამონტაჟებული `Secret`/`ConfigMap`/ტომების მეშვეობით ამ `Pod`-ს შეუძლია მიიღოს წვდომა მონაცემებზე ან API-უფლებებზე, რომლებიც თავდაპირველ სუბიექტს პირდაპირ არ ჰქონდა. საბოლოო მასშტაბი დამოკიდებულია იმაზე, რეალურად რომელი `ServiceAccount` და ტომებია ხელმისაწვდომი namespace-ში, ასევე ცალკეულ შემზღუდველ controls-ზე, მაგალითად `automountServiceAccountToken: false`, PSA/PSS, შეზღუდული RBAC-მიბმები არსებული `ServiceAccount`-ებისთვის. workload-ის შექმნის უფლება არ უნდა განვიხილოთ როგორც უპირობო გზა კლასტერის ნებისმიერ `Secret`-თან ან ნებისმიერ `ServiceAccount`-თან - ის შესაძლო გავლენას ზუსტად იმდენად აფართოებს, რამდენის საშუალებასაც namespace-ის დანარჩენი კონფიგურაცია იძლევა.

## 10.5 როგორ გამოიყენება ეს პრაქტიკაში

პლატფორმის გუნდი ადამიანურ და მანქანურ ვინაობებს ერთმანეთისგან გამოყოფს. თანამშრომლები კორპორაციული OIDC-ის მეშვეობით შედიან, ავტომატიზაცია ცალკე სააღრიცხვო მონაცემებს იღებს, ხოლო `Namespace`-ში თითოეული კომპონენტი ცალკე `ServiceAccount`-ს იყენებს.

აპლიკაციის HTTP-სერვისისთვის, რომელიც Kubernetes API-ს არ იძახებს, აყენებენ `automountServiceAccountToken: false`-ს. კონტროლერს, რომელსაც API სჭირდება, აძლევენ ცალკე `ServiceAccount`-სა და `Role`-ს კონკრეტული რესურსებითა და verb-ებით. ცვლილების გამოშვებამდე ამოწმებენ `kubectl auth can-i`-ს, შემდეგ კი ატარებენ `RoleBinding` და `ClusterRoleBinding`-ის მიმოხილვას.

რეგულარულად ეძებენ `default`-თან მიბმებსა და ფართო `ClusterRoleBinding`-ებს. თანამშრომლის გათავისუფლების, ტოკენის გაჟონვის ან სერტიფიკატის გასაღების დაკარგვისას სააღრიცხვო მონაცემებს აუქმებენ ან ცვლიან, ხოლო დაკავშირებულ უფლებებს გადახედავენ. ამგვარად ერთი ტოკენის გაჟონვა მთელ კლასტერზე მუდმივ წვდომად არ იქცევა.

## 10.8 არ აგერიოთ და როგორ გვხვდება ეს გამოცდაზე

MCQ-ში (multiple choice question, კითხვა პასუხის არჩევით) ჩვეულებრივ საჭიროა authentication-ის authorization-ისგან განსხვავება და ყველაზე ვიწრო უსაფრთხო წვდომის არჩევა. ხშირი მახეებია:

- ჩათვალოთ, რომ `ServiceAccount` ან ტოკენი თავისთავად იძლევა უფლებებს; უფლებებს RBAC-მიბმები განსაზღვრავს;
- აგერიოთ `RoleBinding` და `ClusterRoleBinding`: პირველი თავისი namespace-ით არის შეზღუდული;
- ჩათვალოთ `default` უპირობოდ სახიფათოდ: რისკი დამოკიდებულია მისთვის მინიჭებულ უფლებამოსილებებსა და ტოკენის დამონტაჟებაზე;
- OIDC მიიღოთ ავტორიზაციის მეთოდად: OIDC ადასტურებს გარე ვინაობას, ხოლო წვდომის შესახებ გადაწყვეტილებას authorizer იღებს;
- აირჩიოთ `cluster-admin` ან wildcard ცალკე როლის ნაცვლად, რომელსაც რესურსებისა და verb-ების ზუსტი ნაკრები აქვს.

ჯერ განსაზღვრეთ, რას ეხება კითხვა: ვინ აგზავნის მოთხოვნას, რა გზით დადგინდა ვინაობა ან რომელი მოქმედებაა ნებადართული. შემდეგ შეამოწმეთ მოქმედების სფერო: ერთი namespace თუ მთელი კლასტერი.

**სწორი პასუხია: c.** RBAC წვდომის შემოწმებად წესებს როლებისა და მიბმების მეშვეობით განსაზღვრავს. OIDC ავთენტიფიკაციას ეხება, Node authorizer კვანძების ვინაობებს ემსახურება, ხოლო ABAC სტატიკურ პოლიტიკებს ეფუძნება.

</details>

### 5. რატომ მოითხოვს `secrets`-ზე `get` ნებართვა განსაკუთრებულ სიფრთხილეს?

   - a. მან შეიძლება გაამჟღავნოს credentials, გასაღებები და ტოკენები, რომლებიც შემდეგ Kubernetes-თან ან გარე სისტემებთან წვდომას იძლევა.
   - b. ის აბრუნებს მხოლოდ Secret-ის metadata-ს და API-კლიენტს შენახული მნიშვნელობის მიღების საშუალებას არასოდეს აძლევს.
   - c. ის სუბიექტს ავტომატურად აძლევს `Pod`-ის შექმნის უფლებას, მაშინაც კი, თუ RBAC შესაბამის ნებართვას არ შეიცავს.
   - d. ის API Server-ს აიძულებს, ყოველი წაკითხვისას Secret ხელახლა დაშიფროს და ამიტომ კლიენტის უფლებებს ზრდის.

<details>
<summary>პასუხი და განმარტება</summary>

**სწორი პასუხია: a.** `Secret` ხშირად შეიცავს მონაცემებს, რომლებიც სხვა რესურსებთან წვდომას ხსნის. ამიტომ `get`, განსაკუთრებით კი უფრო ფართო `list/watch`, least privilege-ის შესაბამისად უნდა გაიცეს. Secret-ის წაკითხვა სხვა RBAC-ნებართვებს ავტომატურად არ ქმნის.

</details>
