# Глава 10. Аутентификация и авторизация

> **Что дальше.** В главах 07-09 мы защищали компоненты кластера, рабочие узлы, `Pod` и сетевые границы. Теперь разберём путь запроса к Kubernetes API: сначала кластер устанавливает личность, затем решает, разрешено ли ей действие. Это домен KCSA **Kubernetes Security Fundamentals** с весом 22%.

## 10.1 Кто обращается к API: пользователи и `ServiceAccount`

Каждый запрос к Kubernetes API проходит аутентификацию, или authentication. Её задача - ответить на вопрос «кто это?». После успешной аутентификации API Server передаёт имя пользователя и группы следующей стадии, авторизации.

Обычный пользователь, например инженер или CI-система за пределами кластера, не является объектом Kubernetes `User`. Kubernetes получает такую личность от настроенного механизма аутентификации. `ServiceAccount` - объект API Kubernetes, предназначенный прежде всего для процессов в `Pod`. Его полное имя содержит namespace: `system:serviceaccount:shop:catalog`.

| Способ | Когда применяется | Важное ограничение |
|---|---|---|
| Клиентский сертификат TLS | Администратор, компонент кластера или автоматизация | Нужно защищать закрытый ключ и срок действия сертификата. |
| Bearer token | Автоматизация или интеграция | Токен передаёт полномочия владельца, его нельзя помещать в код или логи. |
| Токен `ServiceAccount` | Процесс внутри `Pod` обращается к API | Права определяются RBAC, а не самим фактом наличия токена. |
| OIDC | Внешний поставщик идентичности, например корпоративный SSO | API Server должен доверять issuer и проверять claims токена. |
| Authentication webhook | Внешняя служба подтверждает credential клиента | Это authentication integration, а не admission webhook и не authorizer. |
| Bootstrap token | Ограниченный по назначению token для начального присоединения узла | Нужен для bootstrap/TLS bootstrap, не как долгоживущая application identity. |

Анонимный запрос при включённой анонимной аутентификации становится пользователем `system:anonymous` и группой `system:unauthenticated`. Это не удобный режим для обычного доступа к API. В защищённой конфигурации анонимный доступ отключают либо дают ему только намеренно открытые, безопасные конечные точки.

Аутентификация не даёт доступа сама по себе. Сертификат, токен или OIDC-идентичность лишь называют субъекта. Что этот субъект может сделать, определяет авторизация.

## 10.2 Токены `ServiceAccount` и риск учётной записи `default`

Каждый `Namespace` содержит `ServiceAccount` с именем `default`. Если в спецификации `Pod` не указан `serviceAccountName`, Kubernetes назначает именно его. Это не означает, что `default` автоматически имеет широкие права: риск появляется, когда ему выдали `RoleBinding` или `ClusterRoleBinding` для удобства.

Современный Kubernetes, включая v1.36, обычно выдаёт `Pod` проектируемый bound token через механизм TokenRequest. Такой токен связан с `ServiceAccount` и конкретным `Pod`, имеет ограниченный срок жизни и автоматически обновляется kubelet. Долгоживущий Secret с токеном `ServiceAccount` не следует создавать без обоснованной причины.

Если приложению не требуется Kubernetes API, токен не нужен. Его монтирование отключают в `Pod` или в самом `ServiceAccount`:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: web
  namespace: shop
automountServiceAccountToken: false
---
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: shop
spec:
  serviceAccountName: web
  automountServiceAccountToken: false
  containers:
    - name: web
      image: nginx:1.30.4
```

При компрометации контейнера смонтированный токен можно прочитать и применить снаружи кластера, пока он действителен. Поэтому для каждого `Pod` выбирают отдельный `ServiceAccount` с минимальными правами, а `default` не используют как общую учётную запись приложений. Отключение automount не отменяет RBAC, но убирает секрет из файловой системы пода, которому API не нужен.

## 10.3 Авторизация: RBAC и другие authorizer

Авторизация отвечает на вопрос «может ли уже аутентифицированный субъект выполнить это действие?». API Server оценивает сочетание пользователя или группы, `verb`, ресурса, namespace, а иногда имени объекта и пути API.

В Kubernetes могут быть включены несколько authorizer. Они проверяются в настроенном порядке: первый, который возвращает `Allow` или `Deny`, немедленно завершает решение; только если все вернули `NoOpinion`, запрос запрещается по умолчанию. Основным и рекомендуемым механизмом для большинства кластеров является RBAC.

| Механизм | Назначение | Практический смысл |
|---|---|---|
| RBAC | Правила в `Role`, `ClusterRole` и привязках | Обычный выбор для управляемого, проверяемого доступа. |
| Node | Ограничивает действия kubelet от имени узла | Используется для идентичностей узлов, не вместо RBAC пользователей. |
| Webhook | Запрашивает внешнюю службу авторизации | Подходит, когда решение зависит от внешней системы. |
| ABAC | Сверяет запрос со статическим файлом политик | Устаревший для новых проектов подход, сложный для аудита и сопровождения. |

Не путайте RBAC с authentication. `RoleBinding` не подтверждает личность и не создаёт токен. Он связывает уже известный субъект с набором разрешений. Аналогично, `NetworkPolicy` ограничивает сетевые соединения, но не заменяет решение API Server о правах на ресурс.

### Node authorizer и `NodeRestriction`: соседние, но разные слои

**Node authorizer** - специальный authorizer для kubelet/node identity `system:node:<nodeName>` из группы `system:nodes`. Он ограничивает, какие API-операции kubelet может выполнять для своего узла и назначенных ему `Pod`, включая нужные ему `Secret`, `ConfigMap` и сведения о томах. Это **authorization**.

**`NodeRestriction`** - validating admission plugin. Он дополнительно ограничивает, какие объекты `Node` и связанные `Pod` kubelet может изменять: корректно идентифицированный kubelet не должен менять чужой Node/Pod или самовольно выставлять защищённые labels. Это **admission**, а не authorizer.

> **Не путать.** Node authorizer отвечает «разрешено ли node identity это API-действие?». `NodeRestriction` отвечает «даже после авторизации допустимо ли это изменение объекта?». Оба механизма важны для least privilege kubelet, но не заменяют RBAC пользователей, TLS или защиту узла.

## 10.4 RBAC: роли, привязки и минимальные полномочия

`Role` описывает правила только в одном `Namespace`. `ClusterRole` описывает правила уровня всего кластера либо может быть привязан к одному namespace через `RoleBinding`. `RoleBinding` действует в своём namespace, а `ClusterRoleBinding` действует на весь кластер.

Полномочия RBAC аддитивны: несколько привязок складываются, а отдельного правила «запретить» нет. Поэтому принцип наименьших привилегий означает давать только нужные `apiGroups`, `resources` и `verbs`, а также выбирать наименьшую область действия.

Ниже `Role` разрешает приложению прочитать лишь один `ConfigMap` в namespace `shop`. Это пример узкого правила, а не шаблон для всех задач.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: read-site-config
  namespace: shop
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["site-config"]
    verbs: ["get"]
```

Проверить ожидаемое разрешение можно командой `kubectl auth can-i`. Например, администратор может проверить действие для конкретной учётной записи:

```bash
kubectl auth can-i get configmap/site-config -n shop \
  --as=system:serviceaccount:shop:web
```

Команда полезна для проверки, но не заменяет ревью манифестов и фактических привязок. Особого внимания требуют права `get`, `list` и `watch` на `secrets`, а также `create`, `update`, `patch` и `delete` для рабочих нагрузок. Доступ к RBAC-ресурсам, `bind`, `escalate` и `impersonate` может позволить выдать или использовать дополнительные права. `cluster-admin`, `verbs: ["*"]` и `resources: ["*"]` не являются безопасным стартовым вариантом.

Эти специальные authorization checks решают разные задачи:

- `bind` относится к созданию или изменению `RoleBinding` / `ClusterRoleBinding`. Обычно caller должен уже обладать permissions, содержащимися в привязываемой `Role`/`ClusterRole`, на соответствующем scope. Явное разрешение `bind` на конкретную роль позволяет выполнить binding даже без собственного набора всех этих permissions.

- `escalate` относится не к binding, а к созданию или изменению `Role` / `ClusterRole`. Обычно caller не может записать в роль permissions, которыми сам не обладает. Явное разрешение `escalate` является исключением из этой защиты.

- classic `impersonate` разрешает отправлять запросы от имени указанного user/group/ServiceAccount или другого поддерживаемого identity attribute. Это отдельная возможность и её нельзя смешивать с `bind` или `escalate`.

В Kubernetes v1.36 также доступен beta-механизм `ConstrainedImpersonation`, enabled by default. Он добавляет более узкие verbs семейства `impersonate:*` и `impersonate-on:*`, чтобы ограничивать не только identity, но и действия, выполняемые от её имени. Существующие RBAC rules с classic `impersonate` продолжают работать; API Server может использовать constrained checks и при необходимости fallback к classic `impersonate`.

Разрешение `create` на `pods` заслуживает отдельного внимания: сама возможность создать `Pod` может стать шагом к повышению влияния субъекта, даже если этот субъект не имеет прямого доступа к целевым данным. Цепочка рассуждения такая: у субъекта есть право создать `Pod` → новый `Pod` может указать `serviceAccountName` любого `ServiceAccount`, доступного в namespace, если явный запрет не настроен отдельно → через выбранный `ServiceAccount` или через смонтированные `Secret`/`ConfigMap`/тома этот `Pod` может получить доступ к данным или API-правам, которых у исходного субъекта не было напрямую. Итоговый масштаб зависит от того, какие `ServiceAccount` и тома фактически доступны в namespace, и от отдельных ограничивающих controls (например, `automountServiceAccountToken: false`, PSA/PSS, ограниченные привязки RBAC для существующих `ServiceAccount`). Право на создание workload не следует трактовать как безусловный путь к любому `Secret` или любой `ServiceAccount` кластера - оно расширяет возможное влияние ровно настолько, насколько позволяет остальная конфигурация namespace.

## 10.5 Как это применяют на практике

Команда платформы разделяет человеческие и машинные идентичности. Сотрудники входят через корпоративный OIDC, автоматизация получает отдельные учётные данные, а каждый компонент в `Namespace` использует отдельный `ServiceAccount`.

Для прикладного HTTP-сервиса, который не вызывает API Kubernetes, задают `automountServiceAccountToken: false`. Контроллеру, которому API нужен, дают отдельный `ServiceAccount` и `Role` с конкретными ресурсами и verb. Перед выпуском изменения проверяют `kubectl auth can-i`, а затем проводят ревью `RoleBinding` и `ClusterRoleBinding`.

Регулярно ищут привязки к `default` и широкие `ClusterRoleBinding`. При увольнении сотрудника, утечке токена или потере ключа сертификата учётные данные отзывают или заменяют, а связанные права пересматривают. Так утечка одного токена не становится постоянным доступом ко всему кластеру.

## 10.6 Exam vocabulary / Мини-глоссарий

| Термин | Значение |
|---|---|
| authentication | Установление личности отправителя запроса к API. |
| authorization | Решение, разрешено ли этой личности конкретное действие. |
| `ServiceAccount` | Идентичность Kubernetes для процессов, обычно работающих в `Pod`. |
| bearer token | Токен, предъявитель которого получает связанные с ним полномочия. |
| OIDC | Протокол подключения Kubernetes к внешнему поставщику идентичности. |
| RBAC | Управление доступом через роли и привязки ролей. |
| `Role` / `ClusterRole` | Набор правил в одном namespace / на уровне кластера. |
| `RoleBinding` / `ClusterRoleBinding` | Привязка роли к пользователю, группе или `ServiceAccount`. |
| `bind` | Специальное RBAC-разрешение на привязку Role/ClusterRole без необходимости самому обладать всеми permissions привязываемой роли. |
| `escalate` | Специальное RBAC-разрешение на создание/изменение Role/ClusterRole с permissions сверх собственных permissions caller. |
| `impersonate` | Classic Kubernetes permission на impersonation другой identity; в v1.36 также существует beta ConstrainedImpersonation с более узкими verbs. |

## 10.7 Exam Essentials / Итоги главы

- Обычные пользователи аутентифицируются внешними механизмами, а `ServiceAccount` является объектом Kubernetes для процессов в `Pod`.
- Клиентские сертификаты, bearer tokens, токены `ServiceAccount` и OIDC устанавливают личность, но не дают прав без авторизации.
- `default` не имеет широких прав автоматически, однако привязка к нему делает все неявно использующие его поды потенциальными носителями этих прав.
- Не нужный приложению токен `ServiceAccount` не монтируют через `automountServiceAccountToken: false`.
- RBAC - основной authorizer; `Role` и `RoleBinding` обычно уменьшают область доступа по сравнению с кластерными вариантами.
- Разрешения складываются, поэтому опасные verb и широкие wildcard-правила повышают последствия компрометации.

## 10.8 Не путать и как это встречается на экзамене

В MCQ (multiple choice question, вопрос с выбором ответа) обычно нужно отличить authentication от authorization и выбрать самый узкий безопасный доступ. Частые ловушки:

- считать, что `ServiceAccount` или токен сам по себе выдаёт права; права определяют RBAC-привязки;
- путать `RoleBinding` с `ClusterRoleBinding`: первый ограничен своим namespace;
- считать `default` опасным безусловно: риск зависит от выданных ему полномочий и монтирования токена;
- принимать OIDC за метод авторизации: OIDC подтверждает внешнюю идентичность, а решение о доступе принимает authorizer;
- выбирать `cluster-admin` или wildcard вместо отдельной роли с точным набором ресурсов и verb.

Сначала определите, о чём вопрос: кто делает запрос, каким способом установлена личность или какое действие разрешено. Затем проверьте область: один namespace или весь кластер.

## 10.9 Вопросы для самопроверки

### 1. Какое утверждение о `ServiceAccount` верно?

   - a. Он автоматически получает `cluster-admin` в своём namespace.

   - b. Это Kubernetes-идентичность для процессов в `Pod`; её права задают RBAC-привязки.

   - c. Он заменяет `NetworkPolicy` для сетевого доступа.

   - d. Это внешний пользователь, который всегда аутентифицируется через OIDC.

<details>
<summary>Ответ и разбор</summary>

**Верный ответ: b.** `ServiceAccount` обычно используют процессы в подах, а его возможности определяют роли и привязки. OIDC, `cluster-admin` и сетевые правила не следуют из самого создания `ServiceAccount`.

</details>

### 2. Что уменьшает риск для `Pod`, которому не нужен Kubernetes API?

   - a. Включить анонимную аутентификацию API Server.

   - b. Добавить `verbs: ["*"]` в `ClusterRole`.

   - c. Назначить `default` `ServiceAccount` с `cluster-admin`.

   - d. Задать `automountServiceAccountToken: false`.

<details>
<summary>Ответ и разбор</summary>

**Верный ответ: d.** Так Kubernetes не монтирует токен `ServiceAccount` в под. Остальные варианты расширяют доступ или создают ненужную поверхность атаки.

</details>

### 3. Какой объект определяет разрешения, ограниченные одним `Namespace`?

   - a. `Role`

   - b. `ClusterRoleBinding`

   - c. `NetworkPolicy`

   - d. `ServiceAccount`

<details>
<summary>Ответ и разбор</summary>

**Верный ответ: a.** `Role` определяет namespace-ограниченные правила (какие verbs разрешены для каких ресурсов), но сам не выдаёт эти права субъекту - для реальной выдачи прав используется `RoleBinding` в том же namespace, связывающий `Role` с конкретными subjects.

</details>

### 4. Какой механизм Kubernetes является основным выбором для управления разрешениями пользователей и `ServiceAccount`?

   - a. Node authorizer

   - b. ABAC

   - c. RBAC

   - d. OIDC

<details>
<summary>Ответ и разбор</summary>

**Верный ответ: c.** RBAC задаёт проверяемые правила доступа через роли и привязки. OIDC относится к аутентификации, Node authorizer обслуживает узловые идентичности, а ABAC основан на статических политиках.

</details>

### 5. Почему разрешение `get` на `secrets` требует особой осторожности?

   - a. Оно может раскрыть credentials, ключи и токены, которые затем дают доступ к Kubernetes или внешним системам.
   - b. Оно возвращает только metadata Secret и никогда не позволяет API-клиенту получить сохранённое значение.
   - c. Оно автоматически даёт субъекту право создавать `Pod`, даже если RBAC не содержит соответствующего разрешения.
   - d. Оно заставляет API Server повторно зашифровать Secret при каждом чтении и поэтому увеличивает права клиента.

<details>
<summary>Ответ и разбор</summary>

**Верный ответ: a.** `Secret` часто содержит данные, которые открывают доступ к другим ресурсам. Поэтому `get`, а особенно более широкие `list/watch`, должны выдаваться по least privilege. Чтение Secret не создаёт другие RBAC-разрешения автоматически.

</details>
